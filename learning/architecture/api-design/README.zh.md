# 学习：API 设计

能够从零设计一个带版本的公开 API（REST/HTTP 或 gRPC），并演进现有的 API，在修改其契约的同时不破坏依赖它的客户端。

**最新课程：** [19. GraphQL 的位置](lessons/0019-where-graphql-fits.md)

## 成功的标准

- 针对给定的用例，设计 REST/HTTP 或 gRPC API 的契约，包括它的错误模型。
- 在不破坏客户端的前提下演进现有 API 的契约（新增、弃用或修改某个字段或端点），并解释所用的版本管理或迁移策略。
- 把认证、授权和限流当作客户端所依赖的契约的一部分，而不是事后单独拼接上去的东西。

## 约束

- 假定具备构建 HTTP 或 RPC 服务的职业经验；不要求系统学习过 API 设计。
- 同时覆盖 REST/HTTP 和 gRPC，因为本主题的目标对二者同样适用。

## 范围之外

- 让编译器在单个代码库内拒绝不可能的状态：这条边界见 [`programming/typescript`](../../programming/typescript/)。本主题是把同样的直觉应用到一条没有共享编译器的边界上。

## 学习路线

共十二个阶段，从契约到异步投递，再到对照真实行为验证契约本身。一个阶段包含若干课程，边界并不严格；一个阶段是否完成，取决于能力，而不是课程数量。

| 阶段 | 课程 | 内容 | 完成的标志 |
|---|---|---|---|
| 1. 契约 | 0001 | 客户端能依赖的东西比文档写下的更多（海勒姆定律） | 能说出契约在文档之外的隐性表面 |
| 2. 错误模型 | 0002 至 0003 | HTTP 状态码、RFC 9457 Problem Details、gRPC 状态码 | 能为给定的 API 设计错误模型 |
| 3. REST/HTTP 设计 | 0004 至 0005 | 资源建模、分页与过滤、AIP 风格的指南 | 能为给定的用例设计 REST 契约 |
| 4. gRPC 设计 | 0006 至 0007 | proto3、服务设计、流式调用 | 能为同一个用例设计 gRPC 契约 |
| 5. 版本管理与演进 | 0008 至 0009 | 增量式变更、弃用、迁移策略 | 能在不破坏客户端的前提下演进现有 API 的契约 |
| 6. 作为契约的认证、授权与限流 | 0010 | 把它们当作客户端所依赖内容的一部分，而不是事后补充 | 能把认证和限流作为契约来设计，而不是单独拼接上去 |
| 7. 幂等与安全重试 | 0011 | `Idempotency-Key` 请求头、幂等指纹，以及重试与并发请求的区别 | 能设计一套幂等机制，让非幂等方法真正可以安全重试 |
| 8. 作为契约的 HTTP 缓存 | 0012 | `ETag`、弱校验器与强校验器、条件请求、`If-Match` 乐观并发、`Cache-Control` | 能设计缓存与并发控制的契约，并知道每个条件请求头需要哪种比较强度 |
| 9. 长时间运行的操作与异步投递 | 0013 至 0014 | 操作资源与轮询、webhook 签名、重试与顺序 | 能设计异步契约（轮询的操作或推送的 webhook），以及它的失败、重试和顺序保证 |
| 10. 批量操作与部分响应 | 0015 | 原子式与部分成功的批量方法、逐项错误报告、字段掩码 | 能设计批量方法的失败语义和部分响应契约 |
| 11. 机器可读的契约 | 0016 至 0017 | 作为生成产物的 OpenAPI 文档和 `.proto` 文件、用 Buf、Spectral 和 oasdiff 检测破坏性变更 | 能解释机器可读的契约能带来什么，以及风格检查器与破坏性变更检测器有何不同 |
| 12. 契约测试与 GraphQL 的位置 | 0018 至 0019 | 消费者驱动的契约测试与 `can-i-deploy`，以及 GraphQL 相对于 REST 和 gRPC 的位置 | 能解释契约测试如何验证 schema 之外的真实行为，并把 GraphQL 无版本的演进方式与本路线中的 REST/gRPC 内容准确对照 |

## 课程

请按顺序学习。

| # | 课程 | 内容 |
|---|---|---|
| [0001](lessons/0001-the-contract.md) | 契约 | 客户端能依赖的东西比你写进文档的更多，设计必须同时考虑这两部分 |
| [0002](lessons/0002-http-status-codes-and-error-semantics.md) | HTTP 状态码与错误语义 | 状态码在安全性、幂等性以及下一步该做什么上，究竟向客户端承诺了什么，而不只是笼统的 2xx/4xx/5xx 分组 |
| [0003](lessons/0003-problem-details-and-grpc-status-codes.md) | RFC 9457 Problem Details 与 gRPC 状态码 | 一种结构化、机器可读的 HTTP 错误格式，gRPC 与之平行的状态码词汇，以及设计一个在二者之间通用的错误模型 |
| [0004](lessons/0004-resource-modeling-for-rest.md) | REST 的资源建模 | 为什么 REST 围绕名词和状态而不是动词来建模 API，以及资源层级如何决定一个 URL 的含义 |
| [0005](lessons/0005-pagination-and-filtering.md) | 分页、过滤与设计 REST 契约 | 为什么在规模化场景下基于游标的分页胜过偏移量，过滤如何保持为稳定的契约，以及把资源建模组合成完整的 REST 设计 |
| [0006](lessons/0006-proto3-and-grpc-service-design.md) | Proto3 与 gRPC 服务设计 | 为什么 proto3 的字段编号而不是字段名才是真正的传输契约，以及 gRPC 服务如何围绕 RPC 方法而不是资源来组织 |
| [0007](lessons/0007-grpc-streaming.md) | gRPC 流式调用与设计同一个用例 | gRPC 的四种 RPC、各自适用的场景，以及把同一个用例同时设计成 REST 契约和 gRPC 契约 |
| [0008](lessons/0008-additive-changes-and-deprecation.md) | 增量式变更与弃用 | 为什么新增通常是安全的，而删除或改变含义通常不安全，以及如何弃用一个字段或端点而不当场破坏客户端 |
| [0009](lessons/0009-versioning-and-migration-strategy.md) | 版本管理与迁移策略 | 如何发布一个真正的破坏性变更，而不一下子破坏所有现有集成，以 Stripe 的版本管理策略为实例 |
| [0010](lessons/0010-auth-authz-and-rate-limiting-as-contract.md) | 作为契约的认证、授权与限流 | 为什么是作用域而不只是令牌、是可见的限流状态而不只是一个 429，让访问控制和配额成为有意设计的契约的一部分 |
| [0011](lessons/0011-idempotency-keys-and-safe-retries.md) | 幂等键与安全重试 | 单靠一个键只能去重；告诉服务器重复的键是同一个请求的重试、还是另一个请求误用了它的，是指纹，而在原请求仍在执行时到达的重试，得到的是冲突，而不是重放 |
| [0012](lessons/0012-http-caching-as-contract.md) | 作为契约的 HTTP 缓存 | 同一个 ETag 校验器根据所需的比较方式承担两种不同的职责：弱比较足以跳过多余的下载，但只有强比较才能安全地检测别人的并发写入 |
| [0013](lessons/0013-the-operation-resource-and-polling.md) | 操作资源与轮询 | 长时间运行的方法返回一个形如承诺的资源，而不是阻塞等待，执行过程中的失败，与让操作根本无法开始的失败，报告方式并不相同 |
| [0014](lessons/0014-webhooks-and-callbacks-as-delivery.md) | 作为投递方式的 webhook 与回调 | 主动推送通知而不是等待被轮询，颠倒了由谁发起请求，而正是这种颠倒，使签名、重试和顺序都需要在接收端有各自明确的契约 |
| [0015](lessons/0015-bulk-operations-and-partial-responses.md) | 批量操作与部分响应 | 批量方法必须事先选定是全有或全无地失败，还是逐项报告成功与失败，而只想要部分字段的客户端，需要在它所塑造的请求体之外请求这个子集 |
| [0016](lessons/0016-openapi-and-protobuf-as-artifacts.md) | 作为产物的 OpenAPI 与 Protobuf | 一旦契约以机器可读文档而不只是文字描述的形式存在，文档本身就成了需要版本管理、评审并据以生成其他东西的对象，而不是事后补写的说明 |
| [0017](lessons/0017-breaking-change-linting.md) | 破坏性变更检查 | 检查契约风格的检查器，和检查它是否破坏了客户端的差异工具，回答的是两个不同的问题，而差异工具本身也必须在三个问题中被问对那一个 |
| [0018](lessons/0018-contract-testing.md) | 契约测试 | schema 产物检查形状，破坏性变更检查器检查兼容性，但两者都无法确认提供方的实际行为符合真实消费者测试的预期，而这正是契约测试通过记录下来的示例交互所验证的 |
| [0019](lessons/0019-where-graphql-fits.md) | GraphQL 的位置 | GraphQL 通过让每个请求本身就是字段掩码，解决了本主题用两节课讨论的同一个版本管理问题，代价是一份本主题的工具都不适用的契约 |

## 使用方式

每节课都简短且自成一体。答案默认折叠：先自己回忆，再展开查看。真实场景中的练习比阅读更重要，而把练习间隔开来正是关键。课程结束时仍不清楚的地方，值得先追溯到一手资料再继续往下学。
