# 学习：分布式系统

能够为正在设计的系统选择一致性模型并为之辩护，并在分析由部分失败引起的生产事故时，不再把网络当作可靠的。

**最新课程：** [19. 验证一个论断](lessons/0019-verifying-a-claim.md)

## 成功的标准

- 给定一个系统设计，选择一致性模型，并对照其他方案为这个权衡辩护。
- 给定一次由部分失败（网络分区、被误认为已宕机的慢节点）引起的事故，说出背后的机制。
- 解释共识协议能带来什么、为什么代价如此，而不需要从第一性原理证明它的正确性。

## 约束

- 假定具备构建网络服务的职业经验；不要求系统学习过分布式系统。
- 侧重实践和运维：代价与权衡比协议正确性的形式化证明更重要。

## 范围之外

- 单个进程内的并发（goroutine、线程、`Send`/`Sync`）：归各语言主题负责。本主题从跨越进程边界的地方开始。
- 在集群编排器上运行工作负载：归 [`infrastructure/kubernetes`](../../infrastructure/kubernetes/) 负责，它讲 etcd 和调和在实践中意味着什么，理论部分则链接回这里。

## 学习路线

共十二个阶段，从部分失败到诊断一次事故，再到生产系统为挺过部分失败而实际使用的机制，以及如何验证这些机制真的成立。一个阶段包含若干课程，边界并不严格；一个阶段是否完成，取决于能力，而不是课程数量。

| 阶段 | 课程 | 内容 | 完成的标志 |
|---|---|---|---|
| 1. 部分失败 | 0001 | 本主题之后的每个话题都在回应的那一个问题 | 能解释为什么不能把网络当作可靠的 |
| 2. 时间与顺序 | 0002 至 0003 | 时钟、顺序，以及为什么超时是唯一可用的失败信号 | 能解释为什么超时无法区分慢节点和宕机节点 |
| 3. 一致性模型 | 0004 至 0006 | CAP、线性一致性、顺序一致性与最终一致性 | 能为给定的设计选择一致性模型并为之辩护 |
| 4. 共识 | 0007 至 0009 | Raft、领导者选举、共识能带来什么以及为什么代价如此 | 能解释共识协议带来什么、代价是什么，而无需证明其正确性 |
| 5. 诊断事故 | 0010 | 把上述机制应用到一次真实的生产事故上 | 给定一次由部分失败引起的事故，能说出背后的机制 |
| 6. 复制与法定人数 | 0011 | 基于领导者与无领导者的复制、读写法定人数、`R + W > N` 条件 | 能解释法定人数如何保证读到最新的写入，并为给定的工作负载选择 R 和 W |
| 7. 分区与分片 | 0012 | 一致性哈希、虚拟节点、热点键复制、请求路由 | 能解释为什么一致性哈希限制了扩缩容的代价，以及一个裸哈希环还需要什么才能应对失败和热点键 |
| 8. 最终一致性下的冲突解决 | 0013 | 最后写入胜出及其丢失的内容、版本向量、CRDT | 能区分检测冲突与解决冲突，并解释 CRDT 如何无损地合并 |
| 9. 跨服务的事务 | 0014 至 0015 | 两阶段提交及其阻塞式失败模式、saga 与补偿、事务性发件箱、幂等消费者 | 能解释 2PC 为什么会阻塞、saga 为避免阻塞放弃了什么，以及发件箱模式如何避免双写问题 |
| 10. 弹性工具箱 | 0016 至 0017 | 超时预算、带退避与抖动的重试、重试风暴、熔断器、负载削减、背压 | 能解释超时触发后该做什么，并为失败的依赖、过载的服务器或正在填满的队列匹配合适的机制 |
| 11. 部分失败的可观测性 | 0018 | span、追踪、跨网络边界的传播、span 类型 | 能解释追踪如何把一个请求跨服务的各个 span 串起来，以及为什么每一跳都必须显式地传播 |
| 12. 验证一个论断 | 0019 | Jepsen 的黑盒、模型检查式测试，混沌工程在生产中的故障注入，确定性模拟的可复现性 | 能解释每种验证技术做了什么权衡，以及一个给定的测试结果证明了什么、没有证明什么 |

## 课程

请按顺序学习。

| # | 课程 | 内容 |
|---|---|---|
| [0001](lessons/0001-partial-failure.md) | 部分失败 | 本主题之后的每个话题都在回应的那一个问题 |
| [0002](lessons/0002-clocks-and-ordering.md) | 时钟与顺序 | 为什么不同机器上的挂钟时间戳不能用来给事件排序，以及逻辑时钟如何在不需要同步时间的情况下为事件排序 |
| [0003](lessons/0003-timeouts-as-failure-detectors.md) | 作为失败检测器的超时 | 为什么每个实用的失败检测器都建立在超时之上，以及由此带来的准确性与速度之间权衡的形式化术语 |
| [0004](lessons/0004-the-cap-theorem-precisely.md) | 精确理解 CAP 定理 | CAP 实际证明了什么，为什么分区容忍从来不是可选项，以及让“三选二”成为错误表述的那些具体误读 |
| [0005](lessons/0005-linearizability.md) | 线性一致性 | 线性一致性实际保证了什么，为什么它是最强的常见一致性模型，以及在分区期间提供它的代价 |
| [0006](lessons/0006-sequential-and-eventual-consistency.md) | 顺序一致性与最终一致性 | 两种比线性一致性更弱的模型，各自仍然保证什么，以及如何为给定的设计在三者之间做选择 |
| [0007](lessons/0007-what-consensus-is-for.md) | 共识是用来做什么的 | 共识协议所解决的复制状态机问题，以及为什么它是线性一致系统协调背后的机制 |
| [0008](lessons/0008-raft-leader-election-and-log-replication.md) | Raft、领导者选举与日志复制 | Raft 如何选出唯一的领导者并通过它复制日志，这两个机制把复制状态机问题变成了具体的东西 |
| [0009](lessons/0009-what-consensus-costs.md) | 共识的代价 | 为什么每次写入都要付出一次到多数派的往返，为什么少数派分区失去的是可用性而不是一致性，以及如何权衡这笔代价与共识带来的东西 |
| [0010](lessons/0010-diagnosing-a-production-incident.md) | 诊断一次生产事故 | 运用部分失败、失败检测、一致性模型和共识，说出一次真实事故背后的机制，而不是抽象地谈论“网络”或“一致性” |
| [0011](lessons/0011-replication-and-quorums.md) | 复制与法定人数 | 共识协议并不是复制数据的唯一方式，而它那个更便宜的替代方案背后的法定人数条件，是一个单一的重叠保证，而不是模糊的多数同意 |
| [0012](lessons/0012-partitioning-and-sharding.md) | 分区与分片 | 一致性哈希之所以存在，是因为朴素的哈希取模 N 分区在节点加入或离开的那一刻几乎会重新映射一切，而即便是一致性哈希，也需要虚拟节点，才不会把一个失败节点的全部负载倾倒在某个倒霉的邻居身上 |
| [0013](lessons/0013-conflict-resolution-under-eventual-consistency.md) | 最终一致性下的冲突解决 | 检测两次写入是并发的，与决定如何处理它，是两个不同的问题，而最后写入胜出哪个都没有解决，它只是挑出一个幸存者，把输家扔掉 |
| [0014](lessons/0014-two-phase-commit-and-sagas.md) | 两阶段提交与 saga | 两阶段提交看起来像共识（一个协调者、一次投票、一次提交），但它解决的是另一个问题，付出的代价也更糟：如果协调者在投票中途宕机，它会永远阻塞，这正是生产系统转而使用 saga 的原因 |
| [0015](lessons/0015-the-transactional-outbox-and-idempotent-consumers.md) | 事务性发件箱与幂等消费者 | 不借助分布式事务，就无法原子地同时更新数据库和发布事件，所以发件箱模式彻底绕开了这个问题：在同一个本地事务中把事件写成一行普通记录，代价是一条消息可能被发送两次 |
| [0016](lessons/0016-timeouts-retries-and-backoff.md) | 超时、重试与退避 | 第 3 课确立了超时是唯一可用的失败信号，但触发超时后立即重试，恰恰会把一个正在恢复的服务的糟糕一天变成一场围攻，而这正是退避和抖动要防止的具体问题 |
| [0017](lessons/0017-circuit-breakers-load-shedding-and-backpressure.md) | 熔断器、负载削减与背压 | 带退避和抖动的重试仍然假定失败的调用值得尝试，而熔断器、负载削减和背压是它不再值得尝试时的三种答案，分别针对失败的依赖、过载的服务器和不堪重负的队列 |
| [0018](lessons/0018-distributed-tracing-and-correlation.md) | 分布式追踪与关联 | 本主题至今讲过的每个机制都告诉你系统在失败时会怎样，但没有一个告诉你某个具体请求中究竟是哪一跳失败了，而这正是追踪要回答的那件事 |
| [0019](lessons/0019-verifying-a-claim.md) | 验证一个论断 | Jepsen、混沌工程和确定性模拟都试图在客户之前找到真实的缺陷，但它们在真实性与可复现性之间做出了相反的取舍，知道谁是谁，才能明白一个给定的测试到底证明了什么 |

## 使用方式

每节课都简短且自成一体。答案默认折叠：先自己回忆，再展开查看。真实场景中的练习比阅读更重要，而把练习间隔开来正是关键。课程结束时仍不清楚的地方，值得先追溯到一手资料再继续往下学。
