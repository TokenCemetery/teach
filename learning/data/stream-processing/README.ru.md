# Обучение: потоковая обработка

Научитесь создавать, тестировать и запускать приложение Kafka Streams, которое даёт правильный ответ, когда записи приходят с опозданием, не по порядку или дважды, и говорить по его топологии, каких внутренних топиков, состояния и времени восстановления оно будет стоить, ещё до того, как попадёт в продакшен.

**Последний урок:** [20. Изменение топологии, от которой зависят другие](lessons/0020-changing-a-topology-others-depend-on.md)

## Каким выглядит результат

- Вы объясняете, исходя из дуальности потока и таблицы, как связаны топик, changelog и KTable, и предсказываете, что топология выдаст для заданного входа.
- Вы строите топологию с помощью DSL, читаете вывод `describe()` и называете каждый внутренний топик, который она создаёт, и зачем.
- Вы выбираете хранилище состояния для операции с состоянием и говорите, как его состояние восстанавливается, когда экземпляр, который его держит, умирает.
- Вы подбираете окно и grace period для вопроса, связанного со временем, и говорите, какие опоздавшие записи оно отбрасывает и когда выдаёт результат.
- Вы выбираете соединение для двух входов, делаете их ко-партиционированными или объясняете, почему GlobalKTable снимает эту необходимость, и предсказываете выход соединения.
- Вы говорите, что гарантирует `exactly_once_v2` и что остаётся за его пределами, и подбираете число задач, потоков выполнения, экземпляров и standby-реплик приложения под заданное время восстановления.
- Вы тестируете топологию с `TopologyTestDriver` и эксплуатируете работающее приложение по его метрикам, состояниям и обработчикам исключений.
- Вы выбираете между Kafka Streams, обычным потребителем, Flink и ksqlDB для нагрузки, проводите ревью чужой топологии и меняете работающую топологию, не ломая ни её состояние, ни её потребителей ниже по потоку.

## Ограничения

- Предполагается рабочее знание Java и журнала в том виде, в каком его изучает [`data/kafka`](../../data/kafka/): партиции, группы потребителей, гарантии доставки, хранение и компактизация. Эти уроки ссылаются туда, а не выводят всё это заново.
- Kafka Streams это единственный изучаемый движок. Примеры используют Java DSL и Processor API из Apache Kafka 4.3.
- Значения по умолчанию и протоколы меняются от релиза к релизу. Когда урок приводит одно из них, он называет страницу документации или KIP, откуда оно взято, и читателю стоит проверить на этой странице текущее значение.

## За рамками курса

- Сам журнал: партиции, группы потребителей, семантики доставки, цена транзакций, хранение и компактизация, Kafka Connect и Schema Registry. См. [`data/kafka`](../../data/kafka/), на который опирается этот трек.
- Частичные отказы и согласованность как теория: см. [`architecture/distributed-systems`](../../architecture/distributed-systems/). Этот трек учит только тому, что восстановление хранилищ состояния и ребалансировка меняют для приложения Streams.
- Apache Flink, Spark Structured Streaming и ksqlDB как самостоятельные темы. Этап 8 сравнивает их с Kafka Streams как кандидатов для нагрузки; запускать их он не учит.
- Язык Java: см. [`programming/java`](../../programming/java/).
- Загрузка потока в аналитическое хранилище: см. [`data/warehouses`](../../data/warehouses/).

| 3. Состояние | с 0005 по 0007 | Хранилища состояния, changelog-топики, агрегации, обновления KTable, кэш записей, Processor API и пунктуаторы | Можете выбрать хранилище для шага с состоянием и сказать, как его состояние переживает смерть экземпляра |
