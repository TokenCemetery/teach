# Lesson 24. Provenance and SBOMs

**Mission link:** The mission ends its supply-chain goal with proving where an artifact came from. Lesson 23 controlled what goes into the build. This lesson makes the output checkable: a signed statement of which workflow built an image from which commit, a list of what is inside it, and a verification step that refuses an image nobody can account for.

## Know this

### Two different questions

Provenance and an SBOM look alike and answer different questions:

|Document|Answers|Example question|
|---|---|---|
|Provenance|Where, when and how was it built?|Was this image built by the `ci.yml` workflow of my repository from a commit on `main`?|
|SBOM|What is inside it?|Does any image we run contain this vulnerable library?|

The glossary defines [provenance](../GLOSSARY.md) as verifiable information about where, when and how an artifact was built, and an [SBOM](../GLOSSARY.md) as a machine-readable list of components, versions and licences in a format such as SPDX or CycloneDX. A lockfile is an input and an SBOM describes the output. Neither is worth much unaccompanied. A document next to the artifact can be edited next to it, so the useful form is a signed statement bound to the artifact's digest.

### SLSA: what level of proof

SLSA is a framework for supply chain security, and its v1.0 build track has levels that say how much to trust provenance ([SLSA Security Levels](https://slsa.dev/spec/v1.0/levels)):

|Level|Requirement|Focus|
|---|---|---|
|Build L0|None|None|
|Build L1|Provenance showing how the package was built|Mistakes, documentation|
|Build L2|Signed provenance, generated by a hosted build platform|Tampering after the build|
|Build L3|Hardened build platform|Tampering during the build|

Level 3 adds strong controls: runs cannot influence one another even in the same project, and the secret material used to sign the provenance is not accessible to the user-defined build steps. GitHub's docs say artifact attestations by themselves provide SLSA v1.0 Build Level 2. They reach Build Level 3 when the build runs in a reusable workflow shared across repositories, which isolates the build process from the calling workflow ([Artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)). Lesson 25 covers reusable workflows. The levels are a way to say what you do and do not guarantee, not a badge.

### Generating an attestation

An attestation is a cryptographically signed claim. GitHub's includes a link to the workflow, the repository, organization, environment, commit SHA and triggering event, and other information from the OIDC token of the run ([Artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)). The signing uses Sigstore: the signing certificate is issued from the job's OIDC token, which is why the job needs `id-token: write`.

Who can use it matters before you plan around it. Attestations are available for repositories on all current plans, but on GitHub Free, Pro and Team they work only for public repositories. Private and internal repositories need GitHub Enterprise Cloud, and legacy plans such as Bronze, Silver and Gold are excluded ([Using artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)). A public repository signs with the Sigstore Public Good Instance and the result is written to a publicly readable transparency log, so what the attestation names is public. `ci-cd-practice` is public, so it works on a free account.

Two additions to lesson 13's `image` job. The permissions gain three entries, and a step follows the build that attests the pushed digest:

```yaml
  image:
    needs: build
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
      id-token: write
      attestations: write
      artifact-metadata: write
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      # checkout, buildx, login, metadata and the build-push step (id: push) as in lesson 13
      - name: Name the image in lowercase
        id: name
        run: echo "image=ghcr.io/${GITHUB_REPOSITORY,,}" >> "$GITHUB_OUTPUT"
      - name: Attest build provenance
        uses: actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2
        with:
          subject-name: ${{ steps.name.outputs.image }}
          subject-digest: ${{ steps.push.outputs.digest }}
          push-to-registry: true
```

What each piece does, per the docs: `id-token: write` lets the action request the OIDC token, `attestations: write` persists the attestation, and `packages: write` is needed for an image pushed to the registry. `artifact-metadata: write` is what lets the action create a storage record for the artifact on the organization's linked artifacts page, which is optional. `subject-name` is the fully qualified image name with no tag, `subject-digest` is the `sha256:` digest, and `push-to-registry` stores the attestation in the registry beside the image. Because a `permissions` block sets everything it does not list to `none` (lesson 14), leaving one out fails the step. `actions/attest-build-provenance` still exists, but as of version 4 it is a wrapper on `actions/attest`, and its README says new workflows should use `actions/attest` ([README](https://github.com/actions/attest-build-provenance)).

### Generating an SBOM and attesting it

The `attest` action creates a signed SBOM attestation when you give it `sbom-path`, accepting SPDX or CycloneDX in JSON. It does not create the SBOM, so a scanner such as Anchore's `sbom-action` produces the file first ([Using artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)):

```yaml
      - name: Generate an SBOM of the pushed image
        uses: anchore/sbom-action@66cbf4bc1f1c0d2edc94016e65bc221b6bb0ad6c # v0.24.3
        with:
          image: ${{ steps.name.outputs.image }}@${{ steps.push.outputs.digest }}
          registry-username: ${{ github.actor }}
          registry-password: ${{ secrets.GITHUB_TOKEN }}
          format: spdx-json
          output-file: sbom.spdx.json
      - name: Attest the SBOM
        uses: actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2
        with:
          subject-name: ${{ steps.name.outputs.image }}
          subject-digest: ${{ steps.push.outputs.digest }}
          sbom-path: sbom.spdx.json
          push-to-registry: true
```

The SBOM is made from the image that was pushed, not from the repository, so it lists what shipped, which typically includes the operating system packages in the base image as well as the Python packages the Dockerfile installed.

### Verify, or it was decoration

The docs are blunt: generating attestations alone provides no security benefit, the attestations must be verified. The GitHub CLI does it:

```console
$ docker login ghcr.io
$ gh attestation verify "oci://ghcr.io/$OWNER/ci-cd-practice@$DIGEST" --repo "$OWNER/ci-cd-practice"
...
✓ Verification succeeded!
...
```

Here `OWNER` is your GitHub user name in lowercase and `DIGEST` is the digest from a run. For an image, the argument is the image reference prefixed with `oci://`. By default `gh attestation verify` enforces the `https://slsa.dev/provenance/v1` predicate type and requires either `--owner` or `--repo`. The `--predicate-type` flag selects another type, such as `https://spdx.dev/Document/v2.3` for an SPDX SBOM attestation, and `--signer-workflow` also requires that a specific workflow signed it ([gh attestation verify](https://cli.github.com/manual/gh_attestation_verify)). If the attestation was generated by a reusable workflow, that workflow is the signer to name.

Verification checks identity, not safety. The docs warn that an attestation is not a guarantee that an artifact is secure: it links you to the source code and build instructions that produced it, and you define the policy and make the risk decision. The `gh` help adds a precision. Only the certificate fields and the timestamps cannot be manipulated by the workflow that made the attestation, while the predicate contents can be falsified if an attacker controls the workflow's execution, which is why the strongest setups build in a reusable workflow the caller cannot influence.

The place to verify is the deploy. In lesson 18's `staging` and `production` jobs, a verification step before the apply turns provenance into a gate: an image that was not built by your workflow does not run.

```yaml
      - name: Verify provenance before deploying
        env:
          GH_TOKEN: ${{ github.token }}
          IMAGE: ${{ needs.build.outputs.image }}
          DIGEST: ${{ needs.build.outputs.digest }}
        run: |
          echo "$GH_TOKEN" | docker login ghcr.io -u "$GITHUB_ACTOR" --password-stdin
          gh attestation verify "oci://${IMAGE}@${DIGEST}" --repo "$GITHUB_REPOSITORY"
```

When to attest: the docs say to sign software you release and expect people to verify, such as binaries people run and packages people download, and not frequent builds that exist just for automated testing, or individual files like source and documentation. Attesting every pull request build produces noise nobody will check.

## Practice

1. ▢ Which pair correctly says what each document tells a consumer of an image?

    - a) The SBOM names its builder, and provenance lists its contents
    - b) Provenance names its builder, and the SBOM lists its contents
    - c) Provenance lists its contents, and the SBOM names its builder
    - d) The SBOM names its commit, and provenance lists its licences

<details markdown="1"><summary>Check</summary>

**b)** Provenance records where and how the artifact was built, and an SBOM lists the components inside it. (a) and (c) swap them. (d) mixes them up too: the commit is in the provenance, and licences are part of what an SBOM lists.

</details>

2. ▢ Which SLSA v1.0 build level do GitHub artifact attestations provide on their own, what does that level protect against, and what does GitHub say moves a build to Level 3?

<details markdown="1"><summary>Check</summary>

Build Level 2: signed provenance generated by a hosted build platform, which protects against tampering after the build. GitHub says Level 3, which is about tampering during the build, needs the build to take place in a reusable workflow that isolates the build process from the calling workflow, so that the build instructions are known and vetted.

</details>

3. ▢ Predict, then run. Add the permissions, the `Name the image in lowercase` step and the `Attest build provenance` step to the `image` job in `ci-cd-practice`, push to `main`, and take the digest from the run. Then run the two commands below. What does each print?

    ```console
    $ gh attestation verify "oci://ghcr.io/$OWNER/ci-cd-practice@$DIGEST" --repo "$OWNER/ci-cd-practice"
    $ gh attestation verify "oci://ghcr.io/$OWNER/ci-cd-practice@$DIGEST" --repo "$OWNER/some-other-repo"
    ```

<details markdown="1"><summary>Hint</summary>

Verification asks whether the attestation matches the identity you name. The first command names the repository whose workflow signed it.

</details>

<details markdown="1"><summary>Check</summary>

The first succeeds and ends with `✓ Verification succeeded!`. The second fails: no attestation for that digest is linked to the other repository, so the command reports a verification failure and exits non-zero, even though the image is the same. The attestation proves "this workflow of this repository built this digest", and the identity you pass in is the claim being tested. A verification that passes `--repo` for the wrong repository would be checking nothing.

</details>

4. ▢ Debug this. After adding the attest step to a job that only had lesson 13's permissions, the step fails. Name the cause and the fix.

    ```yaml
        permissions:
          contents: read
          packages: write
    ```

    ```console
    Run actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6
    Error: Unable to get ACTIONS_ID_TOKEN_REQUEST_URL env variable
    ```

<details markdown="1"><summary>Hint</summary>

Count what the docs say the action needs, and remember what a `permissions` block does to every permission it does not list.

</details>

<details markdown="1"><summary>Check</summary>

The job has no `id-token: write`, so the runner never provided the OIDC request variable, and the action cannot get the token it signs with. The block also lacks `attestations: write`, which the next error would complain about. Add `id-token: write` and `attestations: write` to the job's permissions, and keep `packages: write` because the image is pushed to the registry. Grant them on the one job that attests, not the whole workflow.

</details>

5. ▢ A team on a free account has a private repository and wants attestations for its internal images. What do the docs say, and what are their options?

<details markdown="1"><summary>Check</summary>

On GitHub Free, Pro and Team, artifact attestations are available only for public repositories, so a private repository needs a GitHub Enterprise Cloud plan. The team can upgrade, make the repository public if its contents allow it, or accept the risk without attestations. It should not pretend that an unsigned SBOM or a checksum file next to the image provides what an attestation does.

</details>
