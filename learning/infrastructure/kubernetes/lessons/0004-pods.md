# Lesson 4. Pods

**Mission link:** The mission is to run a service on the cluster and own what happens to it, and everything you run is a pod. Knowing what a pod shares, what it can run before and beside your application, and why it is never moved or repaired by itself explains most of what a workload controller is for.
**Primary source:** [Docs: "Pods", Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/)

## Know this

### What a pod is

A **pod** is the smallest unit the cluster schedules: a group of one or more containers with shared storage and network, always placed together on one node ([Pods](https://kubernetes.io/docs/concepts/workloads/pods/)). The page describes it as a logical host for tightly coupled containers. Most pods hold one container, and then a pod is a wrapper around it; Kubernetes manages pods, not bare containers.

What the containers in one pod share:

|Shared|Meaning|
|---|---|
|Network namespace|One IP address and one port space for the whole pod. Containers reach each other on `localhost`, and two containers cannot listen on the same port|
|Volumes|Any volume the pod declares can be mounted into any of its containers, and its data survives a container restart|
|Node|All of a pod's containers run on the same node, and are placed there together|
|Hostname|Each container sees the pod's name as the hostname|

What they do not share is the image: each container has its own image and root filesystem. Containers in different pods have different IPs and talk over the network.

### A pod's life

A pod has a `phase`, a coarse summary of where it is: `Pending` (accepted, but containers not yet running, which includes time waiting to be scheduled and time pulling images), `Running`, `Succeeded`, `Failed`, and `Unknown` ([Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)). Each container has a state, `Waiting`, `Running` or `Terminated`. The `STATUS` column of `kubectl get pods` is a display field and not the same thing as the phase, so `CrashLoopBackOff` appears there without being a phase.

If a container exits, the kubelet restarts it in place according to the pod's `restartPolicy`, which is `Always`, `OnFailure` or `Never` and defaults to `Always`. Restarts back off exponentially (10s, 20s, 40s and so on, capped at 300 seconds), and the pod shows `CrashLoopBackOff` while it waits; the timer resets once a container has run for 10 minutes without problems. These restarts only replace containers inside the same pod on the same node. This is the same restart behavior you met in the containers track, now done by the kubelet.

### Why a pod is never rescheduled

Here is the fact the rest of the stage depends on. A pod stays on its node until it finishes, is deleted, is evicted for lack of resources, or the node fails. The Pod Lifecycle page states that a given pod, identified by its UID, is never rescheduled to a different node: it can be replaced by a new, near-identical pod, with possibly the same name and a different UID, which is not guaranteed to land on the same node.

The kubelet restarts containers, but only on its own node. The scheduler places a pod once, when it has no node. Neither moves it. So a pod you created directly, with `kubectl run` or a Pod manifest, has no one watching its count: if its node fails, or someone deletes it, nothing creates another. The pod is also mostly immutable. Most metadata cannot change, and a running pod accepts updates to only a few fields, such as a container `image`, `activeDeadlineSeconds`, `terminationGracePeriodSeconds` and added `tolerations`. To change anything else you replace the pod.

This is why the docs say you rarely create pods directly, even single ones: you create them through workload resources such as a Deployment or a Job, which hold a **pod template** and a controller that creates, counts and replaces pods from it. The next lessons are those controllers. Change the template and the controller makes new pods from it; it does not edit the old ones.

### Containers that run before: init containers

A pod can list `initContainers` beside `containers`. They run before the app containers start, one at a time, and each must finish successfully before the next one starts ([Init Containers](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/)). If one fails, the kubelet restarts it until it succeeds, unless the pod's `restartPolicy` is `Never`, in which case the pod is failed. Regular init containers do not support `livenessProbe`, `readinessProbe`, `startupProbe` or `lifecycle`.

They exist for setup that should not live in the application image: a tool the app image lacks, waiting for a dependency, cloning a repository into a volume, or generating a config file for the app. They can use a different image and see a different filesystem, and share data with the app containers through a volume. While they run, `kubectl get pods` shows `STATUS` as `Init:0/2` (none of two done), then `PodInitializing`, then `Running`.

### Containers that run beside: sidecars

A **sidecar** is a container that starts before the application container and keeps running with it, for logging, proxies or data sync. Kubernetes implements one as an init container with `restartPolicy: Always`; the page [Sidecar Containers](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/) marks this stable since v1.33. The difference from a regular init container is the point:

|Container|Defined in|Runs|On pod shutdown|
|---|---|---|---|
|Regular init container|`initContainers`|To completion, then the next starts|Already finished|
|Sidecar|`initContainers` with `restartPolicy: Always`|Starts in order, then stays running for the whole pod life. Its readiness probe counts toward the pod's readiness|Stopped after the main container, in reverse order of the list|
|App container|`containers`|All start together after the init containers|Stopped first|

```yaml
spec:
  initContainers:
    - name: logshipper
      image: alpine:3.20
      restartPolicy: Always
      command: ["sh", "-c", "tail -F /opt/logs.txt"]
      volumeMounts:
        - name: data
          mountPath: /opt
  containers:
    - name: myapp
      image: alpine:3.20
      command: ["sh", "-c", "while true; do date >> /opt/logs.txt; sleep 1; done"]
      volumeMounts:
        - name: data
          mountPath: /opt
  volumes:
    - name: data
      emptyDir: {}
```

Ordering is what the old way, a second entry in `containers`, could not give you: nothing guaranteed the helper started first or stopped last. A native sidecar also does not keep a Job from completing after its main container finishes. Putting a second container in `containers` is still correct when both are required and you do not care about start and stop order, or when you must support clusters older than the feature.

### How many containers belong in one pod

Containers in one pod scale, schedule and are replaced together. The page says to group them only when they are tightly coupled, and notes that you do not run several containers in a pod to get replication: run several pods. A web server and a helper that refreshes its files fit. A web application and its database do not, because you would not want to scale them, restart them or place them as one thing.

## Practice

1. ▢ Which statement about a pod you created directly, with no controller, is true?

    - a) The scheduler moves it onto a healthy node
    - b) The node controller copies it onto another node
    - c) Nothing recreates it after its node is lost
    - d) Its kubelet restarts it on a different node

<details markdown="1"><summary>Check</summary>

**c)** No controller owns it, so no one compares its count to anything. (a) is wrong because the scheduler places a pod once, while it has no node. (b) is wrong because the node controller marks nodes and evicts pods, and does not create copies. (d) is wrong because a kubelet only manages pods on its own node and a failed node's kubelet is not running.

</details>

2. ▢ Predict, then run. The `probe` container runs only `sleep` and has no web server. What does the `exec` print, and what does `READY` show?

    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: pair
    spec:
      containers:
        - name: web
          image: nginx:1.27
        - name: probe
          image: busybox:1.37
          command: ["sh", "-c", "sleep 3600"]
    ```

    ```console
    $ kubectl apply -f pair.yaml
    $ kubectl get pod pair
    $ kubectl exec pair -c probe -- wget -qO- http://localhost:80
    ```

<details markdown="1"><summary>Hint</summary>

What do containers in one pod share, and what does `localhost` mean inside a pod?

</details>

<details markdown="1"><summary>Check</summary>

```text
NAME   READY   STATUS    RESTARTS   AGE
pair   2/2     Running   0          9s
```

The `wget` prints the start of nginx's default page, which begins with `<!DOCTYPE html>` and `<title>Welcome to nginx!</title>`. `probe` reached nginx on `localhost` because both containers share one network namespace and one IP. `READY` counts containers: 2/2 means both are running and ready.

</details>

3. ▢ Predict, then run. Which `STATUS` values does `kubectl get pod init-demo -w` print, and what does the last command print?

    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: init-demo
    spec:
      initContainers:
        - name: prepare
          image: busybox:1.37
          command: ["sh", "-c", "echo ready > /work/index.html && sleep 10"]
          volumeMounts:
            - name: work
              mountPath: /work
      containers:
        - name: web
          image: nginx:1.27
          volumeMounts:
            - name: work
              mountPath: /usr/share/nginx/html
      volumes:
        - name: work
          emptyDir: {}
    ```

    ```console
    $ kubectl apply -f init-demo.yaml && kubectl get pod init-demo -w
    $ kubectl exec init-demo -- cat /usr/share/nginx/html/index.html
    ```

<details markdown="1"><summary>Hint</summary>

The init container must finish before `web` starts, and it sleeps for 10 seconds after writing the file. The two containers share a volume.

</details>

<details markdown="1"><summary>Check</summary>

```text
NAME        READY   STATUS            RESTARTS   AGE
init-demo   0/1     Init:0/1          0          2s
init-demo   0/1     PodInitializing   0          12s
init-demo   1/1     Running           0          14s
```

and then `ready`. The pod shows `Init:0/1` while the single init container runs, `PodInitializing` once it has succeeded and the app container is being set up, and `Running` when `web` is up. The `exec` reads the file the init container wrote into the shared `emptyDir`, which `web` serves. The pod's `READY` is `0/1` until the app container is ready, so a pod in init is not ready.

</details>

4. ▢ A pod's `STATUS` stays at `Init:CrashLoopBackOff` and the app container never starts. Which commands find the cause, and why does `kubectl logs mypod` alone not help?

<details markdown="1"><summary>Hint</summary>

The app container has not started, so it has no logs. Which container is failing, and how do you select a container?

</details>

<details markdown="1"><summary>Check</summary>

Run `kubectl describe pod mypod` to see which init container is failing, its last state and exit code, and the events, then `kubectl logs mypod -c <init-container-name>`, adding `--previous` for the run before the latest restart. A plain `kubectl logs mypod` asks for a container that has not started, so it shows nothing useful. The init container is restarted until it succeeds, which is why the pod is stuck and not failed: the app container waits for it.

</details>

5. ▢ What is the difference between an entry in `initContainers` with `restartPolicy: Always` and a second entry in `containers`, and when would you still pick the second?

<details markdown="1"><summary>Check</summary>

The first is a native sidecar: it starts in order before the app containers, keeps running, is stopped after the main container, and does not stop a Job from completing. The second starts alongside the app with no ordering guarantee. Pick the second when both containers are required and neither needs to start first or stop last, or when the cluster does not support the native form.

</details>

6. ▢ A teammate proposes one pod holding the web application and its PostgreSQL, "so they talk over `localhost`". Give two reasons that is a poor fit.

<details markdown="1"><summary>Check</summary>

Containers in a pod are scheduled, scaled and replaced together, so the database would be copied with every web replica, which is not what replication of a database means, and a restart or replacement of the pod takes both down. The page also says to group containers only when tightly coupled and that replication comes from more pods, not more containers. A separate pod or StatefulSet reached by a Service is the usual shape (lessons 8 and 17).

</details>
