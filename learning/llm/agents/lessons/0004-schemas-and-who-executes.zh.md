# 第 4 课：参数 schema 与谁执行什么

**使命关联:** 为一个给定的任务写出智能体循环，说清上下文里每条消息在做什么，以及什么会让循环结束。
**主要来源:** [文档：“Tool use with Claude”，Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
**前置知识:** [第 3 课](0003-the-wire-format-of-a-tool-call.md)

## 热身

1. ▢ 向模型服务商发送工具定义时，JSON schema 起什么作用？

<details markdown="1"><summary>检查</summary>

它描述工具接受哪些参数：名称、类型和约束。模型调用工具时，依据 schema 决定发送什么。一份格式良好的 schema，可以防止模型发送无效或格式错误的参数。

</details>

2. ▢ 模型调用了一个工具，运行框架收到这个调用时，它怎么知道应该在本地执行，还是发给服务商？

<details markdown="1"><summary>检查</summary>

你在定义工具时就必须告诉运行框架：把它标记为客户端工具（在本地执行），或服务端工具（由服务商处理）。模型从来不知道其中的区别，它只看得到名称和 schema。

</details>

## 要点

### 作为护栏的 schema

JSON schema 做两件事。第一，它记录工具期望什么：属性名称、类型，以及每个属性是可选还是必填。下面是一个简单的例子：

```json
{
  "type": "object",
  "properties": {
    "city": {"type": "string", "description": "The city name"},
    "units": {"type": "string", "enum": ["celsius", "fahrenheit"], "description": "Temperature scale"}
  },
  "required": ["city"]
}
```

这份 schema 的意思是：工具接受一个对象，其中 `city`（字符串）必填，`units`（"celsius" 或 "fahrenheit" 之一）可选。模型读到这些，就知道必须始终提供城市，但可以省略单位。

第二，schema 起约束的作用。模型调用工具时，只能发送与 schema 匹配的值。如果 schema 规定 `units` 必须是两个字符串之一，模型就不能发送 "kelvin" 或一个数字。严格的 schema 可以杜绝整类格式错误的调用，运行框架无需自己去验证。

### 缺少必填字段时会发生什么

如果模型漏掉了必填字段，服务商的 API 会报错。大多数框架会捕获这个错误，并把它作为工具结果发回给模型：“Error: missing required field 'city'”。这样模型就有机会改正。这不是崩溃，而是循环中正常的一部分。描述清楚的 schema 能减少这种情况的发生，因为模型会仔细阅读 schema。

### 客户端工具与服务端工具

**客户端工具**是你自己代码里的一个函数，由运行框架来执行。实现由你负责：

```python
def get_weather(city: str, units: str = "celsius"):
    # Your code to fetch weather
    return f"18{units[0]}, partly cloudy"
```

模型调用 `get_weather` 时，你的运行框架运行你的函数并收集结果。

**服务端工具**是由服务商在自己的基础设施上执行的东西：网页搜索、沙箱中的代码执行、文件系统访问，或托管的 API 调用。你定义它做什么（名称和 schema），但从不编写实现。服务商运行它并收集结果，运行框架再从响应中读取。

### 为什么这个区别很重要

当你说“模型调用了一个工具”时，用词其实是松散的。模型从不执行任何东西。它发出的是一个结构化的请求，意思是“用这些参数运行这个工具”。由运行框架接收这个请求并执行它，方式可以是：

1. 调用你编写的函数（客户端工具），或
2. 请服务商运行某个托管的东西（服务端工具），或
3. 通过网络把它发给第三方服务。

模型并不关心是哪一种。这个区别是你要关心的：它影响代码放在哪里、你怎么写它，以及失败可能出现在哪里。

### 这对循环为什么重要

在智能体循环里，模型生成工具调用，运行框架执行它们。如果工具失败了，结果是一个带有错误的工具结果，而不是让循环崩溃的异常。无论工具是客户端的还是服务端的，都是如此：

- 客户端工具返回错误，是因为网络断了、数据库查询失败了，或者你的验证逻辑拒绝了这个输入。
- 服务端工具返回错误，是因为服务商的沙箱超时了、代码抛出了异常，或者触及了 API 的速率限制。

无论哪种，错误都只是又一个工具结果，由模型决定下一步做什么。

### 权限与服务端工具

服务端工具带来了一个新问题：模型有没有权限调用它？如果你让模型访问代码执行、文件读取或网络，你就是在信任它（在 schema 所设定的边界之内）会安全地使用这项能力。这是一个安全决策，而不是技术决策。schema 能强制规定工具可以接收哪些参数，但无法阻止模型把这项能力用在你没有预期的地方。这就是工具集设计很重要的原因，也是并非每个工具都适合每个智能体的原因。

## 练习

1. ▢ 一份工具 schema 要求有 `query` 字段（字符串），但没有定义 `max_results` 字段。模型能发送 `max_results` 参数吗？为什么能或为什么不能？

<details markdown="1"><summary>检查</summary>

在严格的 schema 里不能。JSON schema 的定义可以允许或不允许额外的属性。如果 schema 没有提到 `max_results`，模型就不能发送它（否则会被服务商拒绝）。schema 是穷尽的：只有列出的属性才可以出现，除非 schema 明确允许额外的属性。

</details>

2. ▢ 你有一个查询数据库的客户端工具。schema 规定 `user_id` 必填，但模型发来的调用没有它。接下来会发生什么？

<details markdown="1"><summary>提示</summary>

服务商拒绝格式错误的调用时，运行框架会怎么做？

</details>

<details markdown="1"><summary>检查</summary>

服务商拒绝它，运行框架把错误作为工具结果发回给模型：“Error: missing required field 'user_id'”。模型读到这个错误，就有机会改正调用。循环不会崩溃，错误只是一个正常的结果。

</details>

3. ▢ 下面哪项最能描述模型调用服务端工具与客户端工具时发生的事？

    - a) 服务端工具在你的基础设施上运行；客户端工具在服务商的基础设施上运行
    - b) 模型发出对工具的请求；由运行框架决定在哪里执行
    - c) 服务端工具总是完成得更快，因为服务商做了优化
    - d) 两种你都要写实现，只是写法不同

<details markdown="1"><summary>检查</summary>

**b)** 无论哪种，模型发出的都是同样的结构化请求。运行框架读取工具定义，判断它是客户端的还是服务端的，并据此安排执行。(a) 正好说反了：客户端工具归你，服务端工具归服务商。(c) 是错的：速度取决于实现，而不是它是服务端的还是客户端的。(d) 有一部分对，但漏掉了你从不编写服务端工具，只是定义它们。

</details>

4. ▢ 你为“search_the_web”定义了一个服务端工具，其 schema 只要求 `query` 字段。模型用 `query="python", limit=5` 调用它。服务商会怎么做？

<details markdown="1"><summary>检查</summary>

要么只用 query 执行调用并忽略 limit，要么因为 schema 不允许多出来的 `limit` 字段而拒绝这次调用。结果取决于 schema 的定义是否允许额外的属性。如果 schema 是严格的（默认如此），多出来的字段就是错误。

</details>

## 实战练习

- [ ] 为一个真实的任务（搜索、检索、计算或获取）找一份或写一份工具 schema。标出哪些字段必填、哪些有约束（枚举、字符串长度、数值范围）、哪些可选。把其中一个字段的描述改写得更清楚。
- [ ] 运行一个智能体，或写一个调用工具的运行框架，并故意给它发送一个无效的参数（漏掉必填字段、发送错误的类型、发送枚举之外的值）。观察服务商如何响应，以及你的运行框架或框架如何处理。
- [ ] 明天：为同一个任务（比如“列出文件”）设计一个客户端工具和一个服务端工具。为两者都写出 schema。说明工具各自所在的位置带来的一项取舍。
