# 第 5 课：并行调用与作为结果的错误

**使命关联:** 为一个给定的任务写出智能体循环，说清上下文里每条消息在做什么，以及什么会让循环结束。
**主要来源:** [文档：“Tool use with Claude”，Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
**前置知识:** [第 4 课](0004-schemas-and-who-executes.md)

## 热身

1. ▢ 在模型的单个轮次里，它能同时请求不止一个工具调用吗？

<details markdown="1"><summary>检查</summary>

能。模型可以在一次响应里发出多个工具调用块，每个都有唯一的 id。运行框架执行所有这些调用（可能并行），汇集结果，再作为下一条消息发回去。

</details>

2. ▢ 工具失败时，运行框架怎么做：抛出一个让循环崩溃的异常，还是把错误返回给模型？

<details markdown="1"><summary>检查</summary>

把错误作为工具结果返回给模型。循环继续；模型有机会重试、换一个工具，或者解释这次失败。

</details>

## 要点

### 一个轮次里的并行工具调用

智能体循环就是发送、执行、追加、重复。模型的一次响应可以包含多个工具调用：

```json
{
  "role": "assistant",
  "content": [
    {"type": "text", "text": "I'll gather that data for you."},
    {
      "type": "tool_use",
      "id": "toolu_01XYZ",
      "name": "get_weather",
      "input": {"city": "Lisbon"}
    },
    {
      "type": "tool_use",
      "id": "toolu_02ABC",
      "name": "get_weather",
      "input": {"city": "Madrid"}
    }
  ],
  "stop_reason": "tool_use"
}
```

每个调用都有自己唯一的 id。模型已经决定：“我需要里斯本和马德里两地的天气。”你的运行框架现在可以：

1. 按顺序执行两个工具（一个接一个），或者
2. 并行执行它们（同时进行），取决于你的实现。

选择权在你。如果它们相互独立而且很快，并行可以节省延迟。如果它们争用资源，或者其中一个依赖另一个，顺序执行更简单。

### 在下一轮之前汇集结果

所有工具调用完成后，运行框架汇集结果，在一条消息里发回去。每个结果都标着它所回应的那次调用的 id：

```json
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_01XYZ",
      "content": "18C, partly cloudy"
    },
    {
      "type": "tool_result",
      "tool_use_id": "toolu_02ABC",
      "content": "22C, sunny"
    }
  ]
}
```

模型现在拿到了两个结果，通过 id 知道哪个是哪个，并决定下一步做什么。关键在这里：所有结果在一条消息里一起返回，所以模型是把它们当作一组来处理的。

### 把错误当作结果

工具失败时，运行框架不会让循环崩溃。它会捕获错误，像对待成功的结果一样，把它作为结果发回模型。一个错误的工具结果长这样：

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01XYZ",
  "content": "Error: city not found",
  "is_error": true
}
```

`is_error` 字段告诉模型，这个结果表示失败，而不是成功。模型读到它，就得做出决定：换个城市重试同一个工具，试试另一个工具，或者放弃并向用户解释这个错误。

### 为什么错误是结果，而不是异常

在很多系统里，函数调用失败会抛出异常并停止执行。在智能体循环里，工具调用失败只是信息：返回给模型的数据。为什么这样设计？

因为模型才是主导者。调用工具的是模型，工具失败时该怎么办，也应该由它来决定。也许它想重试，也许它想换一个工具，也许它想向用户要更多信息。异常会剥夺这个选择。

这并不是在纵容糟糕的代码，而是一种设计选择：把模型当作编排者，而不是调用栈里的又一个函数。运行框架的工作是执行模型要求的事，收集结果（无论成功还是失败），再交还给模型去解读。

### 错误来自许多地方

工具调用可能因为很多原因失败：

- 客户端工具的代码抛出了异常（数据库宕机、输入无效、超时）。
- 服务端工具执行了，但返回了错误（API 速率限制、文件未找到、权限被拒绝）。
- 运行框架自己拒绝了这个调用（schema 验证失败、缺少必填字段）。
- 网络出了问题（服务商不可达、连接断开）。

所有这些，都会变成带有错误信息的工具结果，而不是崩溃。

## 练习

1. ▢ 模型在一个轮次里发出两个工具调用：一个成功，一个失败。运行框架如何把两个结果都发回模型？

<details markdown="1"><summary>检查</summary>

放在一条 user 角色的消息里，其中有两个 tool_result 块，每个都标着对应调用的 id。一个结果带有 `is_error: true` 或一条错误信息，另一个带着成功的数据。模型在一个轮次里同时拿到两者，并决定下一步做什么。

</details>

2. ▢ 你有一个搜索数据库的工具。模型调用它，搜索超时了。你的运行框架该怎么做？

<details markdown="1"><summary>提示</summary>

想一想，处理超时是谁的工作，以及模型需要知道什么。

</details>

<details markdown="1"><summary>检查</summary>

捕获超时，记录错误信息（例如“Error: search timed out after 30s”），并把它作为带有 `is_error: true` 的工具结果发回模型。然后由模型决定：用更简单的查询重试、换一个工具，或者放弃。循环不会崩溃。

</details>

3. ▢ 模型发出三个并行的工具调用。运行框架应该：

    - a) 一个接一个地执行，这样其中一个失败时可以提前停止
    - b) 并行执行，等所有结果都到齐后再发回去
    - c) 立刻返回成功的结果，失败的结果以后再发
    - d) 一旦有一个失败，就取消剩下的调用

<details markdown="1"><summary>检查</summary>

**b)** 并行执行，并等待所有结果。模型要了三样东西，就应该拿到三个结果（成功或失败）。提前停止 (a) 或取消 (d)，会让模型无从得知发生了什么。在不同的时间返回结果 (c) 违背了协议：结果是在一条消息里一起返回的。

</details>

4. ▢ 你写了一个把两个数相乘的客户端工具。模型用 `x=5, y="hello"` 调用它。运行框架尝试执行，函数抛出了类型错误。运行框架的下一步是什么？

<details markdown="1"><summary>检查</summary>

捕获异常，格式化错误（例如“Error: cannot multiply number by string”），并把它作为工具结果发回模型。模型现在知道这次调用失败了，可以用有效的输入重试，或者尝试别的办法。循环继续。

</details>

## 实战练习

- [ ] 写一个或找一个会发出并行工具调用的智能体。追踪其中一次模型同时请求两个工具的执行。验证两个结果在一条消息里一起返回，并各自带着自己的 id。
- [ ] 故意让一个工具失败（调用一个宕机的数据库、触发验证错误，或给工具发送无效的输入）。观察运行框架如何格式化错误并发给模型，再看模型接下来做什么。
- [ ] 明天：写一个并行执行工具调用的运行框架（用线程、异步，或你所用语言的并发模型），并收集结果。验证即使有些工具失败了，它也会在一条消息里把所有结果发回去。
