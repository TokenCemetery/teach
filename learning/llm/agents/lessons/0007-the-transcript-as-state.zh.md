# 第 7 课：作为状态的对话记录

**使命关联:** 认识到对话记录是智能体唯一的状态，能帮你从轨迹出发诊断出问题的智能体，而不是猜测模型为什么会困惑或重复，这服务于“从轨迹出发诊断出问题的智能体”这一使命。
**主要来源:** [文章：“Building Effective Agents”，Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
**前置知识:** [第 6 课](0006-writing-the-loop.md)、[轨迹](../GLOSSARY.md)

## 热身

1. ▢ 来自第 6 课：运行框架调用模型并收到响应之后，在执行任何工具调用之前必须发生什么？

<details markdown="1"><summary>检查</summary>

响应必须立即追加到对话记录里，先于执行任何工具。否则模型自己的请求就从未被记录，之后的轮次也就看不出为什么会有一个工具结果。

</details>

2. ▢ 来自第 6 课：说出运行框架可以检查的、用来结束智能体循环的两种不同停止条件。

<details markdown="1"><summary>检查</summary>

以下任意两种：模型返回了没有工具调用的一轮，触及最大轮次或 token 预算的上限，模型调用了明确的停止工具，或者超过了错误计数阈值。

</details>

## 要点

### 只有对话记录会留存

在一次模型调用与下一次之间，运行框架保存着两样东西：

1. 对话记录：完整的对话历史，包括每一条模型响应、工具调用和工具结果。
2. 运行框架的元数据：计数器（轮次数、错误数）、限制（最大轮次、最大错误数）、工具注册信息、配置。

模型看不到运行框架的元数据。模型只看得到对话记录。如果某件事不在对话记录里，模型就不知道它发生过。

这件事既简单，又意味深长。它意味着：

- 除非运行框架把它放进对话记录，否则模型无法对运行框架内部做出的决定进行推理。
- 在各轮之间，没有别的东西会留存。没有内部标志，没有隐藏状态，运行框架元数据之外也没有变量。
- 回放一次智能体的运行，就是把同一份对话记录重新喂给模型，并从那里继续。

### 轨迹与对话记录会出现分歧

轨迹是发生过的一切的完整记录：每一轮、每一个决定、每一条日志和每一个副作用。对话记录是展示给模型看的内容。二者并不相同。

例如：

- 运行框架执行了一个工具调用，得到 100KB 的结果，却认为结果太长，在追加到对话记录之前把它截断了。轨迹里写的是“工具调用成功，结果为 100KB”；对话记录里写的是“工具调用成功，结果是前 10KB”。模型只知道第二个版本。
- 运行框架因为第一次尝试失败，决定重试一个工具。这个决策日志被写进文件，留待人以后调试。但运行框架从未把“我要重试”追加到对话记录里。下一轮，模型并不知道发生过重试，它只看到结果。
- 一个工具调用悄无声息地失败了。运行框架记了日志，却没有把错误信息追加到对话记录，因为运行框架的设计者忘了。模型始终不知道这个工具失败了。下一轮，模型可能会再次请求同一个工具，不明白为什么上次没成功。

结果是：你看轨迹，可能会得出“运行框架做了一个合理的决定”的结论，可是只看对话记录，你看到的是一个困惑的模型。模型并没有困惑，只是没有人告诉它。

### 一个完整的例子：从未存在过的工具结果

设想这样一个场景：

智能体要先查一个价格，然后打折，再确认。在第二轮，模型调用工具来获取价格。工具返回“Item XYZ costs $100”。运行框架执行了工具，得到结果，并把它追加到对话记录里：

```text
Agent turn 1: "I will find the price of item XYZ"
Agent turn 1 tool call: fetch_price(item="XYZ")
Tool result: "Item XYZ costs $100"

Agent turn 2: "I will apply a 10% discount. $100 - 10% = $90."
Agent turn 2 tool call: confirm_price(item="XYZ", price="$90")
```

这行得通。模型看到了结果，并正确地进行了推理。

现在设想一个变体：运行框架为了监控，把结果记录到数据库里。日志插入失败了。运行框架把这个错误记到了文件里，但开发者从未向对话记录追加任何内容。下一轮是这样开始的：

```text
Agent turn 1: "I will find the price of item XYZ"
Agent turn 1 tool call: fetch_price(item="XYZ")

Agent turn 2: "I need to fetch the price. Let me call fetch_price again."
Agent turn 2 tool call: fetch_price(item="XYZ")
```

模型又请求了一次价格。它不是在固执，也不是在犯傻。对话记录里从未出现第一轮的结果。模型无从知道调用成功了。这称为分歧：轨迹说“结果已经取得并记录了”，对话记录却说“什么也没发生”。

修复的办法是，在继续之前总是先追加到对话记录里，即使副作用失败了也一样：

```text
Tool result (appended immediately): "Item XYZ costs $100"

[Later, harness logs to database, but the append already happened]
Log to database failed [this error never goes in the transcript]
```

现在，无论下游出了什么错，模型都知道这个结果发生过。

### 为什么把对话记录作为状态，让恢复执行变得容易

假设一次智能体运行被中断了。运行框架崩溃了，网络断了，配额用完了。你想从它中断的地方恢复智能体。

如果智能体把状态存放在内部变量、标志和散落在运行框架各处的决定里，恢复就很难。你得保存所有这些状态，把它们恢复出来，还得祈祷没有遗漏什么。

如果智能体的状态就只是对话记录，恢复就很简单：保存对话记录，然后开始一次新的运行，把同一份对话记录重新喂给模型，从下一轮继续循环。模型会看到它之前看到的一切，并继续推理。没有需要重建的隐藏状态，没有需要恢复的标志，没有需要跟踪的变量。对话记录就是契约。

同样，你可以回放智能体的一次运行来调试它。把轨迹（发生过的一切的完整日志）作为对话记录喂回去，看模型接下来会做什么。你甚至可以手动编辑对话记录，测试模型在某个假设的情形下会怎么做。

## 练习

1. ▢ 一个智能体要搜索一份文档，读取它，并做总结。在第二轮，它调用了搜索工具，工具返回了 10 条结果。在把结果追加到对话记录之前，运行框架把结果过滤成最相关的三条，只追加了这三条。模型看到了什么？为什么读对话记录时，这个设计选择是看得出来的？

<details markdown="1"><summary>检查</summary>

模型看到的是三条结果，而不是十条。它不知道运行框架做过过滤；它只知道对话记录里有什么。如果这是有意为之，这个设计是可以接受的：运行框架选择通过过滤来减少 token 用量。关键在于，通过阅读对话记录，你能确切地看到模型看到了什么（三条结果），并推断在这些信息之下，模型的下一个决定是否合理。你不会因为曾经有十条结果而感到困惑；对话记录展示的是模型视角下的世界。

</details>

2. ▢ 一位运行框架的开发者想记录哪些工具被调用过、各调用了多少次。他们应该把这个计数存在只属于运行框架的变量里，还是在每次模型调用之前，把一份摘要追加到对话记录里？

<details markdown="1"><summary>提示</summary>

想一想，模型需要知道什么才能做决定，而哪些信息只对事后由人调试有用。

</details>

<details markdown="1"><summary>检查</summary>

这取决于用例。如果模型需要知道“你已经调用过三次搜索了，也许换个工具试试”，那么这个计数就必须放进对话记录。如果计数纯粹用于监控，模型不需要据此调整行为，那么只属于运行框架的变量就可以。但如果模型可能因为知道这个计数而受益，就把它放进对话记录，让模型在下一轮看到它。一个稳妥的默认做法是：凡是可能影响模型下一个决定的内容，都追加进去。

</details>

3. ▢ 你在调试一次智能体运行。你读轨迹，看到一个工具调用成功了，结果也被追加了。你再读模型实际看到的对话记录，结果却不在里面。发生了什么？

    - a) 运行框架追加了结果，之后在再次调用模型之前，又把它从对话记录里删掉了
    - b) 轨迹和对话记录本来就应该不同；对话记录是摘要，轨迹是完整的
    - c) 结果被追加到了运行框架的日志里，但没有追加到对话记录里；模型从未看到它
    - d) 工具调用实际上失败了，轨迹是错的

<details markdown="1"><summary>检查</summary>

**c)** 结果被追加到了运行框架的日志里，但没有追加到对话记录里；模型从未看到它。从模型的视角看，轨迹和对话记录应该几乎一致（尽管对话记录为了效率可能被截断或抽样）。如果轨迹说发生了某件事，对话记录里却看不到，最可能的原因是运行框架记了日志，却没有把它追加到对话记录里。这就是完整例子里展示的那个 bug。追加之后又从对话记录里删除 (a) 会很反常，也违背了目的。对话记录不是摘要，它应该是对话历史 (b)。轨迹出错 (d) 是可能的，但不如日志上的 bug 常见。

</details>

4. ▢ 你想构建一个可恢复的智能体。运行在五轮之后被中断了。用一句话描述：为了从第六轮恢复智能体，你需要把什么持久化到磁盘上。

<details markdown="1"><summary>检查</summary>

你需要持久化对话记录（截至第五轮的对话历史，包括每一条模型响应、工具调用和工具结果）。恢复时，把这份对话记录作为起始上下文喂给模型，调用模型，然后继续循环。运行框架的元数据（轮次计数器、错误计数器等）可以重建或重置；只有对话记录是必不可少的。

</details>

## 实战练习

- [ ] 运行一个至少发出三次工具调用的智能体（来自你用的某个库，或你自己写的）。检查它生成的对话记录。对每一个工具结果，验证它是否出现在模型下一轮会看到的内容里。如果有结果缺失，追查原因（是没有被追加，还是被截断了，或者被过滤了？）。

- [ ] 在你的智能体代码或运行框架里，找一个信息被记了日志、却没有追加到对话记录的地方。问问自己：模型需要知道这个才能做出更好的决定吗？如果需要，就把它加进对话记录。如果不需要，就保留为只属于运行框架的日志。

- [ ] 明天：从零设计一个可恢复的智能体。写出运行函数的伪代码，它以对话记录为输入，并从下一轮开始恢复。验证你没有依赖任何只属于运行框架的状态来做决定。
