# Урок 8. Имя и описание инструмента

**Связь с целью курса:** Проектирование поверхности инструментов агента (имена, описания, формы возврата и граница разрешений, которая решает, что агент может делать без присмотра) начинается с понимания того, что имена и описания это не документация API для человека: это поверхность промпта, которую модель читает, чтобы решить, когда и как вызвать инструмент.
**Первоисточник:** [Статья: "Writing Effective Tools for Agents", Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
**Предварительные требования:** [Урок 7](0007-the-transcript-as-state.md), [Инструмент](../GLOSSARY.md)

## Разминка

1. ▢ Из урока 7: как модель «помнит», что произошло на предыдущем ходу цикла агента?

<details markdown="1"><summary>Проверка</summary>

Сама она не помнит. Обвязка заново отправляет полный транскрипт при каждом вызове, поэтому то, что выглядит как память, на деле модель заново читает всё, что ей показывали раньше.

</details>

2. ▢ Из урока 7: почему транскрипт это всё состояние агента, а не какая-то другая структура данных, которую обвязка держит отдельно?

<details markdown="1"><summary>Проверка</summary>

Потому что модель видит только транскрипт. Любой факт, который обвязка знает, но никогда не добавляет в транскрипт, для модели невидим, что бы ещё обвязка ни отслеживала внутри.

</details>

## Что нужно знать

### Описание инструмента это не документация API

Ошибка, которую каждый строитель совершает один раз: писать описание инструмента так, как написали бы докстринг REST-эндпоинта.

```text
Bad:
name: fetch_user
description: Fetches user data
```

Это слишком скупо для модели, выбирающей среди нескольких инструментов. У модели нет контекста, когда использовать `fetch_user`, а когда `get_user` или `lookup_user`. Она не знает, какие данные вернутся и что подавать на вход. Она не может рассудить, вызывать ли его сейчас или позже. Когда модель видит три инструмента и никаких чётких указаний, она гадает, причём ошибается чаще человека.

Вот тот же инструмент, описанный для модели:

```text
Better:
name: fetch_user
description: Look up a user profile by their numeric ID. Returns the user's name, email, account status, and the current version number of their profile. Use this before calling update_user, since update_user requires you to pass the profile's current version number to prevent write conflicts. Returns null if the user ID does not exist.
```

Теперь модель видит всю картину: когда вызывать (перед update_user), что нужно (числовой идентификатор) и что инструмент отдаёт (достаточно информации, чтобы решить следующий шаг). Это описание служит принятию решений моделью, а не человеку, читающему документацию API.

Разница в том, что докстринг REST говорит программисту-человеку, как пользоваться инструментом. Описание инструмента в промпте агента говорит модели, когда и зачем вызывать инструмент, что передавать и какого результата ожидать. У модели нет руководства; ваше описание её единственный путеводитель.

### Называйте инструмент отлично от других

Модель выбирает среди инструментов, читая их имена и описания, без каких-либо других сигналов. Если два инструмента звучат похоже, модель вызовет не тот или вызовет оба на всякий случай.

```text
Bad:
- name: list_files
  description: Lists files in a directory
- name: list_file_contents
  description: Lists the contents of a file
```

Модель может их перепутать или вызвать оба, когда нужен только один. Имена слишком близки.

```text
Better:
- name: list_directory
  description: List all files and subdirectories in a directory. Shows names and file sizes. Does not show file contents.
- name: read_file
  description: Read the complete contents of a single file. Returns text as a string.
```

Теперь имена различаются (list_directory и read_file), а описания ясно показывают, что каждый делает и чего не делает. Модель выберет верный.

Правило: имя инструмента должно говорить, что он делает, так, чтобы его нельзя было спутать с любым другим инструментом из того же набора. Если у вас несколько инструментов поиска, не называйте их все `search`. Назовите их `search_documentation`, `search_code`, `search_logs`.

### Описания параметров важны так же

Описание инструмента верхнего уровня получает больше всего внимания, но описания параметров не менее важны для корректности.

```text
Bad:
name: create_issue
description: Creates a GitHub issue
parameters:
  - name: title
    type: string
    description: Issue title
  - name: body
    type: string
    description: Issue body
```

Модель не знает, в каком формате должен быть заголовок, какой он может быть длины, должен ли он быть вопросом или утверждением. С телом ещё хуже: это Markdown? Простой текст? Насколько подробно? Описывает ли модель проблему или решение?

```text
Better:
name: create_issue
description: Create a new issue in the repository
parameters:
  - name: title
    type: string
    description: A one-line summary of the problem or feature request. Be specific and actionable. Examples: "Handle null config values in startup" or "Add support for JSON output format".
  - name: body
    type: string
    description: Detailed description in Markdown. Include what you tried, what failed, and what you expect to happen. If it is a feature request, explain why it matters. If it is a bug, include steps to reproduce.
```

Теперь модель знает, какой заголовок писать и какую степень подробности включить в тело. Результат получится лучше.

### Частая ошибка: похожие инструменты путают модель

Хуже всего, когда два инструмента настолько похожи, что модель не может их различить даже по описаниям.

```text
Very bad:
- name: update_user
  description: Update user information
- name: change_user
  description: Modify user data
```

Эти имена и описания говорят почти одно и то же. Модель может вызвать оба, вызвать не тот или тратить время на уточнения. Вы не дали ей способа выбрать.

Исправление в том, чтобы сделать имена и описания настолько разными, чтобы для текущей задачи имел смысл только один:

```text
Better:
- name: update_user_profile
  description: Change a user's displayed name, email, or profile picture. Requires the profile version number to prevent conflicts.
- name: update_user_permissions
  description: Grant or revoke access roles for a user, such as admin, editor, or viewer. Only callable by the current account's admin.
```

Теперь модель видит, что первый инструмент для личной информации, а второй для управления доступом. Она выберет верный.

## Практика

1. ▢ У вас два инструмента: `send_email` и `send_notification`. Модель иногда вызывает оба, когда нужен только один. Напишите по одному предложению для каждого инструмента, которое ясно покажет модели, какой использовать и когда.

<details markdown="1"><summary>Проверка</summary>

Возможные ответы: для `send_email` может быть «Send an email message to an email address. Use this for messages longer than a few lines or when you need to include attachments or formatted text.» Для `send_notification` может быть «Send a brief in-app notification to a user. Use this for short status updates or alerts that do not require the user to leave the application.» Главное, чтобы описание говорило модели, какого рода сообщение ожидает каждый инструмент, чтобы она могла выбрать верно.

</details>

2. ▢ Ваш инструмент `get_user` возвращает все поля записи пользователя: id, name, email, phone, address, company, biography, preferences, subscription tier и ещё десять. Описание параметра должно направлять модель в том, что передавать. Чего в описание класть НЕ нужно?

<details markdown="1"><summary>Подсказка</summary>

Подумайте, что модели нужно знать, чтобы корректно вызвать инструмент, и что приятно знать, но для самого вызова не требуется.

</details>

<details markdown="1"><summary>Проверка</summary>

НЕ нужно перечислять каждое поле, которое возвращает инструмент. Описание инструмента говорит, что модель получит обратно; описание параметра говорит, что модель должна предоставить для вызова. Для параметра `user_id` описание должно говорить что-то вроде «The numeric ID of the user. If you do not have the ID, call search_users first.» Не перечисляйте в описании параметра, какие поля вернутся; это относится к описанию инструмента верхнего уровня.

</details>

3. ▢ Какая из следующих причин лучше всего объясняет, зачем писать подробные описания параметров инструмента?

    - a) Чтобы соответствовать стандартам документации API
    - b) Чтобы помочь инженерам-людям, которые будут читать код позже
    - c) Чтобы помочь модели решить, какое значение передавать и вообще когда вызывать инструмент
    - d) Чтобы сократить число вызовов инструментов, которые должен сделать пользователь

<details markdown="1"><summary>Проверка</summary>

**c)** Чтобы помочь модели решить, какое значение передавать и вообще когда вызывать инструмент. Модель читает описания параметров, чтобы понять, какие аргументы ожидает инструмент и что будет, если передать неверное значение. (a) неуместно; это промпт-инжиниринг, а не проектирование API. (b) может быть побочной пользой, но не главной причиной. (d) мимо сути: подробные описания помогают модели реже вызывать не то, а не вызывать реже в целом.

</details>

4. ▢ Вы строите инструмент `search`. У вас есть ещё инструменты `search_documents`, `search_issues` и `search_users`. Почему такое именование инструментов проблема и что делать вместо этого?

<details markdown="1"><summary>Проверка</summary>

Инструмент `search` слишком общий. Модель не поймёт, какой из инструментов поиска вызвать, когда ей нужно искать. Она может вызвать их все или выбрать наугад. Вместо этого переименуйте `search` во что-то конкретное, например `search_logs`, `search_comments` или `search_code`. Правило: каждое имя инструмента должно быть достаточно конкретным, чтобы модель знала, что он делает, и достаточно отличным от других имён, чтобы модель его не путала.

</details>

## Практика в реальной работе

- [ ] Найдите определения инструментов (имя и описание) для LLM-приложения или фреймворка агентов, которым вы пользуетесь. Прочитайте описание каждого инструмента. Запишите один инструмент, описание которого достаточно ясно, чтобы вы понимали, когда модели его вызывать, и один инструмент со слишком расплывчатым описанием. Отметьте, почему первое работает и чего не хватает во втором.

- [ ] Выберите инструмент, которым вы регулярно пользуетесь в командной строке (вроде `grep` или `find`). Представьте, что вам нужно описать его для модели, которая ничего не знает о вашей файловой системе. Напишите одно предложение, которое говорит модели, что инструмент делает и когда использовать его вместо похожего.

- [ ] Завтра: возьмите описание инструмента из реального агента или документации API, которое, по-вашему, написано плохо. Перепишите его для модели, выбирающей среди нескольких похожих инструментов. Сделайте его как минимум вдвое длиннее, включите пример того, когда его использовать, и скажите одну вещь, для которой он НЕ годится.
