# Урок 9. Формы возврата и раздувание набора инструментов

**Связь с целью курса:** Проектирование поверхности инструментов агента включает выбор того, что инструмент возвращает (его форму возврата), и решение о том, сколько инструментов предлагать, потому что оба решения влияют на способность модели верно выбирать среди вариантов и на стоимость каждого последующего хода.
**Первоисточник:** [Статья: "Writing Effective Tools for Agents", Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
**Предварительные требования:** [Урок 8](0008-naming-and-describing-a-tool.md)

## Разминка

1. ▢ Из урока 8: почему описание инструмента должно говорить модели, когда и как его использовать, а не просто перечислять принимаемые параметры?

<details markdown="1"><summary>Проверка</summary>

Потому что у модели нет другого источника указаний для выбора среди инструментов. Голый список параметров объясняет, как вызвать инструмент, но не зачем и когда к нему обращаться, а именно это решение модели и нужно принять.

</details>

2. ▢ Из урока 8: какую проблему вы создаёте, если в одном наборе инструментов есть два инструмента с очень похожими именами и описаниями?

<details markdown="1"><summary>Проверка</summary>

Модель не может надёжно их различить, поэтому может вызвать не тот или вызвать оба на всякий случай. Шум ещё и ухудшает способность модели верно выбирать среди всех остальных инструментов набора, а не только среди двух похожих.

</details>

## Что нужно знать

### Возвращаемое значение инструмента стоит бюджета контекста

Каждое сообщение в транскрипте расходует токены. Когда инструмент возвращает результат, он добавляется в транскрипт, и модель видит его на каждом последующем ходу, пока запуск не закончится или транскрипт не будет усечён. Инструмент, возвращающий небольшой сфокусированный ответ, стоит немного. Инструмент, возвращающий пять тысяч строк базы данных, стоит реальных токенов на каждом ходу до конца запуска, нужны модели были все они или нет.

```text
Bad:
Tool: fetch_user_records
Returns: [complete User record, complete User record, ...]
# 5000 rows, 50KB of JSON, ~10,000 tokens consumed per turn after this call
```

После возврата инструмента транскрипт раздувается. Теперь на следующем ходу модели приходится обработать все пять тысяч строк, просто чтобы прочитать собственный контекст. Это раздувает бюджет токенов и замедляет цикл.

### Проектируйте формы возврата для принятия решений, а не для полноты

Вместо того чтобы возвращать всё, что есть в нижележащей системе, спроектируйте форму возврата, которая даёт модели то, что нужно для решения о следующем шаге.

```text
Better: Option 1 - Return a summary
Tool: fetch_user_records
Returns:
  total_count: 5000
  sample_results: [User, User, User, ...] # top 5 results
  query_was_too_broad: true
  suggestion: "Your query matches 5000 users. Narrow it with a company_id or email domain filter."

# ~500 tokens consumed per turn after this call
```

Теперь модель видит, что запрос был слишком широким, и знает, что делать дальше: вызвать инструмент снова с лучшими фильтрами. Это возвращает десятую часть токенов полного дампа.

```text
Better: Option 2 - Let the model ask for more
Tool: fetch_user_records
Returns:
  count: 50  # number of results returned
  total_matching: 5000  # number of results if the query was not limited
  results: [User, User, ...] # just the first 50
  next_page_token: "abc123xyz"

# Model sees it got 50 of 5000. It can decide to refine the query or ask for the next page.
```

В обоих случаях модель получает достаточно информации для обоснованного решения, не будучи погребена под данными.

### Раздувание набора инструментов: больше инструментов значит хуже выбор

Добавление инструмента агенту не бесплатно. Каждый инструмент, из которых может выбирать модель, делает выбор для модели труднее. Это называется раздуванием набора инструментов.

С тремя инструментами модель в большинстве случаев выбирает верно:

```text
Tools:
- search_documentation
- read_file
- list_directory
```

С десятью инструментами модель начинает сомневаться в себе и вызывает несколько инструментов там, где хватило бы одного:

```text
Tools:
- search_documentation
- search_issues
- search_code
- read_file
- read_logs
- list_directory
- list_repos
- get_git_history
- get_git_diff
- get_git_status
```

Каждый новый инструмент добавляет шум в решение. Модели нужно прочитать и взвесить все десять описаний, прежде чем выбрать один. Если два похожи (search_code и search_documentation), модель может вызвать оба. Эффект неявный: слегка страдает каждый существующий инструмент, а не только новый.

Цена реальна: больше вызовов инструментов, больше токенов в транскрипте, больше ходов, потраченных на избыточную информацию.

### Новый инструмент или новый параметр

Когда хочется добавить инструмент, сначала спросите: не мог бы это быть параметр существующего инструмента?

```text
Bad: Two tools
- name: list_files
- name: list_directories
```

Лучше: один инструмент с параметром

```text
Good: One tool with a parameter
- name: list_contents
  parameters:
    - name: path
    - name: type
      type: enum
      values: [files, directories, all]
```

Модель выбирает нужный ей тип, а вы не добавили шума в набор инструментов.

Но иногда новый инструмент оправдан. Если инструменты принципиально различны (их вызывают в разных ситуациях, они возвращают разные формы, им нужны разные разрешения), то новый инструмент с понятным именем лучше перегруженного параметра:

```text
Good: Two specialized tools
- name: search_database_by_id
  parameters:
    - id
    # Fast, returns a single record
- name: search_database_by_query
  parameters:
    - query
    # Might return many records
```

Модель знает разницу: by_id быстрый и точный, by_query гибкий, но может вернуть много. Имена делают решение очевидным.

Правило: добавляйте новый инструмент, когда его вызывали бы по принципиально разным причинам или когда различие нельзя выразить параметрами. Добавляйте параметр, когда инструмент по сути та же операция с вариацией формата входа или выхода.

### Как раздувание набора инструментов проявляется на практике

Тонкий признак: модель начинает говорить что-то вроде «Сначала вызову поиск, чтобы проверить, существует ли оно, а потом получу, если существует», когда одним инструментом можно было сделать всю работу. Так модель перестраховывается, потому что не уверена, что делает каждый инструмент. Проблема не в модели, а в наборе инструментов.

Другой признак: повторные вызовы инструментов. Модель вызывает один и тот же инструмент несколько раз за запуск, например дважды ищет или дважды перечисляет. Часто это значит, что набор инструментов не даёт модели способа сузить результаты за один вызов, поэтому ей приходится вызывать инструмент с разными параметрами, чтобы найти нужное.

## Практика

1. ▢ Инструмент `get_user_history` возвращает JSON-массив из 100 000 событий действий пользователя за прошлый месяц, каждое подробное. Модель, вероятно, вызовет этот инструмент, посмотрит первые десять событий и проигнорирует остальные. Какое проектное изменение снижает стоимость токенов на каждом ходу после этого вызова?

<details markdown="1"><summary>Проверка</summary>

Ограничить возврат первыми N событиями (например, первыми 20) и включить total_count и способ запросить больше. Так модель увидит, что ей нужно, не платя за все 100 000 событий. Либо вернуть сводку: «50 событий за прошлую неделю, 50 за неделю до неё. Последнее: пользователь вошёл в систему» вместо полных подробностей и позволить модели запросить частности при необходимости.

</details>

2. ▢ У вас набор из 15 инструментов. Модель вызывает search_by_name и search_by_id в одном запуске, хотя оба поиска можно выразить параметрами одного инструмента. Какой вред от того, что их оставили двумя отдельными инструментами?

<details markdown="1"><summary>Подсказка</summary>

Подумайте о работе модели: ей нужно прочитать пятнадцать описаний и решить, какой инструмент вызвать. Чем наличие похожих инструментов усложняет эту работу?

</details>

<details markdown="1"><summary>Проверка</summary>

Раздувание набора инструментов. Модели приходится выбирать из пятнадцати инструментов. Похожие инструменты вроде search_by_name и search_by_id усложняют выбор. Модель может вызвать оба, когда хватило бы одного, или тратить время на решение, какой уместен. Каждый существующий инструмент немного страдает из-за того, что набор стал шумнее. Исправление в том, чтобы слить их в один инструмент поиска с параметром для поля поиска.

</details>

3. ▢ Что из следующего служит признаком того, что форма возврата инструмента слишком многословна?

    - a) Инструмент вызывают очень часто
    - b) Модель читает результат и просит сводку, прежде чем им воспользоваться
    - c) Инструмент долго выполняется
    - d) Инструменту требуется аутентификация

<details markdown="1"><summary>Проверка</summary>

**b)** Модель читает результат и просит сводку, прежде чем им воспользоваться. Это значит, что инструмент возвращает слишком много информации; модели приходится фильтровать или сжимать полученное, прежде чем принять решение. (a) не связано с формой возврата; часто вызываемый инструмент может быть узким по замыслу. (c) касается скорости исполнения, а не токенов. (d) касается разрешений, а не формы возврата.

</details>

4. ▢ Вы проектируете инструменты для агента поиска по коду. Должны ли `search_code` и `get_code_diff` быть одним инструментом или двумя? Объясните в одном-двух предложениях.

<details markdown="1"><summary>Проверка</summary>

Двумя отдельными инструментами. Их вызывают по разным причинам (поиск ищет файлы, соответствующие шаблону, diff показывает изменения между версиями), они возвращают разные формы (список файлов и структурированный diff) и решают разные задачи. Один перегруженный инструмент усложнил бы выбор модели. Если бы они были вариациями одной операции (как search_code с разными параметрами запроса), они могли бы быть одним инструментом с параметром.

</details>

## Практика в реальной работе

- [ ] Найдите набор инструментов в LLM-приложении или агенте, к которому у вас есть доступ. Посчитайте инструменты. Прочитайте траекторию модели и отметьте каждый ход, на котором модель вызывала инструмент. Оцените: вызывала ли модель когда-нибудь два похожих инструмента там, где хватило бы одного? Напишите одно предложение о том, показался ли набор инструментов раздутым или хорошо спроектированным.

- [ ] Выберите инструмент, который возвращает структурированные данные. Прочитайте пример возвращаемого значения. Есть ли в нём часть, которую модель, скорее всего, проигнорирует? Перепишите форму возврата так, чтобы исключить эти данные или вынести их во второй вызов, и оцените, сколько токенов вы сэкономили.

- [ ] Завтра: спроектируйте инструмент, который мог бы пойти в любую сторону (новый инструмент или параметр существующего). Для своего выбора напишите два предложения о том, почему вы выбрали отдельный инструмент или параметр, чего стоила бы альтернатива и когда вы могли бы пересмотреть решение.
