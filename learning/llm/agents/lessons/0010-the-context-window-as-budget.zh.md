# 第 10 课：作为预算的上下文窗口

**使命关联:** 估算智能体循环的 token 成本和延迟，并说出放大效应来自循环的哪个部分。
**主要来源:** [文章：“Effective Context Engineering for AI Agents”，Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
**前置知识:** [第 9 课](0009-return-shapes-and-tool-set-bloat.md)、[轨迹](../GLOSSARY.md)

## 热身

1. ▢ 在第 6 课的智能体循环里，运行框架是在哪个环节决定执行哪个工具调用的？

<details markdown="1"><summary>检查</summary>

模型输出一个工具调用块（名称、参数），运行框架解析它并执行工具。模型通过处理它收到的对话记录来决定用哪个工具。

</details>

2. ▢ 每当一个工具结束，对话记录会发生什么？

<details markdown="1"><summary>检查</summary>

结果（或错误）被追加到对话记录里，新的对话记录在下一次循环迭代时被发回模型。

</details>

## 要点

### 对话记录每一轮都在增长，而且很快变得昂贵

智能体循环的每次迭代都会向对话记录追加内容。智能体运行了 10 轮、20 轮或 100 轮之后，对话记录里包含整次运行中的每条消息、每个工具调用和每个结果。下一次循环迭代时，整份对话记录都会发回模型。再下一次迭代，又发回一遍，而且又长了一轮。

这意味着，即使没有任何新鲜事发生，也有两项成本会随轨迹长度一起增长：

- **token 成本**：发给模型的每条消息都会重新发送所有旧的轮次。一条五轮的轨迹，每次调用消耗的 token 比一条 100 轮的轨迹少 5 倍。对于长时间运行的智能体，这会成为主要的成本。
- **延迟**：上下文越长，要处理的 token 越多，速度就越慢。智能体每次都要等更久才能得到响应。

### 上下文腐化：随着杂物积累，模型的注意力不断下降

随着越来越多低相关性的内容在上下文中累积，模型的注意力变得更嘈杂。当仍然重要的东西（目标、近期的约束、尚未处理的结果）被埋在一大堆旧的死胡同和被放弃的推理之中时，模型区分它们的能力就会下降。这有时被称为“上下文腐化”。臃肿的上下文不仅昂贵，还会让模型在任务上表现更差。

### 简单粗暴的截断是有风险的

最简单的本能做法是，一旦上下文达到大小限制，就丢弃最旧的轮次。但简单粗暴的截断有悄悄丢失关键信息的风险。如果截断的边界恰好落在：

- 模型仍然需要遵循的多步指令中间
- 模型尚未处理的结果中间
- 约束或目标陈述中间
- 系统提示词或示例的一部分中间

那么智能体就会悄悄地坏掉，而运行框架没有任何办法检测到。模型不会知道有一条关键指令被删掉了；它只会带着不完整的理解继续工作，并以出人意料的方式失败。

### 主动整理是一种有意的设计选择

因为简单粗暴的截断很危险，而成本又随轨迹长度增长，所以运行框架不能把对话记录当作只会不断变长的被动日志。“什么留在上下文里，什么被移出去”，必须是内置在运行框架里的、有意的设计决定。轨迹依然存在，但运行框架决定模型在每次调用时看到其中的哪一部分。

对此有两种主要策略（下一课会讲）：压缩和按需检索。

## 练习

1. ▢ 一个智能体在一项长时间的研究任务中发出了 50 次工具调用。在第 51 次调用时，发给模型的对话记录是 20,000 个 token。到第 52 次调用，模型收到的对话记录大约有多少 token？

    - a) 20,000 个 token
    - b) 20,000 加上第 51 次调用新结果的 token
    - c) 40,000 个 token
    - d) 取决于第 51 次调用结果的大小

<details markdown="1"><summary>检查</summary>

**b)** 模型收到的是原来的 20,000 个 token 的对话记录，再加上追加的新结果。如果第 51 次调用的结果是 500 个 token，模型拿到的大约就是 20,500 个 token。token 成本随每一轮增长，在非常长的运行中，这会成为一笔可观的开销。选项 c 是错的，因为模型不会把第 51 次调用的结果收到两次；选项 a 忽略了新追加的内容；选项 d 在精神上是对的（结果的大小确实有影响），但 b 是更精确的答案。

</details>

2. ▢ 你在为代码评审任务设计智能体。智能体读取文件、比较它们、做笔记，并产出摘要。为什么一旦对话记录达到 50,000 个 token 的限制，就直接丢弃最旧的工具结果是有风险的？

<details markdown="1"><summary>提示</summary>

如果截断的边界落在一次旧的文件读取和模型还没做完的比较之间呢？如果关于文件范围的约束恰好在被你丢弃的那部分里呢？

</details>

<details markdown="1"><summary>检查</summary>

简单粗暴的截断可能丢掉模型仍需引用的工具结果（比如某个文件的内容），或者模型需要记住的约束（比如“只评审 src/core/ 里的文件”）。模型不会知道信息缺失了；它会悄悄地基于不完整的图景工作，得出错误的结论。运行框架必须比单纯在 token 上限处一刀切更聪明。

</details>

3. ▢ 关于上下文腐化，下面哪项是正确的？

    - a) 只有对话记录里包含错误时才会发生上下文腐化
    - b) 把工具结果排版得漂亮可以防止上下文腐化
    - c) 一份带有许多不相关旧轮次的庞大对话记录，即使没有任何关键信息被截断，也会让模型更不准确
    - d) 在现代模型里，上下文腐化不是真正的问题

<details markdown="1"><summary>检查</summary>

**c)** 随着低相关性的内容累积，模型的注意力会下降。又大又乱的对话记录，让模型更难找到并优先处理重要的东西。选项 a 是错的，因为即使没有错误，死胡同和已完成的任务也会制造噪声。选项 b 是错的，因为漂亮的排版解决不了信噪比的问题。选项 d 是错的，因为上下文腐化在长上下文任务中有充分的记录。

</details>

4. ▢ 你观察到智能体的延迟随着轨迹变长而增加。说出这样的两个原因。

<details markdown="1"><summary>检查</summary>

第一，模型每次调用收到的 token 更多，处理起来更耗时。第二，模型必须在更多低相关性的内容（上下文腐化）中筛选出重要的信息，这会影响它的推理质量，还可能让它犯错，浪费轮次。

</details>

## 实战练习

- [ ] 向别人（或写在笔记里）解释，为什么对话记录太长时，你不能一直丢弃最旧的轮次。用一个你希望智能体去做的真实任务作例子。
- [ ] 打开你与某个语言模型的一次长篇多轮对话记录，记下进行到第几轮时，模型开始难以记住开头的约束。
- [ ] 明天：规划一个智能体可能做的研究任务（读取 20 个文件、比较模式、产出摘要），并粗略估算：如果智能体始终把每个文件的完整内容保存在内存里，对话记录会有多大；如果它只保留文件路径、按需获取内容，又会有多大。
