# 第 12 课：作为上下文隔离的子智能体

**使命关联:** 从轨迹出发诊断出问题的智能体，而不是在它的提示词里再多加一条指令。
**主要来源:** [文章：“How We Built Our Multi-Agent Research System”，Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
**前置知识:** [第 11 课](0011-compaction-and-retrieval-on-demand.md)

## 热身

1. ▢ 压缩与按需检索有什么区别？

<details markdown="1"><summary>检查</summary>

压缩用摘要替换旧的轮次，节省了 token，却有丢失信息的风险。按需检索则把旧的细节挡在上下文之外，只在模型要求时才获取，用一点延迟换取更小的常驻上下文。

</details>

2. ▢ 在压缩加按需检索中，始终常驻的上下文包含哪三样东西？

<details markdown="1"><summary>检查</summary>

目标和约束、进展摘要，以及元数据（文件名、可用工具、文档标题）。完整的细节要么被压缩（压缩），要么按需获取（检索）。

</details>

## 要点

### 作为上下文管理工具的子智能体

到目前为止，第 10 课和第 11 课关注的是管理单个智能体的对话记录。但还有另一种办法：拉起一个独立的智能体，去完成一项有边界的工作。这属于第 8 阶段（多智能体），不过这里把范围严格限定在上下文预算这一个角度。

子智能体是一次全新的智能体运行，拥有自己的对话记录、自己的运行框架和自己的工具集。它去探索，发出工具调用，积累自己的轨迹。而父智能体在此期间，并没有为这些探索付出任何成本。子智能体的所有轮次，都不会出现在父智能体的对话记录里。

子智能体完成后，会产出最终结果或摘要。这份摘要（只有几句话或一个数据结构）被追加到父智能体的对话记录里。子智能体全部的内部推理、所有的死胡同、所有的工具调用和失败，都留在父智能体的上下文之外。

### 关键洞察：庞大而隔离的轨迹，对父智能体没有任何成本

假设一个子智能体花了 100 轮去读文件、比较模式、碰上死胡同、不断完善它的分析。它的轨迹非常庞大。但从父智能体的角度看，这一切工作都是不可见的。父智能体只看到最终的报告，几百个 token。同时，父智能体的上下文依旧又小又便宜。

这不同于压缩和按需检索，二者都是在单份对话记录之内运作的。子智能体则完全在父智能体的对话记录之外运作。它的成本由子智能体的运行框架承担，而不是父智能体。

### 取舍：看不见的推理意味着丢失的细节

因为子智能体的内部推理对父智能体是不可见的，所以父智能体没想到要问的信息可能会丢失。如果父智能体拉起一个子智能体去“阅读这些文件并做总结”，子智能体可能会发现一些有趣但无关紧要的东西：“我还注意到 util.cpp 里有内存泄漏。”如果父智能体没有问过这个，子智能体就可能在报告里略去它，父智能体也就永远不会知道。

这不同于压缩的风险，压缩中，由运行框架控制总结什么。对于子智能体，“报告什么”和“保留在内部什么”之间的边界，是子智能体自己的选择。如果子智能体是语言模型，它会根据收到的指令，估计父智能体关心什么。这个估计可能是错的。

### 子智能体什么时候值得用，什么时候不值得

当出现下面这些情况时，子智能体值得付出协调成本：

- 子任务很大，会积累很长的轨迹（很多轮、很多工具调用、很多死胡同）。
- 子任务有边界：有明确的停止点，而且父智能体在下游工作中不需要子智能体的推理。
- 拉起新智能体的成本（延迟、协调开销），远小于把子智能体的探索留在父智能体上下文里的成本。

例如：“研究这个代码库的历史，读取 git 日志和主要的 PR，给我一个三句话的摘要。”这是个庞大而有边界的任务。子智能体探索 50 轮，为父智能体省下了 50 轮的上下文成本。

下面这些情况，子智能体不值得用：

- 任务很小（反正只需要几轮）。
- 任务需要与父智能体紧密协调（父智能体会提出澄清问题，子智能体需要完善它的工作）。
- 父智能体之后需要子智能体完整的推理（为了理解为什么得出某个结论、发现某个假设、调试某个错误）。

例如：“获取明天的气温。”这是个只需几轮的任务；拉起子智能体的成本，比直接在父智能体里做还要高。

## 练习

1. ▢ 一个智能体的任务是评审 50 个文件的代码并产出报告。开发者拆分了工作：主智能体评审 5 个文件，并拉起一个子智能体去评审另外 45 个。为什么这是子智能体的合理用法？

    - a) 子智能体总是比单个智能体更快
    - b) 子智能体冗长的轨迹（评审 45 个文件）与主智能体的上下文隔离，使主上下文保持又小又便宜
    - c) 子智能体从不犯错
    - d) 主智能体可以立即看到子智能体的全部推理

<details markdown="1"><summary>检查</summary>

**b)** 子智能体让主智能体把一项庞大而有边界的任务卸载出去。子智能体 100 多轮的探索，不会让主智能体的上下文膨胀。主智能体只收到子智能体的最终报告。选项 a 是错的，因为子智能体可能增加延迟。选项 c 是错的，因为子智能体也会犯错。选项 d 是错的，因为子智能体的内部推理对主智能体是不可见的。

</details>

2. ▢ 一个子智能体在评审代码库时，发现了一个安全漏洞。它与父智能体要求的任务（代码风格评审）没有直接关系，却至关重要。子智能体的不可见性在这里造成了什么风险？

<details markdown="1"><summary>提示</summary>

子智能体的指令让它专注于代码风格。由谁决定向父智能体报告什么，又可能丢失什么？

</details>

<details markdown="1"><summary>检查</summary>

子智能体根据它的指令，决定在最终报告里包含什么。如果指令强调代码风格，子智能体可能根本不会报告这个安全问题，或者只作为父智能体会漏掉的脚注一笔带过。父智能体没想到要问的信息可能会丢失，因为父智能体从未看到子智能体的完整推理。父智能体必须说得非常明确：“无论是不是风格问题，只要发现任何关键问题都要报告。”

</details>

3. ▢ 比较处理一项长研究任务的两种做法：
    - 做法 A：单个智能体，压缩旧的轮次并使用按需检索。耗时 80 轮，常驻上下文始终低于 30,000 个 token。
    - 做法 B：主智能体拉起 3 个子智能体并行探索。每个内部耗时 40 轮。主智能体从每个子智能体收到一份摘要。主智能体最终的上下文是 5,000 个 token，外加协调开销。

哪种做法的总 token 成本更低（计入所有智能体的运行），为什么？

    - a) 做法 A，因为它避免了子智能体的开销
    - b) 做法 B，因为三项探索是隔离的，对主智能体来说很便宜
    - c) 成本相同
    - d) 取决于协调开销有多大

<details markdown="1"><summary>检查</summary>

**d)** 做法 A 把 30,000 个 token 发给模型 80 次，大约 240 万个 token。做法 B 在每个子智能体里，把大约 50,000 个 token 发给模型 40 次，外加与主智能体的协调。如果协调开销很小，而且子智能体的工作确实是并行而有边界的，做法 B 可以更便宜。但如果协调很昂贵，或者子智能体需要迭代地完善它们的结果，做法 A 可能更好。答案取决于拉起并协调子智能体的实际成本。

</details>

4. ▢ 你在设计一个“调试这个失败的测试套件并提出修复方案”的智能体。应该使用子智能体吗，为什么？

<details markdown="1"><summary>检查</summary>

不应该。调试是这样一类任务：父智能体很可能需要子智能体的完整推理，来判断提议的修复是否安全、发现假设，或者提出澄清问题。它不是带着一份简单报告的有边界任务；它需要紧密的协调。子智能体看不见的推理会成为负担。最好把调试保留在父智能体的主循环里，让父智能体能跟随完整的轨迹。

</details>
