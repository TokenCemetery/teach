# पाठ 15. ReAct: Reasoning और Acting को आपस में जोड़ना

**मिशन से संबंध:** असफल agent को जाँचने के लिए आप पहचानेंगे कि वह बिना दिखने वाली reasoning के actions चला रहा है (जहाँ मूल कारण छिपता है), पहले से तय कठोर योजना पर चल रहा है (जहाँ माहौल की अप्रत्याशित बातें एक के बाद एक विफलताएँ पैदा करती हैं), या reasoning को observation से जोड़ रहा है (जहाँ विफलता के संकेत अगले फ़ैसले में लौट आते हैं)।
**मुख्य स्रोत:** [पेपर: "ReAct: Synergizing Reasoning and Acting in Language Models", Yao et al., 2022](https://arxiv.org/abs/2210.03629)
**पूर्व-आवश्यकताएँ:** [पाठ 14](0014-files-as-memory.md), [Agent loop](../GLOSSARY.md)

## वार्म-अप

1. ▢ जब आप runs के पार agent की memory file में रखते हैं (मान लें chat transcript या पिछले फ़ैसलों का log), तो agent के व्यवहार के बारे में क्या debug और सत्यापित करना आसान हो जाता है?

<details markdown="1"><summary>जाँचें</summary>

File-आधारित memory आपको वह ठीक-ठीक state पढ़ने देती है जो agent ने हर फ़ैसले से पहले देखी थी, ताकि आप उसकी reasoning replay कर सकें और जाँच सकें कि उस पल उपलब्ध जानकारी को देखते हुए उसका चुनाव समझदारी का था या नहीं। अगर agent टूटा हुआ लगे, तो आप अंदाज़ा लगाने के बजाय उसकी पिछली trajectory पढ़कर वह ठीक चरण पा सकते हैं जहाँ वह ग़लत गया।

</details>

2. ▢ बड़ी memories को files में रखने का एक जोखिम बताएँ: अगर agent file को कभी छाँटता या compact नहीं करता तो क्या होता है?

<details markdown="1"><summary>जाँचें</summary>

File बिना सीमा के बढ़ती है, और जब model को दी जाती है तो disk की जगह और context budget खाती है। आख़िरकार agent पूरा इतिहास context window में नहीं समा पाता, जिससे harness को चुनना पड़ता है कि कौन-सी पुरानी memories हटानी हैं और कौन-सी रखनी हैं।

</details>

## यह जानें

### Reasoning और acting के तीन आकार

Agent loop स्वाभाविक रूप से कई अलग patterns सँभालता है कि reasoning कब हो, actions चलने के सापेक्ष। ReAct पेपर तीन पहचानता है, और उनके बीच के समझौते समझना agent की विफलताएँ जाँचने की कुंजी है।

**Act-only:** Model को मौजूदा task और state मिलती है, और वह बिना बताई हुई reasoning के तुरंत tool call भेज देता है। Harness tool चलाता है, नतीजा जोड़ता है, और loop दोहराता है। यह सबसे सरल ढाँचा है।

जोखिम: जब कुछ ग़लत होता है, आप नहीं बता सकते कि model ने यह action क्यों चुना। क्या उसने task ग़लत समझा? क्या उसे लगा कि वह दूसरा tool call कर रहा है? Reasoning trace के बिना debugging अंदाज़ा है। आप prompt में स्पष्टीकरण जोड़ते जाते हैं ("चरण-दर-चरण सोचो", "अपना उत्तर जाँचो"), पर model फिर भी आपके जाँचने के लिए कोई दिखने वाली reasoning नहीं बनाता, इसलिए स्पष्टीकरण शायद काम न आएँ।

**Reason-then-act-once:** Model task पढ़ता है, पूरी योजना पहले ही text में तर्क से तय करता है (इसे "thought" चरण कहें), फिर योजना चलाने के लिए tool calls के क्रम पर टिक जाता है। एक बार योजना तय हो जाए, तो harness बिना दोबारा योजना बनाए सारे चरण चलाता है।

इससे act-only का कोरी-स्लेट वाला अंदाज़ा टलता है, क्योंकि आप model की पूरी reasoning देख सकते हैं। पर इसकी एक छिपी क़ीमत है: योजना किसी भी tool के चलने से पहले बनती है। अगर tool call फेल हो या अप्रत्याशित data लौटाए, तो योजना बासी हो जाती है। Model अप्रत्याशित बातों पर प्रतिक्रिया नहीं दे सकता क्योंकि वह पहले ही क्रम पर टिक चुका है। आपको agent फिर चलाना पड़ता है और उम्मीद करनी पड़ती है कि नया reasoning चरण ख़ुद को सुधार लेगा।

**ReAct (Interleaved reason-act-observe):** Model ज़ोर से तर्क करता है कि आगे क्या करना है (छोटा "thought" या "reasoning" text), फिर tool call भेजता है। Harness tool चलाता है, नतीजा transcript में जोड़ता है, और loop दोहराता है। अगले turn में model पिछला thought, उसका चुना action और असली नतीजा पढ़ता है, फिर अब जो दिख रहा है उसके आधार पर अगले चरण पर तर्क करता है।

यही ReAct pattern है। Model की reasoning दिखती है (आप उसे debug कर सकते हैं), पर उससे भी ज़रूरी, हर चरण की reasoning पिछले चरण के असली नतीजे को शामिल कर सकती है। अगर search ने कोई नतीजा नहीं दिया, तो अगला thought दूसरी search की ओर मुड़ सकता है। अगर API call फेल हुई, तो अगला thought उसे ध्यान में रखकर कोई उपाय आज़मा सकता है। Reasoning कठोर पहले की योजना नहीं है; वह अभी-अभी जो हुआ उसका अवलोकन है, जो आगे क्या होगा उसमें जाता है।

### जब माहौल चौंकाए तो ReAct क्यों जीतता है

Reason-then-act-once बंद-दुनिया वाले परिदृश्यों में अच्छा काम करता है जहाँ योजना की धारणाओं का सच होना तय है। असली tool-calling खुली-दुनिया वाले परिदृश्यों में होती है: files ग़ायब हैं, searches कुछ नहीं लौटातीं, APIs बंद हैं, उपयोगकर्ता विरोधाभासी instructions देते हैं। उन मामलों में ReAct का चरण-दर-चरण ख़ुद को ढालना पूरे reason-then-act चक्र को दोबारा चलाने से सस्ता और ज़्यादा मज़बूत है।

पाठ 6 के agent loop के बारे में सोचें। Model का एक turn text बनाता है (जिसमें reasoning हो सकती है) और tool call। वह tool call चलती है, और नतीजा transcript में जुड़ता है। अगले turn में model नतीजा देखता है और नया text और नई tool call भेजता है। डिज़ाइन से ही agent loop ReAct को पहले से सँभालता है: model का भेजा कोई भी reasoning text transcript में सुरक्षित रहता है, अगला turn उसे देख सकता है, और अगला turn देखे गए नतीजे पर प्रतिक्रिया करने वाली नई reasoning भेज सकता है।

"क्या मेरा harness ReAct सँभालता है?" असल में बस यह है कि "क्या मेरा harness model का reasoning text transcript में रखता है और अगले turn में उसे वापस देता है?" इस्तेमाल के लायक़ लगभग हर harness में जवाब है, हाँ।

### Act-only और plan-then-act-once की विफलताएँ जाँचना

अगर आप agent की trajectory जाँचें और tool calls से पहले कोई reasoning text न दिखे, तो आपके पास act-only agent है। विफलताएँ जाँचना कठिन है। Context में ज़्यादा data जोड़ना (लंबे task विवरण, ज़्यादा उदाहरण) मदद कर सकता है, पर reasoning text के बिना आपको कुछ दिखाई नहीं देता। हल है model को reasoning भेजने के लिए prompt करना ("thought" field, tool call में "reasoning" खंड, कुछ भी) और उसे transcript में रखना। फिर आप ReAct में आ जाते हैं और debugging संभव हो जाती है।

अगर आपको शुरू में बड़ा reasoning block दिखे, और उसके बाद बीच की reasoning के बिना actions का क्रम, तो आपके पास plan-then-act-once है। जब agent फेल हो, तो आप शायद ऐसी योजना देख रहे हैं जो हक़ीक़त से टकराकर टिक न सकी। हल है दोबारा योजना बनाने की इजाज़त: हर tool result के बाद अगले action से पहले नई reasoning भेजें। फिर, यह आपको ReAct में ले जाता है। कुछ विफलताएँ ग़ायब हो जाएँगी क्योंकि model अब ख़ुद को ढाल सकता है।

## अभ्यास

1. ▢ एक agent को कहा जाता है "जलवायु परिवर्तन के बारे में जानकारी खोजो, फिर शीर्ष 5 नतीजों का सारांश बनाओ।" वह पहले की reasoning text के बिना एक search tool call भेजता है। Search जलवायु विज्ञान के बारे में 10 नतीजे लौटाती है, और agent अगली बार बीच में बिना reasoning के सारांश वाला tool call भेजता है। सारांश ग़लत है। यह बताना कठिन क्यों है कि model ने task ग़लत समझा, नतीजे ग़लत समझे, या reasoning में असली ग़लती की?

<details markdown="1"><summary>जाँचें</summary>

Transcript में कोई reasoning text नहीं है, इसलिए आप नहीं देख सकते कि model का भीतरी "लक्ष्य" क्या था या उसने search के नतीजों को कैसे समझा। ग़ायब reasoning, मसलन, इनके बीच फ़र्क़ करना असंभव बना देती है: "model ने नहीं पहचाना कि search ने 10 नतीजे लौटाए और उसे लगा कि दोबारा search करनी है" बनाम "model ने 10 नतीजे देखे और task को सबका सारांश बनाना समझ लिया, शीर्ष 5 का नहीं।" सारांश वाले चरण से पहले reasoning text जोड़ना (ReAct-शैली का thought) आपको दिखा देता कि कौन-सी ग़लतफ़हमी हुई और prompt को उसी हिसाब से ठीक करने देता।

</details>

2. ▢ आप ऐसा agent बना रहे हैं जो उपयोगकर्ता की प्रतिक्रिया लेकर document को निखारता है। Agent की योजना (पहले भेजी गई) है "व्याकरण ठीक करो, फिर उदाहरण जोड़ो, फिर लंबाई जाँचो।" पहला दौर सफल रहता है। पर दूसरे run में उपयोगकर्ता की प्रतिक्रिया है "आपने जो नए उदाहरण जोड़े वे मुझे पसंद नहीं, पर व्याकरण के सुधार रखिए।" Agent पहले वाली योजना बिना बदले फिर इस्तेमाल करता है और उदाहरण फिर जोड़ देता है, प्रतिक्रिया को अनदेखा करके।

<details markdown="1"><summary>संकेत</summary>

इस परिदृश्य में योजना बासी क्यों हो जाती है? योजना बनाते समय agent को कौन-सी जानकारी नहीं दिख रही?

</details>

<details markdown="1"><summary>जाँचें</summary>

योजना उपयोगकर्ता की प्रतिक्रिया देखे बिना बनी थी। Plan-then-act-once में reasoning चरण किसी भी tool के चलने से पहले होता है, इसलिए वह trajectory के बीच में आने वाली नई जानकारी शामिल नहीं कर सकता। हल है हर tool result के बाद (यहाँ, हर निखारने के चरण के बाद) reasoning और दोबारा योजना बनाने की इजाज़त, ताकि जब उपयोगकर्ता की प्रतिक्रिया मूल धारणाओं के उलट हो तो agent की योजना ख़ुद को ढाल सके।

</details>

3. ▢ इनमें से कौन-सा संकेत है कि आपको agent को act-only से ReAct पर ले जाना चाहिए?

    - a) Agent बहुत धीमा है और आपको tool calls तेज़ करनी हैं।
    - b) Agent की विफलताएँ जाँचना कठिन है क्योंकि आप नहीं देख पाते कि उसने हर action क्यों चुना।
    - c) Agent को 5 की जगह 10 tools इस्तेमाल करने हैं।
    - d) Agent की context window लगभग भर चुकी है।

<details markdown="1"><summary>जाँचें</summary>

**b)** Act-only agents कोई reasoning text नहीं बनाते, इसलिए उनकी विफलताएँ अपारदर्शी हैं। ReAct पर जाना (हर action से पहले reasoning चरण जोड़ना) model की reasoning को दिखा देता है, जो debugging की मुख्य जीत है। a) ग़लत है क्योंकि ReAct tool calls तेज़ नहीं करता, वह reasoning text जोड़ता है जिसमें समय लगता है। c) ग़लत है, tools की गिनती का इससे कोई संबंध नहीं। d) ग़लत है, context का दबाव अलग चिंता है कि agent ज़ोर से तर्क करता है या नहीं।

</details>

4. ▢ एक agent "Portland में सबसे अच्छे pizza restaurants" खोजता है और 5 नतीजे पाता है। अगर agent ReAct mode में चल रहा है, तो transcript में आगे क्या होना चाहिए?

<details markdown="1"><summary>जाँचें</summary>

Agent को reasoning चरण ("thought" या "reasoning" खंड) भेजना चाहिए जो search के नतीजों को देखे और तय करे कि आगे क्या करना है (जैसे, "ये नतीजे अच्छे लग रहे हैं, अब मेरे पास उत्तर देने के लिए काफ़ी जानकारी है। मैं इनका सारांश बनाऊँगा" या "मुझे restaurants के खुलने के समय की और जानकारी चाहिए, मैं अगला वह लाऊँगा")। यह reasoning इस पर आधारित है कि search ने असल में क्या लौटाया, पहले की योजना पर नहीं। इसे transcript में शामिल करने से अगली tool call (अगर कोई हो) असली नतीजे पर टिकी हो सकती है।

</details>

## असली दुनिया का अभ्यास

- [ ] अपना बनाया या जाना-पहचाना कोई मौजूदा agent लें। उसकी trajectory (एक पूरा run) पढ़ें। गिनें कि कितनी tool calls के ठीक पहले reasoning text है। अगर 80% से कम में reasoning text है, तो prompt या tool schema को reasoning भेजने के लिए दोबारा लिखें, फिर उसे फिर चलाएँ।
- [ ] जानबूझकर किसी ऐसे tool को तोड़ें जिस पर agent निर्भर है (जैसे search API को ख़ाली नतीजा लौटाने दें)। Agent को ऐसे task पर चलाएँ जिसमें वह आमतौर पर सफल होता। Trajectory पढ़ें। क्या agent ने ऐसी reasoning भेजी जिसने टूटे tool को माना और दूसरे तरीक़े की ओर मुड़ा? अगर नहीं, तो reasoning के लिए prompt instruction जोड़ें और फिर आज़माएँ।
- [ ] कल: किसी सहकर्मी से task देखे बिना agent की trajectory पढ़वाएँ। क्या वे सिर्फ़ reasoning text से अनुमान लगा सकते हैं कि agent हर चरण पर क्या करना चाह रहा था? अगर नहीं, तो reasoning के prompts जोड़ें।
