# 第 15 课：ReAct：推理与行动交错

**使命关联:** 要诊断出问题的智能体，你需要认出它属于哪一种：不带可见推理地执行动作（根本原因藏在这里）、遵循僵硬的预先计划（环境中的意外会引发连锁失败），还是把推理与观察交错进行（失败的信号会流回下一个决定）。
**主要来源:** [论文：“ReAct: Synergizing Reasoning and Acting in Language Models”，Yao 等，2022](https://arxiv.org/abs/2210.03629)
**前置知识:** [第 14 课](0014-files-as-memory.md)、[智能体循环](../GLOSSARY.md)

## 热身

1. ▢ 当你把智能体的记忆跨运行存放在文件里（比如聊天记录或过往决策的日志）时，关于智能体的行为，哪些方面变得更容易调试和验证？

<details markdown="1"><summary>检查</summary>

基于文件的记忆，让你能读到智能体在每个决定之前看到的确切状态，于是你可以重放它的推理，检查它在当时可用的信息下是否做了合理的选择。如果智能体看起来坏掉了，你可以阅读它之前的轨迹，找出它出错的确切步骤，而不是靠猜。

</details>

2. ▢ 说出把大量记忆存放在文件里的一个风险：如果智能体从不修剪或压缩这个文件，会发生什么？

<details markdown="1"><summary>检查</summary>

文件会无限增长，当它被传给模型时，既消耗磁盘空间，也消耗上下文预算。智能体最终无法把整段历史塞进上下文窗口，迫使运行框架选择丢弃哪些较旧的记忆、保留哪些。

</details>

## 要点

### 推理与行动的三种形态

智能体循环天然支持几种不同的模式，区别在于推理相对于动作运行发生在什么时候。ReAct 论文指出了三种，理解它们之间的取舍，是诊断智能体失败的关键。

**只行动：** 模型接收当前的任务和状态，立刻发出一个工具调用，不给出任何推理。运行框架执行工具，追加结果，然后循环。这是最简单的结构。

风险：当出了问题时，你无法判断模型为什么选择这个动作。它是不是误解了任务？它是不是以为自己调用的是另一个工具？没有推理轨迹，调试就是猜谜。你最终会在提示词里加上各种说明（“逐步思考”“验证你的答案”），但模型仍然不会产生可供你检查的可见推理，所以这些说明未必有帮助。

**先推理，再一次性行动：** 模型读取任务，用文字把整个计划预先推理一遍（称之为“想法”阶段），然后承诺执行一连串工具调用来实施这个计划。计划一旦确定，运行框架就把所有步骤跑完，不再重新规划。

这避免了只行动那种白纸一张的瞎猜，因为你能看到模型完整的推理。但它有一项隐藏的成本：计划是在任何工具运行之前制定的。如果某个工具调用失败，或返回了意料之外的数据，计划就过时了。模型无法对意外做出反应，因为它已经承诺了这个序列。你最后只能重新运行智能体，并寄希望于新的推理阶段能够自行纠正。

**ReAct（推理、行动、观察交错）：** 模型出声推理下一步该做什么（一小段“想法”或“推理”文本），然后发出一个工具调用。运行框架执行工具，把结果追加到对话记录，然后循环。下一轮，模型读到之前的想法、它选择的动作，以及实际的结果，然后基于它现在看到的内容，推理下一步。

这就是 ReAct 模式。模型的推理是可见的（你可以调试它），但更重要的是，每一步的推理都能纳入上一步的实际结果。如果某次搜索没有返回结果，下一个想法可以转向另一种搜索。如果某次 API 调用失败了，下一个想法可以反映这一点并尝试变通办法。这里的推理不是僵硬的预先计划，而是对刚刚发生的事的观察，它又反过来影响接下来发生的事。

### 为什么当环境出人意料时，ReAct 更胜一筹

先推理再一次性行动，在封闭世界的场景里效果很好，那里计划所依据的假设一定成立。真实的工具调用发生在开放世界的场景里：文件缺失、搜索没有结果、API 宕机、用户给出相互矛盾的指令。在这些情况下，ReAct 的逐步调整，比重新跑一遍完整的“先推理再行动”周期更便宜，也更稳健。

想想第 6 课里的智能体循环本身。模型的一轮产生文本（其中可能包含推理）和一个工具调用。这个工具调用被执行，结果被追加到对话记录。下一轮，模型看到结果，发出新的文本和新的工具调用。从设计上说，智能体循环本来就支持 ReAct：模型发出的任何推理文本都保存在对话记录里，下一轮可以观察到它，并发出新的推理来回应所观察到的结果。

“我的运行框架支持 ReAct 吗？”其实就是问“我的运行框架是否把模型的推理文本保留在对话记录里，并在下一轮把它喂回去？”几乎每个值得使用的运行框架，答案都是肯定的。

### 诊断只行动和先规划后一次性行动的失败

如果你检查智能体的轨迹，发现工具调用之前没有任何推理文本，那它就是一个只行动的智能体。失败很难诊断。往上下文里加入更多数据（更长的任务描述、更多的示例）也许有帮助，但没有推理文本，你就看不见内部。修复的办法是提示模型发出推理（一个“想法”字段、工具调用里的一个“推理”部分，什么形式都行），并把它保留在对话记录里。这样你就进入了 ReAct，调试也就成为可能。

如果你看到开头有一大段推理，随后是一连串中间没有任何推理的动作，那就是先规划后一次性行动。当智能体失败时，你多半看到的是一份没能经受住现实考验的计划。修复的办法是允许重新规划：在每个工具结果之后、下一个动作之前，发出新的推理。这同样把你带进了 ReAct。一些失败会消失，因为模型现在能够调整了。

## 练习

1. ▢ 一个智能体被告知“搜索关于气候变化的信息，然后总结前 5 条结果。”它发出一个搜索工具调用，前面没有推理文本。搜索返回了 10 条关于气候科学的结果，智能体接着发出一个总结的工具调用，中间没有任何推理。总结不准确。为什么很难判断，是模型误解了任务、误解了结果，还是在推理中真的出了错？

<details markdown="1"><summary>检查</summary>

对话记录里没有推理文本，所以你看不到模型内部的“目标”是什么，也看不到它如何解读搜索结果。推理缺失，使你无法区分，比如“模型没有意识到搜索返回了 10 条结果，以为需要再搜一次”，与“模型看到了 10 条结果，却把任务误解成总结全部，而不是前 5 条”。在总结步骤之前加上推理文本（ReAct 风格的想法），就能让你看到发生的是哪一种误解，并据此修正提示词。

</details>

2. ▢ 你在构建一个接收用户反馈并修改文档的智能体。智能体（预先给出的）计划是“修正语法，然后添加示例，然后检查长度。”第一轮成功了。但第二次运行时，用户的反馈是“我不喜欢你新加的示例，但保留语法修正。”智能体原封不动地沿用预先的计划，再次添加了示例，忽略了反馈。

<details markdown="1"><summary>提示</summary>

在这个场景里，是什么让计划过时了？智能体在制定计划时，没有看到哪些信息？

</details>

<details markdown="1"><summary>检查</summary>

计划是在没有看到用户反馈的情况下制定的。在先规划后一次性行动中，推理阶段发生在任何工具运行之前，所以它无法纳入轨迹中途到来的新信息。修复的办法是允许在每个工具结果之后（这里是每个修改步骤之后）进行推理和重新规划，这样当用户反馈与最初的假设相矛盾时，智能体的计划才能随之调整。

</details>

3. ▢ 下面哪一项表明你应该把智能体从只行动改为 ReAct？

    - a) 智能体太慢，你需要加快工具调用。
    - b) 智能体的失败很难诊断，因为你看不出它为什么选择每个动作。
    - c) 智能体需要使用 10 个工具，而不是 5 个。
    - d) 智能体的上下文窗口快满了。

<details markdown="1"><summary>检查</summary>

**b)** 只行动的智能体不产生推理文本，所以它们的失败是不透明的。改为 ReAct（在每个动作之前加一个推理步骤），能让模型的推理变得可见，这是调试方面的核心收益。a) 是错的，因为 ReAct 不会加快工具调用，它增加了推理文本，而这是要花时间的。c) 是错的，工具的数量与此无关。d) 是错的，上下文压力与智能体是否出声推理是两回事。

</details>

4. ▢ 一个智能体搜索“波特兰最好的比萨餐厅”，收到了 5 条结果。如果智能体运行在 ReAct 模式下，接下来对话记录里该发生什么？

<details markdown="1"><summary>检查</summary>

智能体应该发出一个推理步骤（一个“想法”或“推理”部分），观察搜索结果并决定下一步做什么（例如，“这些结果看起来不错，我现在有足够的信息来回答了。我来总结一下”，或者“我需要更多关于餐厅营业时间的细节，接下来去获取”）。这个推理基于搜索实际返回的内容，而不是预先的计划。把它放进对话记录，下一个工具调用（如果有的话）就能以实际的结果为依据。

</details>

## 实战练习

- [ ] 找一个你构建过或熟悉的现有智能体。阅读它的轨迹（完整的一次运行）。数一数有多少次工具调用紧挨着前面有推理文本。如果带推理文本的不到 80%，就改写提示词或工具 schema，让它发出推理，然后再运行一次。
- [ ] 故意弄坏智能体所依赖的一个工具（例如，让搜索 API 返回空结果）。让智能体去做一个它通常能成功的任务。阅读轨迹。智能体有没有发出推理，承认那个工具坏了，并转向另一种做法？如果没有，就在提示词里加一条关于推理的指令，再试一次。
- [ ] 明天：请一位同事在不知道任务的情况下阅读智能体的轨迹。仅凭推理文本，他们能否推断出智能体在每一步想做什么？如果不能，就加上推理提示。
