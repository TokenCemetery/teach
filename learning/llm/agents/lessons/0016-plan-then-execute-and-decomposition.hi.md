# पाठ 16. Plan-Then-Execute और Decomposition

**मिशन से संबंध:** किसी task के लिए एक अकेले prompt, तय workflow और agent में से चुनने के लिए, आपको पहचानना होगा कि स्पष्ट योजना का अतिरिक्त ढाँचा कब अपनी क़ीमत के लायक़ है और कब ReAct का लचीलापन सस्ता है।
**मुख्य स्रोत:** [लेख: "Building Effective Agents", Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
**पूर्व-आवश्यकताएँ:** [पाठ 15](0015-react-interleaving-reasoning-and-acting.md)

## वार्म-अप

1. ▢ ReAct में, tool call चलने और harness के नतीजा transcript में जोड़ने के बाद क्या होता है?

<details markdown="1"><summary>जाँचें</summary>

Model के अगले turn को tool call और उसके नतीजे समेत transcript मिलता है। फिर model नई reasoning भेज सकता है जो इस पर प्रतिक्रिया करे कि tool ने असल में क्या लौटाया, पहले से बनी योजना पर टिके रहने के बजाय।

</details>

2. ▢ एक ऐसा परिदृश्य बताएँ जहाँ ReAct का चरण-दर-चरण ख़ुद को ढालना, पहले की कठोर योजना पर बढ़त है।

<details markdown="1"><summary>जाँचें</summary>

कोई भी परिदृश्य जहाँ माहौल agent को चौंका सकता है: search कुछ नहीं लौटाती (अपेक्षित data नहीं), कोई tool फेल होता है, उपयोगकर्ता ऐसी प्रतिक्रिया देता है जो धारणाओं के उलट है, या task के बीच नई जानकारी आती है। इन मामलों में ReAct model को चौंकाने वाली बात देखकर ख़ुद को ढालने देता है, जबकि कठोर पहले की योजना आँख मूँदकर मूल चरण चलाती और फेल होती या ग़लत नतीजे देती।

</details>

## यह जानें

### स्पष्ट planning और decomposition

Plan-then-execute ReAct से अलग तरीक़ा है। Reasoning और action को जोड़ने की जगह, agent का पहला चरण उप-कार्यों या actions की स्पष्ट, क्रमबद्ध सूची बनाना है। Model (या अलग planner) योजना प्राकृतिक भाषा या संरचित रूप में देता है। फिर harness योजना को चरण-दर-चरण चलाता है। अगर replanning समर्थित है, तो कोई चरण फेल होने पर harness नई योजना माँग सकता है।

Decomposition इसके पीछे का सामान्य विचार है: बड़े अस्पष्ट task को कई छोटे, भली-भाँति परिभाषित tasks में तोड़ना। छोटा उप-कार्य model के लिए सही तरह चलाना आसान है, और इंसान के लिए जाँचना भी आसान। चाहे decomposition स्पष्ट रूप से हो (लिखी योजना के साथ) या अप्रत्यक्ष रूप से (ReAct की हर चरण की reasoning में), सिद्धांत वही है।

### स्पष्ट planning अपनी क़ीमत कब कमाती है

स्पष्ट योजना transcript में जगह घेरती है और किसी भी action के चलने से पहले अतिरिक्त model turn (कम से कम एक) माँगती है। यह अतिरिक्त बोझ है। यह बोझ कब उठाने लायक़ है?

**Execution से पहले मानवीय समीक्षा:** अगर task में बड़ा दाँव है (पैसे लगने वाली API call करना, email भेजना, data मिटाना), तो इंसान harness के कोई भी tool चलाने से पहले योजना पढ़ सकता है। इंसान योजना ठुकरा सकता है, बदलाव माँग सकता है, या भरोसे से मंज़ूर कर सकता है। इसके उलट, ReAct पहला action तब चला देता है जब इंसान को पता भी नहीं कि क्या होने वाला है। जिन tasks में मानवीय मंज़ूरी ज़रूरी है या जोखिम घटाती है, वहाँ स्पष्ट योजना अच्छा सौदा है।

**कई चरणों वाले tasks जहाँ ग़लत actions की क़ीमत ज़्यादा है:** अगर हर चरण को पलटना महँगा है या जोखिम भरा है, तो पहले से योजना पर टिककर और execution से पहले इंसान से समीक्षा करवाकर महँगी ग़लतियों की संभावना घटती है। खोजबीन वाला task जहाँ चरण सस्ते हैं (data पढ़ना, बिना ख़र्च की queries) उसे इस अतिरिक्त बोझ की ज़रूरत नहीं।

**साफ़, स्थिर ढाँचे वाले tasks:** कुछ tasks स्पष्ट क्रम में बँट जाते हैं जो बदलता नहीं: "File A डाउनलोड करो, parse करो, transform करो, नतीजा upload करो।" अगर चरणों के execution के बीच बदलने की संभावना नहीं है, तो उन्हें पहले से लिख देना और चला देना हर चरण पर नए सिरे से तर्क करने से सरल और सस्ता है।

### बासी योजना की समस्या और replanning

जोखिम यह है: योजना किसी भी tool के चलने से पहले बनी थी। अगर चरण 1 को file खोजनी थी, पर वह मौजूद नहीं है, तो चरण 2 की योजना मानती है कि file वहाँ है। चरण 2 फेल होगा या ग़लत नतीजे देगा। तब harness के पास दो विकल्प हैं: बासी योजना को आँख मूँदकर चलाते रहना (और शायद फेल होना) या replanning शुरू करना (model से नई स्थिति को देखते हुए नई योजना माँगना)।

Replanning मुफ़्त नहीं है: उसमें एक और model turn लगता है, और trajectory अब कई योजना-चरण दिखाती है, जो context खाते हैं। पर replanning अक्सर ज़्यादा ढाँचे वाले tasks के लिए ReAct से सस्ती होती है, क्योंकि model चरण-दर-चरण तर्क करने के बजाय नए रास्ते पर तेज़ी से सोच सकता है।

अगर replanning समर्थित नहीं है, तो plan-then-execute harness चुपचाप या शोर के साथ फेल होगा जब हक़ीक़त योजना से मेल नहीं खाएगी। इसीलिए "क्या आप replanning का समर्थन करते हैं?" plan-then-execute agents के लिए मुख्य design सवाल है।

### स्पष्ट planning के बिना decomposition

ध्यान दें कि decomposition और स्पष्ट planning अलग विचार हैं। Agent हर चरण पर ReAct-शैली की reasoning से tasks को अप्रत्यक्ष रूप से तोड़ सकता है। Model तर्क करता है "इसे हल करने के लिए मुझे X करना है, फिर Y, फिर Z" और फिर X करता है, नतीजा देखता है, फिर तर्क करता है, और Y पर जाता है। यह अप्रत्यक्ष decomposition है। स्पष्ट योजना वह "X, Y, Z" सूची execution शुरू होने से पहले संरचित artifact के रूप में लिख देती है।

कई tasks के लिए अप्रत्यक्ष decomposition (ReAct) सरल और ज़्यादा मज़बूत है। स्पष्ट planning तब इस्तेमाल करें जब अतिरिक्त बोझ (मानवीय समीक्षा, स्पष्टता, ढाँचा) क़ीमत के लायक़ हो।

### तीनों patterns की तुलना

Act-only सबसे सरल है पर debug करने में सबसे कठिन। ReAct reasoning और observation जोड़ता है, उसे दिखने वाला और ढलने वाला बनाता है। Plan-then-execute पहले का ढाँचा जोड़ता है जिसे किसी भी action के चलने से पहले जाँचा जा सकता है, अतिरिक्त model turn और योजना की धारणाएँ टूटने पर बासी होने की संभावना की क़ीमत पर।

अपने task और बंदिशों के आधार पर चुनें:

- छोटा खोजबीन वाला task, कोई बड़ा दाँव नहीं? ReAct इस्तेमाल करें।
- साफ़ चरणों वाला task जिनके बदलने की संभावना कम है? Plan-then-execute इस्तेमाल करें।
- ऐसा task जहाँ execution शुरू होने से पहले इंसान को समीक्षा करनी है? Approval gate के साथ plan-then-execute इस्तेमाल करें।
- ऐसा task जहाँ चरण महँगे हैं और विफलताओं की क़ीमत ज़्यादा है? Replanning के समर्थन के साथ plan-then-execute इस्तेमाल करें।

## अभ्यास

1. ▢ Task है "शहर के पास शिकायत दर्ज करो, जाँचो कि वह मिल गई, और उपयोगकर्ता को सूचित करो।" इसमें form भरना (दोबारा करना मुफ़्त नहीं), पुष्टि वाला email जाँचना और email भेजना शामिल है। इस task के लिए स्पष्ट planning बेहतर होगी या ReAct? क्यों?

<details markdown="1"><summary>जाँचें</summary>

स्पष्ट planning बेहतर है। चरण साफ़ और स्थिर हैं: form भरो, पुष्टि जाँचो, email भेजो। इस क्रम के execution के बीच बदलने की उम्मीद का कोई कारण नहीं। Form भरे जाने से पहले इंसान को योजना की समीक्षा करनी चाहिए, क्योंकि वह चरण आसानी से पलटा नहीं जा सकता। ReAct काम करता पर form भरने वाला चरण इंसान के समीक्षा करने से पहले चला देता, जिससे जोखिम बढ़ता।

</details>

2. ▢ आप ऐसा agent बना रहे हैं जो पता लगाता है कि उपयोगकर्ता का account locked क्यों है। Agent account की स्थिति जाँच सकता है, failed logins के लिए logs खोज सकता है, security flag देख सकता है, या support tickets query कर सकता है, इस पर निर्भर कि उसे क्या मिलता है। स्पष्ट planning बेहतर होगी या ReAct?

<details markdown="1"><summary>संकेत</summary>

सोचें कि चरणों का क्रम पहले से पता है या इस पर निर्भर है कि पहले के चरण क्या लौटाते हैं।

</details>

<details markdown="1"><summary>जाँचें</summary>

ReAct बेहतर है। चरण इस पर निर्भर हैं कि agent को हर मंज़िल पर क्या मिलता है। अगर account की स्थिति में security flag दिखे, तो अगला चरण उसे जाँचना है। अगर कोई अलग error दिखे, तो अगला चरण अलग है। क्रम पहले से लिखा नहीं जा सकता। सारी संभव branches की योजना बनाने की कोशिश से ReAct की चरण-दर-चरण reasoning और observation ज़्यादा स्वाभाविक है।

</details>

3. ▢ Plan-then-execute agent में replanning कब ज़रूरी बनती है, इसका सबसे अच्छा वर्णन इनमें से कौन-सा है?

    - a) जब भी agent ऐसे parameter वाली कोई tool call करे जिसका योजना ने ज़िक्र नहीं किया।
    - b) जब tool call फेल हो या अप्रत्याशित data लौटाए जो मूल योजना की किसी धारणा के उलट हो।
    - c) जब भी उपयोगकर्ता task के बारे में अपना मन बदले।
    - d) हर एक tool call के बाद, ताकि योजना ताज़ा रहे।

<details markdown="1"><summary>जाँचें</summary>

**b)** Replanning असली विफलताओं या अप्रत्याशित बातों से शुरू होती है: योजना ने data की उम्मीद की थी पर tool ने कुछ नहीं लौटाया, API call फेल हुई, या search को वह नहीं मिला जिसकी उम्मीद थी। a) ग़लत है, tools में अक्सर ऐसे parameters होते हैं जिन्हें योजना ने सूचीबद्ध नहीं किया; वह error नहीं है। c) ग़लत है, उपयोगकर्ता के बदलाव task-स्तर का मुद्दा हैं, plan-then-execute बनाम ReAct के लिए ख़ास नहीं। d) ग़लत है, हर चरण के बाद replanning योजना होने का मक़सद ही ख़त्म कर देती है और अक्षम है।

</details>

4. ▢ एक agent की स्पष्ट योजना है "चरण 1: उपयोगकर्ता के input के लिए search करो। चरण 2: नतीजों का सारांश बनाओ। चरण 3: सारांश की तुलना उपयोगकर्ता के मूल सवाल से करो।" चरण 1 के बाद search कोई नतीजा नहीं लौटाती। Harness replanning का समर्थन नहीं करता। आगे क्या होने की संभावना है?

<details markdown="1"><summary>जाँचें</summary>

चरण 2 (नतीजों का सारांश) फेल होगा या ग़लत output बनाएगा क्योंकि सारांश बनाने को कोई नतीजे नहीं हैं। Agent या तो अटक जाएगा, error लौटाएगा, या कुछ-नहीं का सारांश बनाएगा। Harness के पास मुड़ने का कोई तरीक़ा नहीं होगा: वह शुरू से योजना पर टिका था। यह replanning के समर्थन के बिना plan-then-execute harness की क़ीमत है। हल या तो replanning जोड़ना है (चरण 1 फेल होने पर model से नई योजना बनवाना) या ReAct पर जाना, जहाँ model चरण 1 के नतीजे के बाद तर्क करता और दूसरी search आज़माने का फ़ैसला करता।

</details>

## असली दुनिया का अभ्यास

- [ ] कोई कई चरणों वाला task लें जो आप नियमित करते हैं (जैसे order process करना, मुद्दे की जाँच करना, compliance के लिए document की समीक्षा)। वे चरण लिखें जो आप असल में अपनाते हैं। क्या चरण हमेशा उसी क्रम में होते हैं, या क्रम इस पर निर्भर है कि आपको हर चरण पर क्या मिलता है? अगर क्रम तय है, तो वह स्पष्ट मंज़ूरी के साथ plan-then-execute का उम्मीदवार है। अगर क्रम ढलने वाला है, तो वह ReAct का उम्मीदवार है।
- [ ] तय क्रम वाले task (जैसे file डाउनलोड करना, parse करना, transform करना, upload करना) के लिए छोटा plan-then-execute agent बनाएँ। उसे अलग inputs पर पाँच बार चलाएँ और trajectories पढ़ें। क्या agent कभी इसलिए फेल हुआ कि मूल योजना हक़ीक़त से मेल नहीं खाई? अगर हाँ, तो उन tool calls के बाद जो फेल हो सकती हैं, replanning gate जोड़ें।
- [ ] कल: आपका बनाया या इस्तेमाल किया कोई मौजूदा agent खोजें। उसकी trajectory के आधार पर उसे act-only, ReAct या plan-then-execute में वर्गीकृत करें। एक वाक्य का नोट लिखें कि वह pattern task में क्यों फिट बैठता है।
