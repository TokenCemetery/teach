# 第 16 课：先规划后执行与任务拆解

**使命关联:** 要针对一个任务，在单个提示词、固定工作流和智能体之间做出选择，你需要认清：什么时候显式计划带来的额外结构值得它的成本，什么时候 ReAct 的灵活性更便宜。
**主要来源:** [文章：“Building Effective Agents”，Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
**前置知识:** [第 15 课](0015-react-interleaving-reasoning-and-acting.md)

## 热身

1. ▢ 在 ReAct 中，工具调用执行完、运行框架把结果追加到对话记录之后，会发生什么？

<details markdown="1"><summary>检查</summary>

模型的下一轮收到的对话记录里，包含工具调用及其结果。模型随后可以发出新的推理，针对工具实际返回的内容做出反应，而不是死守事先做好的计划。

</details>

2. ▢ 描述一个场景，其中 ReAct 的逐步调整优于僵硬的预先计划。

<details markdown="1"><summary>检查</summary>

任何环境可能让智能体意外的场景：搜索什么也没返回（不是预期的数据）、工具失败、用户提供了与假设相矛盾的反馈，或者任务进行到一半出现了新信息。在这些情况下，ReAct 让模型能观察到意外并做出调整，而僵硬的预先计划会盲目地执行原来的步骤，然后失败或产生错误的结果。

</details>

## 要点

### 显式规划与任务拆解

先规划后执行是一种有别于 ReAct 的做法。智能体不再把推理和行动交错进行，而是第一步先产出一份显式的、有序的子任务或动作清单。模型（或一个单独的规划器）以自然语言或结构化的形式输出一份计划。运行框架随后逐步执行这份计划。如果支持重新规划，当某一步失败时，运行框架可以要求给出一份新的计划。

任务拆解是这背后的通用思想：把一个庞大而模糊的任务，拆成几个更小、定义明确的任务。较小的子任务，模型更容易正确执行，人也更容易验证。无论拆解是显式发生的（用一份写下来的计划），还是隐式发生的（在 ReAct 每一步的推理里），原则都是一样的。

### 显式规划什么时候值回成本

显式计划会占用对话记录的空间，并且在任何动作运行之前，需要额外的模型轮次（至少一轮）。这是开销。什么时候这笔开销值得付出？

**人工审核后再执行：** 如果任务涉及高风险（调用要花钱的 API、发送电子邮件、删除数据），人可以在运行框架运行任何工具之前先阅读计划。人可以否决计划、要求修改，或者放心地批准它。相比之下，ReAct 会在人还不清楚即将发生什么之前，就先运行第一个动作。对于需要人工批准、或能借此降低风险的任务，显式计划是一笔划算的交易。

**错误动作代价高昂的多步任务：** 如果每一步都很难撤销，或风险很高，那么预先确定计划并在执行前由人审核，可以降低出现昂贵错误的可能性。对于每一步都很廉价的探索性任务（读取数据、做不花钱的查询），则不需要这项开销。

**结构清晰而稳定的任务：** 有些任务可以拆解成不会改变的明显序列：“下载文件 A，解析它，转换它，上传结果。”如果这些步骤在执行中途不太可能改变，预先把它们写出来再执行，比每一步都重新推理更简单、更便宜。

### 计划过时的问题与重新规划

风险在这里：计划是在任何工具运行之前制定的。如果第 1 步本该找到一个文件，可它并不存在，第 2 步的计划却以为文件就在那里。第 2 步会失败或产生错误的结果。这时运行框架有两个选择：盲目地继续执行过时的计划（多半会失败），或者触发重新规划（让模型根据新的状态发出一份新计划）。

重新规划不是免费的：它要花另一个模型轮次，而且轨迹里现在有多个计划阶段，会占用上下文。但对于结构性强的任务，重新规划往往比 ReAct 便宜，因为模型可以很快想清楚新的路径，而不必一步一步地推理。

如果不支持重新规划，当现实与计划不符时，先规划后执行的运行框架会悄无声息地或惊天动地地失败。这就是为什么“你们支持重新规划吗？”是先规划后执行的智能体的一个关键设计问题。

### 不做显式规划的任务拆解

请注意，任务拆解和显式规划是两个不同的想法。智能体可以通过每一步 ReAct 式的推理，隐式地拆解任务。模型推理“要解决这个问题，我需要先做 X，再做 Y，再做 Z”，然后做 X，观察结果，再次推理，再转向 Y。这就是隐式的拆解。显式计划则是在执行开始之前，把这份“X、Y、Z”的清单作为结构化的产物写下来。

对于许多任务，隐式拆解（ReAct）更简单，也更稳健。只有当开销（人工审核、清晰度、结构）值得付出成本时，才使用显式规划。

### 比较这三种模式

只行动最简单，但最难调试。ReAct 增加了推理和观察，使其可见而且能够适应。先规划后执行则增加了一个预先的结构，可以在任何动作运行之前被审核，代价是多一个模型轮次，以及一旦计划的假设被打破就可能过时。

根据你的任务和约束来选择：

- 简短的探索性任务，没有高风险？用 ReAct。
- 步骤清晰、不太可能改变的任务？用先规划后执行。
- 需要有人在执行开始之前审核的任务？用带审批关卡的先规划后执行。
- 步骤昂贵、失败代价高的任务？用支持重新规划的先规划后执行。

## 练习

1. ▢ 一个任务是“向市政府提交一份投诉，确认已收到，并通知用户。”这涉及填写表格（不能随便重做）、检查确认邮件，以及发送邮件。显式规划还是 ReAct 更适合这个任务？为什么？

<details markdown="1"><summary>检查</summary>

显式规划更好。步骤清晰而稳定：填表、检查确认、发邮件。没有理由预期这个序列会在执行中途改变。在填写表格之前，应该由人审核计划，因为这一步不容易撤销。ReAct 也行得通，但会在人能审核之前就运行填表这一步，增加了风险。

</details>

2. ▢ 你在构建一个调查用户账号为何被锁定的智能体。智能体可能会检查账号状态、在日志中搜索登录失败、查找安全标记，或查询支持工单，具体取决于它发现了什么。显式规划还是 ReAct 更好？

<details markdown="1"><summary>提示</summary>

想一想，步骤的顺序是事先已知的，还是取决于前面的步骤返回了什么。

</details>

<details markdown="1"><summary>检查</summary>

ReAct 更好。步骤取决于智能体在每个阶段发现了什么。如果账号状态显示有安全标记，下一步就是去检查它。如果显示的是另一种错误，下一步就不同。这个序列无法预先写下来。与其试图规划所有可能的分支，ReAct 的逐步推理和观察要自然得多。

</details>

3. ▢ 下面哪一项最能描述先规划后执行的智能体在什么时候必须重新规划？

    - a) 每当智能体遇到的工具调用带有计划里没提到的参数。
    - b) 当工具调用失败，或返回了与原计划中某个假设相矛盾的意外数据时。
    - c) 每当用户改变了对任务的想法。
    - d) 在每一次工具调用之后，以确保计划保持新鲜。

<details markdown="1"><summary>检查</summary>

**b)** 重新规划由实际的失败或意外触发：计划预期有数据，工具却什么也没返回；API 调用失败了；或者搜索没有找到预期的东西。a) 是错的，工具常常有计划里没有列出的参数，这不是错误。c) 是错的，用户的变化是任务层面的问题，与先规划后执行还是 ReAct 无关。d) 是错的，每一步之后都重新规划，违背了制定计划的初衷，而且效率低下。

</details>

4. ▢ 一个智能体的显式计划是“第 1 步：搜索用户输入。第 2 步：总结结果。第 3 步：把总结与用户最初的问题做对照。”第 1 步之后，搜索没有返回任何结果。运行框架不支持重新规划。可能会发生什么？

<details markdown="1"><summary>检查</summary>

第 2 步（总结结果）会失败或产生错误的输出，因为没有可总结的结果。智能体要么卡住，要么返回错误，要么生成一份关于“什么都没有”的总结。运行框架无法转向：它从一开始就被绑定在这份计划上。这就是不支持重新规划的先规划后执行运行框架的代价。修复的办法要么是增加重新规划（第 1 步失败时让模型制定新计划），要么是改用 ReAct，让模型在看到第 1 步的结果之后进行推理，并决定尝试另一次搜索。

</details>

## 实战练习

- [ ] 找一个你经常做的多步任务（例如处理订单、调查问题、审查文档的合规性）。写出你实际遵循的步骤。这些步骤总是按同样的顺序发生，还是顺序取决于你在每一步发现了什么？如果顺序是固定的，那就是带显式批准的先规划后执行的候选。如果顺序是自适应的，那就是 ReAct 的候选。
- [ ] 为一个固定顺序的任务（例如下载文件、解析、转换、上传）构建一个小型的先规划后执行智能体。用不同的输入运行五次，并阅读轨迹。智能体有没有因为原计划与现实不符而失败过？如果有，就在可能失败的工具调用之后加一道重新规划的关卡。
- [ ] 明天：找一个你构建过或用过的现有智能体。根据它的轨迹，把它归类为只行动、ReAct 或先规划后执行。写一句话，说明为什么这种模式适合这个任务。
