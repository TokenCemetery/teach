# पाठ 17. Self-Critique और Reasoning Models ने क्या बदला

**मिशन से संबंध:** असफल agent को जाँचने के लिए आपको पहचानना होगा कि reflection चरण (अलग loop जो पिछली विफलताओं का मूल्यांकन करके सबक़ आगे ले जाता है) कब जोड़ना है और कब model की अपनी भीतरी reasoning उस loop को फ़ालतू बना देती है।
**मुख्य स्रोत:** [पेपर: "Reflexion: Language Agents with Verbal Reinforcement Learning", Shinn et al., 2023](https://arxiv.org/abs/2303.11366)
**पूर्व-आवश्यकताएँ:** [पाठ 16](0016-plan-then-execute-and-decomposition.md)

## वार्म-अप

1. ▢ Plan-then-execute agent में, अगर कोई चरण फेल हो जाए और harness replanning का समर्थन न करे तो क्या होता है?

<details markdown="1"><summary>जाँचें</summary>

Harness के पास ख़ुद को ढालने का कोई तरीक़ा नहीं है। वह या तो मूल योजना पर आँख मूँदकर चलता रहता है (जो शायद फिर फेल होगी), या रुक जाता है। Agent विफलता से सीख नहीं सकता या दूसरे तरीक़े की ओर मुड़ नहीं सकता क्योंकि योजना पहले ही पक्की हो चुकी थी और उसे अपडेट करने की कोई व्यवस्था नहीं है।

</details>

2. ▢ Agent को शुरू से फिर चला देने के मुक़ाबले स्पष्ट replanning का क्या फ़ायदा है?

<details markdown="1"><summary>जाँचें</summary>

Replanning model को ठीक वह विफलता देखने और context में उस पर तर्क करने देती है। अगर आप बस agent को फिर चला दें, तो वह वही योजना फिर बना सकता है। Replanning में harness विफलता को transcript में जोड़ता है और model से नई योजना बनाने को कहता है, ताकि model देख सके कि क्या ग़लत हुआ और सुधार कर सके।

</details>

## यह जानें

### Reflexion: reflection loop जोड़ना

Reflexion पेपर agent loop में स्पष्ट reflection चरण जोड़ता है। जब कोई प्रयास फेल होता है (agent का उत्तर ग़लत है, task पूरा नहीं होता, test फेल होता है), तो harness तुरंत retry नहीं करता। इसके बजाय वह प्राकृतिक भाषा में इस पर reflection बनाता है कि क्या ग़लत हुआ। यह reflection सहेजा जाता है (अक्सर file या memory buffer में) और अगले प्रयास के context में शामिल किया जाता है।

Loop ऐसा दिखता है:

1. Task पर agent चलाएँ।
2. जाँचें कि task सफल हुआ या नहीं (test पास होता है, इंसान उत्तर को सही आँकता है)।
3. अगर फेल हुआ, तो reflection बनाएँ: "मैंने X आज़माया, पर X फेल हुआ क्योंकि Y।"
4. Reflection को टिकाऊ memory में सहेजें।
5. Agent को फिर चलाएँ, इस बार context में सहेजा हुआ reflection शामिल करके।
6. चरण 2 पर लौटें।

यह सादे retry से अलग है। सादा retry agent को उसी context के साथ फिर चलाता है। Reflexion agent को context में reflection के साथ फिर चलाता है, ताकि दूसरा प्रयास पहले प्रयास की विफलता से सीख सके।

### Reflection मुफ़्त क्यों नहीं है

Reflexion अतिरिक्त model calls की क़ीमत लेता है। अगर पहला प्रयास फेल होता है, तो अब reflection बनाने के लिए एक call चाहिए, फिर दूसरा प्रयास चलाने के लिए एक और call। कम विफलता दर वाले tasks के लिए यह अतिरिक्त बोझ चुकाने लायक़ नहीं। जिन tasks में कई प्रयास चाहिए, वहाँ जमा cost ज़्यादा है।

Reflection context budget भी खाता है। हर reflection context window में tokens लेता है। अगर आप प्रयासों के पार कई reflections जमा करते हैं, तो आख़िरकार उन्हें छाँटना या संक्षिप्त करना पड़ता है। यह पहले के पाठों की context-प्रबंधन समस्या का दूसरा रूप है।

Reflection तभी मायने रखता है जब वह ख़ुद असली जानकारी पर टिका हो: फेल हुआ test, error संदेश, इंसानी मूल्यांकन। अगर task में विफलता का कोई साफ़ संकेत नहीं है, तो reflection के पास प्रतिक्रिया देने को कुछ ठोस नहीं होता और वह बस पिछले ग़लत उत्तर को सही ठहरा सकता है।

### लंबी भीतरी reasoning वाले models

हाल के वर्षों में, कुछ अग्रणी models में उत्तर देने से पहले लंबी भीतरी reasoning करने की क्षमता आ गई है। यह reasoning transcript में दिखती नहीं (वह एक ही model turn के भीतर होती है, output लौटने से पहले) पर वह model को ख़ुद को सुधारने, अपना काम दोबारा जाँचने और स्पष्ट ग़लतियाँ output में आने से पहले पकड़ने देती है।

यह स्पष्ट reflection loops के पक्ष को बदलता है, पर ख़त्म नहीं करता। जो कुछ reflection loop पहले देता था (साफ़ ग़लत बीच का चरण पकड़ना) वह अब model की अपनी reasoning के भीतर होता है, इसलिए ऊपर से reflection loop जोड़ने से पहले जितना सीमांत फ़ायदा नहीं मिलता।

फिर भी, स्पष्ट reflection का एक फ़ायदा है जो भीतरी reasoning के पास नहीं: वह ऐसी जानकारी शामिल कर सकता है जो tool call होने के बाद ही मौजूद होती है। अगर tool call "Permission denied" लौटाता है या test फेल होता है, तो model की भीतरी reasoning ने अपने मूल reasoning चरण में वह विफलता का संकेत नहीं देखा हो सकता, क्योंकि tool तब तक चला ही नहीं था। स्पष्ट reflection loop tool का असली नतीजा देखकर उसे अगले प्रयास में शामिल कर सकता है।

तो सवाल "reflection या भीतरी reasoning" नहीं है, बल्कि यह है कि "भीतरी reasoning के बावजूद बाहरी reflection की अतिरिक्त क़ीमत अपनी जगह कब कमाती है?"

### स्पष्ट self-critique अपनी क़ीमत कब कमाता है

बाहरी reflection तब इस्तेमाल करें जब:

- Task में विफलता का साफ़, जाँचने लायक़ संकेत है (test suite पास या फेल होती है, API error लौटाती है, इंसान उत्तर को ग़लत या सही आँकता है)।
- विफलता से सीखा हुआ दूसरा या तीसरा प्रयास वहाँ सफल होने की संभावना रखता है जहाँ पहला फेल हुआ।
- Task दोबारा आज़माने लायक़ है: मूल्य इतना ऊँचा कि अतिरिक्त model calls जायज़ हों।

Reflection तब न जोड़ें जब:

- Task में विफलता का कोई साफ़ संकेत नहीं है (जैसे "सारांश लिखो" जिसमें सही होना जाँचने के लिए कोई test या rubric नहीं)।
- विफलता model की ग़लती नहीं है (जैसे ज़रूरी API बंद है, ऐसा कुछ नहीं जो model ठीक कर सके)।
- पहला प्रयास पहले से ही बहुत संभावित रूप से सफल होगा और विफलताएँ दुर्लभ हैं।

### Reflection के संकेत डिज़ाइन करना

Reflection उतना ही अच्छा है जितना संकेत उसे मिलता है। अगर आप harness को बताते हैं "यह task फेल हुआ क्योंकि उपयोगकर्ता ने ऐसा कहा," तो reflection बना सकता है "मैंने सारांश लिखने की कोशिश की पर उपयोगकर्ता को पसंद नहीं आया।" अगले प्रयास के लिए उस पर कार्रवाई करना बहुत अस्पष्ट है। बेहतर विफलता संकेत होता "सारांश में ग्राहक की बताई ज़रूरतें छूटी हैं" या "सारांश 100-शब्द की सीमा से लंबा है।"

Reflecting agent बनाते समय विफलता की जाँच सावधानी से डिज़ाइन करें। सफलता कैसी दिखती है? विफलता का कौन-सा ठोस प्रमाण है? वही प्रमाण है जिस पर reflection प्रतिक्रिया देगा।

## अभ्यास

1. ▢ एक agent LeetCode की समस्या हल करने के लिए code लिखता है। Test suite code चलाती है और या तो "All tests pass" बताती है या कोई ख़ास फेल हुआ test case print करती है। विफलता के बाद harness reflection बनाता है और agent को context में reflection के साथ फिर चलाता है। यह Reflexion के लिए अच्छा मेल क्यों है?

<details markdown="1"><summary>जाँचें</summary>

विफलता का साफ़ संकेत है: test suite। Reflection कह सकता है "Test case [input] में [output] अपेक्षित था पर मैंने [wrong_output] बनाया।" यह ठोस और कार्रवाई योग्य है। Model अगले प्रयास में इसे पढ़कर ख़ास फेल हुए case को debug कर सकता है। Code generation वैसे भी स्वभाव से दोहराव वाला है; कई प्रयासों की उम्मीद है और वे क़ीमत के लायक़ हैं।

</details>

2. ▢ एक agent से e-commerce साइट के लिए product copy लिखने को कहा जाता है। Agent copy बनाकर जमा कर देता है। कोई test suite नहीं, कोई rubric नहीं, कोई स्वचालित जाँच नहीं। इंसानी marketing manager उसे पढ़कर कहता है "यह सही नहीं है, फिर कोशिश करो।" क्या यहाँ Reflexion मदद करेगा?

<details markdown="1"><summary>संकेत</summary>

Reflection loop के पास काम करने के लिए कौन-सी प्रतिक्रिया है? क्या वह अगले प्रयास के कार्रवाई करने के लिए काफ़ी ठोस है?

</details>

<details markdown="1"><summary>जाँचें</summary>

Reflexion ज़्यादा मदद नहीं करेगा। प्रतिक्रिया "यह सही नहीं है" बहुत अस्पष्ट है। Reflection कुछ ऐसा होगा "Marketing manager को मेरी copy पसंद नहीं आई।" Agent के अगले प्रयास के पास बदलाव करने को कोई ठोस चीज़ नहीं होगी। बेहतर तरीक़ा होगा manager से ख़ास प्रतिक्रिया लेना (जैसे "इसे छोटा करो और कीमत की तुलना जोड़ो") और उसे reflection loop पर निर्भर रहने के बजाय अगले prompt में शामिल करना।

</details>

3. ▢ लंबी भीतरी reasoning वाला model अब अपने ही reasoning चरण में ख़ुद को सुधार सकता है। इस संदर्भ में स्पष्ट बाहरी reflection loop का फ़ायदा इनमें से अब भी कौन-सा है?

    - a) बाहरी reflection हमेशा भीतरी reasoning से तेज़ होता है।
    - b) बाहरी reflection ऐसी जानकारी (जैसे tool error या test की विफलता) शामिल कर सकता है जो model के पहले प्रयास के बाद ही मौजूद होती है।
    - c) बाहरी reflection context tokens में भीतरी reasoning से सस्ता है।
    - d) बाहरी reflection सभी models के साथ काम करता है, भीतरी reasoning की क्षमता के बिना वालों के साथ भी।

<details markdown="1"><summary>जाँचें</summary>

**b)** भीतरी reasoning किसी भी tool के चलने से पहले होती है, इसलिए वह tool का असली नतीजा या test की विफलता नहीं देख सकती। स्पष्ट reflection loop वह जानकारी शामिल कर सकता है, इसलिए वह भीतरी reasoning वाले models के साथ भी मूल्य देता है। a) ग़लत है, भीतरी reasoning अक्सर अतिरिक्त loop चलाने से तेज़ होती है। c) ग़लत है, बाहरी reflection context tokens खाता है (reflection का text और अगला प्रयास दोनों जगह लेते हैं)। d) सच है पर मुख्य अंतर्दृष्टि नहीं; सवाल यह है कि भीतरी reasoning मौजूद होने पर reflection क्या जोड़ता है।

</details>

4. ▢ आप ऐसा agent बना रहे हैं जो नौकरी के आवेदन process करता है। Harness के पास साफ़ संकेत है: hiring manager द्वारा मंज़ूर या अस्वीकृत। आप कई प्रयासों में agent के फ़ैसले बेहतर करने के लिए Reflexion इस्तेमाल करना चाहते हैं। अगले प्रयास के काम आने के लिए हर reflection को क्या दर्ज करना चाहिए?

<details markdown="1"><summary>जाँचें</summary>

Reflection को अस्वीकृति या मंज़ूरी के ख़ास कारण दर्ज करने चाहिए, अगर उपलब्ध हों। उदाहरण के लिए, "आवेदन अस्वीकृत क्योंकि: ज़रूरी certification नहीं थी। अगले प्रयास में मंज़ूर करने से पहले ज़रूरी certifications जाँचें।" या "आवेदन मंज़ूर क्योंकि: ज़रूरी skills में मज़बूत अनुभव और cover letter में अच्छा संवाद।" Reflection आवेदन के लिए ख़ास होना चाहिए, सामान्य सलाह नहीं। इससे अगले प्रयास को कार्रवाई करने के लिए कुछ ठोस मिलता है। अगर hiring manager सिर्फ़ हाँ/ना देता है और कारण नहीं, तो reflection कम कार्रवाई योग्य है।

</details>

## असली दुनिया का अभ्यास

- [ ] ऐसा task लें जिसमें दोहराव हो और जिसका पास/फेल का साफ़ संकेत हो (जैसे समस्या हल करना, test पास करना, rubric पूरा करना)। Reflecting agent loop लागू करें: प्रयास, विफलता की जाँच, reflection बनाना, context में reflection के साथ retry। इसे पाँच बार चलाएँ और गिनें कि reflection के साथ बनाम बिना reflection के agent को कितने प्रयास चाहिए। अंतर दर्ज करें।
- [ ] अपने काम में ऐसा task खोजें जिसमें विफलता का साफ़ संकेत नहीं है (जैसे लेखन, design, रचनात्मक काम)। बताएँ कि आप वह कैसे जोड़ेंगे (जैसे "rubric से तुलना करो," "किसी साथी से समीक्षा करवाओ," "ख़ास मानदंड जाँचो")। क्या विफलता का संकेत जोड़ने से reflecting agent काम का बनेगा, या task इंसानी loop से बेहतर सँभलता है?
- [ ] कल: Reflexion की trajectory पढ़ें (किसी पेपर, blog post या आपके बनाए से)। Reflection का text पहचानें। अगर model के पास भीतरी reasoning होती तो क्या reflection काम का होता? क्यों या क्यों नहीं?
