# पाठ 19. Coordination Cost

**मिशन से संबंध:** एक अच्छी तरह लैस agent और multi-agent system में से चुनने के लिए, आपको जानना होगा कि orchestrator-worker systems की tokens, reasoning और बिखरे context में क्या क़ीमत है, और यह कैसे परखें कि दूसरा agent ऐसा कुछ देता है या नहीं जो पहले agent को सीधे दिया ही नहीं जा सकता था।
**मुख्य स्रोत:** [लेख: "Don't Build Multi-Agents", Cognition](https://cognition.ai/blog/dont-build-multi-agents)
**पूर्व-आवश्यकताएँ:** [पाठ 18](0018-orchestrator-and-worker.md)

## वार्म-अप

1. ▢ पाठ 18 से याद करें: orchestrator-worker system में, क्या कोई worker दूसरे worker के चलते समय उसकी पूरी reasoning trajectory देख सकता है?

<details markdown="1"><summary>जाँचें</summary>

नहीं। हर worker अपने अलग किए हुए transcript के साथ अपना agent loop चलाता है। Workers एक-दूसरे के निष्कर्ष तभी देखते हैं जब orchestrator साफ़ तौर पर उन्हें दे, और सिर्फ़ अंतिम रिपोर्टें, पूरी reasoning नहीं। यह अलगाव एक ख़ूबी है (context साफ़ रखता है) और एक क़ीमत भी (workers task के बीच अंतर्दृष्टियाँ साझा नहीं कर सकते)।

</details>

2. ▢ पाठ 18 से याद करें: fan-out और handoff में क्या अंतर है?

<details markdown="1"><summary>जाँचें</summary>

Fan-out एक ही समस्या के अलग-अलग रूपों पर parallel में कई workers चलाता है, ज़्यादा व्यापक कवरेज और parallelism के लिए एक साथ अलग पहलू खोजते हुए। Handoff क्रमवार है: एक agent अपना task ख़त्म करके साफ़ context अगले चरण के लिए विशेष दूसरे agent को सौंपता है। दोनों multi-agent patterns हैं; fan-out समय इस्तेमाल करता है, handoff विशेषज्ञता।

</details>

## यह जानें

### Token cost: कई agents कई गुना महँगे

हर agent run की एक cost होती है। Orchestrator-worker system वह cost कई बार चुकाता है।

मान लें एक अकेला agent समस्या 10,000 tokens में हल करता है: मसलन, 20 turns जिनमें हर turn 500 tokens का। अब मान लें वही समस्या तीन स्वतंत्र उप-कार्यों में बँटी है, जिनमें से हर एक को worker 8,000 tokens में हल करता है (थोड़ा कम, क्योंकि हर worker का ध्यान संकरा है)। Orchestrator ख़ुद task तोड़ने और नतीजे जोड़ने में 2,000 tokens लेता है।

कुल cost: 8,000 + 8,000 + 8,000 + 2,000 = 26,000 tokens। Multi-agent system की cost अकेले agent से 2.6 गुना थी, भले ही हर worker अपने हिस्से पर अकेले agent से थोड़ा ज़्यादा कुशल था। Workers parallel में खोजबीन करते हैं, इसलिए wall-clock समय तेज़ है, पर token cost कई गुना है।

यह गणित और बिगड़ता है अगर workers अक्षमता से चलें या अगर orchestrator को एक से ज़्यादा बार तालमेल बिठाना पड़े (जैसे orchestrator समझे कि workers से कोई निर्भरता छूट गई, नए workers चलाए, या workers से नए instructions के साथ फिर चलने को कहे)। Cognition का लेख इसे मूल सवाल बताता है: क्या parallelism से मिली गति कई गुना token cost चुकाने के लायक़ है?

### बिखरा हुआ context: workers एक-दूसरे को नहीं देख सकते

जब कोई अकेला agent लंबा task चलाता है, तो वह context बनाता है: वह जानता है कि उसने क्या आज़माया, क्या चला, क्या नहीं, और क्यों। Multi-agent system इस context को बिखेर देता है। Workers A और B एक ही ज़मीन पर शोध कर सकते हैं (जैसे दोनों किसी बंदिश को समझने की कोशिश में), पर Worker A को उस बंदिश पर Worker B की reasoning नहीं दिखती; उसे सिर्फ़ अंतिम रिपोर्ट दिखती है।

ठोस रूप से: Worker A को task के बीच में एहसास होता है कि किसी बंदिश का बारीक निहितार्थ है। Worker A उस पर तर्क करता है, समझ बनाता है, और वापस रिपोर्ट करता है। Orchestrator रिपोर्ट पढ़कर Worker B को देता है। Worker B अब निष्कर्ष जानता है पर वह reasoning नहीं जिससे वह निकला। Worker B task के बीच उस reasoning को निखार या चुनौती नहीं दे सकता, क्योंकि उसे Worker A की सोच नहीं दिखती। Worker B या तो रिपोर्ट मानकर इस्तेमाल करता है (उसे निखारने का मौक़ा खोते हुए) या उसे अनदेखा करके वही अंतर्दृष्टि फिर से निकालता है (tokens बर्बाद करते हुए)।

जिन tasks में सबसे अच्छा उत्तर कई reasoning धाराओं के बीच आगे-पीछे निखरने से निकलता है, वहाँ बिखरा context असली सीमा है। पर्याप्त turns वाला अकेला agent अपनी सारी reasoning एक जगह रख सकता है और अंतर्दृष्टियाँ बनते ही उन्हें जोड़ सकता है।

### टकराते निष्कर्ष: स्वतंत्र खोजबीन असहमति तक ले जाती है

जब दो workers एक ही ज़मीन पर स्वतंत्र रूप से खोजबीन करते हैं, तो वे अलग निष्कर्षों पर पहुँच सकते हैं। यह ज़रूरी नहीं कि ग़लत हो; हो सकता है उन्हें सचमुच अलग (और दोनों वैध) व्याख्याएँ मिली हों। पर इसका मतलब यह भी हो सकता है कि एक worker से ग़लती हुई, या कुछ ऐसा छूटा जो दूसरे ने पकड़ा।

Orchestrator दोनों रिपोर्टें देखता है और उन्हें मिलाना पड़ता है। अगर टकराव अर्थ या तथ्य का है, तो orchestrator के सामने समस्या है: उसके पास सिर्फ़ workers के सारांश हैं, उनकी पूरी reasoning नहीं, इसलिए वह आसानी से नहीं खोज सकता कि असहमति कहाँ से आई। Orchestrator मिलान के लिए नया agent चला सकता है ("judge" या "synthesizer" sub-agent), जो और cost जोड़ता है।

अकेले agent का विकल्प इससे बचता है: एक ही ज़मीन पर क्रम से काम करने वाला अकेला agent हर नए निष्कर्ष को अपने चलते मानसिक मॉडल में जोड़ता है, इसलिए वह विरोधाभास उभरते ही पकड़ सकता है और उन्हें अपने reasoning loop के भीतर सुलझा सकता है।

### निर्णय का सिद्धांत: multi-agent कब सस्ता है?

Cognition का मुख्य स्रोत तर्क देता है कि ज़्यादातर multi-agent systems बेहतर tools वाले अकेले agent से tokens या reasoning की गुणवत्ता में सस्ते नहीं होते। सवाल यह नहीं है कि "क्या parallelism तेज़ है?" (हाँ) बल्कि यह है कि "क्या parallelism ऐसा कुछ ख़रीदता है जो अकेले agent को कम क़ीमत में मिल ही नहीं सकता था?"

यह निर्णय सिद्धांत लागू करें:

**Multi-agent तब सही है जब:**

- उप-कार्य सचमुच स्वतंत्र हों (कोई साझा context नहीं, task के बीच एक-दूसरे के नतीजों पर कोई निर्भरता नहीं)।
- उप-कार्य हर एक मूल task से सरल हों (हर worker सचमुच संकरी समस्या हल करे, ताकि workers की कुशलता के फ़ायदे का योग दोहराव की क़ीमत से ज़्यादा हो)।
- आपको parallelism से मिलने वाली गति चाहिए (समय की बचत token के गुणक को जायज़ ठहराती है; आपके पास wall-clock की ऐसी समय-सीमा है जिसे एक agent और ज़्यादा turns से पूरा नहीं कर सकते)।
- हर worker के tools इतने विशेष हों कि साझा tool suite हर worker को अप्रासंगिक विकल्पों से धीमा कर देती।

**ज़्यादा संसाधनों वाला अकेला agent आमतौर पर तब जीतता है जब:**

- उप-कार्य context साझा करते हों या एक-दूसरे को निखारते हों (अकेला agent अपनी सारी reasoning जुड़ी रखता है; multi-agent system को दोबारा निकालना या दोबारा बताना पड़ता है)।
- आपके पास context budget में गुंजाइश हो (अकेले agent को बड़ी context window, बेहतर retrieval, ज़्यादा tools, ज़्यादा turns दें)।
- उप-कार्य एक-दूसरे पर निर्भर हों या कई सोच-धाराओं के बीच आगे-पीछे निखार माँगते हों।
- Coordination का अतिरिक्त बोझ (orchestrator का समय, संवाद, टकराते निष्कर्षों का मिलान) समस्या के सापेक्ष ज़्यादा हो।

सीधे शब्दों में: बेहतर tools, लंबे context और ज़्यादा turns वाला अकेला agent अक्सर वही समस्या बिखरे context वाले कई agents से सस्ते में और बेहतर reasoning गुणवत्ता के साथ हल करता है। Parallelism से मिली गति असली है पर मुफ़्त नहीं।

## अभ्यास

1. ▢ आप प्रश्नोत्तर system बना रहे हैं। विकल्प A: search, code execution और दस्तावेज़ tools वाला एक agent। विकल्प B: orchestrator जो तीन workers parallel में चलाता है, हर एक के पास एक विशेष tool (search worker, code worker, docs worker)। दोनों का लक्ष्य जटिल उपयोगकर्ता सवालों के जवाब देना है। किन परिस्थितियों में विकल्प B की token cost विकल्प A से सस्ती हो जाती है?

<details markdown="1"><summary>जाँचें</summary>

यह जाल है। ज़्यादातर परिस्थितियों में विकल्प B tokens में ज़्यादा महँगा है क्योंकि आप पूरे agent की cost तीन बार चुकाते हैं, साथ में orchestrator का अतिरिक्त बोझ। विकल्प B की token cost विकल्प A से सस्ती तभी होती है जब विशेषज्ञता का फ़ायदा बहुत बड़ा हो, या जब तीनों workers इतनी जल्दी ख़त्म कर लें (कम turns) कि 3 गुना सस्ता 1 गुना महँगे को हरा दे। ज़्यादा संभावना यह है: विकल्प A (कई tools वाला एक agent) tokens में दोनों विकल्पों से महँगा है, क्योंकि अकेले agent को तय करने में सोचना पड़ता है कि कौन-सा tool इस्तेमाल करे। विकल्प B विकल्प C (धीमे agent) को हरा सकता है पर बराबर गुणवत्ता और tool पहुँच वाले अकेले agent को शायद ही हराता है। समझौता है wall-clock समय (विकल्प B parallelism के कारण तेज़ है) बनाम tokens (विकल्प A सस्ता है)। आप विकल्प B गति के लिए चुनते हैं, cost के लिए नहीं।

</details>

2. ▢ पाठ 18 के orchestrator-worker system (parallel शोध workers) में, मान लें दो workers एक ही स्रोत पर शोध करते हैं और उसके कहने के बारे में अलग निष्कर्षों पर पहुँचते हैं। Orchestrator के पास दोनों रिपोर्टें हैं। Orchestrator के पास क्या नहीं है जो अकेले agent के पास होता?

<details markdown="1"><summary>संकेत</summary>

सोचें कि उस स्रोत पर तर्क करते समय हर worker के transcript में क्या है, बनाम अकेले agent के transcript में क्या है।

</details>

<details markdown="1"><summary>जाँचें</summary>

Orchestrator को दो निष्कर्ष दिखते हैं पर उनके पीछे की reasoning नहीं। वही स्रोत पढ़ने वाले अकेले agent के पास उस स्रोत पर अपनी सारी reasoning एक transcript में होती: उसने text की व्याख्या कैसे की, कौन-सी बारीकी देखी, क्या सोचा और ठुकराया। अकेले agent की reasoning पूरी तरह खोजी जा सकती है। Orchestrator बस पूछ सकता है "आप उस निष्कर्ष पर कैसे पहुँचे?" और worker को दोबारा समझाना पड़ेगा, या orchestrator को असहमति की जड़ खोजने के लिए नया agent चलाना पड़ेगा। यही बिखरा context है।

</details>

3. ▢ आप तय कर रहे हैं कि किसी task के लिए fan-out (orchestrator-worker) इस्तेमाल करें या अकेला agent। Task है: एक dataset और एक सवाल दिया गया है, data साफ़ करो, उसे खँगालो, model बनाओ, और निष्कर्ष बताओ। क्या चरण (सफ़ाई, खोजबीन, modeling, रिपोर्ट) fan-out में parallel चलेंगे या क्रम से?

    - a) Parallel, क्योंकि fan-out सारे workers एक साथ चलाता है।
    - b) क्रम से, क्योंकि खोजबीन सफ़ाई पर निर्भर है, modeling खोजबीन पर निर्भर है।
    - c) Parallel, पर काम ऐसे बँट सकता है कि हर worker सारे चरण स्वतंत्र रूप से करे।
    - d) इस पर निर्भर है कि workers के पास वही dataset है या नहीं।

<details markdown="1"><summary>जाँचें</summary>

**b)** यह task fan-out के लिए अच्छा मेल नहीं है क्योंकि चरण क्रमवार हैं: आप गंदे data की खोजबीन अच्छे से नहीं कर सकते, data को समझे बिना model नहीं बना सकते, आदि। हर चरण पिछले पर निर्भर है। Fan-out स्वतंत्र उप-कार्यों वाले tasks पर चमकता है (शोध का पहलू A, पहलू B, पहलू C parallel में)। क्रमवार काम के लिए handoff (पाठ 18) fan-out से बेहतर मेल है, या पर्याप्त turns वाला अकेला agent सरल है। (a) ग़लत है: parallelism जादू नहीं करता; निर्भरताएँ फिर भी रहती हैं। (c) संभव है पर विशेषज्ञता का मक़सद ही ख़त्म कर देता है; हर worker को सारे tools और ज्ञान चाहिए होंगे। (d) भटकाने वाली बात है; data की पहुँच यहाँ सीमित करने वाला कारक नहीं है।

</details>

4. ▢ Cognition का लेख तर्क देता है कि बेहतर retrieval या ज़्यादा सक्षम tools वाला अकेला agent अक्सर orchestrator-worker system से कम tokens में समस्याएँ हल करता है। इस दावे का मूल कारण क्या है?

<details markdown="1"><summary>जाँचें</summary>

अकेला agent अपनी सारी reasoning एक transcript में रखता है, इसलिए वह निष्कर्षों को जोड़ता है, विरोधाभास पकड़ता है और निष्कर्षों को एक ही reasoning loop के भीतर निखारता है। Orchestrator-worker system कई agent loops की token cost चुकाता है, और उनके बीच context बिखेरता है, इसलिए workers अंतर्दृष्टियाँ दोबारा निकालते या दोबारा बताते हैं। Context को एकजुट और reasoning को जुड़ी रखने से अकेले agent को मिलने वाला कुशलता का फ़ायदा अक्सर multi-agent system की parallelism की गति से ज़्यादा होता है, ख़ासकर जब सवाल में निर्भरताएँ हों या जुड़ी reasoning से फ़ायदा हो। एक agent को ज़्यादा tools या बेहतर retrieval देना (दोनों कई agents चलाने से सस्ते) अक्सर जीतता है।

</details>

5. ▢ आप फेल हो रहे program को debug करने वाला system बना रहे हैं। आप fan-out पर विचार करते हैं: तीन workers चलाएँ, हर एक parallel में अलग debugging रणनीति आज़माए, फिर orchestrator सबसे अच्छी अंतर्दृष्टि चुने। यह design कौन-सी क़ीमत नहीं पकड़ता जो पाठ 19 सिखाता है?

<details markdown="1"><summary>जाँचें</summary>

Token cost तीन गुना (हर worker पूरा agent run है), बिखरा context (कोई worker दूसरे workers की खोजबीन नहीं देखता, इसलिए वे एक-दूसरे से सीखने की जगह वही बंद रास्ता तीन बार दोबारा निकाल सकते हैं), और orchestrator को bug क्या है इस बारे में संभावित रूप से टकराते निष्कर्ष मिलाने पड़ते हैं। तीनों रणनीतियाँ क्रम से आज़माने वाला अकेला agent आगे बढ़ते हुए bug का एकजुट मॉडल बनाता। तीन workers वह नहीं कर सकते, जब तक orchestrator मिलान का चरण न चलाए (एक और agent, और cost)। Fan-out गति ख़रीदता है (तीनों workers सबसे धीमे worker के समय में ख़त्म होते हैं, तीनों के योग में नहीं), पर debugging जैसे task के लिए क़ीमतें ज़्यादा हैं जहाँ अंतर्दृष्टि पर अंतर्दृष्टि बनती है।

</details>

## असली दुनिया का अभ्यास

- [ ] कोई ऐसी समस्या लें जो आपने पहले हल की है (debugging, विश्लेषण, planning, शोध, कुछ भी)। उसे मन में कई turns वाले अकेले agent की तरह बनाम तीन fan-out workers की तरह चलाएँ। Parallelism से आपको wall-clock समय में कहाँ जीत मिलती? बिखरा context आपको कहाँ महँगा पड़ता और दोबारा निकालने या मिलान के काम में धकेलता?
- [ ] Cognition का लेख "Don't Build Multi-Agents" कम से कम एक बार पढ़ें। वह खंड ढूँढें जहाँ लेखक तर्क देता है कि अकेला agent और बेहतर tools orchestrator-worker को हराते हैं। उनका दिया एक ठोस उदाहरण लिखें और बताएँ कि अकेले agent को किस बात ने सस्ता बनाया।
- [ ] कल: कोई task खींचें जिसे आप agent system में बना सकते हैं। उस task के लिए अनुमान लगाएँ: अकेला agent कितने tokens इस्तेमाल करेगा? fan-out system की कितनी cost होगी (तीन workers मान लें, हर एक अकेले agent के प्रति-task हिस्से से थोड़ी कम token cost पर चलता हुआ)? क्या गति का फ़ायदा आपके लिए token के गुणक के लायक़ है?
