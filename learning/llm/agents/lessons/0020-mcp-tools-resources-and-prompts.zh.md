# 第 20 课：MCP：工具、资源与提示词

**使命关联:** 把 MCP 理解为解决集成问题的、与服务商无关的协议，这样你就能推断智能体可以访问哪些工具，以及如何在不重写运行框架的情况下添加新工具。
**主要来源:** [规范：Model Context Protocol](https://modelcontextprotocol.io/specification)
**前置知识:** [第 19 课](0019-coordination-cost.md)、[工具](../GLOSSARY.md)

## 热身

1. ▢ 在第 3 课里，你学到工具有名称、描述和参数 schema。运行框架运行时，它从哪里获得这些定义：从模型、从运行框架的代码，还是从别的地方？

<details markdown="1"><summary>检查</summary>

从运行框架的代码。运行框架的作者手写工具定义，或从配置文件中加载，然后在循环开始之前告诉模型这些工具。

</details>

2. ▢ 当你把智能体连接到一个新的数据源（数据库、API、文件存储）时，谁来做这项工作：模型、运行框架，还是两者？

<details markdown="1"><summary>检查</summary>

两者都有。运行框架的作者编写代码来集成这个数据源（获取、解析、处理错误），然后通过添加一个工具定义告诉模型它的存在。模型决定是否调用它以及何时调用。

</details>

## 要点

### M 乘 N 的问题

没有共同的标准，把智能体的运行框架连接到外部工具和数据源，就需要定制的集成工作。如果你的运行框架能调用 N 个不同的工具或数据源，而有 M 个不同的智能体构建团队或框架，你就会得到 M*N 个独立的集成：每个团队都要写专门的代码，去对接每个工具或数据源。

MCP（Model Context Protocol，模型上下文协议）通过创建一套运行框架一侧和工具一侧都能实现的共享接口，解决了这个问题。一个工具或数据源只需实现一个 MCP 服务器。任何兼容 MCP 的运行框架都能连接到它。运行框架只需实现一个 MCP 客户端。任何兼容 MCP 的服务器都能向它暴露能力。这样你就得到 M+N 个集成，而不是 M*N 个。

这很重要，因为没有它，让智能体使用更多工具，意味着定制代码呈二次方增长。有了 MCP，扩展意味着构建或连接更多标准的服务器。

### 三种基本类型

MCP 定义了服务器可以向客户端暴露的三种能力：

**工具**（与第 3 课的工具相当）：模型可以调用的动作。工具有名称、描述和输入 schema。当模型决定调用它时，客户端把请求发给服务器，服务器执行这个动作并返回结果。模型看到结果并继续。这与你已经了解的客户端工具和服务端工具完全一样，只是接口被标准化了，所以任何一方都可以被替换。

**资源**：MCP 客户端可以直接读取的数据，无需模型把它作为工具调用来触发。资源可以是一个文件、一条数据库记录、一个网页，或一个实时的 API 响应。客户端可以列出可用的资源，并按名称获取其中之一。这与工具不同，因为不是模型来调用它；而是运行框架读取它，并决定是否把数据放进上下文，或者拿它做别的什么。资源让运行框架可以引入相关信息，而不阻塞模型的轮次，也不增加工具调用的开销。

**提示词**（提示词模板）：MCP 服务器暴露出来、供客户端填写并使用的可复用提示词模板。提示词模板可以是“分析这段代码的安全问题”或“总结这份文档”。客户端可以列出可用的提示词模板，按名称获取其中之一，并填入参数。这有别于工具和资源：运行框架不是执行动作或获取数据，而是用模板构造一条发给模型的消息，把它嵌入智能体自己的指令或推理步骤中。

### 基本生命周期

客户端连接到服务器。它们协商能力：这台服务器实际上支持工具、资源和提示词中的哪些。服务器声明它有什么；客户端决定使用什么。

然后，根据客户端支持什么、运行框架需要什么：

- 客户端可以列出可用的工具并获取它们的 schema，然后把它们呈现给模型。
- 客户端可以列出可用的资源并主动获取数据，用学到的内容来辅助智能体的决策。
- 客户端可以列出可用的提示词模板，并用它们来构造指令或反思步骤。

一台服务器可以三者都暴露，也可以只暴露其中一两个。这个协议是对称的：客户端和服务器都了解这套接口，所以任何一方都可以是通用的。

### 传输方式

MCP 服务器可以在本地运行（通过 stdio，也就是同一台机器上运行框架与服务器之间简单的进程到管道的通道），也可以远程运行（通过基于 HTTP 的传输，服务器运行在另一台机器或云服务上）。传输方式会影响延迟、部署和失败模式，但不影响协议本身。同时支持两种传输方式的运行框架，可以连接本地运行的 MCP 服务器以便快速迭代，也可以连接远程的 MCP 服务器以获得弹性或跨团队协作。

## 练习

1. ▢ 你在构建一个需要读取数据库并调用 Web API 的智能体。你们团队的数据库有 MCP 服务器。Web API 没有。你是两者都要写定制的集成代码，还是只写其中一个？

<details markdown="1"><summary>检查</summary>

只写一个。运行框架可以不写定制代码就连接到数据库的 MCP 服务器。对于 Web API，你的团队仍然要写一层封装（要么在运行框架里，要么作为围绕这个 API 的新 MCP 服务器）。这就是 M+N 原则：MCP 服务器替你完成了一半的工作。

</details>

2. ▢ 你的智能体需要查看天气，然后决定是否建议户外活动。这应该是工具（由模型调用），还是资源（由运行框架主动读取）？

<details markdown="1"><summary>提示</summary>

想想运行框架什么时候得知天气、模型什么时候需要知道它。是模型决定是否去问，还是运行框架总是去获取？

</details>

<details markdown="1"><summary>检查</summary>

视情况而定。如果天气总是与决策相关，就把它做成资源：运行框架在每一轮之前获取它，并把它包含在上下文里。如果天气只有在模型考虑户外活动时才相关，就把它做成工具：模型在需要时自己去要。工具让模型决定何时去看；资源则提供运行框架始终希望模型拥有的信息。

</details>

3. ▢ 你的智能体使用三个 MCP 服务器：一个用于电子邮件，一个用于日历，一个用于文档存储。邮件服务器支持工具和资源。日历服务器只支持工具。文档服务器支持工具、资源和提示词。下面哪一项是运行框架可以做的？

    - a) 使用三台服务器的资源，因为三台至少都支持工具
    - b) 使用三台的工具，只使用邮件和文档的资源，只使用文档的提示词
    - c) 使用三台服务器的提示词
    - d) 同等地使用所有服务器的工具和资源

<details markdown="1"><summary>检查</summary>

b) 运行框架只能使用每台服务器实际暴露的东西。邮件支持工具和资源，所以运行框架可以同时使用邮件的两者。日历只支持工具。文档支持工具、资源和提示词。运行框架针对每台服务器协商能力，只调用已声明的内容。提示词只有文档服务器提供，所以 c 是错的。并非所有服务器都支持资源，所以 a 和 d 是错的。

</details>

4. ▢ 你在决定把 MCP 服务器部署在本地（stdio）还是远程（HTTP）。你应该考虑什么取舍？

<details markdown="1"><summary>检查</summary>

本地（stdio）在同一台机器上更快、更容易设置，但会把运行框架与服务器进程耦合在一起。远程（HTTP）意味着服务器可以运行在任何地方，运行框架崩溃时它也能继续存活，但会增加网络延迟和失败模式（服务器可能很慢，或者无法访问）。两者都不会改变 MCP 协议本身；对客户端来说，它们的工作方式是一样的。根据你能容忍多大的延迟，以及你是否需要弹性或跨机器访问来选择。

</details>

## 实战练习

- [ ] 阅读 modelcontextprotocol.io 上的 Model Context Protocol 规范，找出一个已经存在的、针对你所在领域（电子邮件、文档、数据库、代码仓库）某样东西的 MCP 服务器。
- [ ] 为你自己的工作勾画 M*N 与 M+N 的对比：列出你关心的 M 个运行框架或团队，以及 N 个工具或数据源，然后估算 M+N 的做法能省下多少定制集成代码。
