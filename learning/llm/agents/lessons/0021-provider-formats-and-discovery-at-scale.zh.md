# 第 21 课：服务商格式与大规模工具发现

**使命关联:** 理解当智能体连接许多 MCP 服务器时，朴素的工具发现有哪些局限，并认清什么时候该用惰性或程序化的发现，来换掉一次性全部加载工具。
**主要来源:** [文章：“Code Execution with MCP”，Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)
**前置知识:** [第 20 课](0020-mcp-tools-resources-and-prompts.md)

## 热身

1. ▢ 在第 3 课里，你学到了两种传输格式：Anthropic 用 `input_schema` 表示工具调用，而 OpenAI 使用另一种结构，叫 `function.parameters`。如果你从 Anthropic 的 API 切换到 OpenAI 的 API，你需要修改你的 MCP 服务器、你的 MCP 客户端，还是两者都要修改？

<details markdown="1"><summary>检查</summary>

都不用。你的 MCP 服务器保持不变（它知道如何以 MCP 格式暴露工具）。变的是你的运行框架，因为它必须把 MCP 的工具定义翻译成模型所期望的那家服务商的传输格式。模型服务商变了，但 MCP 协议没有变。

</details>

2. ▢ 在第 9 课里，你学到了工具集膨胀：如果你给模型呈现太多的工具定义，它会变慢、变得困惑，或者忘记该用哪个工具。当智能体连接到五个 MCP 服务器、每个有十个工具时，模型一开始就会看到五十个工具定义吗？

<details markdown="1"><summary>检查</summary>

只有当运行框架在循环开始之前，就把全部五十个定义加载进上下文时才会。这是朴素的做法。但还有其他办法：运行框架可以只在模型要求时才加载工具，或者把工具定义翻译成模型可以探索并以程序方式调用的代码。

</details>

## 要点

### 两个相互独立的层

MCP 是智能体的运行框架与外部工具或数据源之间的协议。它定义了客户端和服务器如何彼此交流，以及服务器可以暴露哪些能力。但 MCP 并不关心模型使用什么传输格式。

与此同时，模型有它的服务商，而服务商有自己表示工具调用的特定方式。Anthropic 的 API 以一种结构接受工具。OpenAI 的 API 以另一种结构接受它们。这种传输格式是运行框架与模型之间一个独立的层。

这两层是相互独立的：

- MCP 客户端（运行框架一侧）对 MCP 服务器说 MCP。MCP 服务器不关心最终是哪个模型会使用这些工具。
- 然后运行框架把 MCP 的工具定义翻译成模型所期望的那家服务商的传输格式。Anthropic？用 `input_schema`。OpenAI？用 `function.parameters`。

运行框架必须做这个翻译，因为它位于中间。但改变其中一层，并不需要重写另一层。如果你更换模型服务商，不必重写你的 MCP 服务器。如果你连接了新的 MCP 服务器，运行框架与模型之间的传输格式也不会改变。

### 大规模的工具发现

对于单个智能体，你可能在一开始手动把两三个工具接入上下文。工具集膨胀（第 9 课）大约在五到十个工具时出现。但如果运行框架连接了十几个 MCP 服务器，每个有十到二十个工具呢？那就是几百个工具定义。

朴素的做法是在启动时加载每一个工具定义，把每个都翻译成服务商的传输格式，再全部交给模型放进它的初始上下文。这会在大得多的规模上重现工具集膨胀。模型要读几百个定义，把 token 浪费在它不需要的描述上，而且每一轮都会变慢，因为每个工具都在上下文里。而且，如果已连接的服务器上添加了一个新工具，整个上下文和模型的行为都会改变。

这就是大规模的工具发现问题：你可以连接许多服务器，但不能靠预先加载一切来做到。

### 代码执行的思路

Anthropic Engineering 的文章“Code Execution with MCP”提出了一个解决方案：不把工具定义加载进上下文，而是把可用的工具呈现为智能体可以发现并以程序方式调用的代码。

例如：

- 运行框架定义一个辅助函数 list_available_tools()，它查询已连接的 MCP 服务器，并返回一份可调用函数的目录：它们的名称、描述和参数。
- 运行框架定义一个辅助函数 call_tool(name, args)，它接收工具名称和参数，在已连接的服务器上找到该工具，并调用它。
- 运行框架不是一开始就给模型五十个工具定义，而是告诉模型：“你可以调用 list_available_tools() 来看看你能做什么，或者调用 call_tool(name, args) 来做某件具体的事。”

现在模型有了两个元工具：用于发现和调用其他工具的工具。它可以探索工具空间，而不必一开始就把每个定义加载进上下文。它在需要找一个工具时调用 list_available_tools()，了解那一刻有什么可用，然后使用它需要的。常驻的上下文保持很小。

这是用惰性发现换掉一次性全部加载。模型必须先花一轮调用 list_available_tools()，才能调用具体的工具，所以有延迟成本。但如果运行框架连接了五十个服务器，那么因为不把每个工具定义都留在上下文里而节省的 token，超过了额外一轮的成本。

### 什么时候用哪种做法

一次性全部加载（启动时把每个工具都放进上下文）适用于：

- 你有一小组固定的工具（两到十个）。
- 这些工具与智能体的每项任务都相关。
- 上下文不受限制。

惰性加载（定义 list_available_tools() 和 call_tool()，让模型发现它需要的）适用于：

- 你有许多工具（几十个或更多）。
- 工具是专门的，并非都与每项任务相关。
- 上下文受限，每个 token 都很重要。
- 额外一轮的延迟成本是可以接受的。

程序化发现（把工具呈现为模型可以阅读和运行的代码）结合了这两种思路：初始上下文很小（只有发现函数），并且能够探索工具空间，而不必手动加载定义。

## 练习

1. ▢ 你在用 Anthropic 的 API，连接着三个 MCP 服务器。你切换到 OpenAI 的 API。你需要更新你的 MCP 服务器、你的运行框架，还是两者？

<details markdown="1"><summary>检查</summary>

只需更新你的运行框架。MCP 服务器不变；它们仍然以 MCP 格式暴露工具。你的运行框架原来是把 MCP 定义翻译成 Anthropic 的传输格式；现在改为翻译成 OpenAI 的格式。翻译层变了，但服务器和协议没有变。

</details>

2. ▢ 你的智能体连接了十个 MCP 服务器，总共一百五十个工具。你想采用“代码执行与 MCP”的思路：定义 list_available_tools()，让模型去发现它需要的。这个设计有哪两个后果？

<details markdown="1"><summary>提示</summary>

想想上下文的大小和延迟。模型什么时候去要这份列表？这要付出什么代价？

</details>

<details markdown="1"><summary>检查</summary>

上下文更小，因为你不必一开始就加载一百五十个工具定义，只需两个函数，外加对它们作用的简短描述。延迟增加，因为模型想要探索时，必须在某一轮调用 list_available_tools()，在调用具体的工具之前至少多出一轮。如果上下文很紧张，或者工具很少需要同时全部用到，这是一个值得的取舍。

</details>

3. ▢ 你的运行框架只有三个工具，而且它们都与智能体执行的每项任务相关。你应该用一次性全部加载、惰性加载，还是程序化发现？

    - a) 用 list_available_tools() 做惰性加载
    - b) 一次性全部加载：一开始就把三个都放进上下文
    - c) 用 call_tool() 函数做程序化发现
    - d) 轮换哪些工具在上下文里，以节省 token

<details markdown="1"><summary>检查</summary>

b) 对于一小组始终相关的工具，一次性全部加载最简单、最快。你不会在发现函数上浪费 token，不增加延迟，模型也始终拥有它需要的工具。当工具集又小又通用时，惰性发现和程序化发现只会增加开销，没有收益。选项 d 是反模式：让工具轮换进出，会造成混乱和不确定性。

</details>

4. ▢ 你定义了 list_available_tools()，用来查询所有已连接的 MCP 服务器，并返回它们的工具名称和描述。当模型调用这个函数时，这次调用会计入你的 API token 吗？

<details markdown="1"><summary>检查</summary>

会。调用 list_available_tools() 和调用任何其他函数一样要花 token：模型发出调用，运行框架执行它，结果回到对话记录里。你是在拿预先放入工具定义所花的 token，去换发现调用所花的 token。工具很多时，这笔交易通常是划算的。

</details>
