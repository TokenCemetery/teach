# 第 23 课：作为工具的代码执行

**使命关联:** 要判断某个任务到底需不需要智能体，你必须理解：一个代码执行工具可以取代几十个狭窄的工具，降低 token 成本和延迟，但需要有强健的沙箱来对付任意代码。
**主要来源:** [文章：“Code Execution with MCP”，Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)
**前置知识:** [第 22 课](0022-sandboxing-and-approval-gates.md)

## 热身

1. ▢ 在第 22 课里，我们区分了沙箱和审批关卡。它们各自做什么？要防止模型意外删除文件，你会用哪一个？

<details markdown="1"><summary>检查</summary>

沙箱是阻止代码触及某些资源（比如允许目录之外的文件）的执行边界。审批关卡是在风险动作之前的人工检查点。要防止意外删除，你会使用把工具限制为只能在安全目录树之内写入的沙箱，这样即使模型要求删除，沙箱也会拒绝。审批关卡会在尝试删除之前暂停并请求人工批准，但如果获批，它并不会阻止删除。

</details>

2. ▢ 第 21 课介绍了大规模工具发现的思路：模型可以自省有哪些工具存在，而不是把每个定义都加载进上下文。这解决了什么问题？

<details markdown="1"><summary>检查</summary>

当你有几百个工具时，把每个工具的定义、名称、描述和参数 schema 都预先加载进模型的上下文窗口，会耗尽 token，也让模型更难推理该调用哪个工具。工具发现让模型可以按需请求关于可用工具的信息，或者调用自省端点来探索能力，这样完整的列表就不必放在初始上下文里。

</details>

## 要点

### 作为许多狭窄工具之替代方案的代码执行

设想一个数据分析的场景。没有代码执行时，你可能会向模型暴露这些工具：

- list_files：返回目录中的文件列表
- read_csv：读取 CSV 文件并返回前 N 行
- compute_mean：计算某一列的平均值
- compute_median：计算某一列的中位数
- filter_rows：按条件过滤表格
- sort_by：按某一列对表格排序
- write_csv：把表格写回文件

模型现在得决定以什么顺序调用哪个工具。它可能先调用 read_csv，再调用 filter_rows，再调用 compute_mean：要在模型的循环中往返三次。每次往返，都要消耗 token 去推理下一步该调用哪个工具，而且每个工具定义，也都要占用初始上下文窗口里的 token。

不如只给模型一个工具：沙箱化的代码解释器。模型写一小段 Python 程序：

```python
import pandas as pd

data = pd.read_csv('data.csv')
filtered = data[data['age'] > 30]
result = filtered['salary'].mean()
print(result)
```

模型运行一次，就得到了答案。好处是：一次工具调用，而不是三次；一个工具定义，而不是七个；模型可以在一个轮次里把多个操作串起来，不必再推理下一步该调用哪个工具。

### 成本与延迟上的好处

这种做法同时降低了 token 成本和延迟：

- token 成本：你只需为一个工具定义付费，而不是许多个；模型关于该调用哪个工具的推理开销，也融进了普通的写代码，而这是模型本来就做得很高效的事。
- 延迟：只需一次工具调用的往返，而不是三次或七次，意味着智能体的实际耗时成比例地下降。

对于大规模运行或有实时性要求的智能体，这些节省会不断累积。

### 与大规模工具发现的联系

第 21 课介绍了这样的思路：与其把每个工具定义都预先加载进上下文，不如让模型动态地探索可用的能力。代码执行是这一原则的具体实例：模型不需要预先加载每一个数据转换工具，因为它可以自己写代码来完成转换。可用的能力（函数、库、系统工具）是在代码运行时被发现的，而不是在初始上下文里。

在一些系统里，代码执行工具本身可以带有一套发现机制：模型可以调用的一个函数，用来列出有哪些库可用、能触及哪些数据源，或者有哪些系统命令可用。这是在发现之上再叠加发现。

### 沙箱必须对付任意代码，强制执行什么

在第 22 课里，我们看到沙箱强制规定工具的执行能触及的范围：文件系统路径、网络主机、资源限制。当工具是“运行模型写的任意代码”时，沙箱必须针对表达力强得多、也难以预测得多的代码来强制执行这些边界，而不是一个带有已知 JSON schema 的固定工具调用。

模型可能写出这样的代码：

- 试图通过符号链接、路径穿越技巧（/../..），或调用 find、ls 之类的系统工具去探测边界之外，来逃出文件系统边界。
- 写出网络代码，试图访问白名单之外的主机。
- 产生无限循环、递归函数，或分配内存的循环，试图耗尽资源。
- 调用代码以为存在、而运行框架打算禁止的函数或方法。

沙箱必须足够强健，才能把这一切都控制住。这比给固定工具做沙箱更难，因为代码的攻击面没有边界。真正的代码执行沙箱，通常会让代码运行在隔离的容器或进程里，带有 seccomp 规则、网络命名空间和资源 cgroup，而不只是文件系统的权限检查。

### 什么时候用代码执行，什么时候用狭窄的工具

代码执行很强大，但会带来沙箱的复杂性。在下面这些情况下，你应该优先选择它：

- 模型需要把许多小操作组合起来，否则就需要许多次往返。
- 这些操作是以算法或数据转换为主的（过滤、聚合、计算、格式转换）。
- 可用的能力定义明确，而且相对稳定。

在下面这些情况下，你应该坚持使用狭窄的、专门构建的工具：

- 操作确实是高风险的，并受益于明确的人工监督（发送邮件、公开发布、花钱）。
- 操作的安全性取决于以特定领域的方式验证输入或输出，而这是运行框架理解、代码却不理解的。
- 操作很少发生，单个工具节省的 token 不足以抵消沙箱的复杂性。

两种做法可以共存：智能体可以有一个用于数据整理的代码执行工具，同时有带审批关卡的狭窄工具，用于发送邮件或发布结果。

## 练习

1. ▢ 你有一个智能体，目前用七个独立的工具做字符串处理：split_string、join_strings、uppercase、lowercase、replace_substring、reverse_string 和 trim_whitespace。你能用一个代码执行工具取代这七个吗？你会得到什么，又会失去什么？

<details markdown="1"><summary>检查</summary>

能。模型会得到：一个工具定义，而不是七个；一次工具调用就能完成复杂的字符串操作，而不是七次往返；以及可以写出易读的代码（“result = text.upper()”），而不必去猜工具名称。你会失去：每项操作各自的显式护栏（每个工具都可能验证输入），以及确定的延迟（代码执行现在的耗时取决于模型写了什么，是可变的）。对于字符串处理，代码执行的做法通常更胜一筹，因为这些操作很简单，而且运行框架无需特定领域的逻辑，就能强制执行文件系统或资源边界。

</details>

2. ▢ 你在为一个医疗系统设计一个可以读取病历并生成诊断建议的智能体。你应该通过让模型自己写数据访问代码的代码执行工具来暴露这个能力，还是通过 read_patient_record、filter_by_condition 和 compute_risk_score 这样的狭窄工具？

<details markdown="1"><summary>提示</summary>

想想在医疗场景里，“安全”意味着什么。运行框架需要强制执行什么？通用的代码沙箱能做到吗，还是需要特定领域的逻辑？

</details>

<details markdown="1"><summary>检查</summary>

这里狭窄的工具更好。医疗系统有严格的合规要求（HIPAA、审计日志、数据访问控制），运行框架大概是通过特定领域的逻辑来强制执行这些要求的，而不是靠文件系统沙箱。一个狭窄的 read_patient_record 工具可以包含授权检查、审计日志和数据脱敏；代码执行工具很难强制执行这些，因为运行框架得检查模型写的代码，而这违背了代码执行的初衷。高风险也让审批关卡更有价值。当操作的安全性取决于特定领域的业务逻辑，而不是文件系统边界时，优先选择狭窄、可审计的工具。

</details>

3. ▢ 关于代码执行，下面哪项陈述是正确的？

    - a) 代码执行总是比使用独立的工具更快，因为它减少了往返，即使是简单的单个操作也一样。
    - b) 代码执行降低了 token 成本，因为一个工具定义取代了许多个，但只有当模型把多个操作串起来时，才能节省延迟。
    - c) 代码执行不再需要沙箱，因为代码是可信的。
    - d) 代码执行不需要审批关卡，因为运行框架可以在代码运行之前检查它。

<details markdown="1"><summary>检查</summary>

**b)** 代码执行降低了 token 成本，因为一个工具定义取代了许多个，但只有当模型把多个操作串起来时，才能节省延迟。token 的节省是真实的（一个定义，而不是许多个）。只有当模型要做多个原本需要多次往返的操作时，延迟的节省才有意义；对于单个操作，耗时差不多，甚至更糟。选项 a 是错的（单个操作得不到好处）。选项 c 是错的（因为代码是任意的，代码执行需要强健的沙箱）。选项 d 是错的（对于高风险操作，审批关卡依然合理，而事先检查也无法防止所有的错误）。

</details>

4. ▢ 解释为什么当工具是“代码执行”而不是像“delete_file”这样的具体工具时，沙箱的工作会变得更难。给出一个这种困难会产生影响的具体场景。

<details markdown="1"><summary>检查</summary>

对于具体的工具，运行框架事先就知道这个工具会做什么，可以在那个具体的点上强制执行边界（delete_file 工具只能触碰安全目录里的文件）。对于代码执行，运行框架在代码运行之前，不知道代码会做什么；代码可能调用系统工具、打开网络套接字，或使用运行框架意想不到的语言特性。一个具体场景：模型写出的代码调用 subprocess.Popen 去运行像“ls /../..”这样的 shell 命令，探测预期边界之外的文件系统。仅靠文件系统权限的沙箱拦不住这一点；沙箱需要 seccomp 规则或容器来阻止任意的系统调用。这就是代码执行的沙箱通常比狭窄工具的沙箱更复杂的原因。

</details>

5. ▢ 你的智能体用代码执行来分析数据。模型写的代码本应读取一个 CSV 文件，却改写成了尝试从互联网下载文件。沙箱强制规定没有网络访问。会发生什么？这是沙箱的失败吗？

<details markdown="1"><summary>检查</summary>

代码运行，尝试发起网络调用，网络操作被拒绝或阻塞。这不是沙箱的失败，而是沙箱按预期在工作。沙箱的工作是阻止代码触及边界之外的资源，而不是保证代码正确，或做了模型想做的事。沙箱的失败，应该是尽管有禁止联网的规则，网络调用却成功了。模型的错误（写了错误的代码）与运行框架的工作（强制执行边界）是两回事。

</details>
