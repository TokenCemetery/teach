# 第 24 课：作为观察的截图

**使命关联:** 要从轨迹出发诊断出问题的、使用计算机的智能体，就需要理解它的观察是视觉的，而不是结构化的，所以落点定位错误与漏掉工具参数看起来完全不同。
**主要来源:** [文档：“Computer use tool”，Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
**前置知识:** [第 23 课](0023-code-execution-as-a-tool.md)、[智能体循环](../GLOSSARY.md)

## 热身

1. ▢ 在前面的课程里，智能体调用工具并收到结果时，这个结果是什么形式？它总是结构化的（JSON 或 schema），总是非结构化的文本，还是两者皆可？

<details markdown="1"><summary>检查</summary>

在本系列涵盖的每一种传输格式里，都是结构化的。工具结果总是标着它所回应的那次调用的 id，并且总是携带工具的输出或一个错误，尽管具体的字段名称和结构因服务商和运行框架而异（见第 3 课）。模型从不需要像对待截图那样，对工具结果进行视觉上的解读。

</details>

2. ▢ 来自第 6 课：智能体循环的四个核心步骤，按顺序是什么？

<details markdown="1"><summary>检查</summary>

调用模型，把响应追加到对话记录，检查是否完成，否则执行工具并追加它们的结果，然后回到起点循环。

</details>

## 要点

### 观察的类型变了

在前面的课程里，调用工具的智能体在每个动作之后的观察，是运行框架构造的结构化结果：一个带有 `tool_id`、`status` 和 `value` 之类字段的 JSON 对象。使用计算机的智能体的观察则截然不同。智能体采取屏幕动作（点击、输入、滚动）之后，观察是一张截图：确确实实是一张 PNG 或 JPEG 格式的图像，内容是屏幕此刻显示的一切。

模型必须在视觉上解读这张图像，才能理解发生了什么，而不是读取一个结构化的数据字段。这是智能体理解世界方式上的一次深刻转变。

第 6 课的循环整体形态保持不变：发送对话记录、得到响应、执行动作、追加结果、重复。但现在“追加结果”意味着把一张图像追加到对话记录里，而“得到响应”意味着模型在生成对这张图像中所见内容的描述，并决定下一步做什么。

### 为什么这很重要：通用性

这样设计的理由是能力。在前面的课程里，调用工具的智能体只能调用开发者专门为它构建的工具。如果你想让智能体与一个没有 API 的应用交互，你就得写一个工具来封装该应用的 API。可如果这个应用根本没有 API 呢？如果它只有图形界面呢？

使用计算机的智能体绕开了这个问题。它不需要为每个应用准备 API 或定制工具，而是像人那样，通过屏幕交互。动作空间是固定而通用的：移动鼠标、点击、输入文本、按键、滚动、截屏。这些同样的动作，在任何操作系统上的任何图形界面应用里都有效，从网页浏览器到桌面应用，再到云控制台。模型学会的是做屏幕上的事，而不是做某个特定应用的事。

这就是收益：一个确确实实能操作任何界面的智能体，哪怕是那些在构建时根本没想过要与智能体集成的界面。

### 循环依然成立

因为循环结构在概念上与观察的类型是分开的，所以基本的周期依然成立：

1. 把对话记录（现在包含当前的截图）发给模型。
2. 模型查看截图，理解屏幕上有什么，并决定下一步做什么。
3. 模型发出一个动作：在坐标 (x, y) 处点击、输入字符串“hello”、向下滚动，或再截一次屏。
4. 运行框架执行这个动作。
5. 如果动作是截屏，运行框架就把新的图像追加到对话记录里。
6. 回到第 1 步循环。

何时停止仍然由模型决定，运行框架仍然强制执行限制并终止循环，对话记录仍然随每一轮增长，第 6 课的停止条件（不再有动作、最大轮次、错误阈值）依然适用。唯一变化的是观察的数据类型：从 JSON 对象变成了图像。

### 视觉观察带来的挑战

这种通用性是有代价的。结构化的工具结果没有歧义：它是运行框架构造的，有固定的 schema，模型可以按名称读取字段。截图是有歧义的：模型必须在当前图像中，凭视觉找到它想要的东西（按钮、文本框、菜单项），解读它的位置，并决定采取什么动作。

在第 25 课里，你会看到这种歧义凝结成一个具体的问题，叫落点定位。现在只需知道这个取舍的存在：使用计算机的智能体能做调用工具的智能体做不到的事，因为它们能操作任何图形界面，但观察需要视觉上的解读，这会带来结构化观察所没有的新的失败模式。

## 练习

1. ▢ 你在构建一个与 Web 应用交互的、使用计算机的智能体。你的同事建议添加一个叫 `click_button` 的工具，以按钮名称作为字符串参数，这样智能体就可以写 `click_button("Submit")`，而不必处理坐标。这是个好主意吗？为什么是或为什么不是？

<details markdown="1"><summary>检查</summary>

不是。使用计算机的智能体的全部意义，在于它无需定制工具就能操作任何图形界面。如果你添加像 `click_button` 这样针对特定任务的工具，就等于在上面叠了一层传统的工具调用接口，这违背了初衷。模型应该学会采取通用的动作（在坐标处点击、输入），并在视觉上解读截图。添加封装工具会增加耦合，降低智能体的通用性。

</details>

2. ▢ 一个使用计算机的智能体截了一张屏，看到一个登录表单，却把用户名输入到了密码框里，而不是用户名框。这是模型的 bug、运行框架的 bug，还是动作空间本身的问题？

<details markdown="1"><summary>提示</summary>

是模型决定输入用户名。运行框架执行了这个动作。问题出在把这个决定与屏幕上正确的位置对接起来的环节。

</details>

<details markdown="1"><summary>检查</summary>

这是视觉解读错误：模型看到了表单，却错认了哪个是哪个字段。动作空间（输入这个字符串）工作正常。运行框架也正确地执行了动作。是模型对截图的理解出了错。这称为落点定位错误，是第 25 课的主题。

</details>

3. ▢ 一个读取文件的、调用工具的智能体，使用叫 `read_file(path)` 的工具，并收到带有 status 字段的结果。一个通过在文本编辑器里打开文件来读取文件的、使用计算机的智能体，在打开编辑器之后截一张屏。运行框架更容易验证哪种观察是成功的？

    - a) 调用工具的智能体，因为 status 字段是明确的
    - b) 使用计算机的智能体，因为截图显示了一切
    - c) 同样容易，只是格式不同
    - d) 都不容易，因为无论哪种，验证成功都需要模型来解读结果

<details markdown="1"><summary>检查</summary>

**a)** 调用工具的智能体有一个明确的 status 字段；运行框架可以毫无歧义地检查 `if result.status == "success"`。使用计算机的智能体的截图显示了文件内容，但运行框架得把这张截图交给模型，请它验证文件是否正确打开，这更慢，也更不可靠。观察的类型影响验证的难易。

</details>

4. ▢ 你在阅读一个试图填写表单的、使用计算机的智能体的轨迹。智能体采取了八个动作：点击字段、输入文本、滚动。最后的截图显示表单的字段是空的。要诊断智能体为什么失败，你应该先检查什么？

<details markdown="1"><summary>检查</summary>

把每个点击动作的坐标，与每次点击之后截的屏幕对照着看。智能体点击的是屏幕上正确的位置，还是点击落在了错误的地方？即使模型决定了“点击用户名字段”，实际点击的坐标也可能偏了。这就是落点定位问题：模型的意图与实际的屏幕位置出现了偏差。

</details>

## 实战练习

- [ ] 在浏览器里打开一个 Web 应用。手动截一张屏。对屏幕上的三个元素（一个按钮、一个文本框、一个链接），估计它们的像素坐标 (x, y)。现在调整浏览器窗口的大小或滚动页面，再截一张新的屏，重新估计同样那几个坐标。写下坐标变化了多少，以及第一张截图里的固定坐标在第二张里是否依然有效。

- [ ] 阅读一条使用计算机的智能体的轨迹（来自公开的示例、工具文档，或你自己的测试）。从运行中间挑一张截图。不看后面的截图或动作，写下智能体接下来可能做的三件事。然后看智能体实际采取的动作。你的预测与它吻合吗？

- [ ] 明天：找一份对使用计算机的智能体失败的描述（在博客文章、GitHub issue 或论文摘要里）。在阅读解释之前，先假设这次失败是因为模型误解了任务、工具调用的语法错误、落点定位错误（坐标有误），还是别的什么。然后阅读解释，检查你的猜测是否正确。
