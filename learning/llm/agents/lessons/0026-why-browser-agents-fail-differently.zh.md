# 第 26 课：为什么浏览器智能体的失败方式不同

**使命关联:** 构建和诊断由屏幕驱动的智能体，需要理解它们的失败模式是结构性的，而不只是提示词写得好不好的问题，这样你才会投入精力去做缓解策略，而不是反复调整提示词。
**主要来源:** [论文：“WebArena: A Realistic Web Environment for Building Autonomous Agents”，Zhou 等，2023](https://arxiv.org/abs/2307.13854)
**前置知识:** [第 25 课](0025-grounding-an-action-to-a-coordinate.md)

## 热身

1. ▢ 来自第 24 课：为什么使用计算机的智能体需要处理像素和截图，而不是具名的工具调用？

<details markdown="1"><summary>检查</summary>

因为它需要操作任何图形界面应用，包括那些在构建时从未考虑过 API 或智能体集成的应用。使用计算机的智能体像人一样通过屏幕交互，所以它在哪里都能用。

</details>

2. ▢ 来自第 25 课：说出像素坐标比工具调用参数更脆弱的一个原因。

<details markdown="1"><summary>检查</summary>

当布局变化（窗口大小改变、页面滚动、缩放级别）时，坐标就会失效，而像用户 ID 或记录名称这样的参数则依然有效。当坐标落在错误的东西上时，它还会悄无声息地失效，而工具调用则会得到明确的错误。

</details>

## 要点

### 由屏幕驱动的智能体特有的失败模式

调用工具的智能体失败，是因为调用了错误的工具、传了不正确的参数，或者轮次用完了。由屏幕驱动的智能体（基于浏览器的或使用计算机的）会以所有这些方式失败，同时还会以调用工具的智能体根本不可能出现的方式失败。

**落点定位错误**（第 25 课）：模型的意图是对的，但坐标是错的，使点击落在了错误的元素或空白处。调用工具的智能体没有这个问题，因为它按名称引用事物。

**环境障碍**：弹窗、Cookie 横幅、加载中的转圈图标、模态对话框或错误信息，都可能挡住智能体的下一个动作。调用工具的智能体也许永远不会遇到这些，因为 API 调用只会干脆地成功或失败。由屏幕驱动的智能体必须先绕过障碍，才能继续真正的任务。

**验证的复杂性**：工具调用完成时，运行框架会拿回带有 status 字段的结构化结果。运行框架立刻就知道它是否成功。使用计算机的智能体点击按钮时，除了屏幕发生变化，不会立刻发生任何事。运行框架得截一张新的屏，发给模型，由模型推理这次按钮点击有没有生效。这个解读的步骤比结构化的状态码更慢，也更不可靠。

**布局差异**：同一个 Web 应用，会因屏幕尺寸、浏览器、缩放级别、CSS 框架和服务器状态的不同而渲染得不同。一个在正常缩放的桌面上训练或测试过的智能体，换到手机上，或把缩放设为 150%，就可能失败。布局变化会打乱坐标，需要重新做落点定位。

这些失败并不是因为模型不好，或提示词不够。它们是通过像素而不是 API 来观察和行动所带来的结构性后果。

### WebArena 为什么重要

多年来，使用计算机的智能体都是靠轶事来评估的：厂商展示一段智能体做出令人印象深刻之事的视频，却没有系统的办法来衡量智能体是否真的在变好，也无从知道最大的可靠性问题在哪里。不同的厂商使用不同的环境，所以结果无法比较。这使得很难把真正的进步与营销区分开来。

WebArena 论文（Zhou 等，2023）创建了一个标准化的、自托管的基准测试环境：在私有服务器上搭建的一组逼真的网站和 Web 应用，附有任务说明和正确性检查。智能体的工作是完成诸如订机票、发布评论或配置某项设置这样的任务。只有当智能体的动作产生了正确的、可验证的结果（机票订好了、评论发布了）时，任务才算成功。

WebArena 使三件事成为可能：

第一，它暴露了真实的可靠性差距。在营销视频里令人印象深刻的、由屏幕驱动的智能体，在逼真的多步骤 Web 任务上，成功率只有 10% 到 20%。这是一记警钟：这项技术远不如轶事所暗示的那么可靠。

第二，它让研究人员能够衡量哪些失败模式占主导。通过运行大量智能体轨迹并对失败分类，研究人员发现，落点定位错误、环境障碍和布局偏移占了失败中很大的一部分，而不是逻辑错误或推理不足。这把精力引向了真正有帮助的缓解办法。

第三，它提供了共同的标准。不同的团队可以在同一个基准上运行自己的智能体，并比较结果。进步变得可以衡量，而不是靠宣称。

### 缓解办法与取舍

有几种策略可以减少由屏幕驱动的智能体的失败，每一种都有代价：

**感知结构的工具**（第 25 课提到过）：工具不只返回原始截图，还返回关于页面元素（按钮、表单字段，以及它们的名称和位置）的结构化信息。模型按名称而不是坐标来引用元素。运行框架在动作发生时把名称转换为坐标。这恢复了可靠性，因为如果布局改变，运行框架可以重新计算坐标，而无需让模型重新估计。

取舍：你失去了“适用于任何图形界面”的通用性。感知结构的工具适用于带有语义化 HTML 的网页，却不适用于桌面应用、PDF、游戏，或这个工具没有针对的界面。

**显式的元素交互**：模型不发出像素坐标，而是发出类似“点击 id 为 submit_button 的元素”或“填写标有 email 的字段”这样的引用。运行框架使用浏览器 API（JavaScript、无障碍树或 DOM 检查）找到元素并与之交互。

取舍：运行框架又变得针对具体应用了。你得为你关心的平台（Web、桌面、移动端）构建工具。

**障碍检测与恢复**：智能体定期检查是否有弹窗或横幅挡住了界面，并在继续之前采取步骤关闭或忽略它。

取舍：增加了复杂性和延迟；要求智能体认出没有被明确告知过的障碍。

**多步验证**：每个动作之后，智能体截一张屏，并增加一个额外的推理轮次（不计入主任务的轮次），在继续之前验证动作是否按预期成功。

取舍：增加了 token 用量和延迟。

关键的洞察是，没有任何一种缓解办法能修复所有的失败。每一种只解决一两种失败模式，却会引入新的复杂性，或失去通用性。生产系统往往会组合使用几种。

### 这如何影响诊断

当由屏幕驱动的智能体失败时，了解这些失败模式，会影响你如何诊断：

- 如果轨迹里是一连串说得通、却落在错误位置的点击，就怀疑是落点定位错误和布局差异。
- 如果轨迹里智能体采取了一个本应奏效的动作，而下一张截图却没有任何变化，就检查是否有障碍（弹窗、加载转圈），或者验证动作是否真的执行了。
- 如果智能体在某台机器或缩放级别上能工作，换到不同配置上的另一个相同任务却失败了，就怀疑是特定环境下的渲染问题。
- 如果智能体有 80% 的时候能成功完成同一个任务，却有时在相同条件下失败，就怀疑是时序造成的不稳定（某个动态元素还没加载出来），或者是你还没见过的某种布局变体。

这是一种诊断上的纪律：了解可能的失败模式，能让你不再盲目地添加提示词，而是指引你找到真正的问题。

## 练习

1. ▢ 一个智能体在你的桌面上，以正常缩放级别成功完成了一个任务。当你在完全相同的网站上，把浏览器缩放设为 125% 来运行同一个智能体时，它在第一次点击就失败了。最可能的失败模式是什么？

<details markdown="1"><summary>检查</summary>

落点定位错误加上布局差异。在正常缩放下，坐标是正确的。在 125% 缩放下，同一个元素渲染在不同的坐标。智能体根据新缩放级别下的视觉外观估计了坐标，但很可能估错了，或者它沿用了旧缩放级别下缓存的截图里的坐标。修复的办法不是更好的推理；而是使用能重新计算坐标的、感知结构的工具，或者确保智能体在当前缩放级别下截一张新的屏。

</details>

2. ▢ 一个智能体的轨迹显示，它在第三轮成功点击了一个按钮。在第四轮的截图里，这个按钮不再可见；出现了一个模态对话框。在第四轮，智能体试图在同样的坐标点击同一个按钮，结果点击落在了模态框上。智能体随后抱怨找不到这个按钮。这个失败是落点定位错误吗？

<details markdown="1"><summary>提示</summary>

第四轮的落点定位其实是正确的；这些坐标仍然指向按钮之前所在的位置。问题不出在坐标本身。

</details>

<details markdown="1"><summary>检查</summary>

不是，这是障碍问题，而不是落点定位错误。智能体的推理是合理的：它认为这个按钮应该仍然可以点击。落点定位也是准确的：坐标正确地指向了按钮之前的位置。但环境变了（出现了一个模态框），而智能体没有检测或处理这个障碍。修复的办法是障碍检测与恢复，而不是更好的坐标估计。

</details>

3. ▢ 你在决定为你的智能体使用感知结构的浏览器工具（返回元素名称和位置），还是原始截图工具。你的应用是一个定制的 JavaScript 仪表盘，元素是动态渲染的，没有语义化的 HTML 结构，而且元素在交互过程中会移动。工具文档说，感知结构的工具在“语义化的标准 Web 应用”上效果最好。你应该选哪个？

    - a) 感知结构的工具，因为它更新、更精密
    - b) 原始截图工具，因为你的应用不是语义化的 HTML
    - c) 仍然用感知结构的工具，并用自定义的 JavaScript 来补充它
    - d) 对由屏幕驱动的智能体来说，两者等价

<details markdown="1"><summary>检查</summary>

**b)** 对于非标准的、动态的、定制的应用，原始截图工具是更好的选择。感知结构的工具依赖语义化的 HTML 和稳定的 ID，而你的仪表盘可能都没有。原始截图让模型能够在视觉上解读这个动态的界面。代价是落点定位的脆弱性，但在不受支持的界面上硬用感知结构的工具，多半也会失败。**a)** 是错的，因为更新并不意味着对你的用例更好。**c)** 增加了复杂性；如果工具对你的界面支持得不好，自定义的补充可能也帮不上忙。**d)** 是错的，因为这些工具对不同种类的应用有不同的失败模式。

</details>

4. ▢ 你让一个智能体跑 WebArena 的基准测试，它在 15% 的任务上成功。你用更清晰的指令和推理提示改进了系统提示词。重新测试后，它在 16% 的任务上成功。这个微小的改进，说明了其余失败的可能原因是什么？

<details markdown="1"><summary>检查</summary>

这说明大多数失败并不是由推理或指令的清晰度造成的。提示词上的改进只带来了微乎其微的收益。这些失败很可能是结构性的：落点定位错误、布局差异、障碍、验证问题，或其他单靠更好的指令无法修复的因素。要进一步改进，你需要（通过阅读轨迹）查明究竟是哪些失败模式占主导，然后采用有针对性的缓解办法，比如感知结构的工具、障碍检测，或更好的坐标估计。

</details>
