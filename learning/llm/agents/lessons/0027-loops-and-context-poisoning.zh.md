# 第 27 课：循环与上下文污染

**使命关联:** 要从轨迹出发诊断出问题的智能体，就需要认出智能体是卡在重复同一个动作上，还是在悄悄地基于一个错误的说法继续推进，这样你才能修复根本原因，而不是添加更多指令。
**主要来源:** [文章：“Effective Context Engineering for AI Agents”，Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
**前置知识:** [第 26 课](0026-why-browser-agents-fail-differently.md)、[轨迹](../GLOSSARY.md)

## 热身

1. ▢ 来自第 26 课：为什么在推理能力相同的情况下，由屏幕驱动的智能体比调用工具的智能体更容易失败？

<details markdown="1"><summary>检查</summary>

由屏幕驱动的智能体通过像素来观察，通过坐标来行动，而坐标是脆弱的引用，会随着布局变化、加载状态和障碍而失效。这些失败模式是结构性的，即使有更好的提示词也依然存在。

</details>

2. ▢ 来自第 7 课：如果运行框架把工具结果追加到了它内部的日志里，却从未追加到对话记录里，模型对这个结果知道些什么？

<details markdown="1"><summary>检查</summary>

什么都不知道。模型只看得到对话记录。光有日志是不够的；结果必须追加到对话记录里，模型在下一轮才知道它发生过。

</details>

## 要点

### 重复的循环：智能体卡住的时候

重复的循环，指的是智能体一轮接一轮地用相同或几乎相同的参数调用同一个工具，而任务毫无进展。它在轨迹里既响亮又显眼。

根本原因通常是这两者之一：

第一，智能体没有注意到某个结果与它的计划相矛盾，或没能支持它的计划。模型发出一个命令，期望得到某种结果，收到的却是不同的或空的结果，但它没有更新自己内部对世界的模型。下一轮，它又试了同样的事情，希望得到不同的结果。

例子：一个智能体想在某个目录里创建一个 `config.json` 文件。工具调用失败，提示“permission denied”。运行框架追加了这个错误。但下一轮，模型用同样的路径调用了同一个工具，仿佛这个错误从未发生。模型的推理大致是“我来试着创建这个文件”，当这返回了错误时，它没有转向“我应该试试另一个路径，或者请求权限”。这是被重复所暴露出来的推理失败。

第二，运行框架的停止条件太松。循环不断运行，是因为没有任何条件触发而停下它。有了严格的错误计数保护（第 6 课），循环在几次失败的尝试之后就会退出，并把失败暴露出来供诊断。保护太松，循环就会继续，把同一个失败的动作重复十次或二十次，才终于停止。

如何在轨迹里发现重复的循环：

1. 扫描有相同工具名称的连续轮次。
2. 比较参数：它们是相同的还是几乎相同？
3. 检查结果：它们是相同的、没有变化的，还是全部失败？
4. 查找重复的推理文本：模型在多个轮次里是否使用了同样的措辞和推理？

如果前三项检查都成立，智能体就陷入了重复的循环。重复的推理文本（第 4 项）可以进一步确认，但不是必要条件。

### 上下文污染：错误的说法成为既定事实的时候

上下文污染是另一回事。重复的循环既响亮又显眼，与之不同，污染是悄无声息的：模型一次说出了某个错误的或凭空想象的内容，然后之后的每一轮都把它当作既定事实。

它是这样发生的：

在第五轮，模型说：“我检查了数据库，发现客户 ID 是 12345。”但并没有任何工具调用取回这个事实。之前任何工具结果里都没有真的说过这个客户 ID。是模型编造的，或者记错了，或者根据某种模式猜的。

这条陈述和其他内容一样，被追加到对话记录里。它看起来就像既定事实：就在对话历史里，被当作事实陈述着。

在第六轮，模型以它为基础继续推进：“现在我来查一下客户 12345 的账户。”它用这个 ID 调用工具。工具可能会失败（“customer 12345 does not exist”），或者更糟，可能成功，并对错误的客户采取了行动。

在第七轮，模型投入得更深了：“我看到客户 12345 的账户显示余额为……”，连锁反应就继续下去。

到第十五轮，你阅读这条轨迹，会看到一条庞大的推理和决策链，全都锚定在“客户 ID 是 12345”这个错误的说法上。模型并不愚蠢。模型是前后一致的：对话记录说客户 ID 是 12345，所以模型据此推理。但对话记录已经被污染了。

为什么这不同于幻觉出来的工具参数（第 28 课）：当模型编造出像文件路径这样的函数参数时，工具通常会以明确的错误失败（“file not found”）。污染更糟，因为它往往不会被立刻发现。自然语言里的一个错误说法，可以不受质疑地待在对话记录里，而模型会在它之上继续推进。

如何在轨迹里发现污染：

1. 找一个模型以高度自信、毫无保留的口吻陈述具体事实（数字、名称、日期、ID）的轮次。
2. 向回追溯：之前有没有任何工具调用或工具结果真的支持这个说法？还是模型凭空说出来的？
3. 如果没有依据，就向前追踪：之后的轮次依赖这个说法吗？之后的工具调用是否把这个值用作参数？
4. 如果两点都是，上下文就被污染了。

本课正在培养的诊断纪律是：循环靠观察什么在重复来诊断；污染则靠把错误的说法向回追溯到它的源头、向前追踪到它的后果来诊断。

### 为什么上下文腐化会加剧污染

上下文腐化（第 11 课）是更宽泛的问题：随着对话记录增长，旧的轮次变得不那么相关，模型的注意力发生转移，准确率下降。上下文腐化会发生在每一次长时间的智能体运行中，即使是健康的运行也一样。

污染则更严重。对话记录里的一个错误说法，就能锚定所有下游的推理，而如果这个说法被埋在几十个轮次之中，就很难发现。模型很难拒绝一个已经在它自己的对话记录里的说法；相反，它会把它当作既定事实。

缓解办法既有诊断性的，也有预防性的：

- 仔细阅读轨迹，留意模型用自然语言做出的、没有依据的说法。
- 设计工具时，让它们回显被解析出的内容：不要只返回“success”，而是返回“successfully updated customer ID 67890”，这样模型就能确认实际的值。
- 使用严格的停止条件和错误计数，让循环快速退出，防止建立在早期污染之上的错误决策层层连锁。

## 练习

1. ▢ 你阅读一条智能体轨迹，看到同一个工具调用 `get_user_by_email(email="bob@example.com")` 在第 3、5、7 和 9 轮重复出现。每次结果都是“user not found”。第 10 轮，模型调用了 `send_email(recipient="bob@example.com")`。这是重复的循环吗？

<details markdown="1"><summary>检查</summary>

不，这不是重复的循环。智能体反复调用同一个查找工具并得到同样的失败，但随后它转向，调用了另一个工具（send_email）。查找失败之后，智能体确实调整了它的策略。重复的循环应该是模型在第 10、11、12 轮继续调用 get_user_by_email。这更像是上下文污染：智能体可能在第 2 轮做了一个从未被证实的错误假设（比如“我有这个用户的邮箱”），现在正据此行动。阅读完整的轨迹上下文，查明第 2 轮或更早的轮次里，是否对 Bob 的邮箱做了没有依据的说法。

</details>

2. ▢ 一个智能体在写文件。第三轮，它调用 write_file(path="output.txt", content="...")，得到错误“permission denied”。第四轮，模型说“我来试试另一种办法”，并调用 create_directory(path="/tmp/")，成功了。然后第五轮，它调用 write_file(path="/tmp/myfile.txt", content="...")。这是重复的循环吗？

<details markdown="1"><summary>提示</summary>

看看模型是否用相同的参数调用了同一个工具，以及它的推理在轮次之间是否有变化。

</details>

<details markdown="1"><summary>检查</summary>

不，这不是重复的循环。尽管智能体遇到了错误，它还是做了调整：它改变了推理（“试试另一种办法”），调用了不同的工具，并在写入尝试中改变了文件路径。模型的策略在演变。重复的循环会是同样的 write_file 调用，带着“output.txt”原封不动地重复。这个智能体展现了合理的解决问题的路径，即使最终的目标（写入原来的位置）被放弃了。

</details>

3. ▢ 你在阅读一条轨迹，第 12 轮，模型陈述“这个服务的 API 密钥是 sk-1234567890”。你向回查找第 1 到 11 轮，没有发现任何返回了这个密钥的工具调用。你向前查找第 13 到 20 轮，发现第 15、17 和 19 轮都在 API 调用里使用了这个密钥。发生了什么？

    - a) 模型推理正确，从上下文中推断出了密钥
    - b) 上下文被污染了：一个没有依据的说法，现在成了多个下游工具调用的依据
    - c) 模型陷入了重复的循环，反复调用同一个 API 工具
    - d) 运行框架没有追加包含密钥的工具结果

<details markdown="1"><summary>检查</summary>

**b)** 上下文被污染了。模型陈述了一个事实（API 密钥），之前没有任何工具调用支持它，之后的多个轮次都依赖这个说法。这是污染的教科书式定义：一个没有依据的说法，成了下游推理的基础。仅凭轨迹，你无法判断是运行框架没有追加结果 (d)，还是模型产生了幻觉；无论哪种，对话记录现在都被污染了。**a)** 是错的，因为推断不等于对既定事实的验证。**c)** 是错的；这不是重复的循环，因为工具调用并不相同，模型也没有重复同一个动作。

</details>

4. ▢ 一位同事给你看一条失败的智能体轨迹。前三轮成功了。第四轮，模型卡在一个循环里，反复调用 list_files(directory="/data")，没有任何变化。模型的推理文本写着“我需要找到目标文件”。最可能的根本原因是什么：模型推理中的逻辑错误，还是本应允许更多轮次的严格停止条件？

<details markdown="1"><summary>检查</summary>

这是模型推理中的逻辑错误，而不是停止条件的问题。停止条件不够严格（循环在重复），但修复的办法不是把它放得更松。问题在于模型在没有改变参数或推理的情况下，反复调用了同一个工具。放松停止条件，只会让它重复得更多。修复的办法是诊断模型为什么没有理解第一次调用 list_files 的结果，或者为什么不知道如何继续。停止条件应该收紧，在一两次失败的重复之后就退出，把问题暴露出来供人诊断，而不是任由它无休止地重复。

</details>

## 实战练习

- [ ] 在网上找一条智能体轨迹（来自文档、GitHub 仓库或博客文章）。阅读它并找出：它是否出现了重复的循环？是否出现了上下文污染？写一段话，描述你发现了什么，以及是怎么发现的。

- [ ] 让一个智能体去做一个你预计会失败的任务。有意检查轨迹，找出模型用自然语言做出的、没有依据的说法（没有之前的工具结果支持的说法）。对于每一条，记下如果智能体基于这个错误的说法继续推进，会发生什么。

- [ ] 明天：设计一个有助于防止上下文污染的工具。它可以回显被解析出的值、加上校验和、包含时间戳，或者对照一个已知的集合进行验证。写一段话，描述你的工具的设计，并解释它如何让被污染的说法在轨迹里更容易被发现。
