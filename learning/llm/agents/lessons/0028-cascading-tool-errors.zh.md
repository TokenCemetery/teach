# 第 28 课：级联的工具错误与幻觉参数

**使命关联:** 在轨迹里识别出级联的失败和幻觉参数，能让你在智能体失败的真正源头上诊断问题，在连锁反应陷入螺旋之前把它切断，而不是在下游修补症状。
**主要来源:** [文章：“Building Effective Agents”，Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
**前置知识:** [第 27 课](0027-loops-and-context-poisoning.md)

## 热身

1. ▢ 来自第 27 课：重复的循环与上下文污染有什么区别？

<details markdown="1"><summary>检查</summary>

重复的循环是响亮的：智能体用相同的参数反复调用同一个工具，毫无进展。污染则是悄无声息的：模型一次说出了某个错误的或幻觉出来的事实，之后的每一轮都悄悄把它当作既定事实。

</details>

2. ▢ 来自第 4 课：工具的 JSON schema 验证什么？

<details markdown="1"><summary>检查</summary>

schema 验证参数的结构和类型：必填字段是否存在，值是否符合声明的类型（字符串、数字、布尔值），列表的元素类型是否正确，以及枚举或 minLength 这样的约束是否满足。它不验证这个值是否真实，或者是否指向某个真实存在的东西。

</details>

## 要点

### 级联的失败：一个错误引出另一个

级联的失败，是指一次工具错误导致一个不正确的后续决策，这个决策又导致另一个错误，从而越来越偏离任务。每一次失败都在加剧混乱，而不是解决它。

下面是一个逐步展开的例子：

第 2 轮：智能体调用 search_files(directory="/config") 去找一个配置文件。这个目录不存在。工具返回错误：“directory not found”。

运行框架把这个错误追加到对话记录里。到这里为止，一切正常。

第 3 轮：模型读到错误，决定：“标准的主目录不存在。我一定是在不同的环境里。让我试试 /etc/config。”这是基于不完整信息的合理推理。模型调用 search_files(directory="/etc/config")。

第 4 轮：搜索成功了，却返回了与智能体要找的东西不匹配的结果。模型已经在第 3 轮选定了 /etc/config 这条路径，于是决定：“这些结果差不多够用了。我就用第一个。”模型现在拿到了错误的文件。

第 5 轮：智能体读取了错误的文件。内容与它的预期不符。模型没有认出这种不匹配，而是决定：“文件格式一定改变了。我用更宽松的方式来解析它。”智能体继续前进，仍然建立在错误的基础之上。

第 6 轮到第 N 轮：每个决定都在加剧最初的错误。智能体现在是从一个错误的基础出发进行推理，不大幅回退就无法恢复。

级联的失败之所以发生：当工具返回错误时，模型得对原因做出一个假设。是目录缺失了吗？是权限错误吗？是路径语法不对吗？模型做出一个猜测，然后继续。如果猜错了，下一个工具调用就建立在这个错误的假设之上。接下来，链条就一路向下滑落。

第 6 课的错误计数保护，最终会停止这个循环，但它是在连锁反应已经扩大之后才停下的，而不是在源头。

### 幻觉参数：类型正确，内容却不真实

幻觉参数，是指模型为工具参数编造了一个看似合理、事实上却错误的值。这个值的格式是正确的，能通过 schema 验证，却与任何真实存在的东西都对不上。

这不同于缺少必填字段的错误（第 3 至 5 课）。缺少字段会产生一个明确的 schema 验证错误，模型能看到并做出反应。幻觉参数则悄无声息地通过了验证。

例子：

- 模型应该按用户名查找用户。它调用 get_user(username="alice_smith")，但实际的用户名是“asmith”。schema 接受这个字符串；调用在下游失败，因为这个用户名不存在。
- 模型需要调用一个 API 端点，却编造了路径：call_api(endpoint="/api/v2/users/search")。这个端点并不存在，但看起来很合理。schema 把它当作字符串验证通过；HTTP 调用以 404 失败。
- 模型被要求按名称调用某个函数，却编造了一个名称：call_function(name="validate_order")。这个函数并不存在，但字符串的格式是正确的。调用只在运行时才以“function not found”失败。

为什么这比 schema 验证错误更糟：当 schema 拒绝某样东西（缺少字段、类型错误）时，模型会得到即时的反馈并能修复它。当参数类型正确却不真实时，错误发生在下游，而且往往是晦涩的形式（“user not found”“404 not found”“function not found”）。模型不会立刻明白，问题出在它编造的那个值上；它反而可能怪罪服务（“用户数据库坏了”）或环境（“API 没在运行”），并基于这个误诊做出错误的决定。

如果上一节的级联失败是从一个幻觉参数开始的，连锁反应就更糟了：模型在一个它自己编造、却不知道是自己编造的值之上，构建了一条推理链。

### 缓解办法：验证与回显

核心的缓解办法，是让幻觉参数更快、更清楚地失败，并让模型能看到实际发生了什么。

**按已知集合验证**：如果某个工具接受的参数应该指向某个真实存在的东西（用户名、函数名、端点），工具就应该验证它是否存在。工具不是悄无声息地在下游失败，而是返回一个明确的错误：“user alice_smith not found; valid users are: alice_s, alice_brown, alicia_m”。这样模型就得到了即时的反馈，以及可供选择的一组选项。

**回显被解析出的值**：工具调用成功之后，不要只返回“success”。返回实际操作的对象。例如：

不要这样：

```text
Tool result: Success
```

而是返回：

```text
Tool result: Successfully updated order 12345. Order status is now CONFIRMED.
```

这样，如果模型的参数是幻觉出来的，却碰巧匹配到了某个意料之外的东西，回显会让这种不匹配显现出来。模型看到“我用订单 ID 12345 调用，工具报告说更新了订单 12345”，就能注意到两者是否吻合。

**要求对高风险操作做显式确认**：如果某个工具调用会修改数据或采取某个动作，就让运行框架在执行之前，要求模型确认实际的值。模型看到“你即将更新用户 username_alice_smith；确认吗？”，就能在那个时刻发现幻觉。

### 轨迹中的级联失败

当你阅读轨迹并发现一次级联时：

1. 找出第一个错误（第 N 轮）：某个工具返回了意料之外的结果或错误。
2. 检查第 N+1 轮：模型对错误为什么发生，做了什么假设？
3. 向前追踪：模型的下一个决定是否源于这个假设？
4. 如果这个假设是错的，连锁反应就已经开始了。

诊断上的教训是：第 N 轮的错误，并不是你应该靠重新写提示词去修复的问题。问题在于模型在第 N+1 轮对这个错误的误诊。要修复的是：让工具把出了什么问题讲得更清楚，或者给模型更好的选项来处理这一类错误，或者收紧停止条件，使连锁反应不再扩大。

## 练习

1. ▢ 一个智能体正在从一个 CSV 文件导入数据。第三轮，它调用 parse_csv(filename="data.csv")。工具返回错误：“file not found”。第四轮，模型说“这个文件一定是压缩过的。我先把它解压”，并调用 decompress(filename="data.csv.gz")。这个工具同样以“file not found”失败。第五轮，模型换了一种对错误的解释：“也许文件在某个子目录里”，并调用 search_for_file(pattern="data*")。这次成功了，找到了“data_backup.csv”。第六轮，它解析了这个备份文件，它的列与预期不同，解析成功了，却产生了一堆垃圾输出。这是级联失败吗？它起源于哪里？

<details markdown="1"><summary>检查</summary>

是的，这是级联失败。它起源于第 3 轮，最初的 parse_csv 失败的时候。模型误诊了这个错误：它假定文件被压缩了或被移走了，而真正的问题很可能只是文件名或路径。每一轮，模型都做了不同的假设，每个假设都导致了不同的动作，没有一个修复了根本问题。到第 6 轮，智能体用的是错误的文件（data_backup.csv 而不是 data.csv），垃圾输出就是后果。修复的办法不是让模型推理得更好；而是让最初的错误信息更清楚。工具应该返回“file data.csv not found in current directory; files found: data_backup.csv, old_data.csv”。有了这些信息，模型本可以在第 4 轮就明确地选择备份文件，而不必经历第 4 和第 5 轮的误诊。

</details>

2. ▢ 一个智能体在更新客户记录。第二轮，模型调用 update_customer(customer_id=987654, status="inactive")。schema 接受这个整数和字符串。工具返回“customer not found”。第三轮，模型感到困惑，调用 list_customers()。它返回所有客户的列表。第四轮，模型从列表里挑出第一个客户，并调用 update_customer(customer_id=100001, status="inactive")。成功了。但智能体本应更新的是客户 987654，而不是 100001。为什么第二轮的幻觉参数，没有产生一个模型可以做出反应的明显错误？

<details markdown="1"><summary>提示</summary>

想想 schema 验证错误，与工具在收到类型正确却无效的值时的运行时行为之间的区别。

</details>

<details markdown="1"><summary>检查</summary>

schema 没有拒绝这个参数，因为 987654 是一个有效的整数。工具接受了它并去查找，只是在运行时以“customer not found”失败。错误信息是清楚的（“customer not found”），但模型误解了它：它没有得出“客户 987654 不存在，我需要找到正确的 ID”的结论，而是得出“我的查询方式有问题，让我换一种办法”。更好的工具设计会返回：“customer 987654 not found; customers exist in the range 100001 to 150000”。这会让不匹配变得明确，并给模型一个具体的范围可以依据，从而防止连锁反应。

</details>

3. ▢ 你在构建一个接受文件路径作为参数的工具。schema 规定路径必须是字符串。你预料到模型偶尔会编造出不存在的路径。下面哪种设计选择，最能防止幻觉参数引发级联失败？

    - a) 接受任何字符串路径，当路径不存在时以一个笼统的“file error”失败
    - b) 对照允许的目录列表验证路径；用清晰的错误拒绝列表之外的路径
    - c) 接受任何路径，即使文件不存在也返回成功信息，让模型以为操作成功了
    - d) 要求模型传两个参数：路径，以及一个确认路径正确的布尔值

<details markdown="1"><summary>检查</summary>

**b)** 对照允许的目录列表验证，并用清晰的错误拒绝无效的路径。这让幻觉出来的路径快速而明确地失败，给模型即时的反馈。模型随后可以从允许的列表里选择。**a)** 仍然会让连锁反应扩大，因为错误是笼统的，无助于模型理解出了什么问题。**c)** 很危险；它掩盖了问题，还会导致连锁反应，因为模型以为自己成功了，其实没有。**d)** 需要额外的运行框架逻辑，又解决不了问题；模型可能把路径和确认都幻觉出来。

</details>

4. ▢ 一个智能体应该从一个 API 获取数据。第二轮，它调用 fetch_api(endpoint="/api/v1/customers/123")。这个端点不存在，工具返回 404 错误。第三轮，模型说“API 服务器一定宕机了”，并调用 check_service_health()。它返回“service is up and responding”。第四轮，模型说“API 一定改了。让我试试去掉版本号”，并调用 fetch_api(endpoint="/api/customers/123")。这次同样以 404 失败。对第一个工具做什么样的设计改动，本可以防止这次连锁反应？

<details markdown="1"><summary>检查</summary>

第一次工具调用本应返回比“404 not found”更多的信息。它可以返回：“endpoint /api/v1/customers/123 not found (404); valid endpoints include: /api/v2/customers/{id}, /api/v2/orders/{id}”。有了这些信息，模型会立刻明白出问题的是版本号，而不是服务，于是可以在第 3 轮就调整端点，而不必经历第 3 和第 4 轮的连锁反应。连锁反应的发生，是因为错误信息没有解释实际的问题。

</details>

## 实战练习

- [ ] 找一条显示了失败的智能体轨迹。阅读它并找出：是否存在一条级联的决策链，其中每个决定都在加剧混乱？如果有，连锁反应起源于第几轮？一条更清楚的错误信息本可以起到什么作用？

- [ ] 设计一个工具（挑任何你用过或设计过的工具）。写出这个工具目前针对某个常见失败情形所返回的错误信息。现在把它改写成包含：哪里出了错、预期是什么、有效的替代选项是什么。这条更清楚的错误信息会如何改变模型诊断问题的能力？

- [ ] 明天：构建一个小型的测试运行框架，用一个幻觉参数（工具不认识的值）调用某个工具。观察工具返回的错误信息。然后修改这个工具，让它按已知集合验证并返回更清楚的错误。再用同一个幻觉参数运行一次，比较两条错误信息。写一段话，描述更清楚的错误会如何改变智能体对这次失败的诊断。
