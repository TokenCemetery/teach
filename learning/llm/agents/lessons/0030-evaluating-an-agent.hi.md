# पाठ 30. Agent का Evaluation

**मिशन से संबंध:** असफल agent को उसकी trajectory से जाँचें, कारण का नाम बताते हुए (loop, poisoned context, ग़लत specified tool, ग़लत stopping condition), बेतरतीब ढंग से दोबारा prompt करने के बजाय।
**मुख्य स्रोत:** [पेपर: "tau-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains", Yao et al., 2024](https://arxiv.org/abs/2406.12045)
**पूर्व-आवश्यकताएँ:** [पाठ 29](0029-tracing-and-trajectory-replay.md), [Trajectory](../GLOSSARY.md)

## वार्म-अप

1. ▢ पाठ 29 से: जब आप विफलता का निदान करने के लिए agent की trajectory पढ़ते हैं, तो आपको सबसे पहले कौन-सी दो चीज़ें देखनी चाहिए: model का लिया फ़ैसला, या उस फ़ैसले का असली नतीजा?

<details markdown="1"><summary>जाँचें</summary>

दोनों, पर इस क्रम में: पहले, model ने हर चरण पर क्या फ़ैसला लिया (कौन-सा tool चुना, कौन-से arguments दिए)। दूसरे, tool ने असल में क्या लौटाया। समझदार फ़ैसला पर ग़लत नतीजा tool की implementation की समस्या की ओर इशारा करता है। नासमझ फ़ैसला पर समझदार नतीजा reasoning की विफलता की ओर इशारा करता है। इन्हें गड़बड़ा देना ही वह जगह है जहाँ निदान अटकता है।

</details>

2. ▢ पाठ 29 से: अगर trajectory में model लगातार पाँच बार सही फ़ैसला लेता दिखे पर agent task पूरा करने में नाकाम रहे, तो वह pattern क्या टूटा होने का सुझाव देता है?

<details markdown="1"><summary>जाँचें</summary>

यह सुझाता है कि harness या tool implementations ख़ुद टूटी हैं, model की reasoning नहीं। Model सही चुन रहा है, पर loop में कुछ और इरादे के मुताबिक़ नहीं चल रहा। यह ऐसा tool हो सकता है जो सफलता का दावा करता है पर असल में action नहीं करता, ऐसा harness जो loop को बहुत जल्दी काट देता है, या transcript में ग़लत तरह जोड़ा गया नतीजा।

</details>

## यह जानें

### Outcome बनाम Trajectory

जब आप agent का मूल्यांकन करते हैं, तो आप दो अलग चीज़ें माप सकते हैं, और वे एक नहीं हैं।

**Outcome की सफलता** का मतलब: क्या agent सही अंतिम state तक पहुँचा? File सही अपडेट हुई। Ticket सही श्रेणी में triage हुआ। उपयोगकर्ता के सवाल का सटीक जवाब दिया गया। आप outcome जाँचते हैं उस नतीजे को देखकर जो उपयोगकर्ता देखता है।

**Trajectory की सहीपन** का मतलब: क्या agent ने वहाँ पहुँचने के लिए सही क्रम के चरण लिए? उसने सही tools सही क्रम में समझदार arguments के साथ call किए, नतीजों की सटीक व्याख्या की, और गोल-गोल घूमते loops से बचा।

Agent task में अक्सर एक ही सही outcome तक पहुँचने के कई वैध रास्ते होते हैं। किसी एक संदर्भ trajectory के विरुद्ध ग्रेड करना आमतौर पर ग़लत है; outcome को ग्रेड करना (क्या file सचमुच अपडेट हुई, क्या ticket सचमुच सही triage हुआ) आमतौर पर सही है। फिर भी trajectory मायने रखती है: उसी से आप निदान करते हैं कि कुछ *क्यों* फेल हुआ, जो इस track के पाठ 27 से 29 सिखाते हैं। Outcome बताता है कि agent सफल हुआ या नहीं; trajectory बताती है कि वह क्यों फेल हुआ।

### pass^k: बार-बार के trials में विश्वसनीयता

एक सफल run आपको नहीं बताता कि agent भरोसेमंद है। वही agent उसी task पर दूसरे प्रयास में फेल हो सकता है, क्योंकि agent के कई निर्णय बिंदुओं की यादृच्छिक प्रकृति लंबी trajectory में जुड़ती जाती है। pass^k उस संभावना को मापता है कि agent उसी task के k स्वतंत्र trials में से सभी में सफल होता है। अगर agent किसी task पर 10 में से 8 बार पास होता है, तो आप एक बार पास होने से ज़्यादा जानते हैं: आपके पास प्रमाण है कि वह उस task पर लगभग 80 प्रतिशत भरोसेमंद है। इसे task की accuracy से न मिलाएँ; यह एक बार के पास या फेल run से कहीं मज़बूत और ईमानदार विश्वसनीयता का पैमाना है। अपने evaluations में pass^k को डिज़ाइन और गणना करने के पूरे ब्योरे के लिए, इसके बाद वाला पाठ देखें।

### Benchmark पेपर असल में क्या मापते हैं

तीन पेपर इस चरण के स्रोतों का आधार हैं, और हर एक agents को ग्रेड करने के तरीक़े में अलग चुनाव दिखाता है:

**tau-bench** (Yao et al., 2024) simulated user (इंसान की भूमिका निभाता language model) और domain policy (सफलता क्या है इसके नियम) के विरुद्ध multi-turn tool use का मूल्यांकन करता है। वह बार-बार के trials की विश्वसनीयता के माप इस्तेमाल करता है, इसलिए आप pass^k scores देखते हैं, एक-बार के नतीजे नहीं।

**SWE-bench** (Jimenez et al., 2023) असली repository issues पर agents को परखता है, जिसमें project का अपना test suite outcome की जाँच है। अगर tests पास होते हैं, तो agent ने issue सुलझाया। Trajectory पर कोई बंदिश या ग्रेडिंग नहीं है; सिर्फ़ outcome मायने रखता है।

**GAIA** (Mialon et al., 2023) ऐसे सवाल पूछता है जो इंसान के लिए आसान और agent के लिए कठिन हैं, जिनमें एक असंदिग्ध उत्तर तक पहुँचने के लिए multi-step tool use चाहिए। वह मापता है कि agent सही उत्तर पर पहुँचता है या नहीं, यह नहीं कि उसकी reasoning सुरुचिपूर्ण थी।

तीनों trajectory की सुरुचि से ऊपर outcome की सफलता को प्राथमिकता देते हैं, और तीनों एक-run के संयोग से आगे जाने के लिए बार-बार trials का मूल्यांकन या कई test cases इस्तेमाल करते हैं।

### गहराई को सौंपना

यह पाठ आपको शब्दावली देता है: outcome बनाम trajectory, pass^k, task की सफलता। Agent eval बनाने का पूरा ब्योरा llm/evals track के पाठ 13, Agents और Tool Use का Evaluation में है। वह पाठ metrics, judge के design, held-out test set बनाने, सांख्यिकीय महत्व का मतलब, और ग़लती से ग़लत चीज़ का मूल्यांकन करने से कैसे बचें, यह कवर करता है। इस track का काम सिर्फ़ यह पक्का करना है कि शुरू में ही आप जानें कि क्या मापना है। अवधारणाएँ जानने के लिए यह पाठ पढ़ें; गहराई के लिए llm/evals का पाठ 13 पढ़ें।

## अभ्यास

1. ▢ एक agent पहली कोशिश में आपके issue tracker में ticket सफलतापूर्वक दर्ज करता है। आप उसे अलग ticket पर फिर चलाते हैं, और वह चुपचाप फेल होकर बिना text का ख़ाली ticket बना देता है। आप उसे तीसरी बार चलाते हैं और वह सफल होता है। क्या इस data के आधार पर agent production के लिए तैयार है?

<details markdown="1"><summary>जाँचें</summary>

नहीं। आपके पास एक सफलता, एक विफलता, और एक और सफलता है। यानी 3 trials में से 2 सफलताएँ, जो लगभग 67 प्रतिशत विश्वसनीयता सुझाती हैं। आपके पास अभी पर्याप्त data नहीं है, और ज़्यादातर production उपयोग के लिए 67 प्रतिशत बहुत कम है। भरोसेमंद pass^k स्थापित करने के लिए आपको अलग-अलग tickets पर कम से कम 10 से 20 trials चाहिए। ग़लत सहज बुद्धि यह मान लेना है कि एक विफलता संयोग थी और agent ठीक है; सही यह है कि pass^k को गंभीरता से लें।

</details>

2. ▢ आप ऐसे agent का निदान कर रहे हैं जो database record अपडेट करने में नाकाम रहा। आप trajectory देखते हैं और पाते हैं कि model ने सही record ID और नए मानों के साथ सही update_record tool चुना। Tool ने सफलता लौटाई: "ok, record updated"। पर जब आप database जाँचते हैं, तो record असल में अपडेट नहीं हुआ। इसे ठीक करने के लिए आपको किस स्तर पर देखना चाहिए?

<details markdown="1"><summary>संकेत</summary>

Model का फ़ैसला और trajectory दोनों सही दिखते हैं। समस्या reasoning या फ़ैसला लेने में नहीं है।

</details>

<details markdown="1"><summary>जाँचें</summary>

आपको tool की implementation ख़ुद जाँचनी चाहिए। Trajectory दिखाती है कि model ने सही चुनाव किया और tool ने सफलता का दावा किया, पर outcome ग़लत है। Tool के लौटाए मान और database की असली state के बीच कुछ टूटा है। यह ऐसा tool हो सकता है जो सफलता log करता है पर असल में चलता नहीं, ऐसा harness जो tool के ख़त्म होने का इंतज़ार नहीं करता, या database connection की समस्या। यहाँ trajectory का निदान मतलब है tool के लौटाए शब्दों के पार देखना और जाँचना कि असल में क्या हुआ।

</details>

3. ▢ आप SWE-bench (असली GitHub issues, outcome की जाँच के रूप में project test suites) से agents का मूल्यांकन कर रहे हैं। Agent की trajectory एक ऐसा फ़ैसला दिखाती है जो आपके हिसाब से सबसे अच्छा नहीं है, ज़्यादा सीधे रास्ते की तुलना में अतिरिक्त tool calls लेते हुए। पर issue का test suite पास हो जाता है। क्या आपको कमतर trajectory के लिए agent का score घटाना चाहिए?

    - a) हाँ, क्योंकि trajectory अक्षमता दिखाती है
    - b) नहीं, क्योंकि SWE-bench में सिर्फ़ test suite का पास होना मायने रखता है
    - c) Outcome को पास का score दें पर भविष्य के optimization के लिए trajectory को चिह्नित करें
    - d) तभी जब कमतर रास्ते में baseline से ज़्यादा tokens लगे

<details markdown="1"><summary>जाँचें</summary>

**b)** नहीं, क्योंकि SWE-bench में सिर्फ़ test suite का पास होना मायने रखता है। SWE-bench को outcomes ग्रेड करने के लिए डिज़ाइन किया गया है, trajectories को नहीं। अगर tests पास होते हैं, तो agent ने issue सुलझाया, चाहे उसने सबसे सुरुचिपूर्ण रास्ता लिया हो या नहीं। ग़लत सहज बुद्धि है outcome के ऊपर trajectory की सुरुचि को ग्रेड करना; वह दो अलग मूल्यांकनों को मिला देता है। **a)** आपको ऐसे माप की ओर ले जाएगा जो SWE-bench इस्तेमाल नहीं करता। **c)** ऐसी जटिलता जोड़ता है जो SWE-bench को अपने प्राथमिक लक्ष्य के लिए नहीं चाहिए। **d)** अलग बंदिश (token budget) लाता है जो SWE-bench के design का हिस्सा नहीं है।

</details>

4. ▢ आप किसी task पर agent का मूल्यांकन सिर्फ़ outcome से कर रहे हैं: या तो वह सही अंतिम state तक पहुँचता है, या नहीं। आप उसे 100 बार चलाते हैं, और वह 73 बार सफल होता है। आप system prompt सुधारते हैं और दोबारा परखते हैं। अब वह 100 में से 75 बार सफल होता है। सुधार छोटा है। यह pattern सुझाता है कि आपको आगे क्या करना चाहिए?

<details markdown="1"><summary>जाँचें</summary>

यह सुझाता है कि अकेले prompting के सुधार मूल विफलताओं को सुलझाने के लिए काफ़ी नहीं हैं। 73 से 75 प्रतिशत का फ़ायदा मामूली है; बेहतर instructions के बावजूद ज़्यादातर विफलताएँ बनी रहती हैं। आपको असल failure mode पहचानने के लिए फेल हुए runs की trajectories पढ़नी चाहिए (ग़लत इस्तेमाल हुआ tool, तर्क की ग़लती, context की समस्या, कोई रुकावट जिसे agent नहीं सँभालता) और फिर उसी ख़ास समस्या को ठीक करना चाहिए। या फिर, हो सकता है task मौजूदा model या tool set के लिए बस बहुत कठिन हो, और कोई prompt बदलाव मदद नहीं करेगा। Trajectory का निदान बताता है कि इनमें से कौन-सा सच है।

</details>

## असली दुनिया का अभ्यास

- [ ] कोई सरल, दोहराया जा सकने वाला agent task चुनें (जैसे "directory में किसी व्यक्ति को खोजो", "file format बदलो", "tool से तथ्य वाले सवाल का जवाब दो")। Agent को 10 बार चलाएँ और हर बार पास या फेल दर्ज करें। अनुभवजन्य pass^k निकालें और लिखें कि वह संख्या आपको ऐसा क्या बताती है जो एक run नहीं बताता।

- [ ] Agents पर कोई प्रकाशित benchmark पेपर लें (tau-bench, SWE-bench, GAIA, WebArena, या कोई और)। उसका evaluation खंड पढ़ें और पहचानें: outcome का माप क्या है, trajectory पर बंदिश है या वह खुली है, और वह कौन-सा विश्वसनीयता माप इस्तेमाल करता है।

- [ ] कल: किसी सार्वजनिक स्रोत (दस्तावेज़, blog, GitHub) से agent की trajectory खोजें। ऐसा evaluation rubric दोबारा लिखें जो trajectory को सिर्फ़ outcome से ग्रेड करे (क्या अंतिम state लक्ष्य से मेल खाती थी), और अलग rubric जो trajectory से ग्रेड करे (क्या उसने समझदार चरण लिए)। दोनों rubrics उसी trajectory पर चलाएँ और scores की तुलना करें। एक अनुच्छेद लिखें कि outcome या trajectory ने आपको ज़्यादा बताया कि agent चला या नहीं।
