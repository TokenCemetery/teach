# Урок 32. Наименьшие привилегии и сбитый с толку посредник

**Связь с целью курса:** Проектируйте границы доступа для каждого инструмента агента так, чтобы недоверенное содержимое могло обмануть агента, но не могло заставить его злоупотребить возможностями, которых у него никогда не должно было быть.
**Первоисточник:** [Справочник: "OWASP Top 10 for LLM Applications", OWASP GenAI Security Project](https://genai.owasp.org/llm-top-10/)
**Предварительные требования:** [Урок 31](0031-prompt-injection-and-the-lethal-trifecta.md), [Песочница](../GLOSSARY.md)

</details>

## Что нужно знать

### Наименьшие привилегии: ограничьте каждый инструмент ровно тем, что ему нужно

Наименьшие привилегии (least privilege) это принцип безопасности: у каждого инструмента должен быть доступ только к тому конкретному ресурсу или действию, которое ему действительно нужно, а не широкий доступ «на случай, если пригодится потом». Для агента это значит проектировать границу песочницы каждого инструмента с узким разрешением.

Примеры:

- Инструмент, читающий сегодняшнее расписание, должен читать только из файла календаря, а не из всей файловой системы
- Инструмент, ищущий заказ клиента, должен запрашивать только заказы этого клиента, а не все заказы компании
- Инструмент, отправляющий письмо с квитанцией, должен уметь отправлять только с одного фиксированного адреса, а не из всего почтового ящика
- Инструмент, редактирующий конфигурационный файл, должен редактировать только этот один файл, а не произвольные файлы в каталоге конфигурации

Принцип применим и к учётным данным. Если инструменту нужно аутентифицироваться во внешней службе, он должен использовать учётные данные, ограниченные этой службой и этим действием, а не широкую учётную запись администратора.

Почему это важно для агентов? Потому что широкий доступ это именно то, что делает эксплойт дорогим для организации. Когда агента обманом инъекции заставляют вызвать инструмент, к которому у него есть доступ, последствия зависят от того, до чего этот инструмент реально может дотянуться.

### Схема «сбитый с толку посредник»: законные полномочия, употреблённые во зло

Сбитый с толку посредник (confused deputy) это классическая схема безопасности, названная ещё в 1980-х, которая прямо ложится на агентов. Сбитый с толку посредник это программа с законными широкими полномочиями, которую обманом заставили употребить эти полномочия в интересах атакующего. Программа не скомпрометирована в том смысле, что не запускает вредоносный код; она делает ровно то, что позволяют её законные инструменты, только по указаниям, которые никогда не были указаниями пользователя.

Агент с уязвимостью «сбитый с толку посредник» выглядит так:

1. У агента есть широкий инструмент: send_email может отправлять с любого адреса в почтовом ящике компании
2. Агент читает недоверенное содержимое: приглашение в календаре с внедрённой инструкцией
3. Инструкция просит агента переслать конфиденциальную переписку на внешний адрес
4. Агент вызывает send_email с параметрами атакующего
5. Инструмент исполняет вызов, потому что это законный вызов send_email с допустимыми параметрами. Инструмент не знает, что запрос исходил из инъекции, а не из реального намерения пользователя.

Письмо теперь выведено наружу не потому, что модель «взломали», а потому, что вы дали агенту широкую возможность и не ограничили её узкой задачей.

Исправление не в том, чтобы сильнее промптить модель. Исправление в том, чтобы спроектировать инструмент узко: вместо send_email для всего почтового ящика спроектируйте инструмент send_receipt, который может отправлять только на адреса электронной почты клиентов с фиксированным шаблоном. Теперь инъекция всё ещё может обмануть модель, заставив вызвать send_receipt, но этот вызов ограничен тем, что send_receipt разрешено делать.

### Цепочка поставок MCP: доверие транзитивно

Уроки 20-21 охватывали Model Context Protocol (MCP) и то, как агент подключается к MCP-серверам для доступа к инструментам. С точки зрения безопасности подключение к MCP-серверу означает расширение вашей границы доверия на того, кто этот сервер эксплуатирует.

Вредоносный или скомпрометированный MCP-сервер может:

- Искажать описания инструментов, чтобы вредные вызовы звучали безобидно
- Возвращать вводящие в заблуждение данные в результатах инструментов, о которых агент затем будет рассуждать
- Наблюдать каждый вызов инструмента, который делает агент, и каждый кусок контекста, который он отправляет

Когда ваша обвязка подключается к стороннему MCP-серверу, вы доверяете оператору этого сервера так же, как собственному коду. Если сервер скомпрометирован или управляется противником, он становится ещё одним каналом для инъекции.

Защита та же, что от любого риска цепочки поставок: подключайтесь только к серверам, которым доверяете, и ограничивайте подключение. Например:

- Не давайте агенту доступ ко всем доступным MCP-серверам; подключайте только конкретные серверы, которые ему нужны
- Используйте аутентификацию и шифрование для MCP-соединений
- Проверяйте описания инструментов, которые даёт MCP-сервер, и понимайте, какой доступ вы выдаёте
- Исходите из того, что данные, которые вы отправляете MCP-инструменту, могут стать публичными или быть употреблены во зло

MCP-серверы не уникально рискованны; это просто ещё один инструмент. Принцип тот же: ограничивайте доступ.

### Всё вместе: границы разрешений для каждого инструмента и каждой задачи

Принцип проектирования, связывающий эти уроки, в том, что границу разрешений следует ограничивать осознанно, для каждого инструмента и каждой задачи, а не одним широким набором учётных данных, общим для всего агента.

Когда вы проектируете агента:

1. Перечислите каждый инструмент, который нужен агенту
2. Для каждого инструмента спросите: какой минимальный доступ нужен этому инструменту, чтобы выполнить своё назначение?
3. Создайте для этого инструмента границу песочницы, дающую ровно этот доступ, не больше
4. Если инструменту нужно аутентифицироваться (в базе данных, API, файловой системе), создайте учётные данные, ограниченные этим инструментом и этим уровнем доступа, а не такие, что могут достать до чего угодно

Узко ограниченный инструмент это конкретная вещь, которая превращает «модель обманули инъекцией» из катастрофического взлома в локализованную ошибку с малыми последствиями. Агент читает инъекцию, модель её понимает, модель вызывает внедрённый инструмент, а инструмент отказывается исполнять запрошенное действие, потому что действие вне его области.

## Практика

1. ▢ Вы проектируете инструмент для агента, управляющего учётными записями пользователей. Инструменту нужно обновлять адрес электронной почты пользователя в базе данных компании. В вашем первом черновике он получает такие учётные данные: учётную запись базы данных с разрешением UPDATE на всю таблицу users.

Почему это избыточная область и какой дизайн был бы лучше?

<details markdown="1"><summary>Проверка</summary>

Учётные данные дают разрешение UPDATE на всю таблицу, а значит, инструмент мог бы обновить информацию любого пользователя, а не только конкретный адрес электронной почты конкретного пользователя, которым управляют. Лучший дизайн создал бы в базе данных хранимую процедуру, принимающую только идентификатор пользователя и новый адрес, и дал бы учётным данным инструмента разрешение исполнять только эту процедуру. Так даже если инъекция обманом заставит агента вызвать инструмент с неожиданными параметрами, база данных откажется исполнять что-либо вне области процедуры.

</details>

2. ▢ У агента есть доступ к инструменту send_email, ограниченному отправкой только с `support@company.com` и только на адреса электронной почты по шаблону `*@customer-*.com`. Инъекция пытается заставить его отправить сообщение на `attacker@evil.com`. Что останавливает атаку?

<details markdown="1"><summary>Подсказка</summary>

Область обеспечивает сам инструмент. Подумайте, где происходит эта проверка и почему здесь нет никакой инструкции в промпте.

</details>

<details markdown="1"><summary>Проверка</summary>

Валидация инструмента, которая выполняется в обвязке до отправки сообщения. Инструмент проверяет получателя по разрешённому шаблону и отказывается отправлять, потому что `attacker@evil.com` не соответствует. Инъекция сумела изменить поведение агента (агент намеревался отправить), но не удалась, потому что граница разрешений инструмента не допустила вредного действия. Это контроль на уровне инструмента, а не на уровне промптинга, поэтому он надёжен.

</details>

3. ▢ Ваша организация предоставляет MCP-сервер, открывающий события корпоративного календаря. Вы обнаруживаете, что сторонняя компания построила MCP-клиент, подключающийся к вашему серверу, чтобы помогать управлять встречами. Какое из этих утверждений верно?

    - a) Это безопасно, пока ваш MCP-сервер возвращает только публичные данные календаря
    - b) У стороннего клиента теперь фактически есть доступ на чтение к данным календаря, которые возвращает ваш сервер
    - c) Вам следует использовать шифрование между вашим сервером и клиентом, чтобы гарантировать, что даже операторы вашего сервера не смогут видеть данные
    - d) Сторонняя компания не может злоупотребить данными, потому что это только события календаря, а не учётные данные пользователей

<details markdown="1"><summary>Проверка</summary>

**b)** Сторонний клиент и все, кто им управляет, могут видеть и потенциально злоупотребить всеми данными календаря, которые возвращает сервер. Публичные данные это всё равно данные; даже если события календаря не секретны, у стороннего оператора теперь есть видимость расписания вашей организации, которая может быть использована для корпоративного шпионажа или социальной инженерии. Шифрование (вариант c) защитило бы данные при передаче, но не помешало бы оператору клиента их видеть. Область доступа (публичная или приватная) не меняет последствий для безопасности: вы расширили границу доверия на стороннего оператора. Это риск цепочки поставок MCP.

</details>

4. ▢ Вы проектируете инструмент для агента, обрабатывающего тикеты поддержки клиентов. Инструменту нужно отправлять клиенту ответ по электронной почте. Опишите дизайн с наименьшими привилегиями, который предотвратил бы атаку «сбитый с толку посредник», где инъекция заставляет агента переслать клиенту конфиденциальную внутреннюю переписку.

<details markdown="1"><summary>Проверка</summary>

Вместо общего инструмента send_email спроектируйте инструмент send_support_response, принимающий только два параметра: идентификатор тикета и текст ответа. Инструмент по идентификатору тикета находит адрес электронной почты клиента, проверяет, что текст ответа не превышает разумной длины, и отправляет только ответ (без вложений и без других писем). Учётные данные инструмента имеют разрешение отправлять только с адреса поддержки и только на адреса клиентов, связанные с допустимыми тикетами. Теперь инъекция может обмануть агента, заставив вызвать send_support_response, но вызов ограничен областью инструмента. Агент не может пересылать внутренние письма, не может отправлять на произвольные адреса и не может отправлять ничего, что не является ответом поддержки, потому что инструмент не даёт способа это делать.

</details>

## Практика в реальной работе

- [ ] Возьмите инструмент, который вы проектировали или часто используете. Сопоставьте его текущие разрешения. Запишите одно разрешение, которое у него есть сверх того, что строго нужно для основного назначения, и один способ его убрать.
- [ ] Выберите MCP-сервер, к которому вы были бы готовы подключить агента. Изучите или свяжитесь с оператором и выясните: какие данные видит сервер, как они используются, как защищены, у кого есть доступ к логам? Запишите свой уровень уверенности и остаточный риск.
- [ ] Завтра: спроектируйте инструмент, который осознанно реализует наименьшие привилегии, отказываясь от правдоподобного, но выходящего за область запроса. Напишите спецификацию, называющую запрос, который он получил бы при атаке «сбитый с толку посредник», и объясняющую, почему дизайн инструмента не даёт ей удаться.
