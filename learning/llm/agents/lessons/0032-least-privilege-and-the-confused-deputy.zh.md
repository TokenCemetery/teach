# 第 32 课：最小权限与混淆代理人

**使命关联:** 为智能体的每个工具设计访问边界，使不可信的内容也许能骗过智能体，却无法骗得它去滥用本就不该拥有的能力。
**主要来源:** [参考：“OWASP Top 10 for LLM Applications”，OWASP GenAI Security Project](https://genai.owasp.org/llm-top-10/)
**前置知识:** [第 31 课](0031-prompt-injection-and-the-lethal-trifecta.md)、[沙箱](../GLOSSARY.md)

## 热身

1. ▢ 说出第 31 课里致命三要素的三个条件。

<details markdown="1"><summary>检查</summary>

可访问私有数据、会接触不可信内容、能够向外部通信。去掉任何一个，攻击就会失败。

</details>

2. ▢ 在第 31 课里，你通过打破三要素中的一个条件，设计了一个能避免提示词注入攻击的工具。如果你打破的是外部通信这个条件，在实践中会是什么样子？

<details markdown="1"><summary>检查</summary>

这个工具要么不能向任何地方发送信息，要么只能发往攻击者够不着的渠道。例如，一个只把邮件存在本地、而不发送的 draft_email 工具，或者一个只能写入暂存表、数据在共享之前需要人工审核的工具。

</details>

## 要点

### 最小权限：把每个工具的范围限定在它恰好需要的程度

最小权限是一项安全原则：每个工具只应访问它实际需要的那个具体资源或动作，而不是“以防以后可能有用”而拥有宽泛的访问权限。对智能体来说，这意味着为每个工具的沙箱边界设计狭窄的权限。

例如：

- 读取今天日程的工具，应该只读取日历文件，而不是整个文件系统
- 查询某位客户订单的工具，应该只查询这位客户的订单，而不是公司所有的订单
- 发送收据邮件的工具，应该只能从一个固定的地址发送，而不是整个邮箱
- 编辑配置文件的工具，应该只编辑那一个文件，而不是配置目录里的任意文件

这条原则同样适用于凭据。如果工具需要向外部服务认证，它应该使用限定于该服务和该动作的凭据，而不是宽泛的管理员账号。

为什么这对智能体很重要？因为宽泛的访问权限，恰恰是让一次攻击对组织造成高昂代价的东西。当智能体被注入欺骗，去调用它有权访问的某个工具时，后果取决于这个工具实际上能触及什么。

### 混淆代理人模式：合法的权限，被滥用

混淆代理人是一种经典的安全模式，20 世纪 80 年代首次被命名，它与智能体直接对应。混淆代理人是这样一个程序：它拥有合法而宽泛的权限，却被欺骗，替攻击者滥用了这份权限。这个程序并没有在运行恶意代码的意义上被攻破；它做的恰恰是它合法的工具所允许的事，只不过是依照从来不属于用户的指令。

存在混淆代理人漏洞的智能体，是这样的：

1. 智能体有一个宽泛的工具：send_email 可以从公司邮箱里的任何地址发送
2. 智能体读取了不可信的内容：一份带有注入指令的日历邀请
3. 这条指令要求智能体把一串机密的邮件转发到外部地址
4. 智能体用攻击者的参数调用了 send_email
5. 工具执行了这个调用，因为这是一次带有有效参数的合法 send_email 调用。工具并不知道这个请求源于注入，而不是用户的真实意图。

邮件现在被外泄了，不是因为模型被“黑”了，而是因为你给了智能体一个宽泛的能力，却没有把它限定在一个狭窄的任务上。

修复的办法不是更用力地给模型写提示词。修复的办法是把工具设计得狭窄：不要给整个邮箱用的 send_email，而是设计一个叫 send_receipt 的工具，它只能用固定的模板发往客户的邮箱地址。这样，注入仍然可以骗模型去调用 send_receipt，但这个调用被限制在 send_receipt 所允许做的事情之内。

### MCP 供应链：信任是可传递的

第 20 至 21 课讲了模型上下文协议（MCP），以及智能体如何连接到 MCP 服务器来访问工具。从安全的角度看，连接一个 MCP 服务器，意味着把你的信任边界扩展到包括运营这台服务器的人。

恶意的或被攻破的 MCP 服务器可以：

- 歪曲工具描述，让有害的调用听起来无害
- 在工具结果里返回有误导性的数据，随后智能体会对这些数据进行推理
- 观察智能体发出的每一次工具调用，以及它发送的每一份上下文

当你的运行框架连接到第三方 MCP 服务器时，你对这台服务器的运营者的信任，就如同对你自己的代码一样。如果服务器被攻破，或由对手运营，它就成了注入的又一个渠道。

防御办法与任何供应链风险一样：只连接你信任的服务器，并限定连接的范围。例如：

- 不要让智能体访问所有可用的 MCP 服务器；只连接它所需要的那几个特定的服务器
- 对 MCP 连接使用认证和加密
- 审查 MCP 服务器提供的工具描述，并弄清你授予了什么访问权限
- 假设你发给 MCP 工具的数据可能会被公开或被滥用

MCP 服务器并不是格外有风险；它们只是另一种工具。原则是相同的：限定访问的范围。

### 综合起来：按工具、按任务划定权限边界

把这些课程联系在一起的设计原则是：权限边界应当被有意地限定，按工具、按任务来划定，而不是整个智能体共用一份宽泛的凭据。

设计智能体时：

1. 列出智能体需要的每个工具
2. 对每个工具，问：这个工具要实现它的目的，所需的最小访问权限是什么？
3. 为这个工具创建恰好授予这些访问权限、不多一分的沙箱边界
4. 如果某个工具需要认证（对数据库、API、文件系统），就创建一份限定于该工具和该访问级别的凭据，而不是一份什么都能触及的凭据

一个范围狭窄的工具，是把“模型被注入欺骗了”从灾难性的攻破，变成可控的、后果轻微的失误的具体手段。智能体读到注入，模型理解了它，模型调用了被注入的工具，而工具拒绝执行所请求的动作，因为这个动作超出了它的范围。

## 练习

1. ▢ 你在为一个管理用户账号的智能体设计工具。这个工具需要更新公司数据库里某个用户的电子邮件地址。你的初稿给它的凭据是：对整张 users 表拥有 UPDATE 权限的数据库账号。

为什么这个范围过大，更好的设计是什么？

<details markdown="1"><summary>检查</summary>

这份凭据授予了对整张表的 UPDATE 权限，这意味着工具可以更新任何用户的信息，而不只是被管理的那一位特定用户的电子邮件地址。更好的设计，是在数据库上创建一个存储过程，只接受用户 ID 和新的邮箱地址，并授予工具的凭据只能执行这个过程的权限。这样，即使注入骗智能体用意料之外的参数去调用这个工具，数据库也会拒绝执行过程范围之外的任何东西。

</details>

2. ▢ 一个智能体可以使用一个 send_email 工具，它被限定只能从 `support@company.com` 发送，并且只能发往符合模式 `*@customer-*.com` 的邮箱地址。一次注入试图骗它向 `attacker@evil.com` 发送一条消息。是什么阻止了这次攻击？

<details markdown="1"><summary>提示</summary>

范围是由工具本身强制执行的。想想这项检查发生在哪里，以及为什么这里没有涉及任何提示词指令。

</details>

<details markdown="1"><summary>检查</summary>

是工具的验证，它在消息发出之前，在运行框架里运行。工具对照它允许的模式验证收件人，并拒绝发送，因为 `attacker@evil.com` 不匹配。注入成功地改变了智能体的行为（智能体本来打算发送），但它失败了，因为工具的权限边界阻止了有害的动作。这是工具层面的控制，而不是提示词层面的控制，所以它是可靠的。

</details>

3. ▢ 你的组织提供了一个暴露公司日历事件的 MCP 服务器。你发现有一家第三方公司构建了一个 MCP 客户端，连接到你的服务器来帮助管理会议。下面哪项陈述是正确的？

    - a) 只要你的 MCP 服务器只返回公开的日历数据，这就是安全的
    - b) 这家第三方客户端现在实际上拥有对你的服务器所返回的日历数据的读取权限
    - c) 你应该在服务器与客户端之间使用加密，以保证即使你的服务器运营者也看不到这些数据
    - d) 这家第三方公司无法滥用这些数据，因为它们只是日历事件，而不是用户凭据

<details markdown="1"><summary>检查</summary>

**b)** 第三方客户端以及运营它的人，可以看到并有可能滥用服务器返回的所有日历数据。公开的数据仍然是数据；即使日历事件不是机密，第三方运营者现在也能看到你组织的日程，这可能被用于商业间谍活动或社会工程。加密（选项 c）能保护传输中的数据，却无法阻止客户端的运营者看到它。访问范围（公开还是私有）并不改变安全上的含义：你已经把信任边界扩展到了包括第三方运营者。这就是 MCP 的供应链风险。

</details>

4. ▢ 你在为一个处理客户支持工单的智能体设计工具。这个工具需要向客户发送一封电子邮件回复。描述一种最小权限的设计，防止混淆代理人攻击，即注入骗智能体把一串机密的内部邮件转发给客户。

<details markdown="1"><summary>检查</summary>

不要用通用的 send_email 工具，而是设计一个叫 send_support_response 的工具，它只接受两个参数：工单 ID 和回复文本。工具根据工单 ID 查出客户的邮箱地址，验证回复文本没有超出合理的长度，并且只发送这条回复（不带任何附件，也不带任何其他邮件）。工具的凭据只有从支持地址发送的权限，并且只能发往与有效工单关联的客户邮箱地址。这样，注入仍然可以骗智能体去调用 send_support_response，但这个调用被工具的范围所约束。智能体无法转发内部邮件，无法发往任意地址，也无法发送任何不是支持回复的东西，因为工具没有提供做这些事的途径。

</details>

## 实战练习

- [ ] 找一个你设计过或经常使用的工具。梳理它当前的权限。写下它拥有的一项、超出它主要目的严格所需的权限，以及去掉它的一种办法。
- [ ] 挑一个你愿意让智能体连接的 MCP 服务器。调研或联系它的运营者，弄清楚：服务器能看到什么数据、这些数据如何使用、如何保护、谁能访问日志？写下你的信心程度，以及任何残余的风险。
