# 第 33 课：token 放大与单个完成任务的成本

**使命关联:** 估算智能体循环的 token 成本和延迟，并说出放大效应来自循环的哪个部分。
**主要来源:** [文章：“How We Built Our Multi-Agent Research System”，Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
**前置知识:** [第 32 课](0032-least-privilege-and-the-confused-deputy.md)、[轨迹](../GLOSSARY.md)

## 热身

1. ▢ 在第 10 课里，你学到智能体循环每运行一轮，对话记录就增长一次。为什么这会造成一项沿着轨迹不断叠加的成本？

<details markdown="1"><summary>检查</summary>

每一轮循环，整份对话记录都会发给模型。一条 30 轮的轨迹，意味着第 1 轮的内容被发给模型 30 次，第 2 轮的内容 29 次，依此类推。一条长轨迹的 token 成本，不只是各轮之和；而是旧的轮次被重复传输的所有次数之和。

</details>

2. ▢ 回忆第 19 课：当编排者并行派出三个工作者时，与单个智能体解决同一个问题相比，总共运行了多少个智能体循环？

<details markdown="1"><summary>检查</summary>

运行了三个独立的智能体循环，每个工作者内部一个，外加编排者自己的循环。所以总数至少是三次完整的智能体运行，加上编排者的成本，而单个智能体解决同一个问题只有一次运行。并行让 token 成本成倍增加，而不是成比例减少。

</details>

## 要点

### token 放大的四个来源

智能体系统每完成一个任务所消耗的 token，远多于一个信息充分的单个提示词。这是由四个叠加的因素造成的。其中三个我们在前面的课程里已经点明过；本课把它们汇总起来，并加上第四个。

### 来源 1：对话记录的重复增长（来自第 10 课）

每一轮循环都会向对话记录追加内容。下一轮，整份对话记录会被重新发给模型。这意味着一条 50 轮的轨迹，要把第 1 轮的 token 成本付五十遍，第 2 轮的成本付四十九遍，依此类推。总数大约是总和的一半：1 + 2 + 3 + ... + 50 = 1,275，所以每一轮平均被付费 25.5 次。你只发送一次的简单提示词，花费 X 个 token。同一个问题由一个 50 轮的智能体来解决，在原始 token 传输上，花费的不是 50X（如果每一轮都是独立的话），而是接近 1,275X，哪怕每一轮因为模型的焦点更窄，单轮成本低于 X。

Anthropic 的“Building Effective Agents”文章指出，这种重复增长是长时间运行的智能体上最大的成本倍增因素，这也是第 11 课（压缩与检索）作为防御手段而存在的原因。

### 来源 2：多智能体的重复劳动（来自第 19 课）

如果你把问题拆成子任务，并行运行三个工作者（第 18 课的扇出），你要付的完整的对话记录重复增长成本，不是一次，而是三次。每个工作者都有自己的 50 轮轨迹，所以每个都要付 1,275X。编排者也要运行它自己的循环。协调成本让整体的 token 成本成倍增加。如果你的单个智能体本来花费 50,000 个 token，那么三个工作者每个成本略低，加起来可能总共有 130,000 个 token 甚至更多。

### 来源 3：反思与重试（来自第 17 课）

如果对某个任务的第一次尝试失败了，运行框架生成一段反思，然后再次运行智能体，那么你现在有的是两条完整的轨迹，而不是一条。一个需要三次尝试的任务（一次失败、一次反思、一次成功），花费大约是一次成功的单次尝试的三倍，因为每次尝试都是一次完整的智能体运行，带着它自己的对话记录重复增长。第 17 课讲过，只有当失败信号清晰、第二次尝试很可能成功时，反思才值得付出这笔成本。

### 来源 4：工具定义在每一轮都被重新发送（本课新增）

系统提示词和工具定义，是每一轮循环都要发给模型的上下文的一部分。工具定义通常很大：每个工具都有名称、给人读的描述（来自第 8 课的命名工作）、参数类型、约束和示例。如果你有十个工具，每个描述 200 个 token，那就是 2,000 个 token 的工具定义。在一条 50 轮的轨迹上，那就是 2,000 * 50 = 100,000 个 token，花在重新发送同样的工具定义上，尽管它们在运行中途从未改变。

这项成本有别于对话记录的重复增长（来源 1），因为工具定义不会变化；它们是稳定的、重复出现的前缀。这正是第 34 课（提示词缓存）要解决的问题。

### 做预算的正确单位：单个完成任务的成本

大多数关于成本的讨论，关注的是“单次 API 调用成本”或“单次模型调用成本”。但智能体系统的正确单位是“单个完成任务的成本”，也就是所有尝试、所有重试、所有工作者、所有轮次的完整总和，直到任务完成为止。

一个单个提示词也许只用 5,000 个 token 就能解决的任务，在智能体系统里可能要花 50,000 个甚至更多的 token，如果：

- 问题需要 20 轮才能解决（重复增长的倍数：在单轮成本之上约 200 倍）
- 第一次尝试失败了，基于反思的重试成功了（乘以 2）
- 任务被拆成三个并行的工作者（乘以 3）
- 工具定义很大，并且每一轮都重新发送（再加上 10,000 个 token 的浪费）

这个计算是粗略的，但原理是真实的：5,000 个基础 token，实际上可能变成 50,000 到 150,000 个 token，因为你付费的不是一次调用；而是一次任务的完成，其中涉及许多次调用、许多个来回，以及许多份重复的上下文。

### 为什么“单个完成任务的成本”会改变你的设计决策

当你按单次 API 调用成本来想时，一个长时间运行的智能体，会因为调用次数多而显得昂贵。当你按单个完成任务的成本来想时，问题就变了：多智能体系统是否更快地（按实际耗时）或更可靠地解决了问题，值得付出 token 的倍数？反思是否减少了失败的任务，值得付出重试的成本？任务拆解是否把问题简化到足以让每个工作者，每个任务用的 token 比单个智能体更少？

这些才是真正的取舍问题。按单个任务做成本预算，让这些取舍变得可见。

### 示例：调试一个代码失败

假设你的任务是调试一个失败的测试。一位信息充分的人，可能会写这样一个提示词：“这是测试，这是错误输出。找出 bug。”这个提示词加上响应，总共可能花 10,000 个 token。

现在假设你构建的是一个智能体循环：

- 智能体读取测试（1,000 个 token），读取代码（2,000 个 token），对错误进行推理（500 个 token），第 1 轮共 3,500 个 token。第 2 轮重新发送这 3,500 个 token，再加上工具定义（2,000 个 token），共 5,500 个 token。调试 10 轮之后，你大约花了 3,500 \* 10 + （工具定义 \* 10）= 55,000 个 token，因为每一轮都会重新发送测试、代码和工具定义。
- 智能体的第一次尝试猜错了根本原因。运行框架生成一段反思，并重新运行智能体。现在你有两次完整的 10 轮运行，所以大约是 110,000 个 token，而不是 55,000 个。
- 第二次尝试成功了。

单个完成任务的成本：110,000 个 token。单次成功 API 调用的成本：5,500 个 token（只算最后那次成功的调用）。这两个数字讲述的是不同的故事。按单个完成任务来做预算，更诚实。

解决办法不是避开智能体；而是用第 34 课的提示词缓存，避免重新发送工具定义，用第 16 课的规划来减少轮次，并且只在失败信号清晰时才用第 17 课的反思。

## 练习

1. ▢ 对模型的单轮提示词花费 5,000 个 token，并完美地解决了问题。同一个问题上的智能体循环用了 25 轮，对话记录的重复增长成本意味着，早期各轮的每个 token 平均被付费大约 20 次。智能体循环总共大约花费多少 token？

<details markdown="1"><summary>检查</summary>

大约 5,000 * 20 = 100,000 个 token。重复增长的倍数是最大的因素。（这是一个说明性的估算；确切的数字取决于 token 在各轮之间如何分布，但数量级是对的。）

</details>

2. ▢ 你在构建一个总结研究论文的智能体。智能体的工具定义总共是 3,000 个 token。在一次运行中，智能体检查了 10 篇论文，产出 10 份摘要，总共用了 40 轮。工具定义在运行期间从未改变。重新发送工具定义花了多少 token？为什么这种浪费可以用第 34 课来解决？

<details markdown="1"><summary>提示</summary>

数一数工具定义被发给模型多少次。然后想想上下文中的哪一部分是稳定的、在运行中途从不改变。

</details>

<details markdown="1"><summary>检查</summary>

工具定义被发送了 40 次（每轮一次），所以是 3,000 * 40 = 120,000 个 token，花在重新发送一模一样的定义上。这是浪费，因为定义从不变化；它们是稳定的前缀。第 34 课讲的提示词缓存，缓存的恰恰就是这种稳定的前缀，并且只收一次费，而不是 40 次。

</details>

3. ▢ 一个任务需要三次尝试。第一次尝试失败，生成一段反思，第二次尝试失败，又生成一段反思，第三次尝试成功。每次尝试都是一次完整的 15 轮智能体运行。协调这三次尝试的编排者花了 5 轮。这条轨迹大约总共有多少轮？

    - a) 15 轮（只有成功的那次尝试才算）
    - b) 35 轮（15 + 15 + 5）
    - c) 50 轮（15 + 15 + 15 + 5）
    - d) 150 轮（三次尝试乘以编排者的开销）

<details markdown="1"><summary>检查</summary>

**c)** 三次尝试都运行到了结束，所以 15 + 15 + 15 = 45 轮，再加上 5 轮编排，共 50 轮。选项 a 是错的，因为失败的尝试同样要消耗完整的轮次。选项 b 漏掉了第二次失败的尝试。选项 d 把加法算成了乘法。轨迹包含每次尝试的每一轮，而不只是成功的那次。

</details>

4. ▢ 你在决定一项研究任务用单个智能体，还是扇出三个工作者。单个智能体需要 60 轮，大约花费 100,000 个 token。每个工作者需要 25 轮，大约花费 35,000 个 token，另外编排者需要 10 轮，花费 3,000 个 token。多智能体系统的总 token 成本是多少？它比单个智能体更便宜吗？

<details markdown="1"><summary>检查</summary>

总计：(35,000 * 3) + 3,000 = 108,000 个 token。多智能体系统在 token 上其实略贵一些（108,000 对 100,000），尽管每个工作者的效率更高。这就是第 19 课讲的协调成本。多智能体系统赢在实际耗时上（三个工作者并行运行，所以由最慢的工作者决定时间，而不是三者之和），而不是 token 上。这说明了按单个任务做成本预算为什么重要：如果你要的是速度，多智能体胜出；如果你要的是 token，单个智能体胜出。

</details>

## 实战练习

- [ ] 找一个你用智能体完成过的任务（或你见过的一条轨迹）。梳理这个智能体的一次循环迭代，并数一数 token：对话记录的大小、工具定义的大小、模型输出的大小。乘以轮次数。现在估算一个信息充分的、发给模型的单个提示词会花多少，并比较这两个数字。记录这个倍数。
- [ ] 设计一个小型的智能体任务（你自己能运行的东西）。估算单个完成任务的成本，要猜：需要的轮次、重试的次数、有没有扇出的工作者。用这个公式把完整的预算加起来：(transcript_regrowth_factor) \* (number_of_attempts) \* (number_of_workers) \* (tokens_per_turn)。
- [ ] 明天：找一条或生成一条智能体运行的轨迹（至少 10 轮）。把所有轮次、所有尝试的 token 成本相加，计算单个任务成本（以 token 计）。然后求出单次成功 API 调用的成本（只算最后成功的那一轮）。写下单个任务的成本比单次成功调用的成本大了多少，并解释这个差异为什么对做预算很重要。
