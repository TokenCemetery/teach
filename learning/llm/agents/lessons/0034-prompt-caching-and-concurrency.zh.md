# 第 34 课：提示词缓存与并发

**使命关联:** 估算智能体循环的 token 成本和延迟，并说出放大效应来自循环的哪个部分。
**主要来源:** [文档：“Prompt caching”，Claude Platform Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
**前置知识:** [第 33 课](0033-token-amplification-and-cost.md)

## 热身

1. ▢ 在第 33 课里，你学到工具定义在每一轮循环都会重新发给模型，尽管它们从不改变，却依然消耗 token。这是上下文的哪一部分？为什么缓存会有帮助？

<details markdown="1"><summary>检查</summary>

工具定义是发给模型的每条消息中稳定的前缀：它们在运行中途不会改变。缓存之所以有帮助，是因为缓存在第一次请求之后，把这个稳定的前缀存起来，并在同一条轨迹的后续请求中重用，只对追加在它后面的新内容收费。

</details>

2. ▢ 回忆第 19 课：与按顺序运行一个智能体相比，并行运行三个智能体，会降低解决问题的 token 成本吗？

<details markdown="1"><summary>检查</summary>

不会。并行运行三个智能体会增加总的 token 成本，因为每个智能体都要独立地付它的全部成本。并行降低的是实际耗时，而不是 token 成本。每个并行的智能体仍然要读取任务、运行自己的循环，并把自己的对话记录传给模型。

</details>

## 要点

### 提示词缓存如何工作

提示词缓存是这样一种机制：在第一次调用之后，把请求中稳定的前缀存起来，并在后续调用中重用它，而不必再为它支付全价。缓存只属于某一个请求序列；来自不同用户或不同智能体运行的请求，不会共享缓存。

机制是这样的：

1. 在一条轨迹的第一条消息里，你发送完整的请求：系统提示词、工具定义和任务。
2. 模型照常处理它，并收取全额的 token 成本。
3. 响应里包含元数据：“Cached 4,000 tokens”（或者无论稳定前缀有多大）。
4. 在同一条轨迹的第二条消息里，你往请求里追加新的内容：也许是一个工具结果、下一条指令，或者后续的一轮。
5. 模型重用已缓存的前缀（系统提示词、工具、任务），只对新追加的内容收费。
6. 如此重复：同一条轨迹里的每一轮，只为自上一轮以来发生变化的部分付费。

缓存是有成本的：第一轮付全价，缓存的查找和存储还有少量的开销。但对一条长轨迹来说，这笔开销很容易就能说得过去。如果你有 30 轮，工具定义是 2,000 个 token，缓存大约节省 2,000 * 28 = 56,000 个 token（第 2 到第 29 轮不再重新发送定义，所以你把它们的成本省了 28 次）。

### 什么会使缓存失效

只有当前缀确实稳定时，缓存才有用。有几件事会悄悄让缓存失效，这对运行框架的设计很重要：

**重新排列工具定义的顺序。** 如果你在第 1 轮和第 2 轮用不同的方式序列化工具列表（例如第 1 轮按字母顺序，第 2 轮按使用频率），前缀就不再匹配，缓存就失效了。运行框架必须每一轮都以相同的顺序序列化工具。

**把动态的值插入系统提示词。** 如果你的系统提示词里包含时间戳（“Current time: 2024-09-13”）、用户 ID 或任何每次调用都不同的值，那个值在各轮之间就会变化，前缀也就不再稳定。缓存在每一轮都会失效。这就彻底废掉了缓存。如果你需要动态的值，把它们放在工具之后（请求中不被缓存的那一部分）。

**编辑较早的消息。** 如果运行框架对旧消息做原地编辑（而不是纯粹的追加），缓存会从那个编辑点往后全部失效。第 7 课讲过，对话记录是智能体的状态；这种理念主张纯粹的追加，永远不去碰旧消息。提示词缓存强化了这一点：任何编辑都会破坏缓存。

### 缓存解决了第 33 课里“工具定义在每一轮都被重新发送”的成本

主要来源“Prompt caching”文档指出，工具定义和系统提示词，恰恰是缓存所针对的那种稳定、庞大、重复出现的内容。一个有 10 个工具、工具描述共 2,000 个 token 的运行框架，现在这 2,000 个 token 在每条轨迹里只花一次，而不是每一轮一次。在一条 50 轮的轨迹上，仅此一项就大约节省 98,000 个 token（没有缓存时定义出现 50 次，有缓存时出现 1 次，所以节省了 49 * 2,000 = 98,000 个 token）。

这就是第 33 课和第 34 课成对出现的原因：第 33 课找出了浪费，第 34 课指出了解决办法。

### 并发：一个独立的、互补的杠杆

提示词缓存降低的是任何单次智能体运行的成本。并发则是另一个问题：并行运行多个智能体实例。

并发可以有几种形式：

- 对同样的输入，并行地用多个智能体运行同一个任务，看它们是否给出不同的答案（对存在多个有效解的任务有用）。
- 并行地运行任务的各个变体（第 19 课的扇出），每个智能体解决一个子任务。
- 并行地运行多个相互独立的用户任务（一个服务许多用户的系统，每个用户有自己的智能体实例）。

在每种情况下，并发提高的都是吞吐量：单位实际时间内完成更多的任务。但并发并不会降低任何单个任务的 token 成本。如果你并行运行三个智能体，每个花费 100,000 个 token，总数是 300,000 个 token，而不是 100,000 除以 3。并行是用 token 换时间。

### 错误：把缓存和并发混为一谈

一个常见的预算错误，是以为并行运行多个智能体，会让每一个在 token 上变得更便宜。其实不会。混淆之处在这里：

- 正确：缓存通过避免重新发送稳定的前缀，降低了单个智能体长轨迹的 token 成本。
- 正确：并发通过并行运行智能体，缩短了实际耗时。
- 错误：“我们并发地运行智能体，所以每个智能体的 token 成本更低。”

并发降低的是时间，而不是 token。让智能体运行得更快（并行），并不会让它们更便宜（以 token 计）。如果你需要降低成本，并且已经有了缓存，可用的杠杆是：

- 更好的规划（第 16 课），以减少轮次。
- 更好的检索（第 11 课），以减小对话记录。
- 更少的工作者（第 19 课），以减少多智能体的重复劳动。
- 更快地失败（第 29 课的诊断），以减少被浪费的尝试。

### token 预算：两个问题

设计智能体系统时，要问两个独立的问题：

1. **单个完成任务的成本：** 一个智能体需要多少 token，才能可靠地解决一个任务？这是缓存有帮助、规划有帮助、反思要花钱的地方。
2. **吞吐量：** 你每秒或每分钟需要完成多少个任务？这是并发有帮助的地方。如果你每秒需要完成 10 个任务，而每个任务按顺序需要 1 秒才能完成，你就需要至少 10 个智能体并行运行。

把这两个问题混淆，会导致错误的决策。如果你想降低每个任务的成本，增加更多并发的智能体没有帮助。如果你想提高吞吐量，并且有一个时限，增加并发就是正确的杠杆（但你要付出总 token 的代价：10 个智能体 * 每个任务的成本 = 总预算）。

## 练习

1. ▢ 你的智能体的系统提示词和工具定义总共是 5,000 个 token。智能体在单个任务上运行了 30 轮。没有提示词缓存时，这 5,000 个 token 被发给模型多少次？有缓存时是多少次？

<details markdown="1"><summary>检查</summary>

没有缓存：30 次（每轮一次），定义的开销总共是 150,000 个 token。有缓存：第一轮一次，之后的所有轮次都重用，所以实际上是一次。（更准确地说，每一轮读取缓存有少量开销，但完整的 5,000 个 token 并不会被重新传输。）在这种情况下，缓存大约节省了 145,000 个 token。

</details>

2. ▢ 你在你的运行框架里实现提示词缓存。工具列表是动态生成的：第 1 轮，智能体可以使用工具 A、B、C；第 3 轮，运行框架添加了工具 D。工具按它们生成的顺序序列化（第 1 轮是 A、B、C；第 3 轮是 A、B、C、D）。第 1 轮的缓存在第 3 轮还有效吗？为什么有效或为什么无效？

<details markdown="1"><summary>提示</summary>

第 1 轮的请求与第 3 轮的请求之间，有什么变了？这个变化是在被缓存的前缀之内，还是在它之后？

</details>

<details markdown="1"><summary>检查</summary>

无效，缓存失效了。第 1 轮，前缀包含“tools: A, B, C”。第 3 轮，前缀包含“tools: A, B, C, D”。前缀不匹配，所以缓存不适用。运行框架必须重新发送完整的定义。这就是为什么动态添加工具（根据智能体的决定，在运行中途添加工具）会破坏缓存。想要缓存的运行框架，要么一开始就确定一个固定的工具集，要么接受运行中途添加工具会使缓存失效这一点。

</details>

3. ▢ 你在为一个使用缓存的智能体设计系统提示词。提示词里包含“Current date: 2024-09-13”，用来让模型对时间有所把握。为什么这是个缓存问题？

    - a) 日期与模型无关，应该删掉。
    - b) 日期每天都变，所以缓存的前缀在一天之后就会过期。
    - c) 日期是在各次运行之间变化的动态值，会使缓存在每次运行都失效，因为前缀不再匹配。
    - d) 任何系统都无法缓存日期。

<details markdown="1"><summary>检查</summary>

**c)** 系统提示词是被缓存的前缀的一部分。如果你包含了一个硬编码的日期，第 1 次运行与第 2 次运行的日期不同，那么第 1 次运行缓存的前缀，与第 2 次运行的请求就不匹配，缓存也就毫无用处。解决办法是把日期排除在被缓存的前缀之外（放在工具之后，放进每轮的内容里），或者，如果日期并不真的关键，就对所有运行使用一个固定的日期。这是一个常见的错误：把每次运行的元数据放进被缓存的部分，会废掉缓存。

</details>

4. ▢ 你有两种扩展智能体系统的方案：方案 A 是通过缓存和规划来优化单个智能体每个任务的成本，把它从 100,000 个 token 降到 60,000 个 token。方案 B 是在不优化的情况下并行运行十个智能体，每个仍然花费 100,000 个 token。如果你需要完成 10 个任务，并且算力无限，哪种方案能让 token 成本最小？

<details markdown="1"><summary>检查</summary>

方案 A：10 个任务 \* 每个任务 60,000 个 token = 总共 600,000 个 token。方案 B：10 个任务 \* 每个任务 100,000 个 token = 总共 1,000,000 个 token，尽管它们是并行运行的。并发提高的是速度（方案 B 在一个任务的时间内完成，而方案 A 按顺序要花 10 倍的时间），而不是成本。方案 A 在 token 上更便宜。如果你需要尽可能快地完成 10 个任务，你会把两者结合起来：把每个智能体优化到 60,000 个 token（方案 A 的做法），并并行运行 10 个经过优化的智能体，总共 600,000 个 token，实际耗时也最短。

</details>

## 实战练习

- [ ] 看一个你写过或评审过的智能体运行框架。找到系统提示词和工具定义被序列化的地方。验证它们总是以相同的顺序序列化，并且那一部分里没有插入任何动态值（时间戳、用户 ID、每次运行特有的元数据）。如果有，记下它是如何破坏缓存的。
- [ ] 为一个你熟悉的任务，估算提示词缓存能节省多少 token。猜测：系统提示词和工具定义的大小、轮次数、每轮的 token。计算不重新发送定义能节省多少 token。这笔节省值得为实现缓存而增加的复杂性吗？
- [ ] 明天：设计一个能从并发中受益的任务（多个用户、多个独立的子任务，或对同一个任务的多次尝试）。估算按顺序（一次一个）运行智能体，与并行运行智能体时的总 token 预算。证明这两种预算是相同的，并解释每种做法让你得到什么、失去什么。
