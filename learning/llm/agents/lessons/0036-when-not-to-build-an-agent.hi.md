# पाठ 36. Agent कब नहीं बनाना चाहिए

**मिशन से संबंध:** यह तय करने का विवेक बनाएँ कि किसी task को तय workflow की जगह agent की ज़रूरत है भी या नहीं, और उस फ़ैसले का बचाव संगठन के दबाव और agent जैसे हलों के आकर्षण के सामने करें।
**मुख्य स्रोत:** [लेख: "Building Effective Agents", Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
**पूर्व-आवश्यकताएँ:** [पाठ 35](0035-durability-and-what-frameworks-buy.md), [Autonomy spectrum](../GLOSSARY.md)

## वार्म-अप

1. ▢ पाठ 2 से याद करें: control flow के लिहाज़ से workflow और agent में बुनियादी अंतर क्या है?

<details markdown="1"><summary>जाँचें</summary>

Workflow का रास्ता developer ने पहले से तय किया होता है; सारी branches और क्रम developer ने जोड़े हैं। Agent का control flow run के समय model तय करता है, यह भी कि जारी रखना है या रुकना है।

</details>

2. ▢ पाठ 2 से याद करें: autonomy spectrum पर, कौन-सी ठोस कसौटी लगाकर आप तय कर सकते हैं कि task की branches की गिनती असल में गिनी जा सकती है या नहीं?

<details markdown="1"><summary>जाँचें</summary>

अगर आप उन सारे अलग रास्तों की सूची बना सकते हैं जो workflow को task कवर करने के लिए चाहिए, तो branches की गिनती गिनी जा सकती है और workflow काफ़ी हो सकता है। अगर नए रास्ते आपके जोड़ने से तेज़ी से आते हैं, या सही रास्ता सचमुच ऐसी जानकारी पर निर्भर है जो task के बीच ही मिलती है, तो branches की गिनती प्रभावी रूप से असीमित है और agent ज़्यादा बचाव लायक़ है।

</details>

## यह जानें

### यह फ़ैसला पाठ 2 में दिखे से कठिन क्यों है

पाठ 2 ने autonomy spectrum को साफ़-सुथरे तकनीकी चुनाव की तरह सिखाया: क्या task का आकार जाना हुआ है या अनजाना, गिना जा सकने वाला या असीमित? व्यवहार में, वह चुनाव असली दबाव के नीचे होता है।

कोई product manager agent का किसी जटिल समस्या को हल करने का प्रभावशाली demo देख चुका है और पूछता है, "क्या हम अपने product के लिए वह बना सकते हैं?" कोई संगठन AI में पीछे महसूस करता है और अपने platform में "agents जोड़ना" चाहता है। कोई हितधारक किसी task की ओर इशारा करके कहता है, "यह agent लायक़ लगता है," यह जाँचे बिना कि सरल विकल्प असल में आज़माया गया या नहीं। उसी समस्या को हल करने वाले workflow को पेश करना कम रोमांचक है, तब भी जब workflow बेहतर engineering फ़ैसला हो।

इस पाठ की भूमिका पाठ 2 का ढाँचा दोबारा सिखाना नहीं है; ढाँचा सही है। भूमिका यह बताना है कि उसे सही तरह लागू करना दबाव में विवेक की बात क्यों है, और आपको ठोस चेतावनी के संकेत देना जो बताएँ कि agent अनुचित है, हर एक किसी ख़ास पहले के पाठ से जुड़ा, ताकि आप pattern को तब पहचान सकें जब उसे किसी प्रस्ताव या architecture समीक्षा में देखें।

### चेतावनी का संकेत 1: किसी ने पहले सरल workflow नहीं आज़माया

सबसे मज़बूत चेतावनी का संकेत यह है: कोई हितधारक या प्रस्ताव कहता है कि agent चाहिए, पर किसी ने उस दावे को परखने के लिए workflow विकल्प असल में बनाया नहीं।

पाठ 2 हर चुनाव का बचाव यह बताकर करता है कि छोड़े गए विकल्प की क्या क़ीमत होती। वह बचाव तभी काम करता है जब आपने छोड़े गए विकल्प को असल में परखा हो। अगर प्रस्ताव दावा करता है "agent ज़रूरी है" बिना workflow का प्रयास दिखाए और बिना समझाए कि workflow क्यों फेल हुआ, तो दावे को विकल्प के सामने परखा नहीं गया। आपसे जटिलता बढ़ाना स्वीकार करने को कहा जा रहा है, बिना प्रमाण के कि जटिलता की ज़रूरत है।

व्यवहार में यह ऐसा दिखता है: प्रस्ताव कहता है, "हमें इन customer support tickets को सँभालने के लिए agent चाहिए क्योंकि वे चालीस अलग श्रेणियों में बँटते हैं।" Workflow के प्रयास के बिना, आप नहीं जानते कि चालीस श्रेणियाँ जोड़ने के लिए सचमुच बहुत ज़्यादा हैं, या प्रस्ताव के लेखक ने बस अभी आज़माया नहीं। Workflow router बनाकर और उसे असली tickets पर परखकर, आप पा सकते हैं कि चालीस श्रेणियाँ सँभालने लायक़ हैं, या आप पा सकते हैं कि workflow की सटीकता घटती है क्योंकि नियम-आधारित classifier सीमांत मामलों में दो श्रेणियों में फ़र्क़ नहीं कर पाता। उसी task पर workflow को परखना आपको बताता है कि agent पर जाकर आप असल में क्या ख़रीद रहे हैं।

अनुशासन: agent पर टिकने से पहले पूछें "कौन-सा workflow आज़माया गया, और वह क्यों फेल हुआ?" अगर जवाब है "कोई नहीं," तो पहले एक बनाने पर अड़ें। आप सीख सकते हैं कि workflow समस्या को काफ़ी अच्छी तरह सुलझाता है, या आप सीख सकते हैं कि workflow ख़ास तरीक़ों से फेल होता है जिन्हें agent असल में बेहतर करता।

### चेतावनी का संकेत 2: विफलता का रूप विश्वसनीयता है, क्षमता नहीं

पाठ 2 ने कहा कि agent अपनी अनिश्चितता तब कमाता है जब आपको लचीलापन चाहिए। पर लचीलेपन की विश्वसनीयता में क़ीमतें हैं जिनके नाम बताने में इस track के चरण 11-12 ने पाठ लगाए: computer-use agents में grounding की ग़लतियाँ (पाठ 25), cascading tool errors जहाँ एक tool की विफलता अगले चरण को गिरा देती है (पाठ 28), context poisoning जहाँ झूठा दावा transcript में आता है और हर आगे का turn चुपचाप उसे तथ्य मानता है (पाठ 27)।

अगर किसी task की विफलता का रूप इन विश्वसनीयता श्रेणियों में से एक है, और task ऐसा है जहाँ तय, अच्छी तरह परखा हुआ workflow उस श्रेणी की ग़लती कभी करता ही नहीं, तो agent एक ऐसी विश्वसनीयता की समस्या की क़ीमत पर अनिश्चितता ख़रीदता है जो पहले थी ही नहीं।

उदाहरण: दस्तावेज़ वर्गीकरण system जिसे documents को पाँच जानी हुई श्रेणियों में से ठीक एक में भेजना है। Agent लचीले ढंग से भेज सकता है और दस्तावेज़ में कुछ ऐसा पढ़कर, जो उसका मन बदल दे, दोबारा वर्गीकृत भी कर सकता है। पर अगर task तय, ऑडिट योग्य प्रक्रिया से वित्तीय दस्तावेज़ वर्गीकृत करना है, और ग़लत वर्गीकरण की सज़ा नियामक उल्लंघन है, तो agent का लचीलापन context poisoning के जोखिम के लायक़ नहीं, जो agent को अपनी ही पिछली reasoning पर शक करवाकर दस्तावेज़ ग़लत श्रेणी में भिजवा दे। प्रति दस्तावेज़ एक routing फ़ैसले वाला workflow, चरण-दर-चरण ऑडिट योग्य, पूर्वानुमेयता की क़ीमत लेता है पर विश्वसनीयता वहाँ पाता है जहाँ वह मायने रखती है।

अनुशासन: जिन tasks में विफलता महँगी है या जहाँ विश्वसनीयता पर समझौता नहीं हो सकता, वहाँ बताएँ कि agent कौन-सी विश्वसनीयता की समस्या लाएगा जो workflow में नहीं होती। अगर वह समस्या पर्याप्त गंभीर है, तो workflow बेहतर चुनाव है, भले ही वह कम परिष्कृत लगे।

### चेतावनी का संकेत 3: Lethal trifecta पूरी मौजूद है और कोई फ़ायदा नहीं

पाठ 31 ने lethal trifecta का नाम दिया: private data तक पहुँच, untrusted content का सामना, और बाहर संवाद करने की क्षमता। Agent के पास तीनों शर्तें तब होती हैं जब वह untrusted input पढ़ता है और उसके पास ऐसे tools हैं जो data का दुरुपयोग या उसे बाहर निकाल सकते हैं।

कोई एक शर्त हटाने से हमला टूट जाता है। पर जिस agent के पास तीनों शर्तें हैं वह exploit करने लायक़ है भले ही injection कभी-कभी ही सफल हो। पाठ 32 ने सिखाया कि बचाव model को ज़्यादा ज़ोर से prompt करना नहीं, बल्कि tool की पहुँच को संकरा करना है।

अगर प्रस्तावित agent के पास trifecta की तीनों शर्तें हैं और task को agent की अनिश्चितता से कोई फ़ायदा नहीं, तो आप बिना किसी लाभ के exploit किए जा सकने की क़ीमत ख़रीद रहे हैं। ज़्यादा संकरा workflow-आधारित integration, या ऐसा tool सेट जिसमें जानबूझकर तीन में से एक शर्त न हो, वही लक्ष्य बिना जोखिम जुटाए पूरा करता है।

उदाहरण: content सुझाव engine items सुझाने के लिए user profiles और बाहरी content स्रोत पढ़ता है। अगर engine को ऐसे agent के रूप में लागू किया गया है जिसके पास बाहरी content लाने, user data query करने और messaging system को सुझाव भेजने के tools हैं, तो उसके पास trifecta की तीनों शर्तें हैं। पर अगर engine का काम सरल नियमों के आधार पर सुझावों के तय सेट में से चुनना है (अगर user ने A देखा है, तो B सुझाओ), तो workflow बिना user data और सुझाव system को ऐसे prompt injection channel के सामने उजागर किए काम कर देता है जो पहले था ही नहीं।

अनुशासन: trifecta की हर शर्त के लिए पूछें कि task को असल में उसकी ज़रूरत है या नहीं। अगर agent के पास तीनों हैं ऐसे task के लिए जिसे agent के लचीलेपन की ज़रूरत नहीं, तो tool सेट को दोबारा डिज़ाइन करें ताकि कम से कम एक शर्त जानबूझकर हट जाए। System demo के रूप में कम प्रभावशाली होगा, पर कम exploit होने लायक़ और ज़्यादा भरोसेमंद होगा।

### चेतावनी का संकेत 4: Token cost task के मूल्य से ज़्यादा है

पाठ 33 ने token amplification और cost per completed task सिखाया, जिसमें multi-agent का गुणक भी था। पाठ 19 ने दिखाया कि orchestrator-worker system उसी समस्या को हल करने वाले अकेले agent से tokens में कई गुना महँगा है।

एक ठोस सवाल: retries, लागू हो तो multi-agent coordination, और context की लंबाई या caching के अतिरिक्त बोझ से किसी भी token amplification समेत, असली cost per completed task का अनुमान लगाएँ। क्या वह cost उस चीज़ के लिए स्वीकार्य है जो task पैदा करता है?

यह सवाल अक्सर तब तक नहीं पूछा जाता जब तक बहुत देर न हो जाए। टीम agent बनाती है, लॉन्च करती है, और पाती है कि प्रति task cost उस मूल्य से ज़्यादा है जो task business में देता है। Agent चलता है, पर उसे चलाना बहुत महँगा है।

अनुशासन: agent (ख़ासकर multi-agent system) पर टिकने से पहले, prototype के असली turns या trajectories से cost per completed task का अनुमान लगाएँ। उस अनुमान को task के मूल्य से मिलाएँ। अगर token cost मूल्य से ज़्यादा है, तो agent उचित नहीं, चाहे system कितना भी सुरुचिपूर्ण हो।

### सब कुछ जोड़कर: agent पर टिकने से पहले ये चार सवाल पूछें

1. क्या सरल workflow असल में आज़माया गया और अपर्याप्त पाया गया?
2. क्या task की विफलता का रूप ऐसा है जहाँ agent नई विश्वसनीयता की समस्या लाता है जो workflow में नहीं होती?
3. क्या agent के पास trifecta की तीनों शर्तें हैं, और क्या वह जोखिम task के लिए ज़रूरी है?
4. क्या cost per completed task उस चीज़ के लिए स्वीकार्य है जो task पैदा करता है?

अगर इनमें से किसी का जवाब "नहीं" या "हम नहीं जानते" है, तो agent उचित नहीं हो सकता। Agent को मना करना विफलता नहीं है; यह अनुशासन है। आप agent के ख़रीदे लचीलेपन से ऊपर पूर्वानुमेयता, विश्वसनीयता, सुरक्षा या cost को चुन रहे हैं। यह बचाव लायक़ चुनाव है, और यही वह चुनाव है जो आपको भरोसे से हाँ कहने देता है जब agent असल में उचित हो।

## अभ्यास

1. ▢ एक product टीम आंतरिक रिपोर्टिंग के लिए customer support tickets का सारांश बनाने वाला agent बनाने का प्रस्ताव रखती है। Agent ticket पढ़ेगा (untrusted उपयोगकर्ता content), संदर्भ खोजने के लिए कंपनी के customer database तक पहुँचेगा, और सारांश Slack channel में पोस्ट करेगा। Workflow विकल्प में इंसान हाथ से tickets को श्रेणियों में छाँटेगा और फिर हर श्रेणी पर template-आधारित summarizer चलाएगा। टीम कहती है "agent ज़्यादा कुशल है।" Workflow चलाए बिना, आपको सबसे पहले कौन-सा सवाल पूछना चाहिए?

उनसे कहें कि workflow को असली tickets पर असल में बनाकर परखें। मापें कि agent कितना तेज़ है, और क्या कुशलता का फ़ायदा token की खपत की cost और lethal trifecta के उजागर होने (agent untrusted content पढ़ता है, private customer data तक पहुँचता है, और बाहरी संदेश भेजता है) को जायज़ ठहराता है। अगर workflow 90 प्रतिशत उतना अच्छा है और 10 प्रतिशत जितनी cost का है, तो workflow जीतता है। Workflow परखे बिना, दावा "agent ज़्यादा कुशल है" बिना परखा है।

</details>

2. ▢ आप ऐसे agent के प्रस्ताव की समीक्षा कर रहे हैं जो analysts को बड़े codebase में फेल हो रहे tests debug करने में मदद करता है। Agent के पास repository code, test नतीजों और logs की पहुँच होगी। वह code खोजने, अलग tests चलाने और bug reports दर्ज करने के tools call करेगा। प्रस्ताव कहता है, "Agent codebase को script से ज़्यादा लचीले ढंग से खँगाल सकता है।" पाठ 27 कौन-सी विश्वसनीयता की चिंता सिखाता है जो इस प्रस्ताव के मूल्यांकन के लिए प्रासंगिक है?

<details markdown="1"><summary>संकेत</summary>

सोचें कि जब agent tool calls के outputs पढ़ रहा है और बना रहा है कि code क्या कहता और करता है, तब क्या होता है। कौन-सा error pattern agents के लिए अनोखा है?

</details>

<details markdown="1"><summary>जाँचें</summary>

Context poisoning (पाठ 27)। अगर agent किसी log या code के टुकड़े की ग़लत व्याख्या करता है और bug के अपने मॉडल में झूठा दावा बना लेता है (जैसे "यह function None लौटाता है"), तो हर आगे का reasoning चरण उस झूठे दावे को स्थापित तथ्य मानेगा। तय रास्ते वाली script अपने output पर इस तरह शक नहीं करेगी। नए प्रमाण के आधार पर मन बदलने का agent का लचीलापन संपत्ति है, पर वह एक चरण से अगले में ले जाए गए ग़लत निष्कर्षों में चुपचाप भरोसे का दरवाज़ा भी खोलता है। मूल्यांकन करें कि task की विफलता का रूप (test को debug करना) लचीलेपन से ज़्यादा नुक़सान पाता है (नए bugs खोजने में बेहतर) या context poisoning के agent को ग़लत रास्ते पर ले जाने के जोखिम से।

</details>

3. ▢ इनमें से कौन-सा परिदृश्य सबसे साफ़ दिखाता है कि प्रस्तावित agent अनुचित है?

    - a) Task workflow से हल हो सकता है, पर workflow में हर बार नए दस्तावेज़ प्रकार के आने पर नई branch जोड़नी पड़ेगी
    - b) Task को workflow के रूप में आज़माया गया और वह सटीकता के लक्ष्य पूरे नहीं कर सका, पर उसी dataset पर परखा गया prototype agent बेहतर करता है
    - c) Task को कभी workflow के रूप में नहीं आज़माया गया, पर कोई हितधारक अड़ा है कि agent ज़रूरी है क्योंकि उसने जो AI demo देखा वह प्रभावशाली था
    - d) Task को untrusted content पढ़ना और private data तक पहुँचना है, पर agent के tool सेट में जानबूझकर बाहरी संवाद नहीं है

<details markdown="1"><summary>जाँचें</summary>

**c)** वह परिदृश्य जहाँ task को कभी workflow के रूप में नहीं आज़माया गया, और प्रस्ताव इस प्रमाण से नहीं बल्कि demo के उत्साह से चल रहा है कि सरल विकल्प फेल होता है। परिदृश्य (a) ऐसे task का वर्णन करता है जहाँ agent चलता हुआ लचीलापन ख़रीदता है; branches की गिनती बढ़ रही है, इसलिए agent उचित है। परिदृश्य (b) दिखाता है कि workflow परखा गया और फेल हुआ, जिससे agent का बेहतर प्रदर्शन उसके पक्ष में प्रमाण है। परिदृश्य (d) सोचे-समझे architecture का वर्णन करता है जो trifecta की एक शर्त हटाता है, जो उचित design चुनाव है। सिर्फ़ (c) का परीक्षण में कोई आधार नहीं है।

</details>

4. ▢ आप अनुमान लगाते हैं कि किसी task के लिए agent की retries समेत प्रति पूरे run की cost 5,000 tokens होगी, और task का business मूल्य मौजूदा बाज़ार दरों पर 2,000 tokens के compute के बराबर है। Agent बनाने या विकल्प चुनने के बीच एक चुनाव का बचाव करें, बताते हुए कि वह चुनाव करके आप क्या स्वीकार कर रहे हैं।

<details markdown="1"><summary>जाँचें</summary>

विकल्प (workflow, सरल system, या task को हाथ से छोड़ना) उचित है। Agent की cost उसके मूल्य से 2.5 गुना है, जिसका मतलब है कि हर run business को compute में उससे ज़्यादा ख़र्च कराता है जितना मूल्य में लौटाता है। फिर भी agent बनाना तभी बचाव लायक़ है जब आप token cost के घटने की उम्मीद करें (सस्ते models, caching रणनीतियाँ, दोहराए tasks पर तेज़ अभिसरण), या अगर business मूल्य अनुमान से ज़्यादा है। अगर इनमें से कुछ सच नहीं है, तो अनुशासन है मना करना। जो क़ीमत आप स्वीकार कर रहे हैं वह agent के देने वाले लचीलेपन को खोना है, पर आप पूर्वानुमेयता और cost-कुशलता पा रहे हैं। इन संख्याओं पर यही सही समझौता है।

</details>

## असली दुनिया का अभ्यास

- [ ] ऐसा task लें जिसे आपके जाने हुए system में अभी agent हल करता है। प्रति पूरे task token cost और हर पूर्णता के business मूल्य का अनुमान लगाएँ। क्या अनुपात स्वीकार्य है? अगर नहीं, तो agent को उचित बनाने के लिए क्या बदलना होगा?
- [ ] कोई प्रस्ताव खोजें (आंतरिक, या किसी system का वर्णन करता लेख) जो agent की वकालत करता है। जाँचें कि क्या वह चारों चेतावनी के सवालों का जवाब देता है: क्या workflow आज़माया गया, क्या विफलता का रूप विश्वसनीयता-संवेदनशील है, क्या trifecta की तीनों शर्तें ज़रूरी हैं, और क्या cost स्वीकार्य है? लिखें कि प्रस्ताव कौन-से चेतावनी के संकेत संबोधित करता है और किन्हें खुला छोड़ता है।
- [ ] कल: किसी product फ़ीचर की कल्पना करें जिसे आप agent के रूप में बनाएँगे। अब उसे इसके बजाय workflow के रूप में डिज़ाइन करें। दोनों की तुलना करें: workflow क्या नहीं कर सकता जो agent कर सकता है? Workflow बनाना कितना कठिन है? क्या फ़ायदे बढ़ी हुई जटिलता को जायज़ ठहराते हैं? अपना ईमानदार आकलन लिखें।
