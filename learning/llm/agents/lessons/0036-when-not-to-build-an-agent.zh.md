# 第 36 课：何时不该构建智能体

**使命关联:** 培养判断力：针对一个任务，判断它到底需不需要智能体，而不是用固定的工作流，并且面对组织的压力和智能体式方案的诱惑，能为这个决定辩护。
**主要来源:** [文章：“Building Effective Agents”，Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
**前置知识:** [第 35 课](0035-durability-and-what-frameworks-buy.md)、[自主性谱系](../GLOSSARY.md)

## 热身

1. ▢ 回忆第 2 课：就控制流而言，工作流与智能体的决定性区别是什么？

<details markdown="1"><summary>检查</summary>

工作流有一条由开发者事先固定的路径；所有分支和顺序都是开发者接好的。智能体的控制流是由模型在运行时决定的，包括是继续还是停止。

</details>

2. ▢ 回忆第 2 课：在自主性谱系上，你可以用什么具体的检验，来判断一个任务的分支数量是否真的可以枚举？

<details markdown="1"><summary>检查</summary>

如果你能把工作流为覆盖这个任务所需的所有不同路径都列出来，分支数量就是可枚举的，工作流可能就够了。如果新路径出现的速度快过你接线的速度，或者正确的路径确实取决于只有任务进行到一半才能获得的信息，那么分支数量实际上是没有上限的，智能体就更站得住脚。

</details>

## 要点

### 为什么这个决定比第 2 课所显示的更难

第 2 课把自主性谱系讲成一个清晰的技术选择：任务的形态是已知还是未知，是可枚举还是没有上限？在实践中，这个选择是处在真实的压力之下的。

一位产品经理看到过一个智能体解决复杂问题的、令人信服的演示，于是问：“我们能为我们的产品做出那样的东西吗？”一个组织觉得自己在 AI 上落后了，想在它的平台上“加入智能体”。一位利益相关者指着某个任务说：“这看起来值得用智能体”，却没有检查是否真的试过更简单的替代方案。解决同一个问题的工作流，推销起来没那么令人兴奋，即使这个工作流才是更好的工程选择。

本课的作用不是重新讲授第 2 课的框架；那个框架是对的。作用在于说明，为什么正确地应用它，是一种在压力下的判断，并给你具体的危险信号，告诉你什么时候智能体是没有道理的，每一个都与前面某一课挂钩，这样当你在提案或架构评审中看到这种模式时，就能认出它。

### 危险信号 1：没有人先试过更简单的工作流

最强的危险信号是：某位利益相关者或某份提案说需要智能体，却没有人真的构建过工作流这个替代方案来检验这个说法。

第 2 课为每个选择辩护的办法，是说出被放弃的那个方案会带来什么代价。只有当你真的检验过被放弃的方案，这种辩护才站得住。如果一份提案声称“智能体是必需的”，却没有给出一次工作流的尝试，也没有解释工作流为什么失败，那么这个说法就没有拿替代方案检验过。你被要求在没有证据表明需要复杂性的情况下，接受复杂度的增加。

在实践中，这看起来是这样的：一份提案说：“我们需要智能体来处理这些客户支持工单，因为它们分成四十个不同的类别。”没有工作流的尝试，你就不知道四十个类别到底是多到没法接线，还是提案的作者只是还没试过。在构建了一个工作流路由器并在真实工单上测试之后，你可能发现四十个类别是可以应付的，也可能发现工作流的准确率会受影响，因为基于规则的分类器在边缘情况下无法区分两个类别。拿工作流去检验同一个任务，能告诉你换成智能体究竟买到了什么。

自律的做法：在承诺使用智能体之前，问“试过什么工作流，为什么失败了？”如果答案是“没有试过”，就坚持先构建一个。你也许会发现工作流已经足够好地解决了问题，也可能发现工作流以某些具体的方式失败了，而智能体确实能改善这些方面。

### 危险信号 2：失败模式是可靠性，而不是能力

第 2 课说，当你需要灵活性时，智能体的不可预测性才物有所值。但灵活性在可靠性上是有代价的，本系列第 11 至 12 阶段花了好几课来点明这些代价：使用计算机的智能体中的落点定位错误（第 25 课）、一个工具的失败拖垮下一步的级联工具错误（第 28 课）、错误的说法进入对话记录，并被之后的每一轮悄悄当作事实的上下文污染（第 27 课）。

如果一个任务的失败模式是这些可靠性类别之一，而这个任务又是一个固定的、经过充分测试的工作流根本不会犯这类错误的任务，那么智能体买到的是不可预测性，代价是一个原本并不存在的可靠性问题。

例如：一个文档分类系统，必须把文档恰好路由到五个已知类别之一。智能体可以灵活地路由，甚至在读到文档中改变它想法的内容时重新分类。但如果任务是以固定的、可审计的流程对财务文档分类，而分类错误的惩罚是违反监管，那么智能体的灵活性就不值得冒这样的风险：上下文污染让智能体怀疑自己之前的推理，并把文档送到错误的类别。每份文档只做一次路由决定、可以逐步审计的工作流，牺牲了可预测性，却在重要的地方换来了可靠性。

自律的做法：对于失败代价高昂、或可靠性不容商量的任务，说出智能体会引入哪些工作流不会有的可靠性问题。如果这个问题足够严重，即使工作流感觉不那么精巧，它也是更好的选择。

### 危险信号 3：致命三要素全部具备，却没有任何收益

第 31 课点出了致命三要素：可访问私有数据、会接触不可信内容、能够向外部通信。当智能体读取不可信的输入，并且拥有可能滥用数据或把数据外泄的工具时，它就同时具备了这三个条件。

去掉任何一个条件，攻击就无法成立。但同时具备这三个条件的智能体，即使注入只是有时才会得手，也是可被利用的。第 32 课讲过，防御办法不是更用力地给模型写提示词，而是收窄工具的访问权限。

如果一个提议中的智能体同时具备三要素的全部三个条件，而这个任务又无法从智能体的不可预测性中获益，那么你买到的是可被利用性，没有任何收益。一个范围更窄的、基于工作流的集成，或一个有意缺少三个条件之一的工具集，不必拼凑出这种暴露面，就能达到同样的目标。

例如：一个内容推荐引擎，读取用户资料和外部内容源来推荐条目。如果这个引擎被实现为一个智能体，带有获取外部内容、查询用户数据，并把推荐发送到消息系统的工具，它就具备了致命三要素的全部三个条件。但如果这个引擎的工作，是根据简单的规则（如果用户看过 A，就推荐 B）从一组固定的推荐类型中挑选，那么工作流就能完成这项工作，而不会把用户数据和推荐系统暴露在一个以前并不存在的提示词注入渠道之下。

自律的做法：对三要素的每一个条件，问问这个任务是否真的需要它。如果智能体为一个并不需要智能体灵活性的任务，同时具备了这三者，就重新设计工具集，有意去掉至少一个条件。这个系统作为演示会没那么令人印象深刻，但它更难被利用，也更可靠。

### 危险信号 4：token 成本超过了任务的价值

第 33 课讲了 token 放大和单个完成任务的成本，包括多智能体的倍数。第 19 课表明，编排者与工作者系统，在 token 上比解决同一个问题的单个智能体贵好几倍。

一个具体的问题：估算单个完成任务的真实成本，包括重试、多智能体的协调（如果适用），以及上下文长度或缓存开销造成的任何 token 放大。这个成本相对于任务所产出的东西，是否可以接受？

这个问题往往要到为时已晚才会被问起。一个团队构建了智能体，上线之后，发现每个任务的成本超过了任务在业务价值上的所得。智能体能用，但运营它太贵了。

自律的做法：在承诺使用智能体（尤其是多智能体系统）之前，用原型里实际的轮次或轨迹，估算单个完成任务的 token 成本。拿这个估算去对照任务的价值。如果 token 成本超过了价值，无论这个系统多么优雅，智能体都是没有道理的。

### 综合起来：在承诺使用智能体之前，问这四个问题

1. 是否真的尝试过更简单的工作流，并发现它不够用？
2. 这个任务的失败模式，是不是智能体会引入一个工作流所没有的新可靠性问题的那种？
3. 智能体是否同时具备三要素的全部三个条件，这种暴露对任务来说是否必要？
4. 相对于任务所产出的东西，单个完成任务的 token 成本是否可以接受？

如果其中任何一个的答案是“否”或“我们不知道”，智能体可能就没有道理。对智能体说不并不是失败；而是自律。你选择的是可预测性、可靠性、安全性或成本，而不是智能体能买到的灵活性。这是一个站得住脚的选择，也正是这个选择，让你在智能体确实有道理的时候，能够有信心地说好。

## 练习

1. ▢ 一个产品团队提议构建一个智能体，为内部报告总结客户支持工单。智能体会读取工单（不可信的用户内容），访问公司的客户数据库来查找背景信息，并把摘要发布到 Slack 频道。一个工作流的替代方案，是由人手动把工单分到各个类别，然后对每个类别运行基于模板的总结器。团队说“智能体更高效”。在没有运行工作流的情况下，你应该先问什么问题？

<details markdown="1"><summary>检查</summary>

请他们真的构建工作流，并在真实的工单上测试。衡量智能体快了多少，以及效率上的提升是否值得付出 token 消耗的成本，和暴露致命三要素的风险（智能体读取不可信内容、访问私有的客户数据，并发送外部消息）。如果工作流有九成好，成本只有一成，工作流就胜出。没有测试工作流，“智能体更高效”这个说法就没有经过检验。

</details>

2. ▢ 你在评审一份提案，要做一个帮助分析师在大型代码库里调试失败测试的智能体。这个智能体可以访问仓库代码、测试结果和日志。它会调用工具来搜索代码、运行单个测试，并提交 bug 报告。提案说：“智能体可以比脚本更灵活地探索代码库。”第 27 课讲到的哪个可靠性问题，与评估这份提案有关？

<details markdown="1"><summary>提示</summary>

想想当智能体在读取工具调用的输出，并构建它对代码内容和行为的模型时，会发生什么。哪种错误模式是智能体所特有的？

</details>

<details markdown="1"><summary>检查</summary>

上下文污染（第 27 课）。如果智能体误解了某条日志或某段代码，并把一个错误的说法建进它对这个 bug 的模型里（例如“这个函数返回 None”），之后的每一步推理，都会把这个错误的说法当作既定事实。路径固定的脚本，不会这样质疑自己的输出。智能体根据新证据改变想法的灵活性是一项优势，但它也为一步步传递下去的、对错误结论悄悄的自信打开了大门。要评估的是，对这个任务的失败模式（调试一个测试）来说，灵活性（更擅长发现新奇的 bug）带来的好处更大，还是上下文污染把智能体带上错误道路的风险造成的损害更大。

</details>

3. ▢ 下面哪个场景最明显地表明，提议中的智能体是没有道理的？

    - a) 这个任务可以用工作流解决，但每当新的文档类型出现，工作流都需要接上一个新的分支
    - b) 这个任务试过用工作流做，没有达到准确率目标，但在同一个数据集上测试的智能体原型表现更好
    - c) 这个任务从没试过用工作流做，但一位利益相关者坚持认为需要智能体，因为他们看到的 AI 演示令人印象深刻
    - d) 这个任务需要读取不可信的内容并访问私有数据，但智能体的工具集有意缺少外部通信

<details markdown="1"><summary>检查</summary>

**c)** 这个场景里，任务从没试过用工作流做，而提案是被对演示的兴奋所推动，而不是因为有证据表明更简单的替代方案行不通。场景 (a) 描述的是智能体买到持续的灵活性的任务；分支数量在增长，所以智能体有道理。场景 (b) 表明工作流已经检验过并失败了，使得智能体更好的表现成为支持它的证据。场景 (d) 描述的是一种去掉了三要素之一的、经过推敲的架构，这是一个有道理的设计选择。只有 (c) 没有任何测试作为依据。

</details>

4. ▢ 你估算，某个任务的智能体每次完整运行（含重试）要花 5,000 个 token，而这个任务产出的业务价值，相当于按当前市场价格 2,000 个 token 的算力。在构建这个智能体与选择替代方案之间做出选择并为之辩护，同时说出你做这个选择所接受的代价。

<details markdown="1"><summary>检查</summary>

替代方案（工作流、更简单的系统，或让任务保持手工）是有道理的。这个智能体的成本是它价值的 2.5 倍，意味着每次运行，业务在算力上花的比它回报的价值更多。只有当你预期 token 成本会下降（更便宜的模型、缓存策略、对重复任务更快地收敛），或者业务价值比估计的更高时，仍然构建这个智能体才是站得住脚的。如果两者都不成立，自律的做法就是说不。你所接受的代价，是失去智能体本来能提供的灵活性，但你换来了可预测性和成本效益。在这样的数字下，这是正确的取舍。

</details>

## 实战练习

- [ ] 找一个你所了解的系统中，目前由智能体解决的任务。估算单个完成任务的 token 成本，以及每次完成的业务价值。这个比率可以接受吗？如果不能，要改变什么，才能让智能体变得有道理？
- [ ] 找一份提倡使用智能体的提案（内部的，或描述某个系统的文章）。追踪它是否回答了全部四个危险信号的问题：是否试过工作流、失败模式是否对可靠性敏感、三要素的三个条件是否都必要，以及成本是否可以接受？写下这份提案解决了哪些危险信号，又留下了哪些没有回答。
- [ ] 明天：设想一个你会做成智能体的产品功能。现在改把它设计成工作流。比较两者：工作流做不到、而智能体能做到的是什么？工作流要难构建多少？收益值得增加的复杂度吗？写下你诚实的评估。
