# 第 37 课：评审别人的智能体设计

**使命关联:** 成为值得信赖的人：能评审别人的智能体设计，并通过查阅一手资料来裁定关于它的有争议的说法，而不是默认站队，或含糊地和稀泥。
**主要来源:** [文章：“Building Effective Agents”，Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
**前置知识:** [第 36 课](0036-when-not-to-build-an-agent.md)

## 热身

1. ▢ 第 2 课的自主性谱系，是检验什么来区分工作流与智能体的？

<details markdown="1"><summary>检查</summary>

检验控制流是由开发者事先决定的，还是由模型在运行时决定的。不看工具的数量、复杂度，也不看涉及多少次模型调用，而是看是谁选择了路径。

</details>

2. ▢ 来自第 35 课：与从零编写运行框架相比，框架可以通过哪一种方式降低在生产中运行智能体的成本？

<details markdown="1"><summary>检查</summary>

缓存稳定的上下文（工具定义、系统提示词），这样重复的任务就不必重新发送这些 token；实现持久的状态，让被中断的运行可以恢复；提供内置的追踪和错误处理，这些靠手工接线是要花时间的。框架买到的是更快达到可靠，以及成本的降低，代价是灵活性或厂商锁定。

</details>

## 要点

### 评审清单：按顺序走过各个阶段

评审一个提议中的或已有的智能体设计时，按顺序把它走过本系列的各个阶段，在每个阶段问同一个问题：这个选择有依据吗，有记录吗？

#### 第 1 至 2 阶段：自主性谱系与控制流

这个系统在自主性谱系上处于什么位置？是单个提示词、开发者固定的工作流，还是由模型主导的智能体？在提案或文档里找这个说法。如果说法只是“这是个智能体”，却没有解释为什么需要自主性，就问问固定路径的替代方案会带来什么代价。好的设计不只是说出选择；它还为选择辩护。

#### 第 3 至 4 阶段：工具面与 schema

工具的命名和描述，是否能让模型的推理觉得有用？第 8 课讲过，工具描述是提示词界面，而不是 API 文档。工具名称应该从模型的角度描述工具做什么，而不是底层的端点。参数描述应该帮助模型决定传什么，而不只是记录技术上的 schema。工具集是否精简（避免第 9 课的膨胀），还是已经堆积了很少被用到的工具？

#### 第 5 至 6 阶段：上下文与记忆策略

对于长时间运行的任务，策略是什么？设计是否区分了草稿区（单个轮次内正在进行的对话记录）和跨运行记忆（在多次运行之间持久保存的事实）？第 11 课讲了压缩；设计是否有计划，说明随着对话记录增长该如何缩短它？如果任务涉及学习事实并把它们带到后面，是否点明了记忆机制，还是设计只依赖对话记录？

#### 第 7 阶段：反思与重试

当某一步失败时，设计是否规划了重试，是否包含显式的反思（智能体在再次尝试之前，用自然语言推理它为什么失败）？还是只是循环下去，希望模型自己纠正？第 17 课讲过，沉默并不等于学习；设计良好的智能体会在失败之后进行反思。

#### 第 8 阶段：多智能体的决定

如果设计是多智能体的，它是否对照单个智能体的替代方案，为这个选择辩护？第 19 课讲了协调成本：编排者与工作者系统会让 token 成倍增加，并在工作者之间割裂上下文。设计应该点明足以抵消这项成本的具体收益。收益是并行（实际耗时）、上下文隔离（每个工作者的对话记录保持干净），还是确实的子任务独立性？而且这项收益适用于这个具体的任务吗？

#### 第 14 阶段：安全与三要素

智能体读取不可信内容吗？它访问私有数据吗？它有外部通信吗？第 31 课讲过，三个条件同时具备，会使它可被利用。设计应该点明哪些条件存在、哪些不存在，或者设计是如何有意去掉至少一个的。如果设计三者都有，却没有承认这一点，那就是一个危险信号。

#### 第 15 阶段：成本与持久性

有没有人估算过单个完成任务的 token 成本？这个成本可以接受吗？如果系统使用了框架，这个框架选择有依据吗，还是默认选的？第 33 课讲过，每个任务的真实成本包括重试和 token 放大。好的设计会点明一个成本估算，哪怕这个估算是粗略的。

### 具体的技能：从一手资料裁定有争议的说法

本系列向你呈现了两种关于多智能体系统的、可信而相反的说法。第 18 课描述了编排者与工作者模式及其好处。第 19 课介绍了 Cognition 的论点：大多数多智能体系统并不值得它们的成本，一个工具更好的单个智能体往往胜出。

两种说法在各自的领域里都是对的。一位只对两者记得一知半解的评审者，可能会下意识地站队（“我读到单个智能体总是更好，所以这个多智能体设计是错的”），或者含糊地和稀泥（“多智能体有时是好的”）。两者都无助于推进讨论。

真正的技能是回到一手资料，检查设计的具体情况，是否符合那份资料的论点成立的条件。

Anthropic 的“How We Built Our Multi-Agent Research System”描述了一个行之有效的多智能体系统。通过阅读那篇文章，可以看出让它奏效的条件包括：子任务确实是独立的（每位研究者专注于一个单独的角度）、并行提供了真实的实际耗时上的收益（结果需要在时间压力下综合）、团队在编排上投入了大量精力，以保持工作者之间的沟通清晰。

Cognition 的“Don't Build Multi-Agents”认为，对大多数任务来说，这个成本不值得。让他们的论点最有力的条件包括：子任务共享上下文，或相互完善；你有时间和上下文预算，让单个智能体去探索顺序的路径；相对于问题本身，协调开销很高。

现在你在评审一个设计。提案说：“我们在构建一个研究系统，带有一个编排者和三个并行的研究者工作者。”在你接受或否决多智能体之前，先问：

- 这三个研究角度确实是独立的，还是共享上下文、相互完善？
- 有没有真实的实际耗时期限，还是你有时间让一个智能体按顺序探索全部三个角度？
- 团队有没有为编排工作做预算，还是把协调当成事后才想到的事？
- 一个工具更广的单个智能体，与这个多智能体系统相比，在 token 上要花多少？

设计实际的情况，决定了适用哪份资料的论点。评审者的工作，不是在两份资料之间做裁判，而是追踪设计的处境，是否符合其中一份资料的论点变强或变弱的条件。如果设计对这些问题没有答案，它就还没有从一手资料出发解决这个问题；它只是断言了这个选择。

### 一次好的设计评审能达成什么

好的评审不会说“这个好”或“这个不好”。它会说：

“这个设计选择了 X，是因为 Y。我把这个选择追溯到了本系列的第 Z 阶段，那里适用这些问题。设计清楚地回答了这些问题，而这些问题它没有解决。在承诺之前，团队应该解决尚未解决的问题，或者记录下风险。”

一份指出具体的、未回答问题的评审，比给出通过或不通过的评审更有用。它给了团队可做的事。它也给了你筹码：你可以用书面形式提出后续问题，让设计对具体的说法负责，而不只是表达怀疑。

## 练习

1. ▢ 你在评审一个处理财务文档的智能体的设计。设计说智能体可以使用：一个从云存储读取文档的工具、一个查询客户数据库交易历史的工具，以及一个把报告记入审计日志的工具。设计没有讨论安全问题。运用第 31 课的框架，你应该问什么问题？

<details markdown="1"><summary>检查</summary>

致命三要素的三个条件都存在：智能体读取不可信内容（上传的财务文档）、访问私有数据（客户的交易历史），并且可以向外部通信（提交审计报告）。好的评审会问：致命三要素的三个条件都是必要的吗？设计能去掉至少一个吗？例如，智能体能否读取文档，却不直接提交报告，而是起草报告交由人批准？或者它能否只处理汇总数据，避免触碰客户数据库？设计应该要么说明为什么三者都需要，要么记录下缓解这个风险的具体安全控制（审批关卡、审计日志、沙箱）。

</details>

2. ▢ 一个设计提议了一个编排者，带两个并行的工作者：一个研究竞争产品，另一个研究客户需求。然后工作者把发现汇报给一位人工分析师，由他综合。你怀疑单个智能体的替代方案可能更便宜。你应该问第 19 课里的哪个问题，来检验这个怀疑？

<details markdown="1"><summary>提示</summary>

想想在这个设计里，编排者在做什么，以及是否存在某件单个智能体做得没有那么好、或没有那么快的事。

</details>

<details markdown="1"><summary>检查</summary>

估算 token 成本：两个工作者智能体加上编排者的开销，与一个按顺序研究两个角度的智能体相比。两个并行的工作者，比一个按顺序运行的智能体完成得更快吗（并行的收益）？还是单个智能体把两条研究线索放在一份对话记录里，能更有效地整合它们（上下文连贯的收益）？如果工作者完成得更快，但 token 成本的倍数很高，而且人工分析师没有时间压力，那么单个智能体胜出。如果研究者急需结果，而并行节省了几个小时，多智能体就值得这笔成本。设计本该做过这个计算；如果没有，你就发现了一个尚未回答的问题。

</details>

3. ▢ 你在评审某个智能体的一个工具定义。这个工具叫 query_customer_database，描述是：“Connect to the customer database and execute any SQL query provided by the user.”

    - a) 这是个设计良好的工具，因为它的灵活性最大
    - b) 这个工具违背了最小权限；应该重新设计成只执行特定的、预先授权的查询
    - c) 这个工具是可以接受的，因为只要系统提示词告诉智能体不要滥用它，智能体就不会滥用
    - d) 只要智能体没有外部通信的能力，这个工具就是可以接受的

<details markdown="1"><summary>检查</summary>

**b)** 这个工具违背了最小权限，应该重新设计。它授予智能体宽泛的数据库访问权限，违背了第 32 课的原则：每个工具都应该恰好限定在它所需要的范围。选项 (a) 是错的：对开发者来说的灵活性，不等于好的工具设计。选项 (c) 是错的：第 31 课讲过，提示词里的指令不是对提示词注入的可靠防御；防御是架构上的。选项 (d) 是错的：去掉外部通信会打破三要素的一个条件，但相对于智能体实际需要的东西，这个工具的范围仍然过大。更好的设计：一个叫 get_customer_orders 的工具，接受 customer_id 并返回他们的订单，完全没有 SQL 注入的途径。

</details>

4. ▢ 一个团队在评审针对同一个任务的两份提案。提案 A：一个可以使用网页搜索、代码执行和文档工具的单个智能体。提案 B：一个带三个工作者（搜索专家、代码专家、文档专家）的编排者，每个工作者只有一个工具。团队读过第 19 课，意见分成了两派。两位工程师认为提案 A 更好，因为“Cognition 说单个智能体胜出”。另外两位认为提案 B 更好，因为“Anthropic 的研究系统用的是多智能体”。你被请去裁定这件事。你的第一步应该是什么？

<details markdown="1"><summary>检查</summary>

回到一手资料，而不是一知半解的摘要。重读两篇文章，找出各自描述的具体条件：在每份资料里，任务的特征、上下文预算、时间压力和协调的复杂度是怎样的？然后拿提案 A 和提案 B 去对照这些条件。它们更符合单个智能体的条件，还是多智能体的条件？提案本身是否描述了任务的特征，并对照这些条件为它们的选择辩护？你的评审应该这样说：“提案 B 符合 Anthropic 的研究系统取得成功的条件（独立的子任务、实际耗时的期限），前提是它能为协调成本辩护。提案 A 符合 Cognition 的场景（需要彼此打磨的工作、宽松的时间预算），前提是单个智能体的工具菜单足够宽，能避免工具决策的开销。”工作不是在两份资料之间做裁判，而是把每一份应用到具体的任务上。

</details>

## 实战练习

- [ ] 找一个你使用或了解的、自称为智能体的系统。试着把它对照本课的清单：它在自主性谱系上处于什么位置？工具是为模型的推理而描述的，还是当作 API 文档写的？它有没有讨论安全问题？写下系统清楚地回应了哪些清单项，又对哪些保持了沉默。
- [ ] 从第 19 课里，挑一条 Cognition 或 Anthropic 关于多智能体系统的说法。重读资料，找出这个说法成立的具体条件。写下：什么样的任务特征，使这个说法成立或不成立？你会如何在你正在设计的系统上检验这个说法？
- [ ] 明天：评审别人的智能体设计（来自工作、某个开源项目或某份技术提案）。使用本课的清单。对于设计没有完全涉及的每个阶段，写下一个尚未回答的问题。把评审分享给设计的作者，看看你的问题是否与他们自己的担忧吻合。
