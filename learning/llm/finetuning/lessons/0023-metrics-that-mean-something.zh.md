# 第 23 课：有意义的指标

</details>

## 要点

### 为什么损失不是指标

留出数据上的交叉熵损失确实有用：它便宜、稳定，是运行期间该盯着看的东西。它不是模型是否胜任你的工作的度量。

损失度量的是相对于某一个特定参考续写的“下一个 token 意外程度”。因此它会惩罚措辞不同的正确答案，奖励流畅的错误答案。两个留出集损失相等的模型，在有用程度上可以相差很大，而且方向是无法预测的。

**用损失来选择检查点。用任务指标来做决策。**

### 按任务的形状来选择

| 任务的形状 | 指标 | 要留意 |
|---|---|---|
| 分类 | 准确率；每个类别的精确率和召回率；F1 | 类别不平衡会让准确率失去意义 |
| 抽取 | 字段上的精确匹配；跨度上的 F1 | 比较之前先归一化 |
| 结构化输出 | schema 的有效率，然后是字段层面的正确性 | 两种不同的失败，两个都要度量 |
| 代码 | 针对测试的执行 | 看是否通过测试，而不是像不像参考答案 |
| 自由形式的生成 | 按评分细则打分，由人或模型来评判 | 困难的情形；见下文 |
| 与检索相关 | 接地性、引用的准确性 | 流畅会掩盖没有依据的论断 |

注意缺了什么：凡是答案可以检查的，**就去检查答案。** 执行代码。验证 schema。比较抽取出的字段。这些都便宜、客观，远胜任何相似度分数。

### 关于表面相似度的指标

BLEU、ROUGE 以及它们的同类，度量的是与参考答案的 n-gram 重合度。它们是为机器翻译和摘要而造的，用于遵循指令的任务就很弱：措辞不同的正确答案得分很低，复用了参考答案词汇的错误答案得分很高。

只有当重合度确实是你在乎的东西时才用它们，而且绝不要把它们当作唯一的指标。如果你发现自己在不是摘要的任务上优化 ROUGE，请停下来。

### 结构化输出：两种失败，两个数字

对于 JSON 或任何 schema，总是同时报告两者：

1. **有效性。** 它解析成功了吗，满足 schema 了吗？
2. **正确性。** 在解析成功的前提下，值对不对？

把两者合并，会掩盖你面对的是哪个问题。有效率 99%、正确率 60% 的模型，需要更好的数据。有效率 60%、正确率 95% 的，需要格式训练，或者在部署时用约束解码，这也许不用重新训练就能让问题消失。

### 把模型当评判者，要小心使用

对于自由形式的输出，让一个强模型按评分细则打分，往往是唯一可以规模化的选择。它行得通，也有文献记载的偏差，你必须加以控制：

- **位置偏差。** 评判者偏爱先出现的那个回复。缓解办法是随机化顺序，对于成对比较，则两种顺序都评测。
- **冗长偏差。** 不论质量如何，更长的答案得分更高。留意你的微调是不是仅仅变得更啰嗦了。
- **自我偏好。** 评判者倾向于偏爱与自己输出相似的文本。
- **对评分细则的敏感性。** 评分细则里措辞的细微变化，就会让分数发生实质性的偏移。

不容商量的一步：**对照人工标签来校准评判者。** 自己给 50 到 100 个样本打分，让评判者对同样的样本打分，并度量一致程度。如果一致性很差，评判者的数字就是摆设。如果很好，你就赢得了把它规模化的资格，还得到了一个量化你该多信任它的数字。

一个具体而稳健的搭配：对基础模型和微调后的输出做成对比较，两种顺序都评测，评分细则点明你在乎的具体标准，以胜率来报告。成对评判比绝对打分更可靠，后者会漂移。

### 要么报告不确定性，要么什么也别报告

没有波动范围的单个数字，不是结果。最低标准：

- 指标上的**置信区间**。对于比例，用自助法（bootstrap），或者用二项区间。
- 比较训练配置时用**多个随机种子**，因为运行间的方差往往比效应更大。
- 在相同的样本上做**成对比较**（第 22 课）。
- 说明这个数字是在多大的 **n** 上算出来的。

“71.2 对 70.8”不是发现。“71.2 ± 2.1 对 70.8 ± 1.9，n=340，三个随机种子”才是发现，而这个发现是：你没有检测到差异。

### 去读输出

不管你的指标是什么，每一次都要读一批实际的生成结果，包括那些失败的。指标是压缩，而被它们压缩掉的东西，通常正是你需要知道的东西：模型开始拒答了，或者输出开场白，或者截断，或者回答了一个微妙地不同的问题。没有任何汇总值能揭示这一点。十分钟的阅读可以。

## 练习

1. ▢ 两个模型的留出集损失相同。其中一个可以有用得多吗？

<details markdown="1"><summary>检查</summary>

可以。损失度量的是与某一个参考续写的一致程度，所以它惩罚措辞不同的正确答案，奖励流畅的错误答案。

损失相等，与任务表现上的巨大差异是相容的，两个方向都有可能。这就是为什么损失用来选检查点，而任务指标用来做决策。

</details>

2. ▢ 你的模型输出 JSON。你报告哪两个数字，为什么不是一个？

<details markdown="1"><summary>检查</summary>

schema 的有效率，以及有效输出中字段层面的正确率。

一个合并的数字，会掩盖你面对的是哪个问题。有效率高而正确率低，是数据问题；有效率低而正确率高，是格式问题，约束解码也许不用重新训练就能解决。

</details>

3. ▢ 你的微调的评判者得分从 6.2 升到 7.1。平均回复长度从 90 升到 340 个 token。有顾虑吗？

<details markdown="1"><summary>检查</summary>

有：冗长偏差。不论质量如何，评判者都一贯地偏爱更长的答案，所以这个增益的很大一部分可能只是长度。

要加以控制：在长度匹配的条件下比较，明确地指示评判者不考虑长度，或者检查用户是否真的更喜欢更长的输出。单看分数，分不清“更好”和“更长”。

</details>

4. ▢ 哪个指标最适合评测代码生成的微调？

    - a) 与所给参考实现的 ROUGE
    - b) 针对每道题的测试集执行
    - c) 代码 token 上的留出集交叉熵损失
    - d) 由模型评判者给可读性和正确性打分

<details markdown="1"><summary>检查</summary>

**b)** 针对每道题的测试集执行。

代码有客观的正确性标准，所以就用它。重合度指标奖励的是像参考答案，而不是能工作；损失也有同样的问题；当你可以直接运行代码时，评判者是不必要的间接。

</details>

5. ▢ 哪一步能赢得把模型评判者规模化使用的信任资格？

<details markdown="1"><summary>检查</summary>

对照人工标签来校准它：自己给 50 到 100 个样本打分，并度量与评判者在同样条目上的一致程度。

没有这一步，评判者的数字就没有经过验证。有了它，你既有了依据，也有了量化的信任程度。

</details>

6. ▢ 你的分类器微调报告了 94% 的准确率。在相信它意味着什么之前，你需要知道什么？

<details markdown="1"><summary>检查</summary>

类别的分布。如果 94% 的样本属于同一个类别，一个永远猜那个类别的模型就能得 94%，却什么也没学到。

报告每个类别的精确率和召回率，或者一个均衡的指标。在不平衡的数据上，准确率是常用数字里最具误导性的之一。

</details>

## 实战练习

- [ ] 选定你的主要指标，写一段话论证它为什么度量了你在乎的东西。指出它遗漏了什么。
- [ ] 为你当前的指标计算置信区间。判断你的留出集是否能支撑你想要的比较。
- [ ] 如果用模型评判者：手工标注 50 个样本，让评判者对同样的样本打分，并报告一致程度。
- [ ] 明天：阅读二十条实际的生成结果，包括每一个失败的。写下指标没有告诉你的一件事。
