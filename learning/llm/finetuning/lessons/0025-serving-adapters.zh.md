# 第 25 课：部署适配器

**使命关联:** “把它发布出去”写在使命里。躺在目录里的适配器，不算发布。

## 热身

1. ▢ 哪种部署选择，让灾难性遗忘变得无关紧要？

<details markdown="1"><summary>检查</summary>

保持适配器不合并，只把相关的请求路由给它，让未被触动的基础模型继续服务其他一切。

</details>

2. ▢ 针对量化基础模型训练出来的适配器，应该合并到哪里？

<details markdown="1"><summary>检查</summary>

合并进全精度的基础模型，如果需要量化的产物，之后再量化。

</details>

3. ▢ 验证合并时，为什么用贪心解码？

<details markdown="1"><summary>检查</summary>

这样任何输出上的差异，都能归因于权重，而不是采样。

</details>

## 要点

### 三种部署形态

**合并的模型。** 一个产物，与任何其他模型没有区别。任何部署栈都能加载它。没有任何适配器机制。

**不合并，单个适配器。** 基础模型加上在加载时应用的适配器。每个被适配的层多出两次小的矩阵乘法。

**不合并，多个适配器。** 内存里一个基础模型，多个适配器，按请求选择。正是这种形态，让适配器在经济上变得有意思，它需要明确的运行时支持。

### 选择

| | 合并 | 不合并，多适配器 |
|---|---|---|
| N 个任务的内存 | N 个完整的模型 | 一个基础模型 + N 个小适配器 |
| 每个请求的开销 | 无 | 很小，在混合批处理下更大 |
| 部署栈 | 任何 | 必须支持适配器 |
| 切换任务 | 加载另一个模型 | 改一个请求字段 |
| 新增任务 | 部署另一个模型 | 放进一个文件 |
| 基础模型仍可用 | 否 | 是 |
| 回滚 | 重新部署 | 停止向那个适配器路由 |

决策规则：**一个任务、运维简单 → 合并。多个任务，或者仍需要基础模型 → 不要合并。**

最后一行被低估了。有了不合并的适配器，回滚一个糟糕的微调，是一次路由变更，而不是一次部署，而基础模型始终都在那里，作为后备。

### 多适配器部署是怎么工作的

朴素的做法，在请求之间切换适配器权重，会让一切串行，毁掉吞吐，因为推理的效率就来自批处理。

真正的实现，会把使用*不同*适配器的请求一起放进一个批次。基础模型的计算对整个批次是共享的，因为对每个人都一样，而适配器的贡献则按请求计算，用的是专门的内核，处理一批小而异构的矩阵乘法。S-LoRA 这项工作（[arXiv:2311.03285](https://arxiv.org/abs/2311.03285)）是并发部署众多适配器的参照点，其中包括把不活跃的适配器保存在主机内存里，需要时再换入。

这在实践中意味着：

- 从一个基础模型部署几十个适配器，是已经解决的问题，有真正的实现，而不是研究设想。
- 开销很小，但是真实存在的，而且会随着一个批次里出现的*不同*适配器的数量而增长。
- 适配器应尽可能共享秩和目标模块。异构的形状更难高效地批处理。

在 vLLM 里，大致的做法是：启用 LoRA 支持，注册适配器，并在每个请求里指明一个。请对照所安装版本的文档，检查当前的开关以及最大秩和最大适配器数的限制，因为这块接口会变，而且限制是在服务器启动时设定的。

### 部署时的量化，单独来看

这是一个独立于上述一切的决定，值得重申，因为两者经常被混为一谈：

- **训练时的量化**（第 4 阶段）是训练运行的内存预算。
- **部署时的量化**缩小你部署的模型，它的质量代价对每个请求都是永久的。

你可以针对 4 位的基础模型训练，却以 bf16 部署。你也可以用 bf16 训练，却以量化部署。它们是互不相关的选择，权衡也互不相关，任何一个都不蕴含另一个。

如果你以量化部署，就要评测量化后的产物。评测 bf16 的模型，却发布 4 位的模型，意味着你的数字描述的是你没有部署的东西，这是一个出人意料地常见的错误。

### 运维要点

**每样东西都做版本管理。** 基础模型及其版本、适配器、分词器、部署栈。一条响应应该能追溯到产生它的确切配置。

**固定采样参数。** 温度、top-p、最大 token 数、停止序列。它们改变输出质量的程度，与微调不相上下，而一个没有文档记录的默认值漂移，会被误诊为模型退步。

**记录输入和输出。** 生产流量是你下一份训练集和下一份留出集的最佳来源，因为它取自真实的分布，而不是你想象中的那个。遵守显而易见的隐私和保留方面的约束；关键是有意地收集，而不是日后才发现自己没收集。

**监控分布，而不只是延迟。** 输入长度、输出长度、拒答率、schema 的有效率。输入分布的漂移，是你的微调所依据的假设已经过期的领先指标。

**保持基础模型可达。** 无论是作为后备路由、对比端点，还是两者兼有。能在生产中对基础模型和微调模型做 A/B 对比，是关于微调是否有帮助的最有力的证据。

### 采样不是修复

有一点要提醒，因为这是常见的陷阱。如果微调表现不佳，温度和 top-p 不是修复手段。它们改变的是分布的形状，而不是它的内容。调整采样来补偿训练上的问题，会把问题藏起来，并让下一次比较无法解读：你不再知道，是两个变量中的哪一个造成了差异。

训练上的问题，在训练里修。固定采样，别去碰它。

## 练习

1. ▢ 五个任务，一个基础模型。合并还是不合并，这个选择要付出什么代价？

<details markdown="1"><summary>检查</summary>

不合并。内存里一个基础模型加五个小适配器，对比五份完整的模型副本。

代价：部署栈必须支持适配器，并且有一个很小的每请求开销，它随一个批次里不同适配器的数量增长。

</details>

2. ▢ 为什么在请求之间朴素地切换适配器，会毁掉吞吐？

<details markdown="1"><summary>检查</summary>

它按适配器把请求串行化，阻碍了推理效率所依赖的批处理。

真正的实现，会把使用不同适配器的请求一起放进批次，共享基础模型的计算，并按请求用专门的内核计算适配器的贡献。

</details>

3. ▢ 你针对 4 位的基础模型训练。你必须以 4 位部署吗？

<details markdown="1"><summary>检查</summary>

不必。训练精度和部署精度是相互独立的。合并进全精度的基础模型，如果你有内存，就以 bf16 部署。

训练时的量化，是这次运行的预算。它不必跟着产物进入生产。

</details>

4. ▢ 你的微调在生产中表现不佳。一位同事建议降低温度。评估一下。

<details markdown="1"><summary>检查</summary>

它也许能改善输出，却没有解决问题。采样是对模型产出的分布重新塑形；它无法添加模型本来缺乏的能力。

更糟的是，它引入了第二个被改变的变量，所以下一次比较无法解读。固定采样，诊断训练。

</details>

5. ▢ 不合并部署的哪个优势，在运维上最重要？

    - a) 服务多个任务时内存占用减少
    - b) 通过修改一条路由规则就能回滚
    - c) 完全没有任何每请求的计算开销
    - d) 与现有的每一个推理服务器都兼容

<details markdown="1"><summary>检查</summary>

**b)** 通过修改一条路由规则就能回滚。

（a）是真实的，也往往是最醒目的理由，但（b）才是凌晨两点你想要的。（c）是错的，因为不合并会增加少量开销。（d）刚好反了；合并才是普遍兼容的选项。

</details>

6. ▢ 你以 bf16 评测，却发布了 4 位量化的模型。错在哪里？

<details markdown="1"><summary>检查</summary>

你的数字描述的是一个你没有部署的模型。部署时的量化，对每个请求都带有永久的质量代价，而它从未被度量过。

评测你发布的那个产物。永远如此。

</details>
