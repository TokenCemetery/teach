# 第 26 课：成本、延迟与吞吐

**使命关联:** “度量它在质量和延迟上付出了什么代价”在成功标准的清单上。微调常常是一个关于*成本*的决策，而这一课就是它背后的算术。
**主要来源:** [博客：“LLM Inference Performance Engineering: Best Practices”，Databricks](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices)
**前置知识:** [第 25 课](0025-serving-adapters.md)

## 热身

1. ▢ 支持不合并部署的运维论据是什么？

<details markdown="1"><summary>检查</summary>

回滚是一次路由变更，而不是一次部署，而未被触动的基础模型，仍可作为后备和对比的基准点。

</details>

2. ▢ 为什么必须评测你发布的那个产物？

<details markdown="1"><summary>检查</summary>

部署时的量化，对每个请求都带有永久的质量代价。bf16 模型的数字，描述不了 4 位的部署。

</details>

3. ▢ 微调不擅长教什么？

<details markdown="1"><summary>检查</summary>

新的事实、原本缺乏的推理能力、最新的信息、精确的计算。

</details>

## 要点

### 推理的两阶段形态

生成有两个阶段，它们的性能特征完全不同，把它们混淆，会让每一场关于优化的讨论都不成体系。

**预填充**一次处理整个输入提示词。所有 token 都已就绪，所以工作是大规模的并行矩阵乘法，使它**受计算限制**。成本随提示词长度而变。

**解码**一次生成一个 token，每个都依赖前一个。每一步都要读取整个模型的权重，只为产出一个 token，所以每搬运一个字节所做的算术很少，使它**受内存带宽限制**。成本随输出长度而变。

![八个提示词 token 都汇入预填充那一行的一次传播，对比解码那一行的四次相互串联的传播，每个输出 token 一次。](images/one-pass-or-one-each.svg)

上面一行一个方框，对比下面一行四个方框，就是全部的不对称。拉长提示词，会让那一次传播变宽；拉长输出，则会给链条添加方框。

后果：

- **长提示词按 token 算很便宜；长输出按 token 算很贵。** 不对称，而且这种不对称很大。
- 解码速度由内存带宽决定，所以更小的模型几乎按其大小的比例变快。
- 批处理对解码的帮助极大，因为权重对整个批次只读一次，而对预填充的帮助要小得多。

### 要紧的指标

| 指标 | 含义 | 由什么决定 |
|---|---|---|
| 首 token 时间 | 预填充的延迟 | 提示词长度、计算 |
| token 间延迟 | 每个输出 token 的用时 | 内存带宽、模型大小 |
| 总延迟 | 端到端 | 两者，加上排队 |
| 吞吐 | 所有请求合计的每秒 token 数 | 批处理的效率 |
| 每请求成本 | 钱 | 吞吐和硬件成本 |

延迟和吞吐通过批大小互相取舍。更大的批次提高吞吐，也提高每请求的延迟。没有唯一的最佳设置：这取决于是否有人在等。

### 微调在哪里改变了经济账

这是人们错过的部分。微调在成本上的好处，通常与权重变得更好无关。

**更短的提示词。** 微调后的模型不需要少样本示例、不需要冗长的格式说明、不需要精心设计的系统提示词，因为这些行为已经在权重里了。如果你的提示词从 2,000 个 token 降到 200 个，你就从每一个请求里，永远去掉了 1,800 个 token 的预填充。在高流量的端点上，这往往就是全部的商业论证。

**更短的输出。** 训练过要按所需格式作答的模型，不再用开场白和含糊其辞来凑数。因为解码是昂贵的阶段，缩短输出长度，按每个 token 算，比缩短输入长度更值。

**更小的模型变得够用。** 这个论证最强的版本：在你狭窄的任务上，能与通用大模型打平的微调小模型，每个请求的成本低得多，延迟也更低，因为解码受带宽限制，而带宽随大小而变。把大的通用模型换成小的专用模型，是数量级的节省所在。

**更少的重试。** 如果通用模型有 15% 的时候产出无效输出，而你重试，你真正的成本是看得见的成本的 1.15 倍。一个达到 99% 有效率的微调，几乎能把这些都去掉。

### 诚实的核算

对照这些节省，数一数成本：

| 成本 | 性质 |
|---|---|
| 训练算力 | 每个版本一次性的，对适配器来说通常很小 |
| 数据的创建 | 往往是主要成本，而且通常是人力时间 |
| 评测基础设施 | 一次性的，之后是持续的维护 |
| 部署的复杂度 | 持续的：支持适配器的栈、版本管理、路由 |
| 重新训练 | 持续的：模型、数据和需求都在变 |
| 专业能力 | 持续的：必须有人负责 |

**决定结果的是那些反复出现的成本，而它们恰恰是初步估算时被漏掉的。** 一个每个请求只省一点点钱、又需要一个人来维护的微调，在低流量时是糟糕的交易，在高流量时是好交易。交叉点是算术，所以就去算。

### 一个算例

假设一个通用大模型，提示词 2,000 个 token，对比一个微调的小模型，提示词 200 个 token，两者都产出 150 个输出 token。

```text
General:  2000 prefill + 150 decode, on a large model
Tuned:     200 prefill + 150 decode, on a small model
```

提示词节省的是 1,800 个预填充 token。模型大小的节省适用于两个阶段，尤其是解码的带宽成本。乘以请求量，再对照上面的固定成本和反复出现的成本，你得到的就是一个实际的答案，而不是一种直觉。

每天一千个请求，也许收不回数据工作的投入。一百万个，很可能收得回。**请求量是决定性的变量，也是最少被说出来的那一个。**

### 要测量，不要建模

上面这一切，形状是对的，精度是错的。实际的数字取决于硬件、部署栈、批大小、序列长度和流量模式，其方式是任何公式都无法概括的。去测量：

- 在你真实的提示词长度下，测首 token 时间和 token 间延迟
- 在几种批大小下测吞吐，找出你的延迟与吞吐的平衡点
- 在你真实的流量形态下，测每千个请求的成本
- 对你拿来比较的替代方案，也做同样的三项

而且要在真实的负载下测量。一次只发一个请求的基准测试，对批处理的生产端点什么也说明不了，因为批处理是吞吐的主导因素。

## 练习

1. ▢ 哪个阶段受计算限制，哪个受带宽限制，由此得出什么？

<details markdown="1"><summary>检查</summary>

预填充受计算限制，因为整个提示词是并行处理的。解码受内存带宽限制，因为每一步都要读取全部权重来产出一个 token。

由此得出：长提示词按 token 算相对便宜，长输出很贵，批处理对解码的帮助远大于预填充，更小的模型几乎按大小的比例加速解码。

</details>

2. ▢ 你的微调把提示词长度从 1,800 个 token 降到 150，输出长度不变。节省来自哪里？

<details markdown="1"><summary>检查</summary>

预填充：每个请求少了 1,650 个 token 的、受计算限制的工作。原先由少样本示例和格式说明规定的行为，现在存在于权重里。

这往往就是微调全部的经济论证，而且与模型变得更聪明毫无关系。

</details>

3. ▢ 微调的哪项好处带来最大的成本降低？

    - a) 提示词缩短了一千个 token
    - b) 更小的模型变得足以胜任这个任务
    - c) 输出缩短了五十个输出 token
    - d) 重试率从百分之十五降到百分之一

<details markdown="1"><summary>检查</summary>

**b)** 更小的模型变得足以胜任这个任务。

它同时降低了两个阶段，而解码这个昂贵的阶段，因为受带宽限制，随模型大小而变。其他几项是真实的，也是可以叠加的，但模型大小的改变，是对一切成倍起作用的。

</details>

4. ▢ 哪些成本最常被初步估算遗漏？

<details markdown="1"><summary>检查</summary>

反复出现的那些：随着模型和需求的变化而重新训练、部署的复杂度、评测的维护，以及负责它的人的专业能力。

适配器的训练算力很便宜，所以被拿来说。持续的人力成本很贵，却被忘了，而它通常才是决定这个问题的东西。

</details>

5. ▢ 你测量了单个请求的延迟，得出结论说你的端点足够快。错在哪里？

<details markdown="1"><summary>检查</summary>

生产环境是分批处理并发请求的。批大小主导着吞吐和每请求的延迟，而单个请求的测量，两者都观察不到。

要在真实的并发下测量，用几种批大小，并有意地在延迟与吞吐的曲线上选定你的点。

</details>

6. ▢ 同一个任务，每个请求节省的相同，每天 500 个请求对比 500 万个。决策相同吗？

<details markdown="1"><summary>检查</summary>

不相同。数据创建、评测、部署复杂度和维护的固定成本与反复出现的成本，基本上与请求量无关，而节省则随之增长。

每天 500 个时，反复出现的人力成本几乎肯定占主导。500 万个时，它相对于节省可以忽略。请求量是决定性的变量，应该出现在方案的第一句话里。

</details>

## 实战练习

- [ ] 在你真实的提示词长度下，测量你的模型的首 token 时间和 token 间延迟。
- [ ] 在批大小 1、4、16 和 64 下测量吞吐。画出延迟与吞吐的取舍，选定你的点。
- [ ] 计算你微调后的路径和替代方案每千个请求的成本。把反复出现的成本也算进去。
- [ ] 明天：找出你的微调收支相抵的请求量。与你的实际请求量比较。
