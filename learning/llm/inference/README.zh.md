# 学习：推理服务

学会为一个真实的模型搭起推理服务器，先在 GPU 上，再依次在 CPU/边缘上，并为它所产生的延迟和吞吐量数字辩护，而不是照搬框架的默认值碰巧给出的那些数字。

**最新课程：** [25. 评审一份服务配置](lessons/0025-reviewing-a-serving-configuration.md)

## 成功的标准

- 为给定的模型搭起一套服务栈（GPU 上用 vLLM，然后在 CPU/边缘上用 llama.cpp），并让它响应请求。
- 针对给定的批大小和模型，给出一个 p99 延迟预算，并从产生它的 KV 缓存、批处理和量化选择出发，为这个数字辩护。
- 评审别人的服务配置，并具体说出它要付出什么代价（一个与所述工作负载的瓶颈不匹配的参数、一个没有瓶颈来证明其合理的拓扑、一次在途中让调用方出问题的上线），而不是只说它感觉不对。

## 约束

- 假定你能自如地运行 Python 机器学习环境，并对语言模型是什么有基本了解；不需要事先有服务基础设施的经验。
- 核心服务栈：vLLM（GPU）和 llama.cpp（CPU/边缘），按这个顺序讲。其他服务栈（TGI、TensorRT-LLM）只在某个概念的迁移方式不同时才会提到。

## 范围之外

- 训练或微调模型或适配器：见 [`llm/finetuning`](../../llm/finetuning/)（第 0025 课，部署适配器，以及第 0026 课，成本、延迟与吞吐），这里链接过去，而不重述。
- 判断输出质量，或为所服务的模型搭建评测：这条边界见 [`llm/evals`](../../llm/evals/)。
- 量化方法如何起作用，以及如何评判它们，从数字格式和仿射映射，到 GPTQ、AWQ、SmoothQuant、QAT，再到度量质量损失：见 [`llm/quantization`](../../llm/quantization/)。这里的第 3 阶段保留的是服务上的决策，也就是针对延迟预算挑选一个方案，并链接到那边去了解基础；这条边界在量化系列写成时就已划定。
- 从提示词一侧请求结构化输出：见 [`llm/prompting`](../../llm/prompting/)。本系列负责约束解码，也就是同一目标在服务一侧的做法。

## 学习路线

共十四个阶段，从第一个请求，到一套被辩护的、集群规模的、有生产监控的、并经过评审的服务配置。一个阶段包含若干课程，边界并不严格；一个阶段是否完成，取决于能力，而不是课程数量。

| 阶段 | 课程 | 内容 | 完成的标志 |
|---|---|---|---|
| 1. KV 缓存 | 0001 至 0003 | 自回归生成为什么昂贵、缓存用内存换掉了什么、缓存大小如何随上下文和批次增长 | 能针对给定的上下文长度和批大小，计算出模型的 KV 缓存内存占用 |
| 2. 批处理 | 0004 至 0006 | 静态批处理与连续批处理、请求调度、吞吐量与延迟的权衡 | 能针对一个给定的工作负载，为一套批处理配置辩护 |
| 3. 服务时的量化 | 0007 至 0009 | 推理时的 int8/int4/AWQ/GPTQ、精度、速度与内存的权衡 | 能选定一个服务时的量化方案，并为这个权衡辩护 |
| 4. 实践中的 vLLM | 0010 至 0012 | 搭起 vLLM、PagedAttention、真正重要的调优参数 | 一套 vLLM 服务栈正在运行，并在响应真实请求 |
| 5. CPU/边缘上的 llama.cpp | 0013 至 0015 | GGUF、llama.cpp 的架构、离开 GPU 之后有什么变化 | 一套 llama.cpp 服务栈在 CPU 上运行，并在响应真实请求 |
| 6. 延迟预算 | 0016 至 0017 | p99 的测量方法，把这个数字追溯到缓存、批处理和量化的选择上 | 能端到端地给出并辩护 p99 延迟预算 |
| 7. 推测解码 | 0018 | 草稿模型、n-gram、Medusa 和 EAGLE 推测解码 | 能说清为什么并行验证几乎免费，并为一个工作负载选定一种推测解码变体 |
| 8. 服务时的采样与约束解码 | 0019 | 共用批次中逐请求的采样参数、基于有限状态机索引的约束解码 | 能说清为什么约束解码的保证是结构性的，以及为什么它每个 token 的开销依然很小 |
| 9. 前缀缓存 | 0020 | 自动前缀缓存作为跨请求的块共享、长文档与多轮对话的工作负载、它只加快预填充的局限 | 能说清前缀缓存何时对一个工作负载有帮助，以及为什么它从不加快解码 |
| 10. 多 GPU 与多节点并行 | 0021 | 张量并行在第 12 课那个单一参数背后的真实机制、流水线并行，以及判断一个部署需要其中哪一种（或两者都要）的决策流程 | 能说清张量并行的合并步骤和流水线气泡各自要付出什么代价，并针对给定的互连和节点数选出合适的切分方式 |
| 11. 集群级服务 | 0022 | 由缓存局部性提供信息的请求路由、由队列深度驱动的自动扩缩容，以及为什么冷启动的模型加载时间，限制了一个新副本多快才能真正派上用场 | 能说清路由、自动扩缩容和冷启动延迟，为什么必须作为一条流水线来考虑，而不是分开调优 |
| 12. 生产环境的可观测性与成本 | 0023 | 持续导出的指标、把指标变成目标的 SLI/SLO/错误预算，以及由实测吞吐量推导出的每百万 token 成本 | 能通过引用一套生产配置的 p99、它所对照的 SLO 和错误预算，以及它每百万 token 的成本，来为它辩护 |
| 13. 服务时的长上下文 | 0024 | RoPE 缩放对比滑动窗口注意力和注意力汇聚点，以及它们各自究竟对第 2 课的缓存增长公式做了什么 | 能说清一种长上下文技术，是扩展了可用长度，是把缓存大小限制在一个常数上，还是修复了被限制的缓存的失败模式 |
| 14. 判断 | 0025 | 评审别人的配置中不匹配的参数、穿过别人所依赖之物的安全上线，以及说出推测解码何时不是白赚的收益 | 值得信任去评审一份服务配置，并说出每个选择要付出什么代价，而不只是说它感觉不对 |

| [0018](lessons/0018-speculative-decoding.md) | 推测解码 | 在一次并行前向计算中验证若干候选 token，开销大致相当于正常生成一个 token，因为解码的瓶颈在于搬运权重而不是算术，这是推测解码的每一种变体都建立在其上的那个事实 |
| [0019](lessons/0019-sampling-and-constrained-decoding-at-serve-time.md) | 服务时的采样与约束解码 | 一个连续批次已经让许多请求共用一次前向计算，而给每个请求各自的采样设置，或者强制其中某个请求只能产出合法的 JSON，都必须在同一次共用计算内部逐行完成，同时不拖慢其他所有人 |
| [0020](lessons/0020-prefix-caching.md) | 前缀缓存 | 第 11 课让同一个请求的并行样本共享一个提示词的缓存块；前缀缓存是把同样的共享用在原本互不相关的请求之间，它加快的恰好是冗余预填充所浪费的那个阶段，从不加快生成答案的那个阶段 |
| [0021](lessons/0021-tensor-and-pipeline-parallelism.md) | 张量并行与流水线并行 | 第 12 课把 tensor-parallel-size 点名为把模型切分到多块 GPU 上的参数；本课打开这种切分在一层内部究竟做了什么，介绍作为同一问题的另一种切分方式的流水线并行，并给出一个决策流程，判断工作负载究竟需要其中哪一种（或两者都要） |
| [0022](lessons/0022-fleet-level-serving.md) | 集群级服务 | 第 5 课的调度器为单台服务器的队列挑选下一个请求；集群在此之前又增加了一个决策，即请求究竟交给哪台服务器，再加上何时增加更多服务器的决策，以及一个冷启动的代价，它让刚加入的服务器在几十秒内毫无用处 |
| [0023](lessons/0023-production-observability-and-cost.md) | 生产环境的可观测性与成本 | 第 17 课为一套配置辩护了一个实测的 p99 数字；本课讲的是，要自动发现退化，必须持续导出什么，把“够好了”变成目标而不是感觉的 SLO 和错误预算，以及必须与 p99 一起而不是代替它来辩护的每百万 token 成本 |
| [0024](lessons/0024-long-context-at-serve-time.md) | 服务时的长上下文 | 第 2 课的容量公式让内存随上下文长度线性计费；RoPE 缩放扩展了上下文能有多长，却完全不改变这笔费用，而滑动窗口注意力和注意力汇聚点则通过把上下文长度限制在一个常数上，改变了公式本身 |
| [0025](lessons/0025-reviewing-a-serving-configuration.md) | 评审一份服务配置 | 评审别人的服务配置，并具体说出它要付出什么代价（一个与所述工作负载的瓶颈不匹配的参数、一个没有瓶颈来证明其合理的拓扑、一次在途中让调用方出问题的上线），而不是只说它感觉不对 |

## 使用方式

每节课都简短且自成一体。答案默认折叠：先自己回忆，再展开查看。真实场景中的练习比阅读更重要，而把练习间隔开来正是关键。课程结束时仍不清楚的地方，值得先追溯到一手资料再继续往下学。
