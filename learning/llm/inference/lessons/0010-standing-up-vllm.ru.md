# Урок 10. Запуск vLLM

**Связь с целью курса:** Каждая формула из этапов с 1 по 3, объём кеша, размер батча, схема квантизации, в этом уроке становится реальным флагом реальной команды; здесь арифметика превращается в сервер, отвечающий на запросы.
**Первоисточник:** [Документация: vLLM Documentation, vLLM Project](https://docs.vllm.ai/en/latest/)
**Предварительные требования:** [Урок 9](0009-picking-a-quantization-scheme.md), [KV-кеш](../GLOSSARY.md)

## Разминка

1. ▢ Сервер превышает свой бюджет задержки при текущем размере батча. Какой флаг, исходя из рассуждений урока 6, нужно проверить первым?

<details markdown="1"><summary>Проверка</summary>

Настройку максимального размера батча: наибольший размер батча, всё ещё удовлетворяющий бюджету задержки, это то, что защищал урок 6, поэтому именно этот параметр напрямую им управляет.

</details>

2. ▢ Почему выбор fp8 для KV-кеша при обслуживании, вместо точности собственных весов модели, вообще может иметь смысл (урок 3)?

<details markdown="1"><summary>Проверка</summary>

Точность кеша это рычаг, не зависящий от точности собственных весов модели. Уменьшение `bytes_per_value` кеша вдвое вдвое сокращает его объём, без изменения самой модели, возвращая ёмкость так же, как её вернула бы меньшая модель.

</details>

## Что нужно знать

### Установка vLLM

vLLM устанавливается как пакет Python, `pip install vllm`, и требует GPU с поддержкой CUDA; это половина цели этого рабочего пространства, относящаяся к GPU, а llama.cpp, который покрывает CPU и периферию, идёт на следующем этапе. Установка автоматически подтягивает подходящий PyTorch и инструментарий CUDA для распространённых конфигураций, и стоит сверить его с версией установленного драйвера CUDA, прежде чем считать, что неудачная установка вызвана чем-то другим.

### Запуск сервера

`vllm serve <model>` запускает совместимый с OpenAI HTTP-сервер для указанной модели (локальный путь или идентификатор в Hugging Face Hub), по умолчанию слушающий порт 8000:

```text
vllm serve meta-llama/Llama-2-7b-hf
```

Эта единственная команда выполняет скачивание (если нужно), загрузку весов и запуск сервера, то есть то, о последствиях чего для памяти и задержки рассуждали все уроки этапов с 1 по 3.

### Отправка запроса

Поскольку сервер говорит в форме API OpenAI, запрос выглядит как любой вызов chat completion OpenAI, только нацеленный на локальный сервер:

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "meta-llama/Llama-2-7b-hf", "messages": [{"role": "user", "content": "Say hello"}]}'
```

### Где уже изученные понятия проявляются как флаги

Командная строка это место, где этапы с 1 по 3 перестают быть арифметикой и становятся конфигурацией:

- `--max-num-seqs`: предел размера батча, который урок 6 учил защищать относительно бюджета задержки.
- `--kv-cache-dtype`: точность кеша, которую урок 3 ввёл как рычаг, не зависящий от собственных весов модели (например, `fp8`).
- `--quantization`: называет схему, например `gptq` или `awq`, выбору и защите которой учили уроки с 7 по 9, при обслуживании уже квантизованного чекпоинта.
- Непрерывный батчинг и чанкованный префилл (уроки 4 и 5) включены по умолчанию; флага, выключающего базовый механизм, нет, есть только те, что настраивают вокруг него, например размер чанка.

## Практика

1. ▢ Команда запускает `vllm serve some-model --max-num-seqs 32 --kv-cache-dtype fp8`. В терминах уроков 6 и 3, чем на самом деле управляет каждый из этих двух флагов?

<details markdown="1"><summary>Проверка</summary>

`--max-num-seqs 32` ограничивает размер батча числом 32, то есть числом, которое урок 6 защищал бы относительно заявленного бюджета задержки и потолка ёмкости из урока 2. `--kv-cache-dtype fp8` хранит KV-кеш в fp8 вместо значения по умолчанию, вдвое уменьшая его размер на токен независимо от точности собственных весов модели, ровно тот рычаг, который описал урок 3.

</details>

2. ▢ Команда запускает сервер командой `vllm serve some-model`, вообще не указывая флаг `--quantization`. В какой точности сервер обслуживает модель и почему?

<details markdown="1"><summary>Проверка</summary>

В той, в которой сохранён сам чекпоинт, чаще всего fp16 или bf16, поскольку никакая схема квантизации не запрашивалась. `--quantization` применяется только при обслуживании чекпоинта, квантизованного заранее, или такого, который флаг велит vLLM квантизовать при загрузке; без него ничего не квантизуется.

</details>

3. ▢ Предскажите, прежде чем проверять: после успешного запуска `vllm serve` какая единственная часть информации из запроса curl в разделе «Что нужно знать» этого урока должна совпадать с тем, с чем реально запущен сервер, иначе запрос завершится ошибкой?

<details markdown="1"><summary>Подсказка</summary>

Посмотрите на поле `"model"` в команде curl.

</details>

<details markdown="1"><summary>Проверка</summary>

Поле `"model"` в теле запроса должно совпадать с именем (или путём) модели, с которой запущен сервер. Сервер обслуживает одну модель за раз; указание другой в запросе чаще всего и даёт ошибку в остальном корректно составленного вызова.

</details>

4. ▢ Какое утверждение верно о поведении vLLM по умолчанию, когда не заданы флаги батчинга или кеша?

    - a) Он откатывается к статическому батчингу, пока не задан `--max-num-seqs`
    - b) Непрерывный батчинг и чанкованный префилл работают по умолчанию; флаги лишь донастраивают их
    - c) Он отказывается запускаться, пока явно не выбран тип данных KV-кеша
    - d) По умолчанию он обслуживает в самой низкой точности, которую поддерживает оборудование

<details markdown="1"><summary>Проверка</summary>

**b)** Непрерывный батчинг и чанкованный префилл это механизм по умолчанию, а не то, что включает флаг; доступные флаги настраивают параметры вокруг них, например максимальный размер батча или размер чанка. (a) неверно: отката к статическому батчингу нет. (c) неверно: если тип данных кеша не назван, используется значение по умолчанию. (d) неверно: по умолчанию используется собственная сохранённая точность чекпоинта, а не самая низкая, которую поддерживает оборудование.

</details>

## Практика в реальной работе

- [ ] Установите vLLM (`pip install vllm`) на машину с GPU с поддержкой CUDA и запустите `vllm serve` с небольшой моделью, которую вы можете позволить себе скачать.
- [ ] Отправьте запрос curl из этого урока на ваш работающий сервер и убедитесь, что вы получаете реальное завершение, а не ошибку.
- [ ] Завтра: перезапустите сервер с `--max-num-seqs`, установленным в малое число (например, 2) и в большое, и посмотрите, заметна ли разница в том, как он ведёт себя при нескольких одновременных запросах.
