# पाठ 13. GGUF

**मिशन से संबंध:** यह workspace का CPU और edge की ओर मुड़ना है: GGUF वह format है जिससे llama.cpp असल में serve करता है, और यह समझना कि वह क्या समेटता है और कैसे load होता है, चरण 5 में जो कुछ आता है उसकी ज़मीनी मंज़िल है।
**मुख्य स्रोत:** [Repo: llama.cpp, ggml-org](https://github.com/ggml-org/llama.cpp)
**पूर्व-आवश्यकताएँ:** [पाठ 12](0012-vllm-tuning-knobs.md), [KV cache](../GLOSSARY.md)

## वार्म-अप

1. ▢ Model के weights quantize करने से ख़ासकर decode ही तेज़ क्यों होता है?

<details markdown="1"><summary>जाँचें</summary>

Decode memory-bandwidth bound है: हर step weights को memory से वापस पढ़ता है, और छोटा quantized footprint उस memory traffic को सीधे घटाता है।

</details>

2. ▢ GPTQ और AWQ (पाठ 7) में इस बात का मुख्य फ़र्क़ क्या है कि वे किन weights को quantization त्रुटि से बचाना तय करते हैं?

<details markdown="1"><summary>जाँचें</summary>

GPTQ column-दर-column quantize करता है और बाद में layer के बचे, अभी quantize न हुए हिस्से को सुधारता है। AWQ पहले activation magnitudes पर calibrate करता है और quantize करने से पहले ही सबसे संवेदनशील channels को बचाता है।

</details>

## यह जानें

### कई files की जगह एक file

Hugging Face ecosystem से serve होने वाला model, जो आकार vLLM उम्मीद करता है, आम तौर पर कई files में आता है: weights ख़ुद, architecture बताने वाली `config.json`, एक tokenizer file, कभी-कभी और भी। **GGUF** यह सब, weights, tokenizer, और architecture दोबारा बनाने के लिए ज़रूरी metadata, एक अकेली binary file में समेट देता है। पूरा Python और Hugging Face stack पहले से मौजूद GPU server पर वह बँटवारा बोझ नहीं है। Edge device पर, जहाँ लक्ष्य अक्सर एक file भेजना और उसे छोटे, कम-dependency वाले binary से चलाना होता है, एक अकेली, अपने-आप में पूरी file ठीक वही है जो deployment को चाहिए।

![दो layouts अगल-बगल। बाईं ओर, Hugging Face checkpoint तीन अलग files के रूप में, उनके बीच ख़ाली जगह के साथ: weights, architecture बताने वाली config.json, और एक tokenizer file। दाईं ओर, एक अकेली GGUF file जिसमें वही तीन हिस्से, weights, tokenizer और metadata, एक file की सीमा के भीतर बिना ख़ाली जगह के साथ समेटे गए हैं, इसलिए पूरा model एक अपने-आप में पूरी इकाई की तरह भेजा और load होता है।](images/gguf-single-file-bundle.svg)

### GGUF का अपना quantization परिवार है

GPTQ और AWQ (पाठ 7) GPU-उन्मुख schemes हैं, जो इस हिसाब से tune हैं कि GPU kernels कैसे dequantize और multiply करते हैं। GGUF इसके बजाय llama.cpp का अपना quantization प्रकारों का परिवार ढोता है, जिनके नाम `Q4_K_M` या `Q5_K_M` जैसे होते हैं। नाम पढ़ने का तरीक़ा: शुरू की संख्या bit width है (`Q4` यानी लगभग 4 bits प्रति weight); `K` एक **k-quant** प्रकार का निशान है, जो weights को 256 के super-blocks में समूहित करता है जिनके हर sub-block का अपना scale होता है, इसलिए tensor के हर weight की bit width एक जैसी है और सिर्फ़ scales उसके भीतर बदलते हैं; आख़िर का अक्षर (`S`, `M` या `L`, छोटा, मध्यम, बड़ा) एक नुस्ख़ा चुनता है जो tensors में प्रकार मिलाता है, कुछ tensors को जो ज़्यादा मायने रखते पाए गए हैं ऊँची-bit का प्रकार देता है (`Q4_K_M` में, कुछ `Q6_K` लेते हैं जबकि बाक़ी `Q4_K` रहते हैं, [k-quants लाने वाले pull request](https://github.com/ggml-org/llama.cpp/pull/1684) के अनुसार), आकार और गुणवत्ता के बीच वैसे ही सौदा करते हुए जैसे पाठ 8 ने int8 बनाम int4 का सौदा बताया, बस llama.cpp की अपनी scheme के भीतर, GPTQ या AWQ की नहीं।

### Load करने के बजाय memory-mapping

क्योंकि GGUF weights को ऐसे format में रखता है जिसे OS सीधे पढ़ सकता है, llama.cpp file को **memory-map** (`mmap`) कर सकता है, बजाय इसके कि उसे RAM में पढ़े और deserialize करे जैसा Python checkpoint loader करता है। Memory-mapping का मतलब है कि file के pages disk से तभी असल में पढ़े जाते हैं जब कोई उन्हें छुए, और क्या resident रहे यह operating system का अपना page cache सँभालता है, न कि process सब कुछ पहले से माँग ले। तेज़, भरपूर system RAM वाले GPU server पर यह कम मायने रखता है। CPU और edge hardware पर, जहाँ RAM अक्सर सबसे तंग संसाधन है, उत्सुकता से पूरी file load करने से बचना, और OS को तय करने देना कि क्या resident रखे, इसमें असली फ़र्क़ डालता है कि कोई दिया हुआ device कितना बड़ा model चलाने की कोशिश भी कर सकता है।

## अभ्यास

1. ▢ Weights, tokenizer और architecture metadata को एक GGUF file में समेटना edge deployment के लिए, पूरा Hugging Face stack पहले से चला रहे GPU server की तुलना में, ज़्यादा मायने क्यों रखता है?

<details markdown="1"><summary>जाँचें</summary>

Edge deployment अक्सर एक अकेली file भेजना और उसे छोटे, कम-dependency वाले binary से चलाना चाहता है, बिना किसी अलग Python या Hugging Face ecosystem के install किए जो config, tokenizer और weight files को दोबारा जोड़े। GPU server में वह ecosystem पहले से मौजूद है, इसलिए multi-file layout उसे कोई अतिरिक्त क़ीमत नहीं देता।

</details>

2. ▢ Quantization नाम `Q4_K_M` को खोलें: हर हिस्से का क्या मतलब है?

<details markdown="1"><summary>संकेत</summary>

इसे तीन हिस्सों में पढ़ें: शुरू की संख्या, underscore के बाद का अक्षर, और आख़िर का अक्षर।

</details>

<details markdown="1"><summary>जाँचें</summary>

`Q4` यानी लगभग 4 bits प्रति weight। `K` k-quant प्रकार का निशान है: tensor के हर weight के लिए एक bit width, और 256 के super-blocks के भीतर प्रति-sub-block scales। `M` मध्यम नुस्ख़ा चुनता है (`S` या `L` के बजाय), जो tensors में प्रकार मिलाता है, कुछ tensors को बाक़ियों से ऊँची-bit का प्रकार देता है।

</details>

3. ▢ GGUF file को memory-map करना llama.cpp को startup पर क्या करने से बचने देता है, और यह GPU server की तुलना में CPU/edge hardware पर ज़्यादा मायने क्यों रखता है?

<details markdown="1"><summary>जाँचें</summary>

यह पूरी file को उत्सुकता से RAM में पढ़ने और कुछ भी चलने से पहले deserialize करने से बचाता है; इसके बजाय OS pages को disk से सिर्फ़ तब पढ़ता है जब उन्हें असल में छुआ जाए, और क्या resident रहे यह अपने page cache से सँभालता है। यह CPU/edge hardware पर ज़्यादा मायने रखता है, जहाँ RAM अक्सर सबसे तंग संसाधन है और उत्सुकता से पूरा load उपलब्ध से ज़्यादा हो सकता है, उस GPU server की तुलना में जिसके पास बचाने को भरपूर system RAM है।

</details>

4. ▢ GPTQ या AWQ की तुलना में GGUF के k-quant परिवार के बारे में कौन-सा दावा सही है?

    - a) यह GPTQ वाली ही scheme है, बस llama.cpp के लिए नाम बदला गया
    - b) यह llama.cpp का अपना quantization परिवार है, GPU-उन्मुख GPTQ और AWQ schemes से अलग
    - c) यह सिर्फ़ 4-bit quantization support करता है, GPTQ और AWQ के उलट
    - d) इसे लगाने के लिए GPU चाहिए, GPTQ और AWQ की तरह

<details markdown="1"><summary>जाँचें</summary>

**b)** GGUF के k-quant प्रकार llama.cpp का अपना परिवार हैं, इस हिसाब से tune कि वह कैसे dequantize और compute करता है, GPTQ और AWQ से अलग। (a) ग़लत है: तंत्र अलग हैं, सिर्फ़ नाम नहीं। (b) वाले कारण से (c) ग़लत है: परिवार कई bit widths तक फैला है (`Q4`, `Q5`, `Q8` और दूसरे), सिर्फ़ 4-bit नहीं। (d) ग़लत है: GGUF और उसके quantization प्रकार ख़ासकर CPU और edge serving के लिए बने हैं।

</details>

## असली दुनिया का अभ्यास

- [ ] उसी checkpoint के उपलब्ध quantization रूप देखें (अक्सर कई `Q*_K_*` विकल्प) और उनमें से दो के बीच file size का फ़र्क़ नोट करें।
- [ ] कल: llama.cpp के दस्तावेज़ों में `mmap` पर एक अनुच्छेद पढ़ें और नोट करें कि कौन-सा flag, अगर कोई है, यह नियंत्रित करता है कि उसका इस्तेमाल हो या नहीं।
