# 第 15 课：离开 GPU 之后有什么变化

**使命关联:** 这是第 5 阶段的收官课，也是使命成功标准的后半部分：一套在 CPU 上运行、响应真实请求的 llama.cpp 服务栈，同时把第 1 到 4 阶段的每个概念重新审视一遍，看看在这个规模上究竟还有哪些适用。
**主要来源:** [仓库：llama.cpp，ggml-org](https://github.com/ggml-org/llama.cpp)
**前置知识:** [第 14 课](0014-llamacpp-architecture.md)、[KV 缓存](../GLOSSARY.md)

## 热身

1. ▢ `--threads` 在 llama.cpp 里控制什么，这与 vLLM 的 `--max-num-seqs` 有什么不同？

<details markdown="1"><summary>检查</summary>

`--threads` 把单个序列自己的矩阵乘法，分到 CPU 的各个物理核上。`--max-num-seqs` 则限制有多少个并发序列共用一个 GPU 批次步，在它们之间分摊内存流量。一个加快单个序列的计算；另一个在许多序列之间分摊内存带宽开销。

</details>

2. ▢ 把量化名称 `Q4_K_M` 解读成它的三个部分。

<details markdown="1"><summary>检查</summary>

`Q4`：每个权重大致 4 位。`K`：一种 k-quant 类型，张量内所有权重使用同一位宽，在 256 个权重的超块内，每个子块各有自己的缩放因子。`M`：中等配方，在不同张量之间混用 k-quant 类型。

</details>

## 要点

### 搭起服务器

llama.cpp 自己的服务器 `llama-server`，加载一个 GGUF 文件，并暴露一个兼容 OpenAI 的 HTTP 端点，请求的形状与第 10 课对 vLLM 所用的相同：

```text
llama-server -m model.Q4_K_M.gguf --threads 8
```

```bash
curl http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "model.Q4_K_M.gguf", "messages": [{"role": "user", "content": "Say hello"}]}'
```

请求和响应的形状是熟悉的。变的是它下面的一切。

![三行对比。批处理：在 GPU 上，连续批处理在数百个并发请求之间分摊内存带宽；在 CPU/边缘规模上，并发请求只有个位数到二十几个，由把单个序列的计算分到各个核上的线程取而代之。缓存管理：在 GPU 上，PagedAttention 管理一个庞大的、不断变化的共享池；在 CPU/边缘规模上，一个简单的、每个序列连续存放的缓存就足够了。量化时机：在 GPU 上用 vLLM，方案是在启动时选定的一个服务时参数；在 llama.cpp 上，这个决定在挑选某个具体的 GGUF 量化级别时就已锁定，早在服务器启动之前。](images/gpu-vs-cpu-edge-mechanisms.svg)

### 在这个规模上，批处理没那么要紧

vLLM 的连续批处理（第 4 和第 5 课）存在的目的，是在数百个素不相识的并发请求之间，分摊 GPU 的内存带宽开销。CPU 没有数以千计的并行核心可以把这笔开销摊开；llama.cpp 的服务器确实支持少量并行请求槽位，但规模是个位数到二十几个，而不是数百个。这不是缺了某个功能：边缘部署的典型工作负载，是一台设备服务它自己的用户，本来就很少有数百个并发请求可以批在一起。大力批处理解决的，是 CPU/边缘服务通常没有的问题。

### 在这个规模上，缓存也不需要分页

PagedAttention（第 11 课）存在的目的，是让许多序列高效地共享内存，并在一个庞大的、不断变化的并发请求池里避免碎片。在 CPU/边缘规模上，并发序列很少，也没有需要避免碎片的大型共享池，一个更简单的、每个序列连续存放的缓存分配方式很常见，也足够用。PagedAttention 所要解决的问题，原则上并没有消失，只是很少达到它的复杂度值得付出的规模。

### 量化的决定已经做出了

在 vLLM 上，`--quantization` 是一个服务时的参数：方案是在服务器启动时选定的，来自一个已经量化好的检查点，或者一个要在加载时量化的检查点。在 llama.cpp 上，这个决定更早就做出了，是在挑选（或生成）某个具体量化级别（比如 `Q4_K_M`）的 GGUF 文件时。没有服务时的参数可以改变它；要改变量化，就得下载或生成另一个 GGUF 文件。第 7 到 9 课的权衡，即内存、精度与速度的取舍，仍然适用，只是它在服务器启动之前就已敲定，而不是在启动时配置的。

## 练习

1. ▢ 三个请求同时到达一个 `llama-server` 实例，都来自同一台边缘设备自己的用户。在检查之前先预测：每个请求的吞吐量会怎样，为什么这与连续批处理在 GPU 上所做的不同？

<details markdown="1"><summary>检查</summary>

每个请求的吞吐量大致按它现在要共享的线程数成比例地下降，因为 CPU 固定的核数被分摊到并发的请求之间，而不是每个请求独占全部线程数。这不同于 GPU 的连续批处理，后者是在并发序列之间分摊一笔本来就必须付出的内存带宽开销，每个序列几乎不增加额外成本；把 CPU 的计算分摊到各个请求之间，则没有这种“反正已经在付了”的开销可以分摊。

</details>

2. ▢ 为什么 vLLM 式的大力连续批处理，对典型的 CPU/边缘部署，不如对 GPU 服务器那么要紧？

<details markdown="1"><summary>检查</summary>

连续批处理的复杂度，是在许多素不相识的并发请求共享 GPU 的内存带宽开销时才值得付出的。典型的边缘部署，是一台设备服务它自己的用户，本来就很少有那么多并发请求可以批在一起，所以这套机制所要解决的问题，在这个规模上通常并不存在。

</details>

3. ▢ 对 llama.cpp 部署来说，量化的决定是在哪里做出的，这与 vLLM 部署的相比如何？

<details markdown="1"><summary>检查</summary>

对 llama.cpp，它是在挑选或生成某个具体的 GGUF 文件（具体的量化级别，比如 `Q4_K_M`）时做出的，早在服务器启动之前；要改它，就得用另一个文件。对 vLLM，它是一个服务时的参数 `--quantization`，在启动服务器时选定。权衡本身与第 7 到 9 课教的是同一个；不同的只是决定在何时被锁定。

</details>

4. ▢ 关于 PagedAttention 式的内存管理在 CPU/边缘规模上为什么不那么常被需要，哪种说法是对的？

    - a) CPU 硬件使得分页在技术上不可能
    - b) 典型的工作负载并发序列很少，一个更简单的、每个序列连续存放的缓存就足够了
    - c) llama.cpp 的 GGUF 格式与任何形式的分页内存都不兼容
    - d) CPU 服务中根本不存在 KV 缓存

<details markdown="1"><summary>检查</summary>

**b)** 并发序列很少，也没有需要避免碎片的大型共享池，一个更简单的分配方案通常就够了；PagedAttention 所要解决的问题，很少达到它的复杂度值得付出的规模。(a) 是错的：CPU 硬件并不排除分页，这是设计上的权衡，而不是限制。(c) 是错的：GGUF 描述的是模型文件，而不是运行时的缓存布局。(d) 是错的：解码在 CPU 上仍然需要 KV 缓存，原因与第 1 课确立的相同；只是它通常被管理得更简单。

</details>
