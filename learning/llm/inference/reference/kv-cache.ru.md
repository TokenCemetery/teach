# KV-кеш

Учёт байтов KV-кеша. Сделан для быстрого поиска при расчёте размера развёртывания.

## Стоимость на токен

```text
bytes per token = 2 (K and V) × num_layers × num_kv_heads × head_dim × bytes_per_value
```

`head_dim = d_model / num_heads`. Кеш хранит одну пару K/V на **KV-голову**, а не на голову запроса. При многоголовом внимании (MHA) `num_kv_heads = num_heads`, и формула сводится к `2 × num_layers × d_model × bytes_per_value`. При внимании с групповыми запросами (GQA) или с единым запросом (MQA) `num_kv_heads` меньше, и кеш уменьшается в то же число раз, бесплатно, без изменения длины контекста или размера батча.

| Схема | `num_kv_heads` | Относительный размер кеша |
|---|---|---|
| MHA | равно `num_heads` | 1x |
| GQA | доля от `num_heads` | та же доля |
| MQA | 1 | `1 / num_heads` |

**Разобранный пример, Llama-2-70B** (80 слоёв, 64 головы запросов, 8 KV-голов, `head_dim` = 128, fp16):

```text
GQA: 2 × 80 × 8  × 128 × 2 bytes =   327,680 bytes ≈ 320 KB/token
MHA: 2 × 80 × 64 × 128 × 2 bytes = 2,621,440 bytes ≈ 2.5 MB/token   (8x GQA, the num_heads:num_kv_heads ratio)
```

## От стоимости на токен к суммарному объёму

```text
total cache bytes = bytes per token × context length × batch size
```

| Модель | На токен | Контекст | Батч | Всего |
|---|---|---|---|---|
| Llama-2-7B, MHA, fp16 | 512 КБ | 4096 | 1 | ~2 ГБ |
| Llama-2-7B, MHA, fp16 | 512 КБ | 4096 | 16 | ~32 ГБ |
| Llama-2-70B, GQA, fp16 | 320 КБ | 4096 | 1 | ~1,25 ГБ |
| Llama-2-70B, GQA, fp16 | 320 КБ | 4096 | 32 | ~40 ГБ |

## Бюджет ёмкости

```text
max concurrent sequences = (total memory - weights - overhead) / (bytes per token × context length)
```

Llama-2-70B, тензорный параллелизм по четырём GPU по 80 ГБ (пул в 320 ГБ), веса вместе с накладными расходами фреймворка измерены в 160 ГБ, контекст в 4096 токенов:

```text
160 GB / 1.25 GB per sequence ≈ 128 concurrent sequences
```

Именно этот потолок, а не сырая пропускная способность модели, обычно и есть то, с чем договаривается планировщик батчинга; см. [Батчинг](batching.md).

## Префилл занимает большую часть объёма за один шаг

| Фаза | Что делает | Рост кеша |
|---|---|---|
| Префилл | Обрабатывает весь промпт за один прямой проход | Сразу прыгает до `bytes per token × prompt length`; ограничение вычислениями |
| Декодирование | Генерирует по одному токену вывода | Растёт на `bytes per token` за шаг; ограничение пропускной способностью памяти |

**Разобранный пример**, промпт в 2048 токенов и затем 128 шагов декодирования, Llama-2-70B при 320 КБ на токен:

```text
prefill: 320 KB × 2048 ≈ 640 MB   (94% of the request's final cache)
decode:  320 KB × 128  ≈  40 MB   (6%, added gradually)
total:   680 MB
```

План ёмкости, построенный лишь на «итоговой длине контекста», скрывает, что большая часть объёма приходится на префилл, на один шаг, а не распределена по запросу.

<a id="cache-precision-is-a-lever-independent-of-the-models-own-weights"></a>

## Точность кеша это рычаг, не зависящий от собственных весов модели

`bytes_per_value` выше не обязан совпадать с точностью, в которой модель вычисляет. Стек обслуживания может хранить сам кеш в более низкой точности, обычно fp8, тогда как модель считает в bf16 или fp16. Он перемножается с совместным использованием голов, а не заменяет его.

```text
Llama-2-70B, GQA, fp16: 320 KB/token
Llama-2-70B, GQA, fp8:  160 KB/token   (half, only bytes_per_value changed)
```

64 последовательности при контексте в 4096 токенов: fp16 стоит ~80 ГБ, fp8 стоит ~40 ГБ, ровно вдвое меньше, поверх того, что GQA уже вернул по сравнению с полным MHA.
