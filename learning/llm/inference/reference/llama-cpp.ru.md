# llama.cpp

Стек обслуживания на CPU и периферии. Сделан для быстрого поиска при запуске развёртывания llama.cpp или рассуждениях о нём.

## GGUF

Один двоичный файл, объединяющий веса, токенизатор и метаданные архитектуры, вместо нескольких отдельных файлов (`config.json`, токенизатор, веса), в которых поставляется чекпоинт Hugging Face. Объединение важнее всего для периферийного развёртывания: поставить один файл для запуска небольшим бинарником с минимумом зависимостей, без установки Python или экосистемы Hugging Face для сборки частей.

Поскольку GGUF раскладывает веса в формате, который ОС может читать напрямую, llama.cpp может **отображать файл в память** (`mmap`) вместо жадного чтения его в RAM и десериализации. Страницы читаются с диска только по мере обращения к ним, а то, что остаётся резидентным, управляется собственным страничным кешем ОС. Это важнее всего там, где RAM самый дефицитный ресурс, на CPU и периферийном оборудовании, и меньше на GPU-сервере с щедрым запасом системной RAM.

### Имена квантизаций

GGUF несёт собственное семейство квантизации llama.cpp, отдельное от ориентированных на GPU GPTQ и AWQ. Расшифровка имени вроде `Q4_K_M`:

| Часть | Значение |
|---|---|
| `Q4` | Разрядность: примерно 4 бита на вес (бывают также `Q5`, `Q8` и другие) |
| `K` | Тип **k-quant**: одна разрядность на тензор, с суперблоками по 256 весов, в которых каждый подблок несёт собственный масштаб |
| `M` | Рецепт, смешивающий типы по тензорам и дающий некоторым тензорам тип с большей разрядностью: `S` (малый), `M` (средний), `L` (большой). См. [лист курса по квантизации «Измерение и хранение»](../../quantization/reference/measuring-and-storing.md) |

## ggml: одна кодовая база, много бэкендов

llama.cpp построен на **ggml**, тензорной библиотеке на C без зависимостей (внешний BLAS не требуется). Прямой проход это статический граф вычислений, построенный один раз и затем выполняемый, а не пооперационное нетерпеливое исполнение PyTorch. Именно это отделение «что вычислять» от «что это запускает» позволяет одному и тому же графу нацеливаться на несколько **бэкендов**, CPU (AVX2/NEON), CUDA, Metal, Vulkan, из одной кодовой базы и без среды выполнения Python, на оборудовании от ARM CPU телефона до GPU Metal на Mac и Raspberry Pi. Дизайн vLLM, напротив, специфичен для CUDA и не может работать без GPU NVIDIA.

## Потоки заменяют батчинг на GPU

| | Распределяет | Ограничено |
|---|---|---|
| Батчинг на GPU (`--max-num-seqs`) | Стоимость пропускной способности памяти между одновременными последовательностями | Ёмкостью кеша и бюджетом задержки |
| Потоки CPU (`--threads`) | Матричные умножения одной последовательности между ядрами | Числом физических ядер CPU |

Многопоточность ускоряет вычисления одной последовательности; у неё нет эквивалента «чтение памяти и так уже оплачено», которое можно распределить между запросами незнакомцев, как это делает батчинг на GPU.

## Запуск сервера

```text
llama-server -m model.Q4_K_M.gguf --threads 8
```

```bash
curl http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "model.Q4_K_M.gguf", "messages": [{"role": "user", "content": "Say hello"}]}'
```

Та же совместимая с OpenAI форма запроса, что и у [vLLM](vllm.md); меняется всё, что под ней.

## Что меняется вне GPU

| Механизм | На GPU (vLLM) | В масштабе CPU и периферии (llama.cpp) |
|---|---|---|
| Конкурентность | [Непрерывный батчинг](batching.md) распределяет пропускную способность памяти между сотнями запросов одновременных незнакомцев | Несколько параллельных слотов (от единиц до низких десятков); типичная периферийная нагрузка, одно устройство обслуживает своего пользователя, редко содержит сотни одновременных запросов, которые можно объединять в батч |
| Управление кешем | [PagedAttention](vllm.md#pagedattention) управляет большим, постоянно меняющимся общим пулом | Достаточно более простого непрерывного кеша на последовательность; проблема, которую решает PagedAttention, редко достигает масштаба, на котором её сложность окупается |
| Момент квантизации | Флаг времени обслуживания (`--quantization`), выбираемый при запуске | Уже зафиксирован, когда выбран или создан конкретный уровень квантизации GGUF; смена означает использование другого файла, а не флаг |

Сами компромиссы ([память, скорость и точность](quantization-at-serve-time.md)) не меняются; различается лишь то, когда принимается каждое решение и при какой конкурентности оно окупается.
