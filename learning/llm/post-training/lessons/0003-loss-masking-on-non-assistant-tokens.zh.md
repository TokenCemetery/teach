# 第 3 课：非助手 token 上的损失掩码

**使命关联:** “写出一个对非助手 token 做损失掩码的 SFT 训练循环，并解释不加这个掩码训练出来的聊天模型会出什么问题”是“成功的标准”下的第一条，本课就是对它的直接回答。
**主要来源:** [论文：“Llama 2: Open Foundation and Fine-Tuned Chat Models”，Touvron 等，2023](https://arxiv.org/abs/2307.09288)
**前置知识:** [第 2 课](0002-instruction-data-and-the-chat-template.md)、[损失掩码](../GLOSSARY.md)

## 热身

1. ▢ 什么是聊天模板？为什么训练和服务时使用同一个模板很重要？

<details markdown="1"><summary>检查</summary>

用特殊 token 以固定、一致的方式标出角色边界（系统、用户、助手轮次），使模型能学到一种它之后会稳定再次见到的结构。训练与服务所用模板不一致，会让模型面对一种它从未见过与所学行为配对出现的结构，使其行为变差或不稳定。

</details>

2. ▢ 按 Touvron 等人的做法，他们在 SFT 训练数据中用什么特殊 token 来分隔提示词和它的回答？

<details markdown="1"><summary>检查</summary>

一个专门插入的特殊 token，专门用来标出提示词片段与回答片段之间的边界。

</details>

## 要点

### 这个损失最朴素、不加掩码的版本是错的

普通的语言建模损失，训练模型在序列的每个位置上预测下一个 token，并与序列在那里实际包含的内容做比较。如果不加任何调整，直接用在一个拼接起来的提示词加回答的样本上，这就会训练模型把提示词自己的 token 也预测出来，而不只是回答的 token，因为提示词和回答一样，都是这个序列的一部分。

### Touvron 等人实际上是怎么做的

Touvron 等人直接陈述了他们的做法：“我们采用自回归目标，并把来自用户提示词的 token 上的损失置零，因此我们只对回答的 token 做反向传播。”这就是**损失掩码**：属于提示词的每个 token（或者在多轮样本中，属于任何用户轮次或系统轮次的 token），它对损失的贡献都被设为零，所以只有模型真正要去生成的那些 token，也就是助手的回答，才会产生梯度。从机制上说，这通常是这样实现的：给每个被掩码的位置一个损失函数被告知要忽略的标签值（对标准交叉熵损失，常见的约定是把它设为 `-100`），而不是那里实际出现的 token。

### 不做掩码会出什么问题

跳过这个掩码，浪费的不只是一点算力；它改变了模型实际被训练去做的事。直接由此产生两个具体的问题：

- **模型学会预测它没有生成、也永远不需要复现的文本。** 训练模型把用户自己的提示词原样预测回去，对 SFT 的目标没有任何帮助，SFT 的目标是塑造模型作为回答所产生的内容，而不是它能把问题复述到什么程度。
- **提示词往往比紧随其后的回答长得多。** 不加掩码的损失，会被提示词 token 的数量所主导，稀释了回答 token 上的梯度信号，而回答 token 恰恰是序列中 SFT 真正想要塑造的唯一部分，大量的损失却花在了一项（预测提示词）从来不是重点的任务上。

### 结果：掩码把目标集中到被教授的东西上

把每个非助手 token 都掩码掉，对两个问题都起到相反的作用：SFT 一步中的每一份梯度信号，都来自模型真正要学着生成的 token，没有一丁点花在预测模型只是被给定的文本上。这就是为什么 SFT 教的是它本来要教的那项具体技能，即模仿期望的回答，而不是这项技能与一项无关技能（预测任意的用户文本）的混合，后者只是碰巧与它处在同一个训练序列里。

## 练习

1. ▢ 一个训练样本把 200 个 token 的提示词和 20 个 token 的回答拼接在一起，没有做任何损失掩码。这个样本的总损失中，大约有多大比例来自并非 SFT 实际目标的 token？

<details markdown="1"><summary>检查</summary>

220 个 token 里大约有 200 个，约 91%，是提示词 token，它们贡献的损失与 SFT 想教模型生成的回答无关。不加掩码的损失中，只有约 9% 来自回答本身。

</details>

2. ▢ 下面哪一项最恰当地描述了损失掩码在机制上实际做了什么？

    - a) 把提示词 token 从输入序列中完全移除
    - b) 给每个被掩码 token 的位置一个损失函数被告知要忽略的标签，使只有未被掩码的（助手）位置贡献梯度
    - c) 在处理提示词 token 时专门降低学习率
    - d) 专门为提示词 token 训练一个单独的模型

<details markdown="1"><summary>检查</summary>

**b)** 才是实际的机制：提示词 token 仍然作为输入存在，所以模型可以以它们为条件生成回答，但它们的位置被排除在损失计算之外。(a) 会移除模型生成回答时需要依据的信息。(c) 和 (d) 并不是本课或它的来源所描述的任何技术。

</details>

3. ▢ 在完全相同的 SFT 数据上，把一个没有对非助手 token 做损失掩码训练的模型，与一个做了掩码的模型进行比较。说出一种你预计未掩码模型的 SFT 训练会有所不同的具体方式。

<details markdown="1"><summary>检查</summary>

任何合理的说法，大意是：梯度信号被学着预测提示词 token 稀释了，或者花在了这件事上，而没有完全集中在回答 token 上，所以在同样的训练步数下，模型学到的东西里，实际用于塑造回答生成行为的更少，而这正是 SFT 要教的唯一一件事。

</details>

## 实战练习

- [ ] 找到你能用到的某个训练框架中，对聊天风格的 SFT 数据实现损失掩码的地方（`ignore_index`、带有被掩码位置的 `labels` 字段，或类似的东西），并确认它用哪种约定来标记被掩码的位置。
- [ ] 取一段简短的示例对话（一条系统消息、一个用户轮次、一个助手轮次），按本课的规则，逐 token 或逐片段标出哪些部分会被掩码、哪些会贡献损失。
- [ ] 明天：对一段有两个用户轮次和两个助手轮次的多轮对话，写出哪些轮次被掩码、哪些没有，并对照本课的规则检查你的答案：每一个非助手轮次都要被掩码，而不只是第一个提示词。
