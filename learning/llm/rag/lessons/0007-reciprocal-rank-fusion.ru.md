# Урок 7. Слияние по взаимным рангам

**Связь с целью курса:** Это завершающий урок этапа 4: BM25 и векторный поиск (уроки с 4 по 6) каждый выдают рейтинг, а этот урок о том, как эти два рейтинга становятся одним гибридным результатом, настроенным по измеренному числу, а не по угаданной смеси.
**Первоисточник:** [Документация: "Reciprocal rank fusion (RRF)", Elasticsearch](https://www.elastic.co/guide/en/elasticsearch/reference/current/rrf.html)
**Предварительные требования:** [Урок 6](0006-bm25-and-lexical-search.md), [Чанк](../GLOSSARY.md)

## Разминка

1. ▢ Приведите пример запроса, где BM25 справился бы, а векторный поиск мог бы не справиться, и запроса, где верно обратное.

<details markdown="1"><summary>Проверка</summary>

Точный идентификатор вроде «код ошибки E502» в пользу BM25, поскольку модель эмбеддингов векторного поиска не обучали точно сопоставлять конкретные коды. Синонимичная формулировка без общих слов, как «прорыв трубы» против «протечки в водоводе», в пользу векторного поиска, поскольку BM25 даёт ноль документам, не имеющим общих терминов с запросом.

</details>

2. ▢ Почему использование неверного оператора расстояния с индексом pgvector заставляет запрос откатиться к последовательному просмотру?

<details markdown="1"><summary>Проверка</summary>

Индекс строится под одну конкретную функцию расстояния (один класс операторов); запрос с другим оператором не соответствует тому, под что построен индекс, поэтому индекс использовать нельзя и запрос вместо этого просматривает таблицу напрямую.

</details>

## Что нужно знать

### Проблема: два рейтинга на несравнимых шкалах

BM25 выдаёт неограниченную, зависящую от корпуса оценку; косинусное сходство выдаёт оценку, ограниченную между -1 и 1. Усреднять их напрямую, даже после какой-то нормализации, значит решать, как сделать две принципиально разные шкалы сопоставимыми, а такое решение хрупко: оно зависит от корпуса, запроса и выбранной схемы нормализации, и нет принципиального способа узнать, честно ли оно.

### RRF: использовать позицию в рейтинге, а не саму оценку

**Слияние по взаимным рангам (reciprocal rank fusion, RRF)** полностью обходит проблему шкал, игнорируя исходные оценки и используя только **позицию в рейтинге** каждого документа в каждом рейтинге. Для документа *d*, стоящего на месте `rank_r(d)` в рейтинге *r*, его оценка RRF суммирует член с обратным рангом по каждому рейтингу, где он встречается:

```text
RRF(d) = sum over rankings r of 1 / (k + rank_r(d))
```

`k` это константа, которая приглушает влияние самых верхних мест; общепринятое значение по умолчанию из исходной статьи `k = 60`. Поскольку важна только позиция в рейтинге, а не величина оценки, RRF объединяет рейтинг BM25 и рейтинг векторного поиска без необходимости нормализовать любой из них: позиция в рейтинге уже общая валюта, самонормализующаяся для любого метода ранжирования.

### Разобранный пример

Возьмём упрощённое `k = 1`, чтобы арифметика была чистой (в продакшене чаще берут по умолчанию `k = 60`, которое приглушает различия между верхними местами сильнее, чем `k = 1`): для запроса BM25 ставит документ A первым, документ B четвёртым, документ C вторым; векторный поиск ставит A четвёртым, B первым, C вторым.

```text
RRF(A) = 1/(1+1) + 1/(1+4) = 0.500 + 0.200 = 0.700
RRF(B) = 1/(1+4) + 1/(1+1) = 0.200 + 0.500 = 0.700
RRF(C) = 1/(1+2) + 1/(1+2) = 0.333 + 0.333 = 0.667
```

A и B делят первое место, каждый блестящ в одном методе и слаб в другом; C, лишь посредственный в обоих, проигрывает им обоим. RRF вознаграждает документ, в который сильно верит любой один метод, а не только документ, с которым оба метода слегка согласны.

![Два ранжированных списка рядом, рейтинг BM25 и рейтинг векторного поиска, в каждом по четыре позиции. Документ A стоит первым по BM25, но четвёртым по векторному поиску; документ B стоит четвёртым по BM25, но первым по векторному поиску; документ C стоит вторым в обоих. Линии ведут каждый документ от его двух позиций в объединённый рейтинг RRF справа, где A и B делят первое место, каждый блеснув в одном методе, а C, всегда лишь средний, оказывается позади них, хотя ни в одном списке не стоял плохо.](images/rrf-worked-example.svg)

### Настройка смеси по измеренной метрике

RRF можно расширить весом на каждый рейтинг, `sum of w_r / (k + rank_r(d))`, позволяя векторному поиску значить в итоговом слиянии больше или меньше, чем BM25. Верный вес и верное `k` не нужно угадывать: их нужно измерять, так же как урок 3 измерял качество эмбеддингов при размерностях-кандидатах, вместо того чтобы предполагать одну. С помощью метрик поиска этапа 6 (recall@k, MRR) на размеченном или синтетическом наборе запросов, репрезентативном для реального трафика корпуса, разные веса можно сравнить напрямую, и выпускать стоит ту смесь, которая для этого корпуса действительно чаще находит верные документы, а не разбиение 50 на 50 по умолчанию.

## Практика

1. ▢ Для запроса BM25 ставит документ X вторым, а документ Y первым; векторный поиск ставит X первым, а Y третьим. Используя `k = 1`, вычислите оценку RRF каждого документа и скажите, какой выше.

<details markdown="1"><summary>Подсказка</summary>

`RRF(d) = 1/(k + rank_in_bm25) + 1/(k + rank_in_vector)`.

</details>

<details markdown="1"><summary>Проверка</summary>

`RRF(X) = 1/(1+2) + 1/(1+1) = 0.333 + 0.500 = 0.833`. `RRF(Y) = 1/(1+1) + 1/(1+3) = 0.500 + 0.250 = 0.750`. X выше, поскольку это сильный результат (первое место) в векторном поиске и лишь умеренно хороший в BM25, и он слегка опережает Y, который силён в BM25, но слабее в векторном поиске.

</details>

2. ▢ Почему RRF использует позицию каждого документа в рейтинге, а не его сырую оценку BM25 или косинусного сходства напрямую?

<details markdown="1"><summary>Проверка</summary>

Оценки BM25 и косинусного сходства лежат на несравнимых шкалах (одна неограниченная и зависящая от корпуса, другая ограничена между -1 и 1), и нет принципиального, не зависящего от корпуса способа нормализовать их друг относительно друга. Позиция в рейтинге уже общая валюта для любого метода ранжирования, поэтому её использование полностью обходит проблему нормализации.

</details>

3. ▢ Что делает с формулой RRF малое `k` (например 1) по сравнению с большим `k` (например 60) в смысле того, насколько важна точная позиция документа в рейтинге?

<details markdown="1"><summary>Проверка</summary>

Малое `k` делает член с обратным рангом гораздо чувствительнее к небольшим различиям в позиции у верха списка (разрыв между первым и вторым местом пропорционально больше), а большое `k` приглушает эту чувствительность, делая разницу между, скажем, первым и пятым местом сравнительно меньше. Большие значения `k` дают более мягкое, менее чувствительное к позиции слияние.

</details>

4. ▢ Как команде решить, взвешивать ли векторный поиск сильнее, чем BM25, в гибридной смеси, вместо разбиения поровну по умолчанию?

<details markdown="1"><summary>Проверка</summary>

Измерить качество поиска (recall@k или MRR, метрики этапа 6) на размеченном или синтетическом наборе запросов, репрезентативном для реального шаблона запросов корпуса, при нескольких весах-кандидатах и выбрать тот, который для этого корпуса действительно чаще всего находит верные документы, вместо допущения, что разбиение поровну или любое другое значение по умолчанию верно без проверки.

</details>

5. ▢ Какое утверждение верно про слияние по взаимным рангам?

    - a) Оно требует нормализовать оценки BM25 и косинусного сходства на одну шкалу перед объединением
    - b) Оно объединяет рейтинги, используя только позицию в рейтинге, что обходит необходимость сравнивать несравнимые шкалы оценок
    - c) Документ, стоящий первым в одном рейтинге и последним в другом, всегда опередит документ, стоящий умеренно в обоих
    - d) Константа `k` не влияет на объединённый рейтинг, а только на величину числовой оценки

<details markdown="1"><summary>Проверка</summary>

**b)** Использование позиции в рейтинге вместо сырых оценок как раз и избегает проблемы нормализации. (a) неверно: это подход со слиянием сырых оценок, которого RRF как раз избегает. (c) неверно: разобранный пример показал, что стабильно умеренный документ всё же может проиграть двум документам, каждый из которых блестит в одном методе, но результат зависит от реальных значений рангов, а не от универсального правила, что крайность бьёт умеренность. (d) неверно: `k` меняет то, насколько важны различия в позиции, а это может изменить порядок объединённого рейтинга, а не только его масштаб.

</details>

## Практика в реальной работе

- [ ] Для одного запроса из вашего корпуса получите ранг BM25 и ранг векторного поиска для нескольких документов-кандидатов и вычислите их оценки RRF вручную с `k = 60`.
- [ ] Если у вас есть размеченный или синтетический набор запросов, сравните recall@k для рейтинга только по BM25, рейтинга только по векторам и объединённого рейтинга RRF на одних и тех же запросах.
- [ ] Завтра: попробуйте два разных значения веса векторного поиска во взвешенной формуле RRF и посмотрите, улучшает ли какое-то из них recall@k измеримо по сравнению с разбиением поровну.
