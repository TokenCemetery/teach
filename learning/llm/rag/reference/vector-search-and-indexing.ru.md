# Векторный поиск и индексация

Приближённый поиск ближайших соседей и его реализация в pgvector. Для быстрого поиска при развёртывании или настройке индекса.

## Почему точный поиск не масштабируется

Точный поиск ближайших соседей сравнивает запрос с каждым вектором: линейно по размеру корпуса, слишком медленно на миллионах чанков. Индекс **приближённого поиска ближайших соседей (ANN)** допускает небольшую, управляемую неточность в обмен на время поиска, которое не растёт линейно.

## IVF и HNSW

| Индекс | Механизм | Параметр этапа поиска | Цена построения |
|---|---|---|---|
| IVF (inverted file) | Заранее разбивает векторы на кластеры (k-средними); ищет только в `nprobe` ближайших кластерах | `nprobe`: низкий = быстро, может пропустить соседей у границы кластера; высокий = приближается к точному поиску | Нужна репрезентативная выборка корпуса, чтобы хорошо расставить центроиды |
| HNSW (hierarchical navigable small world) | Многослойный граф; разреженные верхние слои для длинных прыжков, плотный нижний слой для точного локального поиска, спуск жадный | `ef_search`: сколько кандидатов отслеживается на каждом шаге; низкий = быстро, но может остановиться на локально хорошем узле; высокий = больше полнота | Больше памяти (рёбра графа) и более медленное построение индекса, чем у IVF |

Оба параметра выбирают точку на **кривой «полнота и задержка»** для данного корпуса; универсально верной настройки нет ни у одного. HNSW обычно достигает лучшей точки на этой кривой, чем IVF (более высокая полнота при той же задержке), ценой памяти и времени построения. Верная точка зависит от бюджета задержки нагрузки и от того, какую потерю полноты может поглотить последующий этап (реранкинг), измеренную, а не предположенную.

## pgvector: столбец, оператор, индекс

```sql
CREATE EXTENSION vector;
CREATE TABLE chunks (id bigserial PRIMARY KEY, content text, embedding vector(1536));
```

| Оператор | Расстояние | Класс операторов (для индексации) |
|---|---|---|
| `<->` | Евклидово/L2 | `vector_l2_ops` |
| `<#>` | Отрицательное скалярное произведение | `vector_ip_ops` |
| `<=>` | Косинусное | `vector_cosine_ops` |

`<#>` это *отрицательное* скалярное произведение именно для того, чтобы, как и у двух других, меньшее значение означало большее сходство, и `ORDER BY` по возрастанию оставался согласованным для всех трёх. Оператор должен соответствовать [метрике, под которую обучали модель эмбеддингов](chunking-and-embeddings.md#similarity-metrics-must-match-training): использование `<=>` с моделью, обученной на скалярное произведение (или наоборот), это то же самое несоответствие метрики, теперь как конкретный выбор в SQL.

```sql
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

**Индекс строится под одну конкретную функцию расстояния.** Запрос, упорядочивающий по оператору, не совпадающему с классом операторов индекса, этот индекс не использует вовсе: он молча откатывается к полному последовательному просмотру, теряя всю выгоду в производительности, ради которой индекс и существовал. Автоматического преобразования между функциями расстояния нет.

## Параметры pgvector это параметры урока 4 под другими именами

| Понятие | HNSW | IVFFlat |
|---|---|---|
| Параметры времени построения | `m` (максимум связей на узел), `ef_construction` (глубина поиска при построении), задаются при `CREATE INDEX` | `lists` (число кластеров), задаётся при `CREATE INDEX` |
| Параметр «полнота и задержка» на этапе запроса | `SET hnsw.ef_search = 100;` | `SET ivfflat.probes = 10;` (это `nprobe`) |

## Порядок построения важен для IVFFlat, но не для HNSW

Шагу кластеризации IVFFlat нужна репрезентативная выборка реальных векторов таблицы, чтобы хорошо расставить центроиды: построение по пустой или разреженной таблице даёт плохие кластеры. Сначала загрузите данные, затем стройте индекс IVFFlat. Граф HNSW строится постепенно по мере вставки векторов, и аналогичной зависимости у него нет, что отчасти и объясняет, почему HNSW часто предпочитают для таблицы, которая будет расти со временем.
