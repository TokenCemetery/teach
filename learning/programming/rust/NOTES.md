# Rust Notes

Working notes for the teaching session. Not linked from `README.md`.

## Preferences

- **Lessons are written for a general reader, deliberately.** No machine, OS, editor or installed version appears in any lesson, reference sheet, `README.md` or `RESOURCES.md`. Requested explicitly; do not personalise the lesson material to whoever is running the session.
- Mission is the full arc: zero to senior specialist, assuming no prior Rust and no systems-programming background. Start at stage 1 rather than calibrating against a particular reader.
- Skill-heavy topic, and the compiler is the answer key. Every early lesson should have a "predict what the compiler says, then compile" rep, because that is the only way the borrow rules stop feeling arbitrary.
- Reps must fit one sitting.

## The rep project, settled

**Resolved before stage 2, and published as `reference/the-project.md`.** The open thread asked for a crate that grows across the arc, and named a command-line tool as the obvious candidate because it needs no framework. That instinct was right; what needed deciding was which tool, and the decision was made by building the stage 2 slice and running it.

**The project is a line-oriented log summariser**: it reads records from a text stream, models each line as an enum, rejects the malformed ones, and reports a summary. Verified on the current stable toolchain, rustc 1.98.0 with edition 2024, with **no dependencies at all**: the prototype parses a seven-line input into 3 requests, 1 note, 1 blank and 2 rejected lines, totals 2000 bytes for `/index` and 90 for `/login`, and names the busiest path. That matters because stage 2 has no vocabulary for adding a dependency, so a project that needs one before stage 3 would have to be introduced twice.

Why this one rather than the other obvious candidates, argued from what each stage needs:

- **Its core model wants an enum with payloads**, which is stage 2's own done-when clause: a line is a request, a note, or blank, and the parse either produces one or fails. A word-count clone has nothing worth modelling as an enum; a to-do application needs serialisation, which means a dependency, before stage 3.
- **Its failure surface is genuinely `Option` and `Result`**, not a contrivance: a field can be missing and a number can fail to parse, so `ok_or`, `map_err` and `?` all appear because the problem needs them.
- **It is iterator-shaped and needs a map**, which covers the rest of stage 2 without inventing exercises.
- **Every later stage has a real hook.** Stage 3 splits it into a library and a binary and gives it a proper error type, which the prototype's `ParseError` with its `Display` implementation already gestures at. Stage 4 generalises the input source behind a trait and takes borrowed lines rather than owned strings. Stage 5 parallelises across files with threads and channels. Stage 6 reads from many sources with async I/O. Stage 7 measures the per-line allocation cost and only then considers a faster path. Stage 8 publishes it, versions its public API, and reviews it.

The reps grow it a piece at a time, one per lesson, so no lesson asks for a build that does not fit a sitting. The sheet records what state the project should be in at the end of each stage, so a reader who skipped a rep knows what to catch up on.

## Stage 3's decision: whether the arc uses a crate, and when

Stage 3 had no recorded blocking decision and has an obvious one, because it is the first stage where the standard library stops being the whole answer: error handling in real Rust is done with `thiserror` and `anyhow`, and the project sheet already says stage 3 is where dependencies arrive. Settled before writing, on evidence.

**Both versions were written and compiled, and both are needed, in that order.** The hand-written error type is 47 lines with its documentation: an enum, a `Display` implementation that is one `match` arm per variant, and an `Error` implementation whose `source` returns the inner error. The same type with `thiserror` is 36 lines, replacing both implementations with an `#[error("...")]` attribute per variant and a `#[source]` on the field. Verified that they are observably the same rather than merely similar: a test asserting `to_string()` and `source()` on the derived version passes with exactly the values the hand-written one produces, so the derive generates the code the reader has already written by hand.

**The crates are not optional knowledge, which the download counts settle rather than my opinion.** Checked on crates.io: `thiserror` 2.0.20 has about 343 million recent downloads against 1.4 billion all time, and `anyhow` 1.0.104 about 203 million against 922 million. A reader will meet both in the first repository they open, so an arc that never names them leaves them to guess what the macro did.

**So the order is the decision, and it follows this workspace's standing rule about workarounds.** Lesson 0015 hand-writes the error type. Lesson 0016 hand-writes the `From` conversions that make `?` work across boundaries, then shows `thiserror` as the derive that generates exactly what those two lessons wrote, naming what it replaces line by line. The closing lesson introduces `anyhow` for the binary's top level and states the split that the ecosystem actually uses: a typed error in a library, because a caller may want to match on it, and an opaque one in an application, because nothing above `main` is going to. Deriving before you can write it by hand is the thing the arc refuses, for the same reason it refuses reaching for `clone` before understanding the borrow.

**One fact that dates the material and is easy to get wrong.** A private type in a public signature is no longer the hard error older writing describes: on 1.98.0 it is a warning from the `private_interfaces` lint, on by default, reading "type `Private` is more private than the item `leak`". Lesson 0018 teaches what the compiler actually does now and says which release changed it.

## Stage 4's decision: where variance and higher-ranked bounds belong

The open thread said variance and higher-ranked trait bounds were unplaced, implied by stage 4 but possibly deserving a late lesson near stage 8. Settled by compiling the cases a stage 4 reader actually writes and reading what the compiler says about them, because the question is not which topic is harder but which vocabulary the diagnostics require.

**Higher-ranked bounds go in stage 4, because the compiler puts them in front of the reader without naming them.** A closure annotated `|s: &'static str|` passed to a parameter bounded `Fn(&str) -> usize` produces an error with no code and no `--explain` page: "implementation of `Fn` is not general enough", then "closure with signature `fn(&'2 str) -> usize` must implement `Fn<(&'1 str,)>`, for any lifetime `'1`", then "but it actually implements `Fn<(&'2 str,)>`, for some specific lifetime `'2`". That message is unreadable without the idea that a bound can be quantified over every lifetime, and a reader meets it the first time they take a closure that borrows. A related case compiles into the same wall from the other side: a closure returning a borrow of a captured local, against a bound of `Fn(&str) -> &str`, gives `E0597` saying "returning this value requires that `owned` is borrowed for `'static`", where the `'static` comes from nowhere the reader wrote. So stage 4 names the concept and teaches reading `'1` against `'2`, and leaves writing an explicit `for<'a>` bound to stage 8, where API design is the subject.

**Variance stays out of stage 4, because every stage 4 case is reported in terms of scopes instead.** Two invariance-driven failures were compiled: overwriting a `&mut &'a str` slot with a shorter borrow, and pushing a shorter borrow into a `&mut Vec<&'a str>` whose element lifetime is pinned by an annotation. Both report as ordinary `E0597` with "borrowed value does not live long enough" and, in the second case, "type annotation requires that `owned` is borrowed for `'static`", pointing at the annotation that caused it. A reader who understands scopes fixes both without the word variance, and neither diagnostic uses it. Variance becomes necessary vocabulary when you own a type with a lifetime parameter and have to say whether substituting a different lifetime is allowed, which is API evolution, so it goes near stage 8 with the semver material. The open thread is resolved rather than deferred: the reason is recorded, not the preference.

**The stage's order follows from the same evidence.** Traits, bounds, associated types, then the dispatch choice, then implementing traits you do not own, then lifetimes, is the usual order and it is kept, with one departure: lifetime elision is taught with what a lifetime says rather than alongside borrowing in stage 1. Stage 1 deliberately never wrote an annotation, so elision had nothing to elide there; here `E0106` arrives with a `help` that names the actual question, whether the return borrows from `a` or from `b`, which is the shortest route to a lifetime being information.

## Stage 5's decision: what to share with, and in what order to teach it

Two questions, both settled by compiling and running rather than by preference, because the stage's done-when clause is that a sharing strategy gets chosen from the data rather than from habit, and a stage taught in the conventional order teaches the habit instead.

**Scoped threads come before `Arc`, and the evidence is that the borrowing version needs nothing.** A summariser that hands each thread a slot to write into and a line to read compiles under `thread::scope` with no `Arc`, no `clone` and no lifetime annotation, and the locals are still owned by the caller afterwards. The same code under `thread::spawn` fails with `E0373`, "closure may outlive the current function", whose note says the function requires the argument type to outlive `'static` and whose help offers `move`, which then moves the data the caller still wanted. So the honest order is spawn and join first, because a reader has to see the `'static` demand to understand what scope removes, then scoped threads as the default answer, and only then `Arc` for the case where the data genuinely has to outlive the scope. Teaching `Arc<Mutex<_>>` first, as most material does, produces exactly the habit this stage exists to prevent. Scoped threads stabilised in release 1.63, so this order was not available to older writing, which is part of why older writing does not use it.

**The stage is standard library only, and this is a change of situation rather than a purist preference.** `crossbeam-channel` was merged into `std::sync::mpsc` in release 1.67, so a reader using std channels is already using the crate the ecosystem would have told them to add. What std still does not have was checked by compiling: `std::sync::mpmc` is unstable, rejected with `E0658` and a pointer to its tracking issue, so multiple consumers on one channel remains the one place a crate is required. The other two candidates were tested rather than dismissed: `rayon` does the project's parallel summarise in three lines with `par_iter`, verified against version 1.12, and that is precisely why it cannot carry the teaching, since the reader would learn a method call instead of a decision. So the stage names all three once, with what each is for, and teaches none of them: rayon for data parallelism once the decision is understood, crossbeam for multiple consumers, and a non-poisoning lock crate for the case poisoning is genuinely unwanted.

**Memory ordering is deferred to stage 7 and atomics are not.** Atomic counters belong here, because `fetch_add` is the answer to a shared counter and a reader who has just met `Mutex` needs to know the cheaper option exists. The orderings are a different subject, closer to undefined behaviour than to sharing, so stage 5 uses one ordering, says the choice matters, and names stage 7 as where it is settled. Recorded so a later stage does not quietly teach `Relaxed` against `SeqCst` twice.

## Stage 6's decisions: the runtime, and the source gap that was recorded as unresolved

Two questions, and the second has been an open thread since the arc was planned.

**A future is taught by hand before any runtime exists, and that turns out to be possible with the standard library alone.** Verified: a working `block_on` is about a dozen lines using `Waker::noop`, which stabilised in release 1.85, with `Context::from_waker` and `Box::pin`, and it drives a real `async fn` to completion. So the first lesson of the stage has no dependency at all: a future is a state machine with a `poll` method, `Poll::Pending` means not yet, and the reader writes the loop that polls it. That matters because most treatments start with an annotation on `main` and a runtime nobody has looked inside, which is the same mistake as deriving an error type before writing one. The hand-written executor also busy-loops, which is the honest way into why a waker exists: the reader has to see the spin before the waker looks like anything but ceremony.

**The runtime is tokio, at version 1.53.1, and it is the only crate this stage teaches.** Read from crates.io rather than assumed: about 213 million recent downloads against 932 million all time, so a reader meets it in the first async repository they open. `futures` at 0.3.34 is not taught, because what this stage needs is in the standard library or in tokio, and `Stream` stays out of the arc rather than being taught from a crate whose trait the standard library has not settled.

**The recorded source gap is resolved, and the answer is that the source is API documentation rather than a book.** The open thread said cancellation safety was under-sourced and warned this stage would need real source-finding. What the search found: tokio documents cancel safety **per method**, in a dedicated section on each one, precisely enough to teach from. The `AsyncReadExt` page alone carries twenty-five of those sections, one reading "this method is cancel safe. If you use it as a branch in `tokio::select!` and another branch completes first, then it is guaranteed that no data was read." That is a better source than a chapter, because it is checkable per call rather than general, and the honest instruction to a reader is to look up the method they are about to put in a `select!` branch. `RESOURCES.md` gains tokio's API documentation as an entry of its own, separately from the tutorial it already lists, and the gaps section is corrected rather than left claiming nothing covers this.

**Why `async-trait` still has about 137 million recent downloads, long after `async fn` in traits stabilised, was verified rather than guessed.** A trait with an `async fn` compiles here, but the returned future carries no `Send` guarantee, so a caller that spawns it fails with "future cannot be sent between threads safely", and the compiler itself suggests rewriting the method as `fn next_line(&mut self) -> impl Future<Output = ...> + Send`. That explains the crate's continued use, and it belongs in the stage because a reader who writes an async trait and then spawns it hits exactly this.

**Nine lessons rather than eight, and the reason is the arc's own note.** This workspace records async as one of Rust's three hard walls, and the stage has to cover the poll model, executors and wakers, tasks and the `Send` bound, blocking, shared state across an await, cancellation, cancellation safety, pinning, and a closing triage lesson. Merging cancellation with cancellation safety was considered and rejected: the mechanics are simple, the design property is not, and the failure it produces is silent data loss rather than an error.

### Stage 3

All compiled on **rustc 1.98.0, edition 2024**, in a library crate rather than a binary, because this is the stage where the reader's code acquires callers.

- **`#[non_exhaustive]` does nothing inside the crate that defines it, which took two crates to show.** A `match` on a `#[non_exhaustive]` enum without a wildcard compiles fine in the defining crate and only fails downstream, with `E0004` naming `_` as the missing arm. Teaching it from one crate would have taught the opposite of the truth, so the lesson uses a consumer crate and says why the single-crate version looks like the attribute is inert.
- **`std::error::Error` requires `Debug`, not just `Display`.** Omitting the derive gives the trait-bound error rather than anything mentioning errors, which is worth quoting because the diagnostic does not say "your error type is missing something".
- **`#[from]` is narrower than it looks.** `thiserror` rejects a variant carrying a `#[from]` field alongside any other data, with a message saying the variant must have "no fields other than source and backtrace". That is the concrete reason a hand-written `From` implementation is still the answer whenever a conversion needs to add context, which is exactly the case lesson 0016 builds the stage around, and the orphan rule (`E0117`) is the other half of the same boundary.
- **Overflow is two different things and only one of them is a panic.** A literal operand that overflows is rejected at compile time by the `arithmetic_overflow` lint, which is deny by default, so it never reaches a runtime check; a computed overflow panics in a debug build and wraps in a release build. Lesson 0017 needed both, because "overflow panics" alone is false in either direction depending on which case a reader tries.
- **`panic = "abort"` changes observable behaviour, not just speed.** With it, `Drop` does not run during a panic and the process exits 134 rather than 101. That is the fact that makes the panic-against-error decision a design decision rather than a style preference: a library cannot know whether its caller unwinds.
- **Cross-crate intra-doc links fail silently under `--no-deps`.** A link to another crate's type renders as plain text with no warning at all, so a documentation build that looks clean can still ship dead links. Recorded because it is invisible by construction and will recur in stage 8.
- **`anyhow`'s report changes shape with depth.** One layer prints unnumbered; two or more print a numbered `Caused by:` list starting at `0:`. A lesson that quotes only the numbered form teaches a reader to expect output they will not see.
- **Private-in-public is a warning now, and half of the old error survives.** Defining `pub fn leak() -> Private` compiles with the `private_interfaces` lint only, but calling it from outside the defining module still hard-fails with a message saying that the type is private, and with no error code at all. The author found the second half; teaching only the lint would have overstated what the change buys. The lint replaced `private_in_public` in release 1.74.0, read from that release's notes.
- **The stage's ordering rule was verified rather than assumed.** The hand-written type is 47 lines with its documentation and the `thiserror` version is 36, and a test asserting `to_string()` and `source()` passes identically against both, so lesson 0016 can name what the derive replaced line by line instead of asserting that it replaces something.
- **One gate-4 fix.** The Reference renamed the `?` section: the anchor is now `the-try-propagation-expression`, and the page carries a note that the operator "is sometimes called the question mark operator". Lesson 0014's citation was corrected to the current anchor. Every other external link in the stage resolved with its anchor present, `fasterthanli.me` excepted for the reason recorded under stage 2.
- **`RESOURCES.md` gained two entries and needed them.** The rustdoc book and the API guidelines were already listed, but `thiserror` and `anyhow` are taught here and had no source, so their `docs.rs` pages are now listed with the split they exist for.

### Stage 4

All compiled on **rustc 1.98.0, edition 2024**. Eight lessons, and the first stage here where the central brief was not contradicted by a single author: everything in the shared spec reproduced, and the sheet writer re-ran every load-bearing claim independently and got the same output. What execution added rather than corrected:

- **A version attribution had to be settled centrally, and the release notes were no help.** The rename of object safety to dyn compatibility does not appear anywhere in the compiler's own `RELEASES.md`, which the lesson's author found and flagged rather than guessing quietly; their estimate of 1.85 was wrong. The rename PRs are milestoned 1.83.0 for the compiler's diagnostics and 1.84.0 for rustdoc, so the lesson names those and says the notes never mention it, which is the reason the old term keeps appearing in otherwise current writing. **Rule for later stages: when the release notes are silent, the milestone on the merged pull request is the next authority, and the silence itself is worth teaching.**
- **`E0038` says "not dyn compatible" now**, with a note about building a vtable and two suggestions, giving a `&self` or adding `where Self: Sized`. Any source using the object-safety wording predates 1.83.
- **Edition 2024's `impl Trait` capture change bites in both directions**, verified on both editions from one file: a function returning `impl Iterator<Item = char>` from a `&str` fails on 2021 with `E0700` and compiles on 2024, and a function returning a closure that captured only a `usize` compiles on 2021 and fails on 2024 with `E0597`, whose note names the edition change and suggests `use<>`. The 2024 failure is also **more fragile to reproduce than the brief implied**: the note and the `use<>` help appear only when the borrow is dropped in a narrower block before the closure is called, and wrapping the call in a function gives a bare `E0597` with no note at all. The lesson uses the form that produces the teaching.
- **Monomorphisation is provable rather than assertable.** A generic function called with two types leaves two symbols in the built binary, one per type, against one for the `dyn` version, and the current mangling puts the type name in the symbol. Two lessons and the sheet writer each reproduced the counts. The prose keeps the technique tool-neutral, listing symbols rather than naming a demangler.
- **The compiler explains `&self` elision picking the wrong lifetime without an error code**, as `error: lifetime may not live long enough` with numbered `'1` and `'2`, which covered both the wrong-choice case and the numbered-lifetime vocabulary in one example.
- **The strongest evidence for the stage's thesis was an identical diagnostic.** Eliding and explicitly writing `<'a>` on the same failing function produce byte-identical `E0597` output, which proves the annotation changes nothing about drop timing better than any prose could.
- **A new warn-by-default lint showed up unprompted**: `Cow<str>` without the explicit `'_` trips `mismatched_lifetime_syntaxes`, suggesting `Cow<'_, str>`. The audit checked the rest of the stage for signatures of that shape and found none.
- **`#[non_exhaustive]`'s stage 3 lesson has a sibling here**: a blanket `impl<T: Display> Label for T` coexists with a concrete `impl Label for Tag` until `Tag` gains a `Display` implementation, at which point the pair becomes `E0119`. A conflict created later by an impl that looks unrelated is the sharpest available argument that a blanket impl is a commitment.
- **One source rule was nearly broken and the citation was rescoped.** Lesson 0028 cited the Nomicon's higher-ranked page as a forward pointer, and `RESOURCES.md` reserves the Nomicon for stage 7 on the grounds that quoting it earlier makes the safe subset look optional. Replaced with the Reference's trait-bounds page, whose `higher-ranked-trait-bounds` anchor was verified. The rule held rather than being amended, because its reason still applies.
- **`RESOURCES.md` needed nothing.** Stage 4 cited the Book, the Reference, the standard library, the error index and the Edition Guide, all already listed. Recorded as a non-change.
- **Two method notes worth keeping.** One author re-extracted every fenced Rust block from its finished file and recompiled it, to confirm the published text matches real compiler output rather than the run it remembered; that is a cheap check and it should become standard. And eight parallel authors all had to guess their neighbours' filenames, since nobody's file existed when they started; every guess happened to be right, but a future stage should publish the filenames in the shared spec rather than relying on the naming convention holding.

### Stage 5

All run on **rustc 1.98.0, edition 2024**. Eight lessons, and the stage where the honest-reporting rule stopped being a formality: three of the stage's central claims changed shape once they were measured properly rather than measured once.

- **The lost update's magnitude was measured three times and disagreed three ways, which became the teaching.** My first probe, twenty runs, was wrong in twenty of twenty with a closest wrong total of 39992 out of 40000, so the brief told the authors the loss was small and consistent. The lesson's author ran a hundred and got wrong in a hundred of a hundred, worst total 22437, a loss of nearly half. A central re-measure of fifty runs got **wrong in forty-seven of fifty, worst total 13915**, so three runs came out exactly right. All three sets are real and the lesson now carries two of them: the loss ranges from a handful of increments to two thirds, and the failure rate itself moves, so an approximate assertion can pass while the code is wrong. **The rule this proves: one sample of a race is not a measurement.** A single run told the opposite story from fifty.
- **A fabricated quotation was caught by the audit, and it is the defect worth remembering.** Lesson 0030 presented "panic after all threads are joined" as `thread::scope`'s documented rule. That phrase appears nowhere on the page; the real sentence is "if any of the automatically joined threads panicked, this function will panic". Verified centrally and corrected. Everything else in that lesson reproduced, including the runtime message "a scoped thread panicked", so the failure was specifically a remembered quote inside otherwise executed work. **Quotation marks now need the same treatment as a diagnostic: fetched, not recalled.**
- **A lesson author stalled after writing but before verifying, and the stage 2 rule handled it.** Lesson 0033 was re-verified centrally, claim by claim: the four-thread counter printed 4000 in ten of ten runs; the held-too-long and narrowed guard examples produced their claimed orderings in three of three runs each; the same-thread double `lock` and the guard-held-across-a-call case each hung in three of three attempts under a six-second watchdog; the `RwLock` example had every "sees" line before any "releasing" line with the writer last, three of three; poisoning reproduced with the exact message, `into_inner` yielding a `MutexGuard` rather than a bare value, and `clear_poison` restoring the lock; all three standard-library quotations are verbatim and all five links resolve. The sheet writer then reviewed everything a run cannot check, and its format, cross-references and Practice answers were sound.
- **Two convention decisions the audit forced, both settled here rather than left to the next stage.** First, **panic output: trim the numeric thread identifier and say you trimmed it.** Stage 5's lessons do that, stage 2's lessons 0009 and 0010 instead keep it and explain that it varies per run, and both are honest, so those two are not being rewritten; new work follows the trim, which matches the same discipline as trimming a library path. Second, **naming a crate: lesson 0035 may name `crossbeam-channel` and the rule stands otherwise.** The audit flagged it as a rule break, correctly by the letter, but the fact being stated is that release 1.67 replaced `std::sync::mpsc`'s own implementation with that crate's, which is a fact about the standard library rather than a dependency recommendation, and it cannot be stated without the name. Lesson 0036 remains the only lesson that names a crate as something a reader might add.
- **Scoped threads earn their place at the front.** The borrowing version compiles with no `Arc`, no `clone` and no annotation, and the `spawn` version fails with `E0373` demanding `'static`; a scoped thread's panic is also observably different from a spawned one's, since dropping its handle unjoined makes `thread::scope` itself panic after joining the rest.
- **The two hangs and the never-ending receiver all needed watchdogs, and the deadlock's sleep is load-bearing.** With the fifty-millisecond sleep the two-lock cycle hung in three of three attempts; without it, **zero of ten** attempts hung, which is the honest reason the bug survives a test suite.
- **`Arc::clone` against the inner type's `clone` caught an author out**, usefully: `.clone()` on an `Arc<HashMap<..>>` resolves to `Arc::clone` and copies the pointer, so a practice item that meant to demonstrate a deep copy demonstrated nothing. Found by running it.
- **`RefCell`'s two panic messages are different and both are worth quoting**: "RefCell already borrowed" when a shared borrow blocks a mutable one, and "RefCell already mutably borrowed" when the outstanding borrow is the exclusive one.
- **`RESOURCES.md` needed nothing.** Stage 5 cited the standard library, the Book, the Reference and two release announcements, all already listed, and the release-notes convention already covers reading a stabilisation from the blog. Recorded as a non-change.

### Stage 6

All run on **rustc 1.98.0, edition 2024, with tokio 1.53.1**. Nine lessons, and the audit found no contradiction between them. What execution changed:

- **Three independent measurements of the same race gave three different distributions, and that is now the recorded rule for this repository.** The cancel-unsafe consumer was run centrally at ten attempts and gave ten identical results, which the brief then stated as a fact. Lesson 0043 ran it thirty times: twenty-seven kept one set of values, three kept another, none completed. Lesson 0045 ran it ten times and got nine and one. The auditor built its own version and ran thirty-five: thirty-five identical, and **losing a different set of values again**, because a small difference in the harness changes which values are lost. The invariant across all four sets is the only thing worth teaching: **every run loses data and no run reports an error.** Each lesson states its own counts as its own observation, which is why they do not contradict each other. **Rule: the central probe may not state a distribution from fewer than about thirty runs, and a lesson quotes its own counts rather than the brief's.** This is the second consecutive stage where a "reproduces identically" claim in the brief was a sampling artefact.
- **The async-fn-in-a-trait diagnostic needs a caller that is generic over the trait, which the brief had wrong.** With a concrete implementer, rustc drills through to the concrete type and reports the ordinary value-used-across-an-await error; the "cannot promise `Send`" diagnostic with its trait-rewriting `help` appears only when the caller is generic, because bounding the type parameter `Send` provably says nothing about the opaque future its method returns. Found by lesson 0039's author, reproduced by the auditor, and it is the truer lesson: my version would have shown the right error for the wrong reason. This is also the honest explanation of why `async-trait` still has about 137 million recent downloads, re-confirmed live at 137,176,325.
- **A stale documentation badge disagreed with the source, and the source won.** The rendered page badges `Waker::noop` as release 1.83; the standard library at this release carries `since = "1.85.0"` and the 1.85 notes list the API, confirmed by two agents independently against `core/src/task/wake.rs`. **A rendered stability badge is now a third-tier source here, behind the attribute and the release notes.**
- **The stage's best teaching moment is a compile error rather than a runtime failure.** Holding a standard-library `MutexGuard` across an await inside a spawned task is refused at compile time, with a note reading that the future is not `Send` as this value is used across an await, the guard's binding underlined and the await pointed at. It is stage 5's `MutexGuard`-is-not-`Send` fact arriving somewhere new, which is why the stage cites lesson 0034 rather than re-teaching it.
- **Poll counts, not durations, are the right measurement for an executor.** A parking executor polled twice where a spinning one polled between two and four million times across three runs, reported as three separate observations. Blocking was measured only as a ratio: about four to one on a current-thread runtime, and about two to one with two deliberately chosen worker threads, which is the number that matters because it shows a multi-worker runtime hides the problem rather than fixing it.
- **Cancellation's two surprises were both verified**: an aborted task stops at whichever await it had yielded at and runs its locals' destructors, and **dropping a `JoinHandle` does not cancel anything**, it detaches, so the task runs on and its result is discarded. Both quoted from tokio's own documentation character for character.
- **The recorded source gap is closed with a better answer than expected.** Cancel safety is documented per method: the `AsyncReadExt` page alone carries twenty-five such sections, in at least three distinct phrasings including "is not cancel safe" and a caveat case, since `Mutex::lock`'s documentation says cancelling it makes you lose your place in the queue. Two authors independently found the same page uses both "no data was read" and "no data were read" for different methods, which is exactly why the rule is to quote per method rather than generalise.
- **One agent's cleanup deleted the shared scratch tree, including the stage spec, while six authors were still running.** Nothing in the repository was touched and the spec was restored from the central copy, but the fix for next time is structural: **give each author its own scratch root and tell it to delete only that.** Recorded because it cost real time and could have cost verification.
- **A sheet agent was killed by a session limit before writing anything.** The mechanical half of its audit was then done centrally, which is cheap, and the relaunched agent was given only the work that needs a subagent: reproductions and contradiction-hunting. That split is worth reusing whenever an audit has to be retried.
- **`RESOURCES.md` changed for the first time since stage 2.** Tokio's API documentation is now its own entry, because it is where cancel safety actually lives, and the gaps section no longer claims the topic is unsourced. `Stream` is named there as what remains genuinely unsettled.

## On the arc

Eight stages, which is more than the other workspaces here, and the reason is that Rust has three separate hard walls rather than one: ownership in stage 1, lifetimes and traits in stage 4, and async in stage 6. Compressing any of them produces a reader who copies patterns.

Two boundaries worth revisiting once lessons exist:

- Stage 5 and stage 6 could merge into one concurrency stage. They stay apart because sharing across threads is understandable from ownership alone, and async is a separate model layered on top.
- Stage 7 pairs `unsafe` with performance. The link is real, since most `unsafe` in application code is written for speed that was never measured, and the pairing is meant to make that visible. If it reads as two topics, it splits.

## What not to do here

- Do not teach a fight with the borrow checker as a set of workarounds. `clone`, `Rc<RefCell<_>>` and lifetime annotations all make an error go away, and a lesson that reaches for one without saying what the design should have been teaches the wrong habit permanently.
- Do not reach `unsafe` before stage 7. The Rustonomicon is listed for that stage only, and quoting it earlier makes the safe subset look optional.

## Version policy

The arc names no Rust version. Where a lesson depends on an edition or a stabilised feature, it says which, and checks the release announcement rather than recalling it. Async and trait features move fastest, so a claim that something "cannot be expressed" dates quickly.
