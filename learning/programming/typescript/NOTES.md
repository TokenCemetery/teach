# TypeScript Notes

Working notes for the teaching session. Not linked from `README.md`.

## Preferences

- **Lessons are written for a general reader, deliberately.** No machine, OS, editor or installed version appears in any lesson, reference sheet, `README.md` or `RESOURCES.md`. Requested explicitly; do not personalise the lesson material to whoever is running the session.
- Mission is the full arc: zero to senior specialist, assuming no prior TypeScript and no more JavaScript than the arc teaches. Start at stage 1 rather than calibrating against a particular reader.
- Reps must fit one sitting. Many are type experiments rather than programs, and the playground is enough for those.

## What execution changed

Every behavioural claim in stage 2 was run on TypeScript 7.0.2 rather than recalled, and the stage found more drift than any other opening stage in this repository, because the compiler had been rewritten since almost everything written about it.

- **The headline is in the version policy above: TypeScript 7 type-checks strictly with no configuration.** It is repeated here because it is the fact most likely to be undone by a reviser working from older material.
- **Passing files on the command line while a `tsconfig.json` is present is now an error**, `TS5112`, suggesting `--ignoreConfig`. Earlier releases silently ignored the config file. This bit immediately when setting up the verification harness, and any script that checks a single file needs the flag.
- **Property narrowing survives an arbitrary function call.** Narrow `b.v` to `string`, call an unrelated function, use `b.v`, and it compiles. The widely repeated claim that any intervening call invalidates a narrowed property is wrong on this compiler. What does lose it is capturing the property in a closure, which errors with `TS2322`, because the closure may run later.
- **Local narrowing is about reassignment, not about `let` against `const`.** A narrowed `let` survives being captured in a closure so long as the variable is never reassigned anywhere afterwards. One reassignment later in the function loses the narrowing, for a direct use and for a closure use alike.
- **A tuple's fixed length is enforced on reads and not on `push`.** `t[5]` and destructuring a third element both give `TS2493` naming the length, while `t.push(3)` compiles, because a tuple is an array at run time and `push` belongs to the array type.
- **`readonly` is not part of assignability for object types.** A `{ readonly a: number }` value is assignable to `{ a: number }` with no diagnostic, so a readonly object can be handed straight to something that mutates it. Enforced where you use it, forgotten where you pass it.
- **A parameter written with method syntax is checked bivariantly and the same parameter written as a function-typed property is checked contravariantly.** The identical narrower callback is rejected in one declaration style and accepted in the other. This is a deliberate exemption rather than a bug, and it decides whether the compiler is helping on a given line.
- **`noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` are not in `strict`**, verified, so `a[99]` on a `string[]` types as `string`. `tsc --init` turns both on anyway, which is the clearest available evidence of what the team now considers sane and is stage 3's material.

- **The readonly hole is specific to object properties and does not generalise.** A readonly array or readonly tuple assigned to a mutable one is caught, `TS4104: The type 'readonly number[]' is 'readonly' and cannot be assigned to the mutable type 'number[]'`, while the object-property case compiles silently. So `readonly` is part of assignability for arrays and tuples and is not part of it for object properties. This was found by the sheet writer, which noticed that lesson 0009 discusses both side by side and had only stated the hole, leaving a reader free to over-generalise it. The lesson now carries both facts.

Two that behaved exactly as expected and are worth recording because a reader will doubt them: excess property checking fires on a fresh object literal with `TS2353` and does not fire when the identical object arrives through a variable; and `const f: () => void = () => 42` compiles, because a `void` return type promises only that the caller ignores the result.

Stage 3 was written against the same compiler and found a second round of drift, mostly in the configuration surface rather than in the type system.

- **Two flags are refused as configuration rather than applied to code.** With `strictNullChecks` off, the compiler rejects `strictPropertyInitialization` and `exactOptionalPropertyTypes` outright: `TS5052: Option 'X' cannot be specified without specifying option 'strictNullChecks'.` It will not hold an incoherent configuration.
- **And one flag is accepted while doing nothing at all.** `noUncheckedIndexedAccess` without `strictNullChecks` is not refused and also has no effect, because it makes an index access `string | undefined` and without `strictNullChecks` `undefined` is assignable to `string` anyway. The proof is that assigning `a[0]` to a `number` in that configuration reports that **`string`** is not assignable, naming a type with no `undefined` in it. This is the stage's most useful finding: a flag that is on, correctly spelled and buying nothing reads as covered to anyone reviewing the configuration.
- **`target: es5` has been removed.** `TS5108: Option 'target=ES5' has been removed. Please remove it from your configuration.` A project carrying that setting does not build on this compiler, which makes it a migration fact rather than trivia.
- **Naming `lib` replaces the default rather than adding to it.** `--target es2020 --lib es2022` fails with `TS2584: Cannot find name 'console'`, because the default library for a target includes the DOM declarations, `console` is declared there, and naming `lib` discarded them. The error is bewildering the first time and the cause is one setting behaving unlike every other.
- **The DOM library is on by default**, even for a project that will run on the arc's chosen runtime and never see a browser, so `document.title` type-checks in a Node project. That is the claim-against-guarantee theme again, at the level of the type environment.
- **`target` changes emit and not checking.** A `#x` private field type-checks identically at an older target; what changes is the output, where the field is lowered to a `WeakMap` with a mangled name. Verified by compiling and reading the emitted file rather than by asserting it.
- **Module resolution turns on `package.json`, not only on compiler options.** With `{"type": "module"}` an extensionless relative import is `TS2835`; with `{}` the identical import in the identical project compiles. And you write the extension the *output* will have: importing `"./dep.js"` resolves `dep.ts`, while importing `"./dep.ts"` is `TS5097` unless a flag allows it.
- **`catch (e: string)` is refused by the language**, `TS1196: Catch clause variable type annotation must be 'any' or 'unknown' if specified.` Nothing can guarantee what was thrown, so the annotation is not permitted, which is a rare case of the language closing a hole rather than leaving it open.
- **An unused `@ts-expect-error` is itself reported**, `TS2578`, which is the whole argument for preferring it over `@ts-ignore`: the suppression cannot rot silently.

- **The default for `types` is now `[]`, and the effect is narrower than that sounds.** Historically an unset `types` field meant every package under `node_modules/@types` was included automatically; since TypeScript 6.0 the default is empty. Corrected during stage 5 and re-verified centrally, because the stage 3 wording was true of the case it tested and too broad as written: `types` gates only `@types` packages contributing **unreferenced global** declarations, so an ambient global disappears and gives `TS2304`, while an `@types` package that backs an actual `import` still resolves through ordinary module resolution regardless of `types`. Both directions were run. So `tsc --init` writing `types: []` states the default rather than changing it, and it does not cut a dependency's own types off.
- **An error message's helpfulness is not uniform.** With the DOM declarations dropped, `console`, `Object.hasOwn` and `Array.prototype.at` all fail with a diagnostic that names the library setting and suggests changing it, while `fetch` fails with a bare `TS2304: Cannot find name 'fetch'.` and no hint at all. Lesson 0020 built a practice item on that difference rather than implying the hint is always there.
- **File extensions override the `package.json` field.** `.mts` forces ES module rules even in a CommonJS package and `.cts` forces CommonJS rules even in a module package, both verified in each direction by lesson 0021's author. So the ordered rule is extension first, then the nearest `package.json` `type`, then the default.

One correction to the shared spec, found by the lesson author rather than by me: `tsc --all` lists **eight** options carrying "default: `true`, unless `strict` is `false`", not the five the spec named. Confirmed independently: they are `noImplicitAny`, `noImplicitThis`, `strictBindCallApply`, `strictBuiltinIteratorReturn`, `strictFunctionTypes`, `strictNullChecks`, `strictPropertyInitialization` and `useUnknownInCatchVariables`, so the group is lesson 0015's seven plus `strictBuiltinIteratorReturn`. Lesson 0015 catalogues seven and cites the eighth only as evidence that the set is not fixed, which is the right treatment: the size of the group is a version fact and will change again. No minimal failing case for `strictBuiltinIteratorReturn` was found cheaply, so the stage names it and does not catalogue it, and the sheet's row says so rather than implying a diagnostic exists somewhere in the stage. If a later revision wants it, that example is the thing to go and build.

The sheet writer's audit also produced two useful non-findings worth recording so they are not re-raised. It flagged that no Practice item in the stage walks through repairing flagged code, only diagnosing it, which is true and is the format rather than an omission: Practice items in this workspace are prediction tasks by design, and the repair work is in the reps, where lesson 0015 asks the reader to decide whether a silenced line should be fixed instead and lesson 0018 asks them to replace an assertion on an indexed read with a check. And it could not trace two of the lessons' claims, the eight-flag count and the `types` default, because it had no compiler; both were re-run here and both hold.

Stage 4 found less platform drift than stages 2 and 3, which is expected since it teaches the type system rather than the compiler's surface, and it found more refinements to what the material actually does.

- **A union without a discriminant does not reject the impossible object.** `{ a: number } | { b: string }` accepts `{ a: 1, b: "both" }`, because excess property checking on a union only flags a property absent from **every** arm, and `b` is present in the second. So splitting fields across two arms is not enough: the literal discriminant is what makes the compiler pick one arm and reject the extra member. Lesson 0022's replacement type is discriminated for exactly this reason, and the reason is worth keeping if it is ever revised.
- **The `never` exhaustiveness diagnostic is uglier than the textbook version.** For a literal union it reads `Type '"c"' is not assignable to type 'never'`, which names the missing member cleanly. For an object-shaped discriminated union, which is what a reader arrives with after lesson 0022, it names the whole leftover object type instead. Lesson 0023 teaches both forms, because the verbose one is what readers will actually see.
- **`satisfies` on an `any` buys nothing.** It passes trivially and the result stays `any`, so reaching for it on the output of a parse does not check anything. That is the sharpest place to misapply it and lesson 0027 makes it a practice item.
- **`satisfies` is expression-only.** In a parameter position it is `TS1005` and in a return-type position `TS1144`, so it cannot replace an annotation on a signature. A reader who has just learned it will try.
- **`keyof typeof` is where `satisfies` pays.** Verified centrally: an annotated `Record` widens the keys to `string`, so `keyof typeof` gives `string`, while the same object under `satisfies` keeps `"host" | "port"`. This is the concrete reason to prefer it rather than a stylistic one. `satisfies` arrived in TypeScript 4.9, established from the release notes rather than recalled.
- **Generic inference has two fallbacks worth knowing**, both verified centrally: a type parameter inferred from an empty array unifies with `never`, and a generic with nothing at all to infer from falls back to `unknown`, so `wrap()` gives `unknown[]`.
- **The brand really is gone at run time.** Confirmed by compiling and running: `typeof` reports the underlying primitive and `JSON.stringify` shows no trace of the phantom property, which no value ever carries. So a brand records that a check happened and cannot itself be checked.

The sheet writer's audit was the most productive yet and produced three fixes rather than one. It found that lesson 0024 stated its counting rule as "an optional field permits that type's states plus one for absence", which is wrong for a `string` or object field whose value space is not enumerable, while every worked example correctly counted presence rather than values; the rule now says that optionality multiplies by two because presence is its own axis. It found that lesson 0024 deferred range invariants to lesson 0025 as though lesson 0025 demonstrated one, when its brands are all identifiers; 0024 now points at stage 5 for the check and describes 0025 as a pattern applied rather than an example shown. And it found lessons 0022 and 0024 working the same payment shape at full depth, so 0024's example is re-domained to a stored document, which also makes the point that the shape turns up everywhere. It also confirmed that 0028 explicitly distinguishes its accidental `never` from 0023's deliberate one, which was the risk worth checking. Three claims it could not trace were all re-run centrally and all hold.

Stage 5's findings, on TypeScript 7.0.2 with Zod 4.5.4.

- **The gating check passed.** Zod 4.5.4 type-checks clean on 7.0.2 under `strict` plus `noUncheckedIndexedAccess` plus `exactOptionalPropertyTypes` with `skipLibCheck` off, and runs. This had to be established before the stage could commit to the library at all, since Zod leans on inference and 7 is a compiler rewrite. Repeat it before revising the stage.
- **A schema describes two types and most write-ups treat it as one.** With a `.default()` in the schema, `z.infer` makes the field required and `z.input` makes it optional. So using `z.infer` for the type of something you are about to hand *in* is a real bug that type-checks, which lesson 0031 makes a practice item.
- **A type predicate's body is never checked against its claim.** A function declared `x is number` whose body tests `typeof x === "string"` compiles in full. That makes a predicate lesson 0018's assertion wearing a function signature, with a wider blast radius, since the lie is then trusted at every call site rather than at one.
- **`TS2775` for assertion functions is stricter than it first looks.** An `asserts x is T` function assigned to a `const` without an explicit annotation fails, and verified centrally, so does calling it through an object property: `const helpers = { check: assertString }; helpers.check(x)` gives the same diagnostic while the direct call compiles.
- **A lying declaration compiles and the program then fails.** Declaration claims `number`, implementation returns a string, caller calls `.toFixed`, and the result is `TypeError: n.toFixed is not a function` at run time with a clean build. This is lesson 0035's spine and the sharpest single demonstration in the stage.
- **`skipLibCheck` does nothing about it, and is widely believed to.** Zero errors with the flag off and zero with it on, against the same lying declaration. The flag governs whether errors *inside* declaration files are reported, not whether a declaration is true.
- **The quick fix the compiler suggests is a trap.** `TS7016` for an untyped dependency suggests a bare `declare module 'x';`, which silences the error by typing the entire module `any`, so it is lesson 0017's mistake applied to a whole dependency.
- **A failure arm of literal kinds breaks callers and a `string` arm does not.** Verified centrally: adding a kind to a literal union fails every exhaustive caller with `TS2322` against `never`, while widening the arm to `string` compiles silently everywhere. That contrast is the argument for typed errors rather than stringly ones and is lesson 0033's payload.
- **Two more removed options in TypeScript 7**, found while building the stage's projects and confirmed centrally: `moduleResolution: node10` and `moduleResolution: classic` both give `TS5108`, joining `target: es5`. Three removals now, and worth treating as one migration story if stage 7 ever covers upgrading.

**A limitation of the external-link gate, so it is not rechased.** Gate 4 checks that a cited `#anchor` exists on the page. Two sites this arc cites cannot be checked that way, and both look like failures when they are not. `nodejs.org` serves its API pages with no `id` attributes at all, over seven hundred kilobytes of `process.html` and zero of them, so its anchors are attached client-side. `typescriptlang.org/tsconfig/` links its own options as `href="#declaration"` without emitting a matching `id`, and every TSConfig anchor this arc cites across stages 3 to 5 is in that same position, so treating one as broken would mean churning all of them. A genuine anchor defect looks different and this stage had one: `everyday-types.html#unknown` was cited and does not exist, which was provable because the identical check finds `#unknown` present on `functions.html`, a within-site comparison that isolates the difference rather than testing the site's rendering. Prefer that shape of evidence before editing a citation.

All had already written their files and were in final trimming or read-through passes, so nothing was lost structurally: the checker passed, fence parity was intact in every file, word counts had come *down* from a mid-run measurement, and the two claims most likely to be unverified, being the exact items two agents were editing when they died, were both re-run centrally and both hold. What was lost is the sheet writer's cross-lesson audit, which has been worth a real finding in each of the last three stages. That is a thinner audit than an agent reading all seven end to end, and it is recorded as thinner rather than presented as equivalent.

Stage 6's findings, all on TypeScript 7.0.2.

- **The performance case against clever types no longer carries the weight it used to, and the stage says so.** A tail-recursive type taken to length 900 produces about 443600 types and 440000 instantiations and checks in under half a second. Lesson 0042's author re-measured independently and got 443629 and 440786 in 0.448 seconds against the central run's 443626 and 439881 in 0.479, close agreement, and quoted both rather than picking one. So the number worth watching is the instantiation count, which grows alarmingly, and check time is a weak lever on this compiler. The lesson therefore argues maintenance rather than speed. **Do not reinstate the folklore about slow builds**; it was measured here and found wanting.
- **The recursion ceiling is exact**: a tail-recursive tuple type compiles at a target length of 999 and fails at 1000 with `TS2589`, verified at six lengths.
- **All the performance tooling survives the rewrite**, and `--generateTrace` now writes several `types_N.json` files rather than one, which is a consequence of the native compiler working in parallel. `--extendedDiagnostics` showed no extra detail over `--diagnostics` on a single-file project, and lesson 0042 says so rather than claiming a richer breakdown it could not produce.
- **Distribution is observable, not just assertable.** A distributive conditional filtering a `string | number` down to `number` rejects a string with a diagnostic that **names `number`**, which is the proof the union was taken apart. Wrapping the check as `[T] extends [U]` turns distribution off and the whole union survives. That pair is how the stage demonstrates the behaviour instead of describing it.
- **A wrong variance annotation is checked, but only in one position, and the stage nearly shipped that under-specified.** `out T` on an interface that also takes a `T` in gives `TS2636` at the declaration with no assignment needed, when the offending member is written as a function-typed **property**. Write the identical member with **method** syntax and it compiles silently, because a method's parameter is bivariant, which is lesson 0013's exemption resurfacing one stage later. The sheet writer caught that lesson 0040 quoted the diagnostic without showing the interface that produces it, while the only interface it did show used method syntax, so a reader reproducing it would have seen nothing and concluded the lesson was wrong. Verified centrally in both forms; the lesson now shows the code and teaches the contrast.
- **A mapped type's filtering diagnostic needs a generic context to read well.** Applied to a concrete type the error names the resolved type; inside a generic function it names `OnlyNums<P>`, which is the form worth showing. Lesson 0036's author found this while reproducing the central run.

**A new rendering-defect class, now caught mechanically.** Three lessons shipped a construct that renders wrong and passes every source-level rule: a backslash before a backtick inside an inline code span. A backslash is not an escape there, so the span ends at the inner backtick and leaks a stray `</code>` and a literal backslash mid-sentence. Template literal types make this near-inevitable, which is why the stage that teaches them is where it surfaced. Four occurrences across lessons 0038 and 0039 are fixed, the rule is in the checker, and it is recorded in the skill's `PUBLISHING.md` beside the `<?` trap.

Worth recording how the rule was narrowed, because the first version was wrong. Flagging any backslash-backtick immediately failed a **correct** Java lesson, whose span content is a single backslash because it is discussing a line-continuation escape. The rule now looks for two on one line, which is the signature of an author wrapping an inner backtick-delimited expression and escaping both ends, and leaves the legitimate single case alone. A checker rule that fails correct work is worse than no rule, so verify a new one against the whole repository before keeping it.

## On the arc

- Stage 1 is JavaScript, and that is the decision most likely to be questioned. It stays because every hard TypeScript bug is a runtime behaviour the types described wrongly, and a reader who cannot predict the runtime cannot tell which of the two is lying.
- Stage 5 is the load-bearing stage for the mission. If the arc has to be cut short, stages 1 to 5 are the part that makes someone dangerous to leave alone with a codebase; stage 6 mostly prevents self-inflicted damage.
- Stage 6 has a failure mode built into it: type-level puzzles are enjoyable and mostly do not pay. Every lesson there needs a caller who benefits, or it does not get written.

## Version policy

The arc names no TypeScript version. Where a lesson must assume one, it states which and checks the release notes rather than recalling the feature. Inference and narrowing improve in ordinary releases, so a claim that something "cannot be expressed" dates faster than anything else here.

**Settled for stage 2, and it is bigger than a version bump.** The recheck before stage 2 found that the current release is **TypeScript 7.0.2**, published 2026-07-08. That is the native compiler rewrite, not another point release on the 5.x line: 5.9.3 was the last 5.x, the 6.0.x line was the short-lived bridge, and 7 is now `latest` on the registry. Two consequences the arc has to live with.

The first is that **TypeScript 7 type-checks strictly out of the box.** Verified by running it: bare `tsc`, with no flags and no configuration file, reports `TS7006: Parameter 'x' implicitly has an 'any' type` and `TS2322: Type 'null' is not assignable to type 'string'`. `tsc --all` states the mechanism, that `noImplicitAny`, `noImplicitThis`, `strictBindCallApply`, `strictBuiltinIteratorReturn` and `strictFunctionTypes` now default to `true` unless `strict` is explicitly `false`, and passing `--strict false` does disable them. Every piece of writing about TypeScript that predates this describes the opposite default, which is the drift most likely to reach a lesson unnoticed. Stage 2 is therefore written assuming strictness rather than promising it later, and **the arc's stage 3 row needed rewording**: its done-when used to be turning the strict flags on, and the honest version is keeping them on and knowing which strict-shaped flags `strict` still does not include. That row is updated in `README.md`.

The second is that a rewritten compiler means **no behavioural claim carried over from 5.x-era writing is trustworthy without a run**. Stage 2 was written against 7.0.2 with every claim executed; see "What execution changed". When stage 3 is written, recheck the version again rather than assuming 7.0.2 still holds, and note that `tsc --init` now emits a configuration that goes beyond `strict`, adding `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` along with `verbatimModuleSyntax`, `isolatedModules`, `noUncheckedSideEffectImports`, `moduleDetection: force` and `skipLibCheck`. That generated file is stage 3's material and is the best single piece of evidence about what the team now considers a sane default.

No version is named in a lesson unless the lesson's claim depends on it, which is the existing policy and still the right one. Where stage 2 states a version it states 7.0.2 and says the behaviour was run.
